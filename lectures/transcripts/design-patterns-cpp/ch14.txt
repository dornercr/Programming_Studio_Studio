Chapter 14: Command — requests, history, and honest undo
Dr. Charles Dorner

1. A request has a creation time and a running time
Problem and first design

SAY
Imagine a planning screen with a marker at zero. A student selects move to three, then move to seven, but playback has not started. The screen should still show zero. This is the first distinction: asking for work and doing work may happen at different times. We also want undo, which brings a second requirement. After both requests run, undoing only the latest one must show three, not zero. A request must therefore retain its destination before execution and learn the previous position during execution. Today we will follow those two kinds of data separately, because mixing their timing creates a believable but wrong history.

3. A queue of integers is still a valid alternative
Problem and first design

SAY
Suppose the only new requirement is delayed movement. A vector of destination integers and a loop over the checked setter is enough. We should keep that option on the table. The pressure for Command appears when one queue must also rename a marker or change its color, or when each request has its own reversal rule. Now a plain integer does not describe every request. Separate action-code and argument arrays can drift apart. A command object groups one request's data with its execute operation. The shared interface lets the playback loop trigger different requests without knowing each concrete type. The benefit is a stable place for execution policy, not an automatic guarantee of undo.

5. The contract we must preserve
Requirements and mechanism

SAY
An undoable queue of marker moves. Move holds the receiver, destination, prior position, and an applied flag. The queue owns commands but borrows no internal marker storage. Receiver validation happens before the command commits success.

Keep marker positions within 0 through 10. Construction must not execute a request. Undo applied moves in reverse order and reject invalid command states.

The marker stays within its allowed range. Only successful executions set applied_ true. Commands must not outlive their borrowed receiver. Undo history assumes no unrelated edits to the receiver. These are the rules that define a correct extension, even if it has the right C++ types. A vector of integers with a loop is sufficient for a fixed set of move-only requests. A std::function<void()> queue is compact for delayed work, but an undo contract still needs saved state and pairing between forward and reverse behavior.

6. The problem: moving a marker is easy until timing changes
Requirements and mechanism

SAY
A planning screen shows a marker at an integer position from zero through ten. Moving it immediately is simple: call marker.set(7). The setter rejects values outside the range and otherwise stores the new position. That direct call is the right first design when every request happens now and never needs undo. The new requirements are different: collect several moves, perform them later in order, and let the user undo that group in reverse order. The program must also reject a second execution of a move that is already applied.

A vector of destination integers can delay this one operation. However, if the screen later queues a rename or a color change, a vector of integers no longer describes all actions. A growing collection of parallel arrays for action codes and arguments is easy to misalign. The missing idea is to store a request together with the data and behavior needed to carry it out. That stored request is a command. We introduce an interface only because a single queue may need different kinds of requests with the same execute and undo operations.

7. A command has intent before it has a history
Requirements and mechanism

SAY
Move stores a borrowed Marker reference and a target position. Its constructor records intent but does not move the marker. The reference means there is one actual marker: copying the marker into each command would create private markers and leave the screen unchanged. target_ is stored by value so a later change to a caller variable cannot silently change the queued destination. before_ becomes meaningful only when execute runs. Saving it during construction would record the wrong old position for the second command in a delayed queue.

The interface has virtual execute and undo functions, so callers can use a Command reference without knowing which concrete request it holds. A virtual destructor allows deletion through the base type. Move uses override to ask the compiler to confirm that its functions truly replace those interface functions. std::unique_ptr<Command> owns each queued command. The vector owns its smart pointers, while each command merely borrows the marker. In main the marker is declared before the queue and is destroyed after it, so all borrowed references remain valid.

8. Execution has a commit point
Requirements and mechanism

SAY
Move begins with applied_ false. execute first rejects a repeated call. It then saves the current marker position, asks the marker to accept the target, and only after success sets applied_ true. This last step is a commit point: the flag now says there is a completed change that can be undone. If the setter rejects eleven, the marker remains unchanged and applied_ remains false. before_ may have been refreshed, but it does not authorize undo because the flag is still false.

This order is not cosmetic. Setting applied_ true before the setter succeeds would mark a failed request as part of the undo history. Updating the marker before validating the target would allow an invalid state even if an exception is thrown afterward. Here the setter validates first and then assigns one integer, which cannot throw. The program therefore gives a clear guarantee for a bad target: the visible marker stays as it was. This guarantee depends on the receiver behavior; a command cannot make a partly failing external service atomic merely by adding a bool.

9. Undo reverses successful requests in reverse order
Requirements and mechanism

SAY
The first queued move records zero and sets three. The second records three and sets seven. To reverse the group, undo the second move to restore three, then undo the first to restore zero. The reverse iterators rbegin and rend traverse the vector from its last element toward its first. In (*it)->undo(), *it obtains the unique pointer stored at the iterator position; the arrow accesses the owned command. Iteration changes which command is selected, not who owns it.

An undo operation is permitted only for an applied command. After restoration, applied_ becomes false and another execute is allowed; that is the limited redo behavior of this implementation. Redo reads a new before_ value at execution time. It does not promise to replay the exact historical environment. The design assumes exclusive, ordered changes to this marker while a history is active. If unrelated code changes the marker to nine between execution and undo, blindly restoring before_ can erase that later change. Real editors often route all edits through one history owner or use version checks to detect conflicts.

10. Queueing, undo, and transactions are separate promises
Requirements and mechanism

SAY
The primary queue loop runs commands in order but does not automatically undo earlier commands if a later one fails. A transaction is a group treated as one success or failure under a stated contract. The lab adds a small transaction runner for range failures: it counts successfully applied commands and reverses only that prefix. An empty batch succeeds without changing the marker. A batch containing targets six and eleven returns failure and restores the original zero. This works because the local receiver and undo operations have tightly controlled behavior.

A command can also represent an operation that cannot truly be undone. Sending a message may be followed by a correction, but the recipient may already have read it. A compensation is a new action that tries to offset an earlier effect; it is not time travel. Another option for local state is a snapshot, developed in Chapter 17, which remembers the state instead of how to reverse each action. For this marker, two integers and a flag are cheaper and clearer than a general snapshot system. Choose what must be preserved before promising undo to a user.

11. One owner of commands; one borrowed receiver
Mechanism in C++

SAY
In the chapter program, the queue owns its command objects through unique_ptr. Ownership means responsibility for ending those objects' lifetimes. A Move holds Marker&, which is a reference to the real marker, not ownership of it and not a copy. This is why two commands affect one visible position. The marker is declared before the queue in main. Local objects are destroyed in reverse declaration order, so the commands disappear before their receiver. If an application returned this queue while destroying a local marker, no smart pointer around the commands would save the borrowed reference. Review the lifetime of the receiver separately from the lifetime of the requests.

12. Dispatch is checked twice in different ways
Mechanism in C++

SAY
The queue sees Command, while the object behind each pointer is a Move. Calling execute through that interface selects Move::execute during execution; this selection is virtual dispatch. Earlier, during compilation, override asks the compiler to check that the function really replaces a matching virtual function in the base class. These are different jobs. The compiler cannot prove that saving before_ at the wrong time preserves history. The virtual destructor matters when unique_ptr<Command> deletes a concrete command through the base type. The interface is therefore more than a name shared by methods: it defines both callable behavior and safe destruction through the chosen owning handle.

13. Commit after the receiver succeeds
Mechanism in C++

SAY
Treat applied_ as a claim backed by evidence. False means this command currently has no completed change to reverse. execute checks that claim, reads the current position, and asks Marker to apply the destination. Only a successful return permits the assignment applied_ equals true. With destination eleven, Marker throws before assignment; the command remains unapplied and undo must reject it. This ordering provides a useful guarantee because the receiver validates before changing one integer. If a receiver instead wrote half a file before throwing, this flag would not repair the file. The command's guarantee can be no stronger than the receiver and recovery behavior it actually controls.

14. Reverse the effects, not the display order
Mechanism in C++

SAY
After moves to three and seven, the first command remembers zero and the second remembers three. Reverse traversal first asks the second command to restore three, then the first to restore zero. In the source, rbegin starts at the newest queue entry and rend marks the reverse end. The expression (*it)->undo first obtains the smart pointer at the iterator position, then calls through it. If undo runs in forward order, the first restoration gives zero and the second overwrites it with three. Even correct reverse order assumes nobody independently changed the marker. A background edit to nine can be lost unless the application routes edits through one history or checks a version.

15. A batch needs a stronger contract than a loop
Mechanism in C++

SAY
The primary queue loop does not promise all-or-nothing behavior. In the extension, a transaction-like batch applies fresh commands in order and remembers how many completed. The counter increases only after execute returns. For targets six and eleven, one command succeeds and one throws, so rollback undoes exactly the first. It never attempts to undo the failing command. The lab catches the stated range error, not every possible error in the universe. This small contract works because the receiver's saved positions remain valid and undo does not fail under the stated assumptions. A production batch needs an explicit response to rollback failure; catching an exception does not erase that design question.

44. Choose the smallest history that satisfies the promise
Recall and transfer

SAY
Command is useful when the request itself must travel: through a queue, a menu action, a macro, or a controlled history. It is not a requirement for every setter call. A callable can represent delayed work compactly, but pairing it with reversal still needs a contract and retained information. An absolute move to seven cannot be undone by subtracting seven unless the previous position happened to be zero. Saving the old position expresses the real operation. For larger state, Chapter 17's snapshots may be clearer. For a remote message, a later correction is compensation, not true reversal. Choose among these designs by what the user has been promised, not by the pattern name.

45. Debug the claim, the timing, and the owner
Recall and transfer

SAY
A useful debugging session separates three failures. If undoing the second move jumps straight to zero, inspect when before_ was captured. If an invalid request can be undone, inspect when applied_ became true. If delayed execution touches a dead object, inspect who owns the receiver and how long the queue can survive. These failures require different repairs, even though they appear near the same command class. Add a focused test for each path: construction leaves the marker unchanged, a failed execute cannot be undone, and the execution owner never retains requests past receiver lifetime. Do not rely only on the final group-undo value; the early-capture bug can accidentally restore zero after both wrong undos.

46. Explain Command without naming its classes
Recall and transfer

SAY
Close the code and describe the design in ordinary words. We keep a request so someone else can decide when it runs. The request holds its destination and a way to reach the real object. When it runs, it records the prior state, asks for a valid change, and marks success only afterward. Undo reverses successful changes under a stated ordering and isolation rule. That explanation is stronger than reciting client, invoker, and receiver. Now transfer it to a drawing editor: a menu and a keyboard shortcut can create the same action, while one history controls its timing. The editor still needs its own rules for document lifetime and edits arriving outside that history.
