Chapter 18: Observer — registration, lifetime, and delivery contracts
Dr. Charles Dorner

1. The audience changes while the producer stays useful
Problem and first design

SAY
A feed receives a reading of four. A total display needs it now, and a log or alert view may need the next reading too. Those views can open and close independently. Hard-coding every view into the feed makes the producer change whenever its audience changes. Polling can also be a poor fit when every event matters. Observer gives interested objects a way to register for updates through a shared contract. That solves the connection problem, but it does not choose ownership, duplicate handling, or failure behavior for us. In this lecture we will treat those delivery rules as part of the design, not as details hidden behind a notify method.

3. Sending events is a contract, not just a loop
Problem and first design

SAY
Before selecting a smart pointer, write three event stories. The same view registers twice: does it receive one event or two? A callback opens another view: can the registration list change during traversal? A callback throws after changing its own state: do later listeners still run? The chapter answers one, no, and no. It suppresses duplicate live identities, rejects subscription mutation during publish, and stops on the first callback exception. These are deliberate choices, not rules imposed by the Observer name. Writing them first gives tests meaningful targets. A different event library may make different choices and still implement Observer correctly, provided its observable contract is clear.

4. An exception does not undo earlier listener work
Problem and first design

SAY
This short program models two registered actions using callable objects so we can focus on delivery order before lifetime machinery. The first action adds five to first and throws. The loop exits through the catch, so the second action never receives the event. The outputs are therefore first five and second zero. Both facts matter: the failing listener was not unchanged, and the later listener was not called. This is fail-fast delivery with partial effects. A catch block is not a rollback operation. The chapter's Total behaves similarly when its optional after hook throws, and Feed promises only to reset its temporary busy flag so another publication can begin later.

5. The contract we must preserve
Requirements and mechanism

SAY
A feed with explicit notification rules. Feed keeps weak registrations and locks each one for the duration of its call. A scope guard clears the in-progress flag on all exits. Callback errors stop delivery and propagate without claiming rollback.

Accept readings from zero through one hundred. Notify each registered live listener once in registration order. Skip expired listeners; reject null registration, nested publish, and subscription changes during publish.

Only a successfully locked listener receives update. Duplicate live registrations produce one call. Registration storage does not change while being traversed. notifying_ is cleared when a publish call exits, including by exception. These are the rules that define a correct extension, even if it has the right C++ types. Borrowed raw pointers can be lean when a strict external lifetime and unsubscribe protocol is enforced. A snapshot of strong pointers simplifies stable delivery but keeps listeners alive for the whole batch and changes removal semantics.

6. The problem: several views need the same new reading
Requirements and mechanism

SAY
A data feed receives small integer readings between zero and one hundred. A total display needs each new reading; another view may later log values or raise a local alert. The simplest feed directly calls the known views. For a fixed pair that may be enough. The limitation appears when views open and close independently. Adding every view type to the feed couples data delivery to user-interface details, while repeatedly polling the feed can miss changes or waste work.

We need a way for a view to ask for notifications and later disappear without leaving a callable pointer to a destroyed object. A listener is an object that receives an update. A publisher sends updates to registered listeners. The Observer pattern connects these roles through a shared interface so the publisher knows how to notify, but does not need to know each view’s class. Choosing the interface is only the start; the more difficult work is deciding lifetime and behavior during notification.

7. Separate registration from ownership
Requirements and mechanism

SAY
Listener declares virtual update(int), and Total implements it. Feed stores weak_ptr<Listener> values. A weak pointer observes an object managed by shared_ptr without keeping that object alive. main owns the live Total through shared_ptr; Feed owns only registration entries. Before calling a listener, publish uses weak.lock to obtain a temporary shared_ptr. A successful lock keeps that particular listener alive until the local live pointer is released. A failed lock means the listener has expired, so the feed skips it.

The statement if (auto live = weak.lock()) both creates the temporary pointer and tests whether it is nonempty. That C++ condition keeps the temporary in scope for the controlled statement. The arrow calls update through the live base-class pointer, choosing the concrete listener function during execution. The compiler checks the shared interface and override signature earlier. Expiration is a normal condition, not an exception. The primary example deliberately destroys one subscriber before publication to show that a registration need not become a dangling raw pointer.

8. Registration rules prevent surprises
Requirements and mechanism

SAY
subscribe rejects an empty shared pointer, because a null registration has no useful meaning. It scans existing entries and returns if the same live object is already registered. Subscribing twice therefore produces one update, not two. Expired entries remain in the primary vector but are skipped during publication. This makes the small example simple; a long-lived feed with many short-lived views should periodically remove expired entries so its registration list does not grow forever.

The implementation forbids changing the registration list while it is publishing. subscribe checks notifying_ before doing anything else, even before duplicate detection. This policy protects iteration from vector changes and makes callback behavior predictable. The lab adds unsubscribe with the same rule. A different design could queue registration changes or publish through a stable snapshot of registrations, but then it must state whether a removed listener receives the current event. There is no universal answer that all observers share.

9. Reentrancy is a second call before the first has finished
Requirements and mechanism

SAY
A callback can call back into its publisher. If a listener tries feed.publish(1) while handling an earlier publication, the second call is reentrant: the first publish has not returned. Unrestricted recursion can create surprising order, repeated updates, or unbounded calls. This feed rejects nested publish with logic_error. A listener may catch that error and continue, as the primary test does, or allow it to propagate. The behavior is chosen deliberately instead of being an accidental consequence of recursive calls.

The notifying_ flag is set only after input validation and the reentrancy guard. A local Reset object borrows that flag and clears it in its destructor. Its destructor runs on normal return and while an exception unwinds the stack. This is resource acquisition is initialization applied to temporary state, not only memory: the local object owns the duty to reset the flag. Without it, a throwing listener could leave notifying_ true and make every later publication look nested even though the old call had already ended.

10. Failure during delivery is not an all-or-nothing update
Requirements and mechanism

SAY
Total first adds the reading to sum and then invokes an optional after callback. In the failure test, adding two changes the total from seven to nine, then after throws. Feed does not catch and continue to later listeners; it propagates the exception and stops the current delivery. Earlier listeners and the throwing listener may already have changed their own state. The Reset destructor clears the flag, so a later publication can run. The next reading of one makes the tested total ten.

This policy is called fail-fast delivery: stop when a callback fails. It is not atomic delivery, in which every listener either receives the change or no listener does. The latter would need much stronger coordination and often cannot be promised for arbitrary outside code. An alternative feed might collect callback errors and continue notifying other listeners. That favors availability but changes error reporting and ordering. In either case, identify whether the feed stores a new reading before publishing and how subscribers recover missed updates. The sample passes event values and keeps no authoritative reading history.

11. Keep callback captures inside a known lifetime
Requirements and mechanism

SAY
Total exposes a std::function<void()> named after solely as a test hook. The empty wrapper means no extra action. The lambda written [&] borrows local objects, including the feed, from main. Those locals remain alive whenever the callback is invoked in this program. Feed itself must stay alive through every active publish call; locking a listener does not keep the publisher alive. Feed deletes copying and assignment and has no implicit move operation, so a callback cannot replace its registration storage by assigning another Feed. Capturing a shared pointer by value inside an object it owns could instead create an ownership cycle. Capturing a short-lived local by reference and invoking it later would leave a dangling reference. A callback is executable state, so its captures deserve the same ownership review as normal members.

The example is single-threaded. weak_ptr provides lifetime coordination for managed objects, but the listener vector, notifying_ flag, and Total::sum are not protected for concurrent access. The total uses int for a small bounded demonstration sequence; an unbounded real stream would require an overflow policy or a wider checked total. Use the pattern to separate interest from production, then write precise rules for delivery, registration, expiration, failure, and concurrency. A diagram with one arrow to each listener is not a substitute for those contracts.

12. Registration observes; a temporary owner protects the call
Mechanism in C++

SAY
A weak pointer records a relationship to an object managed by shared ownership without keeping that object alive. Feed therefore does not force a closed view to survive merely because it once subscribed. Before calling update, publish invokes lock on the weak registration. If an owner still exists, lock returns a shared pointer that keeps the listener alive through this callback. If the object has expired, it returns an empty pointer and the feed skips the entry. The if statement both creates live and tests it; live remains in scope inside the branch. This protects the listener during its call. It does not keep Feed itself alive or make arbitrary captured references safe.

13. Compile the interface; select the listener at runtime
Mechanism in C++

SAY
Listener defines the one operation Feed needs. virtual allows update to select the concrete implementation during execution, even though Feed holds a pointer through the Listener interface. Total uses override so the compiler checks the signature matches the intended base operation. Those build-time checks do not prove that each listener receives exactly one update. That guarantee also needs registration logic: subscribe rejects an empty pointer and returns when the same live object is already registered. Two distinct Total objects are two listeners even if their sums happen to match. Identity means which object it is, not whether its current fields contain equal values.

14. Reject list mutation before touching the list
Mechanism in C++

SAY
The callback is arbitrary user code, so it might try to change subscriptions. The chapter chooses a simple rule: reject that operation while publishing. subscribe checks notifying_ before duplicate detection, which means subscribing the current listener again is still rejected during its callback. The extension gives unsubscribe the same rule. This keeps vector traversal stable and avoids a question about whether a newly added listener receives the current event. A snapshot-based dispatcher can allow other policies, but it has different lifetime and event-membership costs. Expired entries in the primary program are simply skipped. A long-running feed needs a cleanup plan so dead registrations do not accumulate forever.

15. A destructor can own the duty to clear a flag
Mechanism in C++

SAY
Reentrancy means entering publish again while an earlier publish is still active. A callback can do that on the same thread; no second thread is needed. The chapter rejects the nested call to keep event order simple. Once valid publication starts, a local Reset object borrows the busy flag. Its destructor clears that flag when the scope exits, including while an exception unwinds the call stack. This is resource acquisition is initialization used for a cleanup duty rather than heap memory. Clearing the flag only at the last line would fail if a callback threw before reaching it. The guard restores the ability to publish later; it does not roll back listeners' earlier effects.

16. Callback captures carry lifetime promises too
Mechanism in C++

SAY
The test hook after is a stored callable. Its lambda capture written with an ampersand borrows the local objects used inside the body. That is safe in the chapter because those objects remain alive whenever the hook is called. Retaining the same hook after a borrowed local died would break a different lifetime rule than the listener registration rule. Capturing a shared pointer can keep an object alive, but storing that callback inside the same owned object can create a cycle. Also separate lifetime from concurrency: a successful weak lock does not lock Total::sum, the vector, or the busy flag. The sample is single-threaded and has no promise of concurrent delivery safety.

45. Choose delivery policy for the application
Recall and transfer

SAY
For dependent listeners, stopping after the first failure may be the clearest policy. For independent dashboard views, continuing and collecting errors may keep more of the screen current. Both require tests that include a throwing listener followed by a healthy listener, because normal-path totals cannot distinguish them. Atomic delivery is stronger: either every effect happens or none do. Arbitrary callbacks do not provide a shared rollback mechanism, so Observer alone cannot honestly make that promise. Likewise, weak registrations are one ownership choice, not the pattern's definition. Raw borrowed pointers can work with a strict external lifetime and removal protocol, while strong registrations intentionally retain their listeners.
