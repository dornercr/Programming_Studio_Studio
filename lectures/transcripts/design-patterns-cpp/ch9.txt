1. Two small display features already have an order
Problem and first design

SAY
A status panel needs optional features around a basic message. One feature adds an alert prefix. Another keeps only the first five bytes of text. Some screens need both. Before naming a pattern, ask what the final screen should show, because prefixing and limiting can interact. If the limit runs first, the later prefix increases the visible length. If the prefix runs first, a later limit can cut the body away entirely. The chapter uses simple single-byte text, so these examples are easy to trace. A real Unicode layout requirement would need a separate definition of visible character boundaries.

4. Make each feature usable as a Message
Problem and first design

SAY
When screens choose different combinations at runtime and clients expect Message objects, the fixed function is no longer the whole solution. A decorator implements the same public operation as the object it surrounds. Plain supplies the starting text. Prefix and Limit also implement Message, but each asks an inner Message for its result and then transforms that result. Because an inner Message can itself be another decorator, the arrangement can form a chain. This replaces a separate subclass for every combination with reusable features and explicit assembly. The important evidence is the preserved interface and delegated behavior, not merely the word wrapper in a class name.

5. The contract we must preserve
Requirements and mechanism

SAY
Two ways to decorate a status message. Each wrapper owns exactly one Message and implements the same query. Ownership makes the assembled chain self-contained; explicit nesting makes order reviewable.

Support plain text, prefixing, and a length limit. Permit either wrapper order through Message::text. Reject a wrapper with no inner object and preserve empty-string behavior.

Every wrapper has one non-null inner owner. text returns a new value and does not mutate the chain. Limit applies to the complete result returned by its immediate inner object. These are the rules that define a correct extension, even if it has the right C++ types. A pair of string functions is better for one fixed transformation sequence. A vector of transformation functions fits a pipeline that does not otherwise need a Message object interface.

6. When two small features produce many variants
Requirements and mechanism

SAY
A status panel starts with plain text such as ready now. Some screens add WARN before the text. Some limit the display to five characters. A screen may need both behaviors, and its policy must say which applies first. For this chapter, strings contain simple single-byte characters. The program is not a full Unicode layout engine.

With one fixed policy, a direct expression is the simplest implementation. Add the prefix and take a substring. That clearly states the order. The problem appears when screens choose different combinations at runtime. Classes named PrefixedMessage, LimitedMessage, PrefixedLimitedMessage, and LimitedPrefixedMessage repeat pieces of behavior. Adding a suffix or a timestamp creates more combinations. We need reusable features that can be assembled without defining a new class for every pairing.

7. A wrapper with the same public operation
Requirements and mechanism

SAY
A decorator is an object that adds behavior around another object while keeping the same interface. Message provides text(). Plain returns its stored text. Prefix and Limit are also Messages, but each owns an inner Message and calls that object's text before adding its own behavior. Since the inner object may itself be another decorator, the same construction rule supports a chain of features.

The important fact is that every layer remains usable as a Message. This is why the common interface is needed now: callers must accept an assembled chain without knowing its exact shape. Public inheritance supplies that substitutability. Containing an inner Message supplies the behavior being extended. The inheritance link and the ownership link answer different questions and must remain distinct in the diagram.

We do not add a generic Decorator base class merely to repeat the inner_ member. Two small wrappers do not yet need that additional inheritance layer. If many wrappers later share forwarding behavior and validation, a base wrapper can remove useful duplication. First show the repeated need; then judge whether sharing that implementation makes the code easier to change.

8. Order is visible behavior
Requirements and mechanism

SAY
The first chain is Prefix around Limit around Plain. A call enters Prefix, which asks Limit for text. Limit asks Plain and receives ready now. Limit keeps the first five characters, ready, and returns them. Prefix then adds WARN and returns WARN ready. The five-character rule applied only to the inner body, so the final string is longer than five.

The second chain is Limit around Prefix around Plain. Plain again returns ready now. Prefix returns WARN ready now. The outer Limit keeps its first five characters: W, A, R, N, and a space. The printed single quotes make the trailing space visible. The final result is 'WARN '. This is not an implementation accident. The outermost operation runs last on the returned text in this design.

Operations whose order changes the result are noncommutative: swapping them changes behavior. Prefix and Limit are a concrete example. Never document a stack merely as 'prefix plus limit' if the order matters. Show the nesting or the actual transformation sequence. For logging, validation, caching, and compression wrappers in real systems, a wrong order can matter much more than a shortened message.

9. Follow ownership separately from the call stack
Requirements and mechanism

SAY
Each wrapper stores unique_ptr<Message>. Its constructor receives an owner by value and moves that owner into inner_. The caller gives up ownership as part of construction. A null pointer is rejected immediately, so text can safely call inner_->text without a null check on every request. If construction throws, the already-initialized member owner cleans up its inner object automatically.

make_unique constructs each object and returns its owner. main nests those calls from the plain object outward. When first is destroyed, its Prefix is destroyed, which destroys its inner Limit, which destroys its Plain. Message has a virtual destructor so deleting through unique_ptr<Message> reaches the correct derived destructor. No caller needs to remember the chain's exact concrete types to clean it up.

During text(), each layer also creates local strings. body receives the inner result by value; result stores this layer's transformed text. These values own their character storage, so the method never returns a reference to a local string. Returning a string value permits safe transfer of the result to the caller. The chain's object lifetime is much longer than each local string's lifetime, and the two should not be confused.

Message explicitly allows default construction but deletes copy and move construction and assignment. The = delete notation asks the compiler to reject those operations. Derived wrappers therefore cannot be moved as whole objects, which would empty inner_ in the source and violate its non-null rule. Move the owning unique_ptr handle instead: ownership changes hands while the wrapper object and its inner chain stay in place. Compile-time static_assert checks use the type traits from <type_traits> to verify that Prefix and Limit cannot be copied or moved. The Suffix solution checks the same property. A type trait is a library query about a type; static_assert rejects a false condition during compilation.

10. Syntax, cost, and boundary assumptions
Requirements and mechanism

SAY
The compiler verifies that every concrete Message implements text() const with the right return type. override makes the check explicit. const permits reading through a const Message reference and promises not to alter the object through that method's ordinary members. It does not automatically make an arbitrary chain thread-safe if future decorators introduce mutable caches or shared services.

At execution, virtual dispatch chooses each layer and each layer delegates once. substr(0, limit_) begins at position zero and takes at most limit_ characters. If the requested length is larger than the body, it returns the whole body. A zero limit returns an empty string. std::size_t is an unsigned size type; a negative signed value converted to it would become a large positive size. The program constructs limits from nonnegative literals, and a user-input interface would need to reject negative values before conversion.

A chain with many layers may allocate and copy many intermediate strings. This example favors clarity over a claim of best performance. A fixed transformation pipeline made of ordinary functions can be simpler and cheaper when callers do not need objects sharing an interface. A streaming design may avoid large intermediates, but then each layer must define how it handles partial input and failures.

Decorator is useful when features are independently selectable and have a consistent component contract. It is less useful when the features depend on many details of one another or when an object needs a radically different interface. Keep the assembly code readable, test the important orders, and document whether repeated decoration is meaningful. Applying Prefix twice adds two prefixes; it is not automatically idempotent, meaning it does not necessarily leave the result unchanged after the first application.

11. Calls travel inward; text returns outward
Mechanism in C++

SAY
The outer object receives the first call, but that does not mean its transformation happens first. Prefix calls its inner object before joining its prefix. If that inner object is Limit, Limit first calls Plain, obtains ready now, and returns ready. Prefix then returns WARN ready. 12. Same interface, different responsibility
Mechanism in C++

SAY
A Prefix has two relationships with Message. It is usable as a Message because it publicly implements the interface. It also owns another Message through inner_. These relationships answer different questions. Inheritance says what calls the outer object can receive. Ownership says who keeps the inner object alive and destroys it. The diagram's inheritance triangle must not be read as an ownership arrow. Compared with Composite, this chapter's wrapper delegates through one inner component instead of combining a collection of children. Similar recursive shapes can therefore serve different intentions. Decorator adds a feature while keeping the component contract available for the next wrapper.

13. Reject missing components during assembly
Mechanism in C++

SAY
A wrapper cannot add behavior around nothing, so its constructor rejects a missing inner owner. The constructor receives a unique_ptr by value, then moves it into the member. That transfer records who is responsible for the inner object's lifetime. If validation throws, C++ destroys completed member objects, and the owning pointer cleans up its child automatically. In ordinary construction, nested make_unique calls build the chain from the inside outward. Destruction follows the ownership links inward when the outer owner disappears. Message needs a virtual destructor so deleting through the common base pointer reaches each actual derived object correctly.

14. Move handles without moving service objects
Mechanism in C++

SAY
The chapter makes a careful distinction between moving an owner and moving the object it owns. A default move of a wrapper's unique_ptr member could leave the source wrapper with a null inner pointer, breaking its class invariant. Message therefore deletes copy and move operations, and the wrappers inherit that restriction. Equals delete means an attempted use is rejected during compilation. The outer unique_ptr handle can still move to a new owner while the wrapper stays at the same object location with its inner chain intact. Static assertions verify these type properties at build time. This is a policy choice that keeps the set of valid wrapper states small.

15. Returned strings are values with their own lives
Mechanism in C++

SAY
Each call creates temporary local strings while the longer-lived message chain remains in place. Returning a string value safely gives the result to the caller. Returning a reference to a local result would instead leave the caller referring to destroyed storage. Substr takes a starting position followed by a maximum count; reversing their purpose can produce an empty result or an out-of-range error. The lab's Suffix follows the same ownership contract while appending text after delegation. Test it on both sides of Limit, because a suffix may be removed by an outer limit or extend a result after an inner limit. Reusing the interface does not remove interaction tests.

45. Order and repetition are part of the API
Recall and transfer

SAY
Two operations commute when swapping them preserves the result. Our prefix and limit do not, as the visible outputs demonstrate. Repetition is another question. An operation is idempotent when applying it again has the same effect as applying it once. Applying the same plain length limit again is idempotent for this text rule, but adding the prefix again adds another marker. These properties belong in the usage contract because a configuration system might accidentally repeat or reorder features. Also keep the unit precise: the current std::string operation counts bytes. A requirement phrased in displayed characters needs more design before it can safely reuse the same implementation.
