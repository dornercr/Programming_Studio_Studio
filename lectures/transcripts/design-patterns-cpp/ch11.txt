1. A thousand marks need not mean a thousand shapes
Problem and first design

SAY
A drawing tool places marks at different horizontal positions. A mark has a style name and size as well as its position. Storing all three values in every mark is easy to understand, and for a small drawing it may be the best design. Now imagine each style also includes a large shape outline. Copying that outline into ten thousand marks spends memory on the same information again and again. Our question is whether we can keep that common part once without making the positions common too. Before designing the sharing, measure the repeated data. The small strings in this teaching example do not by themselves prove a memory saving.

3. A pool can share the wrong thing perfectly
Problem and first design

SAY
This demonstration intentionally uses an incomplete lookup key. The bad pool remembers styles by name only. Requesting stamp size twelve creates an object; requesting stamp size twenty finds the same name and returns the earlier object. The output therefore reports requested twenty but received twelve. Nothing crashed, no object died early, and the pointer is valid. The failure is a false claim about equality: the key treats two different styles as interchangeable. The correct chapter pool uses both name and size. If color later becomes shared state, color must enter the key too. A compiler cannot infer that design promise from the name of a map.

4. Share the stable facts; keep each use separate
Problem and first design

SAY
Flyweight is a design that shares repeated state while leaving each use's changing details outside the shared object. The shared part has the technical name intrinsic state. In our chapter that is the style name and size. The per-use part is extrinsic state, here the horizontal position. These names describe a design choice, not a property that every program must assign the same way. A StylePool returns owners of an immutable Style, and a Mark stores one such owner beside its own position. Two marks can refer to the same style without becoming the same mark. That separation is the central mechanism to find in code.

5. The contract we must preserve
Requirements and mechanism

SAY
Several marks, one immutable style. A map interns immutable Style objects by a complete structured key. shared_ptr allows marks to retain styles after a pool is destroyed.

Share styles only when both name and size match. Keep each mark position separate. Reject empty names, size outside 1–100, and missing style pointers.

One active pool returns the same object for the same key. Published Style objects are immutable. Each Mark owns its own position and shares only intrinsic style state. These are the rules that define a correct extension, even if it has the right C++ types. Store style fields by value for a small number of small styles. Integer style IDs into a stable central table can use less per-mark memory but require a clear table lifetime and ID-validity contract.

6. Repeated data can outweigh useful differences
Requirements and mechanism

SAY
A drawing tool places many marks on a page. A mark has a style name, a style size, and a horizontal position. Thousands of marks may use the same style while each position differs. For a few marks, store all three fields directly in every object. That is simple, clear, and often the right answer.

The limitation appears when the shared portion becomes large. Imagine that a style later contains a loaded shape outline or a rendering table. Copying that payload for every mark may consume far more memory than the positions themselves. Before changing the design, measure the repeated data and the number of uses. Our small program keeps style data intentionally short so the ownership mechanism is visible; it is not evidence that this tiny representation saves memory.

7. Split stable shared data from each use
Requirements and mechanism

SAY
Flyweight is a memory-sharing design that stores repeated state once and gives each use a connection to it. The shared state is called intrinsic state. Here name and size identify the style. The state that belongs to a particular use is called extrinsic state. Here x is the mark's position. A Mark holds a shared style owner and its own x value. Two Marks can therefore agree on style without becoming the same mark.

StylePool looks up a style by a Key containing both name and size. If that key already exists, it returns another shared owner of the same Style object. Otherwise it creates one immutable Style, stores an owner in the map, and returns another owner. Reusing an existing object is often called interning. It is useful only when equality of the chosen key truly means the shared data is interchangeable.

The key is a std::pair<std::string, int>, not two fields joined into an unstructured string. A pair keeps field boundaries unambiguous. If a later style includes color, color must become part of the key too. A pool keyed only by name would wrongly reuse dot size twelve for a request for dot size twenty. The visible mistake would be a correct position with the wrong style size.

8. Read the shared pointer type carefully
Requirements and mechanism

SAY
StylePtr is an alias for std::shared_ptr<const Style>. shared_ptr means several owners can keep the same object alive. const Style means the object reached through this owner is read-only. It is not the same as const shared_ptr<Style>, which would prevent reseating that particular pointer variable but would still permit changing the Style through it.

The pool constructs the object with make_shared<const Style>. The actual allocated Style is const, not merely viewed through one const handle while another mutable handle is retained. Its fields are initialized once and then read. Immutability means the object does not change after construction. That matters because a mutation to one shared style could otherwise change every mark using it. The public fields remain safe to read because access is through a pointer to const; the pool gives out no mutable owner.

A shared_ptr copy increments a shared ownership count; it does not copy the Style. When one pointer is destroyed, the count decreases. The object remains alive while at least one owner remains. The pool owns styles through its map, and each Mark owns its style through style_. This is shared ownership, so an ownership diagram must not imply that a mark exclusively owns its style. The arrows are labeled shared owner to make that distinction explicit.

9. Trace a lookup and a draw
Requirements and mechanism

SAY
main requests (dot,12) twice. The first lookup misses, creates one Style, and stores it. The second lookup finds the existing entry and returns found->second, which is the map's shared_ptr value. first and same therefore point to the same object. A request for (dot,20) uses a different key and receives a different object. The pointer equality checks test identity, not merely equal field values.

Mark left takes an owner of the twelve-size style and stores x = 3. Mark right receives another owner of that same style and stores x = 8. draw reads the shared name and size, then appends its own position. The outputs dot/12@3 and dot/12@8 show the separation directly. Neither draw call changes the style or the other mark.

In draw, const auto& name borrows the string inside Style while the Mark's owner keeps the Style alive. const auto size copies the small integer. Both are suitable choices: copying an int is cheap; copying the string is unnecessary for this local read. The returned formatted string is a new owned value. It does not expose a reference into shared state and remains valid after the Mark is destroyed. Mark explicitly defaults its copy operations, which suppresses automatic generation of move operations. Constructing from std::move(left) therefore copies the shared owner; both marks stay usable. This value-like policy avoids a moved-from Mark with a null style.

10. Lifetime is independent of the pool scope
Requirements and mechanism

SAY
The program creates a short-lived StylePool inside a nested scope and saves one returned owner in survivor outside that scope. When the pool is destroyed, its map releases its owner. survivor still owns the Style, so reading survivor->name afterward is valid. This test checks a real advantage of shared ownership: the pool's lifetime need not enclose every use.

The pool uses strong owners, so it also retains each style until the pool is destroyed or entries are removed. An unused style does not vanish merely because its last Mark disappears. That is a cache-retention policy, not a leak caused by missing delete. A long-running application may require a size limit, explicit clearing, or weak_ptr entries. A weak pointer observes a shared object without keeping it alive, but it requires checking whether the object still exists before reuse. That complexity should be justified by actual retention needs.

The compiler checks const access and pointer types; it cannot prove that the key includes every meaningful field. At runtime, map lookup compares keys and finds a matching entry. std::map lookup takes logarithmic comparisons in the number of styles. shared_ptr adds a control block and ownership bookkeeping. Neither cost disappears because the design has a name.

11. Calculate the tradeoff before calling it an optimization
Requirements and mechanism

SAY
Suppose N marks each have U bytes of unique state and would otherwise carry S bytes of shared payload. The direct representation costs roughly N times (U + S), ignoring container and allocation overhead. With K distinct styles and a per-mark handle of H bytes, sharing costs roughly N times (U + H) plus K times S, plus pool and control-block overhead. When K is nearly N or S is tiny, sharing may lose. When S is large and K is much smaller than N, it can win substantially.

This example does not report exact saved bytes because object layout, string storage, allocator overhead, and platform details matter. Measure the real workload. Also test semantic isolation: changing a mark's position must not change another mark, and equal style keys should share exactly when that is part of the pool contract. Flyweight is a targeted optimization, not a reason to turn every small value into a shared pointer.

12. Read const on the object, not just the handle
Mechanism in C++

SAY
A shared pointer is an owning handle: several handles can keep the same object alive. In shared_ptr<const Style>, const describes the Style reached through the handle, so field updates through that handle are forbidden. Putting const before shared_ptr instead fixes that particular handle variable; it can still reach a mutable Style. This distinction matters because one change to shared mutable style would appear in all marks using it. The chapter calls make_shared<const Style>, making the allocated object itself const, rather than retaining a secret mutable owner elsewhere. Each style is fully initialized and then read. Changing style means choosing another style owner, not quietly editing the shared object.

13. A copy of an owner is not a copy of the style
Mechanism in C++

SAY
Follow owners rather than guessing from variable names. StylePool's map owns one handle for each retained style. A successful get returns another handle to the same object. Copying that handle updates ownership bookkeeping; it does not copy the style payload. Each Mark then owns a handle, so destroying the pool does not necessarily destroy a style. The style remains alive until its final strong owner disappears. The current sharing graph has no back pointer from Style to the pool or to marks, so it does not create an ownership cycle. In a review, label these links as shared ownership. An arrow that suggests one mark exclusively owns the style would teach the wrong lifetime.

14. Identity and equality answer different questions
Mechanism in C++

SAY
Two styles can have equal field values without being the same object. Pointer equality checks object identity in this example. Before clearing the pool, repeated requests for the same key return the same retained object. The solution lab then clears the map. Old marks remain valid because their owners keep the old object alive, but a later lookup must create a new object for that key. 15. Moving a Mark still copies in this chapter
Mechanism in C++

SAY
The chapter includes a subtle lifetime choice. Mark explicitly defaults its copy constructor and copy assignment. That choice suppresses automatic generation of a move constructor. When the example constructs copied from std::move(left), the available copy constructor can accept the argument and copies its shared owner. Both marks remain usable. The name std::move is easy to overread: it permits move-aware overload selection, but it does not itself remove an object from storage or force a move operation to exist. Here the value-like copy policy avoids leaving a moved-from Mark with a null style that draw would dereference. If you later add moving, define and test the moved-from contract.

16. A sharing budget must include the handles
Mechanism in C++

SAY
Let N be the number of marks. Let U be bytes unique to each mark, S the shared payload size, K the number of distinct styles, and H the per-mark handle size. The direct design roughly uses N times U plus S. Sharing roughly uses N times U plus H, then adds K copies of S and the pool's own overhead. These are estimates, not exact sizeof promises. For example, with ten thousand marks, one thousand payload bytes per style, and only ten styles, the repeated payload shrinks greatly. If nearly every mark has a unique style or the payload is tiny, lookup and handle costs may outweigh the saving. Measure the actual workload.

46. Retention is a policy; it is not automatically a leak
Recall and transfer

SAY
A memory graph can be correct and still retain more data than the application wants. Our map holds strong owners until entries are cleared or the pool dies. If all marks using one style disappear, the map can still keep that style alive for reuse. Calling that a missing-delete leak would misdiagnose the code. The question is whether the retention policy fits the workload. A bounded cache, explicit clear, or weak entries may be appropriate in a long-running editor. A weak pointer does not keep the style alive, so lookup must detect an expired object and recreate it. That adds states and tests. Do not add this complexity merely because weak ownership sounds cheaper.

47. Diagnose the symptom before replacing the mechanism

Three failures look like a sharing problem but have different causes. A request for size twenty that draws size twelve suggests an incomplete key. 48. Explain the optimization without hiding the cost
Recall and transfer

SAY
A useful explanation of Flyweight begins with repeated data, not with shared_ptr. We measured that many uses carry the same large stable payload. We split that payload from per-use values, stored it once per complete key, and gave each use an owner that preserves its lifetime. Immutability prevents one use from changing every other use. The price is lookup, handles, bookkeeping, and a retention policy. If the direct representation is already small and clear, keeping it may be the better engineering decision. For a new drawing feature such as color, first ask whether color belongs to shared style or individual use. The answer controls the key, storage, and tests.
