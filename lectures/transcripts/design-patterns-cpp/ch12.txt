1. A simple question can hide a service cost
Problem and first design

SAY
A visitor screen asks what hour a building opens. The answer is one small integer, but obtaining it could require a remote request or an expensive setup. Our teaching source is deliberately an in-memory object. It performs no network I/O, and its reads counter lets us measure how often the real-service operation runs. Start with the simplest requirement: return the current source hour. Then add three pressures: construct the service only if used, reuse an answer until it is invalidated, and deny every read when permission is revoked. These pressures affect object lifetime, data freshness, and control order. A correct printed hour alone will not prove that all three were respected.

2. Direct calls give fresh values and repeated work
Problem and first design

SAY
This baseline has no interface hierarchy because there is only one operation and no substitute yet. The function borrows Source through a reference. A reference names the caller's existing object, so incrementing reads updates the same counter that main later prints. The first call returns eight. We change hour to nine, and the next call returns nine. Two answers required two real-service reads. That is a fine contract if the source is cheap or freshness dominates. A cache would intentionally change this behavior: the second answer might remain eight. Before optimizing, make sure callers agree to that weaker freshness promise and know how an old answer becomes unusable.

3. A fast return can bypass the access rule
Problem and first design

SAY
The two functions here differ only in the order of two checks. The cache already contains eight and permission is false. The buggy function sees a present cached value and returns it before asking whether access is allowed. The repaired function rejects first, so the cache does not create a bypass. An optional stores either one value or no value. Testing it asks whether a value exists, and the asterisk reads that value after the test. This example is a local control-flow model, not a real authentication system. It proves an ordering rule inside this function. A deployed system must also prevent callers from reaching protected data through another entrance.

4. A substitute controls access through the same interface
Problem and first design

SAY
A proxy is an object that stands in for a service while controlling access to it. The client uses the same Hours interface whether the object is RealHours or HoursProxy. Virtual means a call through that interface selects the implementation of the actual object during execution. Override asks the compiler to check that our method really implements the intended virtual operation. This type relationship permits substitution, but types alone do not promise identical freshness. The proxy deliberately caches. The shared service contract must permit that policy or provide an explicit freshness operation. The pattern is not simply a class with a pointer inside; it is a substitute enforcing an access or lifecycle decision.

5. The contract we must preserve
Requirements and mechanism

SAY
A lazy cached opening-hour service. One proxy keeps permission, lazy ownership, and cache state beside the service access they control. optional distinguishes no result from a valid zero result.

Do not create RealHours until the first permitted cache miss. Reuse cached values until explicit invalidation. Deny both cached and uncached reads when permission is false. Treat hour zero as a real cached value.

Denied reads never reach the service or return cached data. An engaged cache contains a successful prior result. Invalidation removes the result but does not destroy the service. Source outlives the proxy and its real service. These are the rules that define a correct extension, even if it has the right C++ types. Direct service calls are simpler when freshness is always required or calls are cheap. A standalone caching function may fit one caller; a proxy fits interchangeable Hours users.

6. A cheap question can trigger expensive work
Requirements and mechanism

SAY
A visitor display asks for a building's opening hour. In a real system that answer may require opening a connection or reading a remote schedule. This example uses a tiny in-memory Source so the behavior is deterministic. The source hour starts at eight, and a reads counter records real-service requests. The interface accepts hours already supplied by a trusted source; it does not validate a full calendar or time zone.

The simplest caller invokes the real service every time. That is appropriate when the service is cheap and fresh data matters more than reuse. The new requirements are to avoid creating the real service until needed, reuse the most recently fetched hour until told it is stale, and deny reads when local permission has been revoked. Repeating those rules at every caller would spread state management and make it easy to return a cached value after access was removed.

7. Use the same interface with an access-controlling substitute
Requirements and mechanism

SAY
A proxy is a substitute object that controls access to another service while offering the same interface. Hours defines opening(). RealHours reads Source and increments its reads counter. HoursProxy also implements opening, but it checks permission, checks its cache, creates RealHours if necessary, and calls it only when a fresh value is needed. Code written against Hours can use either object.

The proxy holds a Source reference and an optional unique_ptr<RealHours>. The pointer starts empty. Constructing the proxy therefore does not construct RealHours. Creating the real object only on first demand is called lazy initialization. Once created, the real service remains owned by the proxy even if cached data is invalidated. The two states answer different questions: is a service object present, and is there a remembered result?

Caching means retaining a result for later reuse. std::optional<int> stores either no value or one integer. It is a better representation than using zero as an empty marker because midnight, hour zero, is valid. Testing cached_ asks whether a value exists; it does not ask whether the stored integer is nonzero. Dereferencing it with *cached_ reads that value only after the program knows it is present.

8. Permission comes before the fast path
Requirements and mechanism

SAY
opening first checks allowed_. If false, it throws runtime_error immediately. It does this before consulting cached_. Revoking permission must stop both real-service reads and returns of data fetched earlier. A misplaced permission check after the cache hit would deny new reads but still expose old cached data. That is a precise ordering bug, not a reason to abandon caching.

This Boolean permission is a local teaching model, not an authentication system. There is no user identity, secret, network enforcement, or protection against a caller directly using RealHours. In a real application, access decisions need an authoritative policy and a boundary that unauthorized callers cannot bypass. The pattern explains where a check can sit; it does not make the check trustworthy by itself.

After permission succeeds, an engaged cache returns immediately without creating or reading a real service. On a cache miss, the proxy creates RealHours only if real_ is still empty. Then it calls real_->opening, stores the returned integer in cached_, and returns it. The virtual interface is the same, but allowed caching deliberately changes freshness. That semantic difference must be part of the service contract a caller accepts.

9. Trace old data and explicit invalidation
Requirements and mechanism

SAY
The first opening call sees no cache and no real service. It creates RealHours, reads eight, stores eight, and leaves source.reads equal to one. main changes source.hour to nine. The next opening call still returns eight, and the read counter stays one. That stale value is expected under this cache policy. Stale means no longer known to match the current source.

invalidate calls cached_.reset(), which removes the stored result but leaves real_ alive. The next permitted opening call reuses the already-created service object, reads nine, stores it, and advances reads to two. main then denies access and confirms that even this warm cache cannot be read. After re-enabling access, it changes the source to zero, invalidates, and calls twice. Both calls return zero, but only the first reads the source, leaving the final counter at three.

An invalidation policy says when remembered data stops being usable. This program makes that decision explicit in main. It does not watch Source automatically. A production design might attach a revision number, receive a change notification, use a maximum age, or always fetch fresh data for critical operations. Each choice has a cost and a freshness promise. A cache without a stated invalidation policy is an unfinished design.

10. Object lifetime and failure state
Requirements and mechanism

SAY
main creates Source before HoursProxy, so the borrowed source outlives the proxy. The proxy owns its RealHours through unique_ptr. RealHours itself borrows the same Source. Destroying the proxy destroys the optional cache and the real-service owner, but it does not destroy Source. Local declaration order supplies the required lifetime arrangement without manual deletion.

At compilation, override checks that both classes implement Hours::opening. The method is not const because obtaining an answer may change the cache and the source's diagnostic counter. A logically read-only business operation can still mutate implementation state; the interface should state that honestly rather than adding mutable everywhere without discussing consequences.

If allocation of RealHours fails, the owner remains empty and the cache remains empty. If a future real-service call throws before returning an integer, assignment to cached_ is not reached, so a miss remains uncached. The example's real service does not throw, but placing assignment after a successful call naturally avoids remembering a fabricated success. The exact state of a real service after its own failure would still depend on that service's contract.

The program is single-threaded. Concurrent calls could race while creating real_, reading Source, or changing cached_. shared ownership or virtual functions would not fix those races. A concurrent version would need synchronization and a clear rule for the order of revocation, invalidation, and in-flight requests. We do not add those mechanisms without the requirement because they would obscure the state transitions being taught.

Hours defaults construction but explicitly deletes copy and move operations. The = delete declarations make service objects stable in place; callers transfer an owning unique_ptr handle when ownership must change. Without this rule, an implicit proxy move would transfer real_ while leaving copied scalar cache and permission state in the source, creating two surprising service identities. Preventing object moves keeps the lifecycle contract simpler. Static type-trait checks verify that HoursProxy is neither copy-constructible nor move-constructible.

11. Distinguish the purpose of similar wrappers
Requirements and mechanism

SAY
Proxy and Decorator can both implement an interface and contain another implementation. A decorator normally adds independently selectable behavior to a component. A proxy stands in for a service to control access, location, or lifecycle. Our proxy creates its own real service on demand and manages a freshness policy. A diagram alone cannot settle which intent best describes a design; the requirements explain it.

For an inexpensive local value, directly reading Source may be simpler than either wrapper. For a service used exactly once, caching may add memory and complexity without avoiding work. Measure actual request patterns before optimizing. When a proxy is useful, expose enough diagnostics to test the behavior. The reads counter and loaded query let the example verify avoided work rather than merely checking that the printed hour looks right.

12. Keep service existence separate from cached data
Mechanism in C++

SAY
The proxy has two different empty-or-present states. The unique pointer real_ owns the service after it has been constructed. The optional cached_ remembers an integer result after a successful read. Initially both are empty. A permitted cache miss creates the service, reads it, and fills the cache. Invalidation clears only the remembered integer. The next read therefore reuses the already-created service but fetches new data. Confusing these states can cause needless reconstruction or a stale answer after invalidation. The loaded query reports service existence, not freshness. A diagram of this code needs both facts; a single vague loaded flag would conceal an important distinction.

13. Zero is a value, not the absence of a value
Mechanism in C++

SAY
Using zero as an empty marker creates a hidden collision with midnight. If the cache variable starts at zero and a condition treats zero as missing, a valid zero result looks uncached forever. The chapter uses optional<int> so presence is stored separately from the integer. An engaged optional holding zero tests true as an optional. Dereferencing it yields zero, which is then returned normally. This is why the chapter performs two reads after caching midnight and checks that only the first reaches Source. The output value alone would not catch repeated unnecessary reads. When designing state, ask whether your chosen marker can also be a valid business value.

14. Revocation and invalidation are different operations
Mechanism in C++

SAY
Revocation answers who may obtain a result now. Invalidation answers whether the remembered result may be reused. The source implements them as separate operations. Denying access does not itself erase cached data, and changing Source does not automatically invalidate it. After we reallow access, the old cached answer may therefore remain until an explicit invalidation or refresh. This is not a bug if it is the stated policy. It would be a bug if the application promised that every permission change forces freshness. Write state-transition tests that distinguish these promises. A realistic service may use revisions, change notifications, or maximum age, but each choice needs a precise rule for when it takes effect.

15. The proxy owns the service but borrows the source
Mechanism in C++

SAY
Ownership tells us who keeps an object alive and eventually destroys it. HoursProxy owns RealHours through unique_ptr, so destroying the proxy releases the service automatically. Both proxy and real service borrow Source through references. Neither reference extends Source's lifetime. Main therefore constructs Source first, then the proxy, so local destruction happens safely in the reverse order. Hours deletes copying and moving, keeping service objects stable in place. You may move a unique_ptr that owns one without moving the service object itself. The compiler checks these deleted operations and override signatures. It does not generally prove that an arbitrary borrowed source will outlive every user, so that remains a construction and review responsibility.

16. Record success only after the real operation succeeds
Mechanism in C++

SAY
The miss path assigns to cached_ only after real_->opening returns a value. If a future real-service operation throws before returning, that assignment is not reached and no invented successful answer is stored. The service may still exist, so a retry can use it; what state it retains after failure depends on its own contract. Allocation failure before real_ is assigned leaves the owner empty. These are distinct failure states worth testing if the real service later gains failures. The current program is single-threaded. Two simultaneous misses, or a revocation racing a return, would require a synchronization policy. Virtual methods and smart pointers do not automatically make the shared state safe for concurrent access.

42. Extension solution and design review
Practice and extension

SAY
The solution checks permission before invalidating, then calls opening to reuse the ordinary lazy-fetch path. Checking only inside opening after invalidation would erase valid cached state on a denied request, violating the lab requirement. Repeated permission checking is small and keeps the existing opening contract unchanged; a factored private permission helper is a reasonable cleanup.

A useful proxy must document freshness, access checks, and failure behavior as carefully as its interface. Test the work it avoids and the states it preserves.

46. Refresh has a failure-ordering contract too
Recall and transfer

SAY
The lab adds refresh, which promises to fetch a new answer during this call rather than wait for a later one. It first checks permission, then invalidates, then calls opening. Why check permission before clearing the cache? Because a denied operation should not silently discard the old cached state in this design. The solution tests that distinction: deny refresh, change the source, reallow access, and observe that an ordinary opening still returns the retained old value until a successful refresh. Reusing opening keeps one implementation of lazy construction and read behavior. Notice that a permitted refresh whose future real read fails would leave the cache empty; that is a separate guarantee from denied-refresh behavior.

47. Similar wrapper shapes can serve different purposes
Recall and transfer

SAY
A class diagram may show both a Proxy and a Decorator implementing an interface while containing another implementation. That shape is not enough to choose the name. Ask why the wrapper exists. Here it stands in for a service, creates the real service on demand, and enforces an access and freshness policy. A decorator usually combines separately chosen added behavior around a component. These intents can coexist in a larger system, but naming the intent helps reviewers find the important tests. For an inexpensive local integer or a service called once, direct reads may be easier and equally fast in practice. Caching is a contract change as well as a possible optimization.

48. Audit every exit that returns an answer
Recall and transfer

SAY
When you review a proxy, start with every line that returns an answer. Can any route reach that line without the required access decision? Next inspect the state that makes a fast route possible. Is cached zero distinguished from an empty cache? What event removes a stale result? Finally inspect ownership: which object keeps the real service alive, and which borrowed source must outlive it? This three-part review catches mistakes that a correct-looking output cannot reveal. Explain Proxy as a controlled substitute, then prove its particular control rules. A pattern name does not validate permission logic, refresh behavior, or lifetime on its own.
