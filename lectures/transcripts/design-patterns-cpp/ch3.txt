Chapter 3: Builder: cross a checked boundary from draft to product
Dr. Charles Dorner

1. An unfinished plan should not reach the presenter
Problem and first design

SAY
A session planner collects choices one at a time. A user types a title, adds an activity, and perhaps adds two more. The presenter should receive a ready plan, not a half-filled form. Our rules cover several kinds of information: the title cannot be empty, the number of activities must be between one and three, each duration must be between one and sixty, and the total cannot exceed ninety. A draft can temporarily fail some of those whole-plan rules while the user edits it. The design problem is therefore not simply storing fields. It is making the moment of readiness visible so other code can trust a finished plan.

2. A draft and a product make different promises
Problem and first design

SAY
An invariant is a rule that must remain true at a stated boundary. The builder's draft does not promise to be ready. It promises only that accepted individual steps have met their local rules. The finished Plan has a stronger promise: it is complete and within the total limit. If both states use one publicly mutable structure, every consumer must remember which state it received and whether validation was already done. The Builder pattern separates these duties. One object gathers choices; another represents a valid result. This is useful when inputs arrive in stages. If all required values arrive together in one small call, a checked constructor may be simpler.

5. The contract we must preserve
Requirements and mechanism

SAY
A staged planner that publishes independent snapshots. PlanBuilder stores draft values and alone can call the private Plan constructor after validation. Products own copied data and expose only read access, so partial setup cannot leak through the product API.

Require a nonempty title and 1–3 activities. Accept activity durations 1–60 minutes and finished totals at most 90. Keep earlier products unchanged when the builder changes or rejects a step.

Every successfully built or copied Plan has a title, valid activity count, valid durations, and total at most 90. The builder may be incomplete but never publishes that state as a Plan. Previously built snapshots are independent of later builder changes. These are the rules that define a correct extension, even if it has the right C++ types. A checked Plan(title, durations) constructor is smaller when all data is available together. A validated factory function also works. The builder is justified by staged input and reusable construction recipes.

6. The plan has rules that span several inputs
Requirements and mechanism

SAY
A teaching session planner needs a title and between one and three timed activities. Each activity lasts from 1 through 60 minutes, and the whole plan lasts no more than 90 minutes. A valid plan can be handed to a presenter. An unfinished draft cannot. The title and durations arrive in separate setup steps, perhaps from a form or a configuration reader.

The simplest implementation is a struct with a title and a vector of minutes. Fill the fields and then call validate before using it. That can be enough in a short local function. The difficulty appears when the draft escapes to other code before validation or when one caller forgets the check. The same type then means both “possibly incomplete” and “safe to present.”

7. Separate the draft from the finished product
Requirements and mechanism

SAY
A builder is an object that gathers construction choices in steps and produces a usable product when those choices are complete. This is the Builder pattern. PlanBuilder can be incomplete. Plan cannot be created through the public interface until build succeeds. The design makes the boundary visible: collecting settings is different from possessing a valid plan.

named sets a nonempty title. add accepts one valid activity while respecting the three-activity limit. build checks rules that need the whole draft: a title exists, at least one activity exists, and the sum is at most 90. A draft with two 60-minute activities can exist, but build rejects it. That is deliberate; intermediate choices are not claimed to be a finished plan. A form could let a user edit such a draft before trying again.

8. Why friendship is narrow here
Requirements and mechanism

SAY
Plan has a private constructor and private data. friend class PlanBuilder grants this one named class access to the private constructor. Friendship is permission, not inheritance, ownership, or automatic trust in every caller. It is not symmetric or transitive. The builder is responsible for checking its draft before using that permission. No other public function in this example can create an invalid Plan by filling fields afterward.

The finished Plan exposes a title reference for reading and a computed total. Its public interface has no setters. Calling title returns a borrowed const string reference, valid only while that Plan remains alive and unchanged by assignment or movement. Returning a copy would provide a simpler lifetime contract at the cost of copying the title. Do not retain the borrowed reference after the plan dies.

build returns Plan by value. The constructor receives a string and vector by value and moves those parameters into its members. Because build itself is const and passes its own members as lvalues, the constructor parameters are copies of the draft. The resulting plan therefore owns independent data. Later builder changes cannot alter earlier products. Plan explicitly defaults its copy constructor. This suppresses implicit move operations, so constructing or assigning it from an rvalue uses copying instead and leaves the source valid. Moving the builder’s temporary constructor parameters into the new product is still safe: those parameters are ordinary local values, not previously published plans. C++17 can construct the returned product directly in its destination; correctness must not depend on counting visible copy calls.

9. Chaining steps does not create magic
Requirements and mechanism

SAY
named and add return PlanBuilder&, a reference to the same builder. return *this dereferences the implicit this pointer to refer to the current object. This supports builder.named("Practice").add(30).add(30): each call returns the object on which the next call operates. Chaining is an optional convenience. It is not what makes the design Builder; staged construction and the valid-product boundary are the important parts.

The member functions check invalid values before changing their vectors or titles. A rejected add(0) leaves the existing draft unchanged. A fourth activity is rejected even if it would fit the time total, because count and total are separate rules. The maximum sum of a draft is 180, so this example’s int arithmetic cannot overflow on the required compiler platform. A production planner with unbounded counts needs a different bound or checked accumulation.

The program demonstrates two snapshots from one builder. After 30 and 30, first totals 60. Adding another 30 produces second at 90. first still totals 60 because it owns its own copied durations. build does not reset the builder in this design. That policy is part of its contract, not a universal rule. A consuming builder might move data out and require a reset; a reusable builder might return snapshots, as ours does.

10. A director is just a reusable recipe
Requirements and mechanism

SAY
introduction records a repeated sequence of builder calls. Such a recipe is called a director in the classic Builder vocabulary. A director does not have to be a class. Here an ordinary function creates a builder, names the plan, adds two activities, and returns the result. The caller receives a Plan without knowing every construction step. If no recipe repeats, callers can drive the builder directly.

The broader Builder pattern can use one recipe with different builders to produce different representations, such as an executable session plan and a printed outline. Those products need not share a base type. A common step interface can express named and add, while each concrete builder exposes its own finished result. A function template can also apply one recipe to builders with matching operations. Introduce that machinery only when the second representation exists; one valid-plan builder does not need an abstract builder hierarchy.

For a small object with two required values available at once, a checked constructor or a named factory function is simpler. A builder becomes valuable when many optional choices accumulate, validation spans choices, or setup order and product readiness need clear separation. A fluent chain of trivial setters on a publicly mutable product does not provide the same guarantee. Ask what invalid state the design prevents, not how attractive the chained syntax looks.

11. build is the gate that turns choices into a promise
Mechanism in C++

SAY
PlanBuilder stores the draft fields privately. named rejects an empty title, and add rejects a bad duration or a fourth activity. build performs the checks that need the assembled draft: a title, at least one activity, and a total at most ninety. It then calls the private Plan constructor. The result is a separate value that the caller may hand to a presenter. This division gives errors a useful location. A zero-minute activity fails at add because no later choice can make that activity valid. A total of one hundred twenty fails at build because it is a property of the assembled plan. The API shows exactly where the stronger promise begins.

12. Friendship grants access; it does not perform validation
Mechanism in C++

SAY
Private access keeps ordinary callers from filling Plan fields or invoking its checked construction path incorrectly. The friend declaration gives PlanBuilder permission to use the private constructor. That permission is checked during compilation. It does not make the compiler understand the ninety-minute rule, and it does not automatically run validation. A careless new method inside the friend could still call the constructor with bad data. Friendship is therefore a deliberate trust boundary. It is not inheritance: the builder is not a kind of Plan. It is not ownership either. When maintaining this code, review each place that can create a Plan and confirm that it establishes the same invariant.

13. A snapshot owns its data instead of borrowing the draft
Mechanism in C++

SAY
The term snapshot means a value representing the draft at one point in time. build is const, and it passes the draft's string and vector into constructor parameters by value. Those parameters become copies. The constructor moves the temporary parameter values into Plan members, but it does not move the builder's own stored fields out. This distinction explains the chapter's sixty-minute and ninety-minute plans: adding a third activity changes the builder and the second product, while the first remains sixty. Returning by value gives the caller its own Plan. Correctness should not depend on counting copies, since C++ can construct the returned object directly in the destination.

14. Chaining returns the same builder, not a fresh draft
Mechanism in C++

SAY
In named and add, the result type is PlanBuilder followed by an ampersand. That is a reference to a builder, not a copied builder value. The implicit this pointer identifies the current object; writing *this refers to that object itself. Returning it lets named(...).add(...).add(...) act on one draft in sequence. This fluent syntax is convenient, but it is not the essential Builder idea. The ready-product boundary matters more. Each operation checks a rejected argument before mutating the draft, so add(0) leaves the old state usable. A version returning a copy by mistake could make later chained edits land on temporary drafts and produce surprising results.

15. A director is a recipe; reset is a separate policy
Mechanism in C++

SAY
The introduction function names a plan and adds twenty and thirty minutes. It packages a repeated recipe so callers do not need to repeat those steps. In Builder vocabulary, that recipe is a director. A separate director class would add little here, so the chapter uses a function. Another independent choice is what happens after build. Our builder keeps its draft, allowing another snapshot after additional edits. The extension adds reset, which clears only the builder's draft. Existing products keep their own copied data. A builder that consumes its draft can also be reasonable, but clients need a different contract. Never assume that all builders reset or consume just because they share a pattern name.

38. Exercise 03.6: Justify a decision

45. Test failure without destroying useful state
Recall and transfer

SAY
The best tests inspect what is left after an error, not only whether an error happened. Starting with a valid ninety-minute draft, add(0) should throw and leave the draft able to build the same ninety-minute Plan. A fourth activity should fail for the count rule even if it is only one minute. An overlong draft should fail at build without publishing an invalid product. After reset, build should report an incomplete draft, yet the previously returned Plans should still read correctly. These checks expose accidental mutation before validation, hidden sharing, and an unclear reset policy. They are maintenance tests because future fields and editing operations must preserve the same boundaries.
