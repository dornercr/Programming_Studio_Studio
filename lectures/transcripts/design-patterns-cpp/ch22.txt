1. The parts stay; the reports multiply
Problem and first design

SAY
A workshop order contains bolts and cable. Bolts are measured in pieces; cable is measured in whole metres. Pricing is easy at first: multiply each quantity by its rate and add the results. Then the workshop asks for labels, packing summaries, and audit reports. The data types are stable, but the operations keep growing. Putting every new report into every part class spreads reporting changes across those classes. We need to send a mixed list through one traversal while each outside operation still receives the exact kind of part. Visitor addresses that direction of change. Before reaching its mechanism, keep the two units distinct and the original arithmetic visible.

3. For one operation, direct functions are enough
Problem and first design

SAY
This complete baseline uses two small value records and overloaded price functions. Overloading gives functions the same name with different parameter types. The compiler chooses the Bolts overload for the bolts variable and the Cable overload for the cable variable. Each constructor checks its own quantity before any price calculation. The program prints one total, and it does not need inheritance, heap allocation, or a visitor. This is a strong choice when callers already know the concrete types and pricing is the main operation. The limitation appears when callers traverse a mixed collection through one common interface and many outside operations need each exact type.

4. A base reference does not select a derived overload
Problem and first design

SAY
This demonstration creates one Bolts object and gives it two names: a concrete variable and a reference viewed as Part. The two report calls print different labels even though they refer to the same object. The reason is overload resolution, the compiler's choice among functions with the same name. That choice uses the type known at the call site. report(as_part) selects the Part parameter; it does not search for a better overload based on the object's runtime kind. In the chapter's Visitor interface there is no Part overload, so a direct visit of a Part reference would fail to compile. Adding a fallback overload would compile but would not create automatic concrete dispatch.

5. The contract we must preserve
Requirements and mechanism

SAY
Price a mixed workshop order. Each Part accepts a Visitor, and each concrete part forwards its own precise type. Price implements the type-specific operations and retains a checked running total.

Support bolt counts and cable lengths with distinct units. Compute exact integer-cent totals with a one-million-cent limit. Keep reporting operations outside stable part data classes.

Each part quantity is in 0 through 100. Price is between zero and one million cents. A visitor reads parts without taking ownership. Every concrete visitor supplies an operation for every declared element kind. These are the rules that define a correct extension, even if it has the right C++ types. Virtual price members are simpler if price is intrinsic and the operation set is stable. A variant and std::visit suit a closed set of simple value types. Visitor is useful when adding operations across stable element types is the main change.

6. The problem: the parts stay familiar while reports multiply
Requirements and mechanism

SAY
A workshop order contains two kinds of item: a group of bolts counted by pieces, and a cable measured in whole metres. Each quantity must be between zero and one hundred. A price report charges five cents per bolt and forty cents per metre. The total cannot exceed one million cents. Direct price methods on Bolts and Cable are a reasonable first design when price is the one operation every item must offer. The next requests are labels, packing summaries, and audit reports, each with different output needs.

Adding every report as another virtual member makes stable data types change whenever a reporting team needs a new operation. A large switch on a type code moves the work outside the classes but loses compiler-checked access to the distinct data of each kind. We need to let an outside operation receive the exact kind of part while callers still traverse a mixed list through the common Part interface. The Visitor pattern provides this connection, at a cost: the set of element types becomes explicit in the visitor interface.

7. One visitor operation has one entry point for each kind
Requirements and mechanism

SAY
Visitor declares two overloaded visit functions: one taking const Bolts& and one taking const Cable&. Overloading means several functions share a name but have different parameter lists. Price implements both. It keeps a running cents_ total and uses the correct unit for each kind. Bolts exposes a count getter; Cable exposes a metres getter. Neither class needs to know the price rules or the output format of a future label report.

Part declares accept(Visitor&) const. Each concrete element implements accept and calls visitor.visit with a reference to itself. The const qualifier at the end means this accepting operation cannot change the element through its ordinary members. The visitor reference is not const, because a report visitor may update its own running result. A read-only element and a changing report are compatible: const applies to a particular object and access path, not to the entire call tree.

8. Why a single overloaded call is not enough
Requirements and mechanism

SAY
Imagine a Part& variable that actually refers to a Bolts object. Calling visitor.visit(part) cannot select visit(const Bolts&) merely because the runtime object happens to be bolts. Overload resolution, the choice among same-name functions, uses the expression’s static type during compilation. Here the static type is Part&, and Visitor does not offer a Part overload. A downcast at every caller would move type-checking knowledge into all loops, defeating the goal of a common traversal.

Instead the loop calls part->accept(price). Virtual dispatch chooses Bolts::accept during execution because the actual element is Bolts. Inside that member, *this has the type const Bolts, so the compiler selects visit(const Bolts&) when compiling that function. Calling the selected virtual visit then dispatches to the implementation belonging to the actual visitor object, Price. The behavior depends on both the element kind and visitor kind. This two-stage selection is called double dispatch. It combines static overload choice with virtual calls; it does not make ordinary C++ overload resolution dynamic.

9. Follow ownership without giving it to the visitor
Requirements and mechanism

SAY
The parts vector owns unique_ptr<Part> values whose actual objects are Bolts and Cable. Part has a virtual destructor so destroying an owning base pointer properly destroys the complete concrete object. Price is a separate local object in main. During accept it borrows each part through a const reference. It does not retain those references, own the parts, or change their quantities. After traversal, the visitor owns only its numeric result.

The forward declarations class Bolts and class Cable tell the compiler that those type names exist before Visitor uses references to them. A reference declaration does not need the complete class layout. The later class definitions provide constructors, getters, and accept bodies. This arrangement resolves the header dependency between the visitor interface and its element types. In a multi-file program, separate headers and forward declarations keep that dependency controlled; putting every implementation in one header can make every report change trigger broad recompilation.

10. The price calculation also needs ordinary correctness
Requirements and mechanism

SAY
Design structure does not make arithmetic automatically safe. Constructors reject negative quantities and quantities above one hundred. Each price term is therefore bounded before multiplication: at most five hundred cents for bolts or four thousand cents for cable. Price::add checks whether the accumulated total exceeds one million minus the next nonnegative term. Only then does it add. Checking before addition avoids computing an overflowed result and trying to diagnose it afterward. The chosen limits fit the required int range on the documented compiler platform.

The sample order contains three bolts and two metres of cable. The terms are fifteen and eighty, so the result is ninety-five cents. A fresh visitor starts at zero; a zero-quantity element changes nothing. For the limit test, two hundred fifty visits to a one-hundred-metre cable reach exactly one million. The next visit throws and leaves the old total intact. The visitor therefore has its own invariant and failure policy, separate from those of the elements. Reusing the same Price visitor for another order would accumulate into the previous result unless the caller deliberately creates a new visitor.

11. Choose which direction of change should be easy
Requirements and mechanism

SAY
Adding Labels in the lab changes no Bolts, Cable, or Part class. Labels implements both visits and appends strings with quantities and unit names. The same traversal works. However, adding a new element kind such as Paint requires a new visit overload in the Visitor interface and an implementation in every concrete visitor. This can be useful: the compiler forces every operation to decide how to handle Paint. It can also be costly when new element kinds arrive frequently and the operation set barely changes.

C++17 offers another option for a closed set of types: std::variant<BoltsData, CableData> can store exactly one alternative, and std::visit selects a callable for the active alternative. This can avoid a heap allocation and a virtual base hierarchy for simple value data. It still makes the type set explicit, and visitors must handle its alternatives. Ordinary virtual members remain simpler when new types are common and the operation set is stable. Visitor is a tradeoff between these directions of change, not a general rule to move every method out of its class.

12. Give every operation an entry for every part kind
Mechanism in C++

SAY
Visitor is an interface for outside operations. It declares one visit overload for each supported part type. Price implements both overloads and owns a running cents total. Part is the common element interface and offers accept. Bolts and Cable each implement accept by passing themselves to the visitor. The loop can now work through Part while the operation still receives a precise concrete reference. This arrangement makes a new operation, such as Labels, one new visitor with explicit cases for both kinds. It also exposes the tradeoff immediately: a new kind of part requires another overload in the Visitor interface and a response from every concrete visitor.

13. Trace both runtime choices and the static bridge
Mechanism in C++

SAY
Double dispatch means the result depends on two runtime kinds: the element and the visitor. Follow a Part pointer owning Bolts while the operation object is Price. Calling accept makes the first virtual choice and reaches Bolts::accept. Inside that member, the compiler knows that *this refers to a Bolts object. It selects visit(const Bolts&) when compiling that call. The selected visit is itself virtual, so execution then chooses Price's implementation of that signature. There are two virtual selections with a compile-time overload choice between them. Ordinary overload resolution has not become dynamic. The accept method supplies the concrete static type that the outer mixed-list loop lacks.

14. Read-only parts and a changing report can coexist
Mechanism in C++

SAY
The signature accept(Visitor&) const contains two different permissions. The trailing const says the operation does not change the part through this call. The visitor parameter lacks const because a report may update its own running result. Inside Price::visit, a const reference lets the visitor read the quantity without taking ownership or making a part copy. Price keeps the resulting number, not a pointer to the visited part. This distinction matters when the order goes out of scope. The report's numeric result can remain useful without keeping parts alive. const is attached to particular objects and access paths; it does not mean every object touched by the whole call tree is frozen.

15. Dependencies do not imply ownership
Mechanism in C++

SAY
The mixed vector owns unique_ptr<Part> handles. Destroying the vector destroys those handles and the complete concrete elements. Part needs a virtual destructor because destruction occurs through the base type. Price is a separate local object owned by its scope, not by any part. A dependency arrow in the class diagram means one type knows or calls another; it does not transfer ownership. The source starts by announcing Bolts and Cable before Visitor mentions references to them. Those forward declarations name types without giving their full layout. Reference declarations can use those names; later complete definitions provide getters and accept bodies. In a larger project, this distinction helps control header dependencies and rebuild costs.

16. Check the total before adding the next term
Mechanism in C++

SAY
The pattern handles routing, but Price still needs ordinary arithmetic discipline. Quantity checks keep each bolt term at most five hundred cents and each cable term at most four thousand. Before adding a nonnegative term, add checks whether the current total is greater than one million minus that term. This avoids forming an excessive total and checking afterward. At exactly one million, a further positive term throws and leaves the total unchanged. The visitor also has lifetime state: its total starts at zero and grows with visits. Reusing the same Price for another order does not reset it. Two identical ninety-five-cent orders produce one hundred ninety if the same visitor accumulates both.

45. Choose which direction of growth should be easy
Recall and transfer

SAY
Think of a grid whose rows are part kinds and whose columns are operations. Visitor groups work by operation, making a new column straightforward: implement each known type's case in one visitor. A new row is broader because every visitor must decide what it means. Ordinary virtual members favor the other direction when new kinds appear often and operations stay stable. For simple value data with a closed type set, std::variant and std::visit can offer another arrangement without the same owning base hierarchy. They still make the alternatives explicit. The right choice depends on expected change, not on whether a diagram has more arrows or a pattern name sounds advanced.
