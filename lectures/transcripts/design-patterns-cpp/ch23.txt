3. The simplest comparison can answer the wrong question
Problem and first design

SAY
The first small design compares a number to eighty and prints a label. That works if every number is already valid Celsius. When one hundred arrives tagged Fahrenheit, the same branch prints ALERT even though the normalized temperature is about thirty-seven point eight Celsius. 5. Rejecting a request is not the same as rolling it back
Problem and first design

SAY
Here we isolate the batch problem using integer identifiers rather than the full monitor. The history begins with ten, and the proposed batch contains eleven followed by an invalid zero. The direct version appends eleven before throwing, so its count becomes two. The staged version copies the old history, changes only the copy, and swaps after the whole batch passes. This simplified program models the capstone’s commit design without adding units, policies, or states yet.

7. The contract we must preserve
Requirements and mechanism

SAY
A transactional workshop temperature monitor. SampleAdapter applies the Adapter lesson through value conversion; Monitor and its replaceable AlertRule implement Strategy; ReportFacade centralizes the reporting request. A private staged vector supplies a single commit point. An enum and checked methods implement the four-state lifecycle without the polymorphic State pattern. No claim is made that this synthesized system appears in the attachments.

Accept only positive increasing identifiers, C or F units, finite values, and normalized temperatures from -40 to 125 C inclusive. Admit batches only while running; commit every record in a batch or none; permit an empty running batch. Store at most eight records; preserve each intake decision through rule changes. Permit rule replacement only when idle or paused; make stopped final; produce deterministic reports.

The live history has at most eight valid Celsius samples with strictly increasing positive identifiers. Every recorded alert is the decision made by the rule active when that sample was admitted. A rejected batch or invalid state action leaves monitor state and stored history unchanged. Every live Monitor has one owned nonnull rule; each rule answers without throwing or external side effects. Monitor object identity is fixed: copy and move operations are deleted; transferring an owning handle does not move the object. These are the rules that define a correct extension, even if it has the right C++ types. A single loop is better when all input is already valid Celsius and only one immediate comparison is needed. A free predicate can replace the virtual interface when policies have no separate lifetime or configuration needs. Direct append with compensating erasure is possible, but its rollback obligations become harder to audit as fields and failures grow.

9. The job: trust the whole path, not just the temperature formula
Requirements and mechanism

SAY
A small teaching workshop records temperatures from benches that use two sensor formats. Some readings arrive in degrees Celsius, marked C. Others arrive in degrees Fahrenheit, marked F. The operator starts a session, admits batches of readings, pauses to change the alert rule, resumes work, and stops the session. A report must show what the program accepted and what decision it made at that time. This is a teaching monitor, not equipment that protects people or controls a heater.

The hard part is not one calculation. It is keeping several promises together. A unit conversion must happen before a rule judges the temperature. An invalid batch must add nothing. A rule change must affect future readings without rewriting history. A stopped session must remain stopped. An object must not use a rule that has already been destroyed. The capstone joins these concerns in one complete program whose printed report is checked against an exact string.

The input is a vector of RawSample values supplied by the program. Each value contains an integer sequence identifier, a number, and a unit character. Identifiers must be positive and increase across the entire session, including within one batch. Accepted temperatures must lie from -40 through 125 Celsius, including both endpoints. The monitor stores at most eight readings so every full history is small enough to inspect. Empty batches are allowed only while running and change nothing.

We deliberately keep file reading, clocks, sensor drivers, threads, and network calls outside this program. They would add failure modes that hide the design lesson. A real integration can place those concerns before the adapter. It must define its own packet, timing, and recovery contracts. The complete C++ program here already has a useful boundary: either a supplied batch becomes accepted history in full, or the monitor keeps its old history.

10. Stage one: the useful ten-line idea and its first failures
Requirements and mechanism

SAY
The first reasonable design is a loop that compares each number with a limit and prints a label. If every input is valid Celsius and nothing must be remembered, that loop is enough. Do not start with an inheritance tree. Begin by stating the assumptions that make this small design correct: one known unit, one rule, no paused state, and no requirement to reject a whole batch together.

The excerpt below shows the first design. It is intentionally an incomplete illustration, not the delivered executable. With the Fahrenheit reading 100 F, it prints ALERT because 100 is greater than or equal to 80. But 100 F is about 37.8 C, which is below the intended 80 C limit. The comparison is mathematically valid and still answers the wrong question. The missing assumption is the unit of the value.

Adding a unit conversion inside the loop fixes this one error. Later a report and a replay tool also need the same conversion. Copying the formula into all three callers creates three places to disagree about unknown units and valid ranges. A named adapter now earns its place: it turns the outside representation into one internal Sample representation and checks the boundary once. Its purpose is agreement, not the extra class syntax.

The next failure appears when a batch contains a valid first item and a bad second item. Appending directly to live history leaves the first item stored even though the whole request is rejected. That result violates the batch contract. A temporary proposed history, followed by one commit step, fixes the actual problem. Only after these concrete failures do we introduce the larger structure in the finished program.

11. Stage two: name the data before spreading behavior
Requirements and mechanism

SAY
RawSample and Sample are small data types with public fields. A raw sample still carries its unit. A normalized sample has a field named celsius, so later code does not need to guess. Record adds the decision made when that sample entered the monitor. Storing this decision matters: a later rule may classify the same number differently, but the old record is an account of what happened earlier.

The adapter first rejects nonpositive identifiers and nonfinite input values. A finite value is an ordinary bounded number rather than infinity or NaN. NaN means not a number. Ordinary comparisons with NaN do not behave like a simple out-of-range test: both NaN < -40 and NaN > 125 are false. That is why the program uses std::isfinite as well as comparisons. It checks the converted value too, because arithmetic on an extreme finite input can produce infinity.

For Fahrenheit, subtract 32, multiply by 5, then divide by 9. The constants have decimal points so the operations use floating-point arithmetic. Writing 5 / 9 first with two integer operands produces zero. Therefore (value - 32) * (5 / 9) produces zero for every ordinary finite value. The correct source keeps the intended order and floating-point operands visible. The uppercase letters C and F are the only supported tags; guessing a unit after receiving K would conceal a data error.

The allowed range is a program contract, not a claim about every real sensor. The boundary checks apply to the represented floating-point result. An outside device that needs tolerance near a physical limit requires a written tolerance policy and tests; silently adding a small epsilon can admit forbidden values. This example uses exact easy-to-check Fahrenheit cases, 176 F and 212 F, to test normalization to 80 C and 100 C.

12. Stage three: two real changes justify one replaceable rule
Requirements and mechanism

SAY
A fixed threshold is still a good implementation for a workshop with one permanent policy. Here the operator must change the policy between batches, and the lab adds a different kind of rule. If that change requires editing conversion, history, and reporting, the boundaries are wrong. We isolate the question that varies: given one normalized sample, should this reading be marked as an alert?

AlertRule describes that question through a virtual function. Virtual means the call chooses the implementation associated with the actual object at execution time. The compiler checks that AtLeast supplies a function with the declared shape; override asks it to catch a mismatch. The = 0 makes the base operation abstract: an AlertRule by itself has no answer. The monitor calls through the shared interface and does not inspect which concrete rule it owns.

The parameter const Sample& is a borrowed view of the existing sample, not a copied sample and not ownership of it. Const prevents changes to that sample through the parameter. The second const, after the parameter list, promises not to change ordinary fields of the rule through this call. Noexcept promises that this operation will not let an exception escape. It does not prove that a rule is correct or free from side effects. A rule that violates noexcept by throwing terminates the program; it does not produce an ordinary rejected batch.

The design contract therefore adds a behavioral rule: judging a sample must have no outside side effects. AtLeast merely compares two numbers and meets that promise. Logging from inside alert, incrementing an external counter, or sending a message would weaken the all-or-nothing story even if records rolled back. If rules later need historical context, change the interface deliberately and review how that context participates in a transaction. Do not hide new state behind mutable fields.

AtLeast stores an inclusive Celsius limit. A reading equal to the limit is an alert. Its constructor rejects a nonfinite or out-of-range limit before the rule can enter service. An alternative is a function object or std::function with a documented signature. That can be simpler for a few stateless policies. The explicit interface here makes ownership, replacement, and a separately named lab extension easy to inspect; it is not a demand that every comparison become polymorphic.

13. Stage four: permitted actions belong to an explicit state
Requirements and mechanism

SAY
Two booleans such as started and paused allow confusing combinations unless every caller is careful. A stopped flag adds still more combinations. A finite-state machine replaces that loose collection with one named state and a defined set of transitions. Finite means there are only a fixed number of possible states. Transition means a permitted change from one state to another after an action.

The monitor begins idle. Start moves idle to running. Pause moves running to paused. Resume moves paused to running. Stop moves either running or paused to stopped. Stopped is final for that object: create a new Monitor to begin another session. Ingest is legal only in running. Replacing the rule is legal in idle or paused. Reporting is a read operation and is permitted in any state.

Every transition checks its precondition before assigning state_. A precondition is something the caller must make true before the operation. Calling resume while idle throws a logic_error and leaves the state idle. A caller should not repair this by forcing the state field. The field is private precisely so a public operation remains the single place that enforces the rule.

An enum class and short member functions are sufficient here. The identifier State names an enum; this is not the polymorphic State pattern from Chapter 19 or the attachment's State, ConcreteStateA, and ConcreteStateB class family. Monitor checks state_ directly instead of delegating requests to a current state object. The State pattern becomes useful when each state has substantial independent behavior, many operations, or state-specific data. Our four states control only a few gates, and a class tree would make the program harder to follow. The state diagram describes behavior without dictating a particular implementation technique.

14. Stage five: validation, a proposed history, and a commit point
Requirements and mechanism

SAY
Monitor::ingest first checks running state and spare capacity. The capacity test subtracts the current record count from eight before comparing the incoming batch size. This is safe because every accepted history already has at most eight records. The operation then copies records_ into a local vector named staged. All further changes go to this proposed history while the real history remains available unchanged.

The range-based for loop reads one raw item at a time. In for (const auto& raw : batch), the colon means take each element from batch. Auto asks the compiler to infer the element type. The ampersand makes raw a reference to that element; const prevents this loop from changing it. Conversion returns a new Sample value called s. Each accepted identifier must exceed the last staged identifier, so the check catches both old duplicates and duplicates introduced earlier in this same batch.

After conversion and order checks, the monitor calls the rule and appends a Record to staged. Only when the loop finishes does records_.swap(staged) exchange the two vector contents. With the standard allocator used here, vector swap is nonthrowing. This is the commit point: before it, records_ is the old history; after it, records_ is the complete new history. The local staged vector then owns the old storage and destroys it when the function returns.

If copying, conversion, order validation, or appending throws before the swap, local cleanup destroys staged and records_ keeps its old contents. This is the strong exception guarantee for the monitor history: failure leaves the observable stored history unchanged. It is a form of rollback achieved by delaying changes, not by trying to undo half a loop. The supplied rules have no outside effects, so there is no external work to reverse.

The guarantee has limits. It does not make the program recover from termination, a process crash, or a defective rule that breaks its contract. It does not write durable records to disk. It does not undo a message sent by a future callback. Strong exception safety concerns ordinary C++ exception flow for the objects covered by the contract. Naming the scope of the promise prevents a useful local technique from being mistaken for a complete database transaction.

15. Stage six: ownership and reports without hidden lifetime traps
Requirements and mechanism

SAY
A Monitor owns exactly one rule through std::unique_ptr<AlertRule>. Ownership means responsibility for ending the resource lifetime. Unique means this pointer cannot be copied to create another owner. The constructor receives an owning pointer by value and moves it into rule_. std::move allows ownership transfer; it does not create a second rule. The monitor rejects a missing pointer so later calls need not repeatedly test for null.

The virtual destructor on AlertRule makes deletion through the base pointer reach the derived destructor. Replacing the owning pointer destroys the old rule after the replacement has passed the state and null checks. Destroying the Monitor destroys its remaining rule and its vector. The LifetimeRule used in checks borrows a flag that remains alive outside the monitor scope. Its destructor changes that flag, letting a test observe real cleanup without assuming that absence of a crash proves correctness.

A Monitor itself cannot be copied or moved. The four declarations ending in = delete make those operations compile-time errors. An automatic move would empty the old rule pointer while leaving the old state possibly running; calling ingest on that moved-from object could then follow a null pointer. For this session object, a fixed identity is the simpler contract. Moving a unique_ptr that owns a Monitor would still transfer its handle without moving the Monitor object. The type-trait static_assert checks verify these restrictions during compilation; they remain active regardless of NDEBUG. The small Sample and Record value types can still move safely because their fields preserve valid values.

ReportFacade supplies one simple request, summary, over history access, row formatting, and alert counting. It borrows a const Monitor for the duration of the call and returns an independent string. The caller need not know how rows are traversed or how counts are formed. A free function would be a reasonable equivalent for this small service. The facade earns its place as a reporting boundary; it does not own the monitor or repair invalid monitor state.

The records accessor returns a reference to the vector object. That avoids copying the history, but callers must respect its lifetime. Do not retain an element reference or iterator across ingest, because the commit can replace storage. A reference to the vector object itself still names records_, but its contents can change. The report uses only a short borrow and returns before any mutation. This single-threaded program does not protect a report from concurrent modification; introducing threads requires a separate synchronization design.

The report uses a classic locale and one digit after the decimal point. Locale describes formatting conventions, such as the decimal separator. Choosing it here keeps the displayed report stable across ordinary machine settings. The final output is not merely illustrative: main compares the generated string with the expected string and fails if they differ. A formatting change is therefore an intentional contract change with a visible test update.

16. Debug the integration by finding the earliest broken promise
Requirements and mechanism

SAY
Consider a wrong implementation that appends the converted first sample directly to records_, then rejects the second sample with an unknown unit. Before the call the history holds identifiers 1, 2, and 3. The submitted batch is {4, 21, C}, {5, 22, K}. The call throws, but the wrong history now ends at 4. A report would gain the row 4: 21.0 C ok and its record count would rise from three to four. The defect is the placement of mutation before full validation, not the wording of the exception.

Another error is rebuilding every Record::alert value after replacement. In the main scenario, reading 2 is 80 C and enters under a limit of 80. After changing the limit to 100, recomputing would print 2: 80.0 C ok and reduce the final alert count from two to one. That silently rewrites the earlier decision. The stored boolean is intentional historical data. If users want a second report that re-evaluates old samples, add it as a clearly named separate operation.

When diagnosing a failure, first write the expected state, count, last identifier, rule, and report before the action. Then trace conversion, order checks, classification, append, and commit. The first point where an invariant becomes false is more useful than the last line that crashes or prints the wrong number. A passing happy-path demonstration would miss both partial commit and rewritten history; the rejection and replacement checks exist to expose those failures.

The tests use check, which throws on a false condition. They do not use assert, whose checks can disappear in a release build when NDEBUG is defined. The rejects helper accepts a callable, runs it, and requires a logic_error-family exception. Invalid arguments and capacity errors belong to that family. Unexpected exception families still escape and fail the executable. These checks prove the listed cases, not every possible input or allocator failure.

17. What the compiler can prove and what execution must establish
Requirements and mechanism

SAY
The compiler verifies names, type relationships, access control, override compatibility, and the use of language syntax. It rejects an attempted copy of a unique_ptr owner. It knows that the declared rule operation is noexcept. It cannot prove that input identifiers arrive in increasing order or that a temperature is meaningful. Those depend on values that the program checks while running.

During execution, raw values enter the adapter, normalized values enter the rule, and completed records enter staged history. Control returns to ingest after each helper call. The heap-allocated concrete rule lives as long as its owning pointer keeps it. The temporary s lives for one loop iteration and is copied into a Record value before it disappears. The finished report owns its characters separately from the monitor.

For n stored records and b new samples, staging and processing take work proportional to n + b, with temporary storage proportional to n + b. A report takes work proportional to n. With the fixed capacity of eight, these costs are tightly bounded for this exercise. Removing the cap while submitting one reading at a time would repeatedly copy growing history and could cause quadratic total work. Measure against the workload before changing the design; a journal, chunked history, or a separate validated batch might support larger sessions with different tradeoffs.

The extension boundary is narrow on purpose. New unit formats belong in adaptation; new alert decisions belong behind AlertRule; new output formats belong beside the report service. A change to ordering, capacity, state rules, or transaction guarantees is a core behavior change and deserves wider tests. Patterns help only when they localize a real source of change. This capstone is complete at its stated boundary while leaving those larger system decisions visible.

18. Reject invalid numbers before ordinary range checks
Mechanism in C++

SAY
A finite value is an ordinary bounded number, rather than infinity or NaN, which means not a number. NaN is an important trap: both a less-than comparison and a greater-than comparison against ordinary limits are false. An implementation that only asks whether a value is below minus forty or above one hundred twenty-five may therefore let NaN pass. SampleAdapter first uses std::isfinite on the incoming number, then validates the converted result as well. Very large finite arithmetic can overflow to infinity during conversion. Unknown tags are rejected rather than guessed. These checks establish the assumptions that alert rules and reports rely on later.

20. The rule’s signature carries several different promises
Mechanism in C++

SAY
Read the rule declaration one piece at a time. The result is bool, a true-or-false decision. const Sample ampersand borrows the normalized sample and prevents changing it through this parameter. 21. Local rollback cannot undo an outside side effect
Mechanism in C++

SAY
Staging protects records_, but it cannot unsend a message. Imagine a future rule increments an external alert counter before a later sample in the batch fails conversion. The live history rolls back, yet the counter has already changed. Even a const noexcept member function could perform such an outside effect through an alias or external service. 25. The commit point is a small operation with a large meaning
Mechanism in C++

SAY
The commit point is the operation that makes the prepared change visible as accepted state. Here records_.swap(staged) exchanges the vectors after every item has passed. With the standard allocator used in this source, vector swap is nonthrowing. Before that line, records_ still holds the old history; after it, records_ holds the entire new history.
