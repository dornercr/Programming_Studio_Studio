1. One sequence is required; global access is a choice
Problem and first design

SAY
Three callers need tickets from one sequence. The successful values must be one, two, and three, with no duplicate within that sequence. After the third ticket, every later request must fail. The chapter resets only when the process starts again; it does not store the count in a file and does not coordinate different programs. Sharing one state is necessary for this small requirement. Giving every function global access to that state is a separate choice. We will first solve sharing explicitly, then inspect what Singleton adds: controlled construction and an access operation that reaches the same instance. We will also study the lifetime and testing costs of that choice.

2. Define the complete state transition
Problem and first design

SAY
An invariant describes the states and transitions we permit. The dispenser starts with next equal to one. A successful take returns the current value and increases next by one. Once next is four, take throws before changing it. Repeated failure must leave the dispenser exhausted; it must not wrap around, restart, or offer another ticket. This small upper bound also avoids integer overflow on the demonstrated path. The expression next_++ is called post-increment: its result is the old value, while the stored value advances. Understanding that one expression is necessary to predict the ticket sequence. We should test both the three successful calls and more than one exhausted call.

Requirements and mechanism

SAY
A bounded process-wide ticket dispenser. A private constructor, deleted copying, and a local static instance control access and lifetime. A separate lock_guard protects mutable state during take. A reference lends the service without transferring ownership.

7. What Singleton adds, and what it combines
Requirements and mechanism

SAY
The Singleton pattern controls construction so callers reach one instance through a shared access operation. TicketDispenser has a private constructor and destructor, deleted copy operations, and a static instance function returning a reference. Ordinary callers cannot create another object or copy the existing one. The function returns a reference because it lends the service; callers must not delete it.

Singleton combines two ideas: restricting instance count and providing global access. You may need the first without needing the second. Passing one ordinary object from main often expresses sharing more clearly, because function parameters reveal who depends on the service. We implement Singleton here to understand its exact mechanism and costs, then use the lab to remove hidden access from a consumer.

static on instance means the member function is called on the class rather than on an existing object. There is no this pointer for that call. The local static variable inside it has a different meaning: its storage lasts beyond one function call. It is initialized when execution first reaches its declaration and is reused on later calls. The returned references therefore all name the same completed dispenser in this program.

8. Once-only initialization is not method synchronization
Requirements and mechanism

SAY
Since C++11, initialization of a function-local static is guarded so concurrent first callers do not each construct the object. One performs initialization while other callers wait for it to complete. If initialization throws, a later call can try again. Re-entering that same local static initialization recursively is not a safe way to resolve dependencies; avoid service constructors that cycle back through one another.

That guarantee concerns construction only. It does not protect later reads and writes to next_. Two threads incrementing an ordinary shared int without synchronization cause a data race and undefined behavior. It is not accurate to promise merely “one lost ticket”: the C++ program has no defined result for that race. Making the constructor private or the object global does not repair it.

The take operation uses a mutex, a lock that allows only one participating thread at a time into the protected region. lock_guard acquires gate_ when the guard is constructed and releases it when the guard leaves scope. Both the exhaustion check and the increment occur under that same lock. If the exception is thrown, stack cleanup still releases the lock. The local static guard and this method lock solve different problems and neither replaces the other.

The expression next_++ returns the old value and then increments the stored integer. The first three successful calls return 1, 2, and 3, leaving next_ equal to 4. Later calls test next_ > 3 and throw before incrementing again. The bounded sequence avoids overflow. Each whole take operation appears indivisible to other calls that use the same mutex. The standard does not promise fairness or which waiting caller gets a particular number.

9. Lifetime and tests reveal the hidden coupling
Requirements and mechanism

SAY
The instance is destroyed during normal program shutdown if it was successfully initialized. Its private destructor prevents ordinary callers from explicitly destroying the borrowed object. In this single executable the accessor identifies one service. Separate processes have separate address spaces and separate instances; dynamic-library boundaries can also require careful linkage and deployment rules. Singleton is not a machine-wide lock, a distributed coordinator, or a persistence mechanism.

Shutdown dependencies deserve care. Another static object’s destructor must not use a service whose lifetime has already ended. A main-owned service with explicit lifetime often makes this ordering easier to see. Deliberately leaking a service to avoid shutdown ordering changes resource cleanup behavior and should never be an unexamined default.

Tests in one process share singleton state. A test that consumes ticket 1 changes what another test sees. Running the second test alone may pass while running the whole suite fails. A reset-for-tests method can hide the problem and may create races if used while work is active. This chapter’s main is a fresh-process demonstration with a known initial state. Its sequential checks verify identity, numbering, and repeated exhaustion; they are not a concurrency stress test.

The lab introduces TicketSource as the operation a consumer needs. admit accepts TicketSource& rather than finding the singleton itself. The production boundary can pass TicketDispenser::instance(), while each test can create a fresh LocalTickets. That technique is dependency injection: supplying a needed object explicitly. It preserves the option of one production instance while making tests independent.

10. Choosing a shared service deliberately
Requirements and mechanism

SAY
A singleton can suit a truly process-wide service with a clear lifetime and little need for alternate instances. It is a poor fit when the program may run two independent sessions, load different configurations in tests, or need controlled startup and shutdown. Global access can make dependencies look smaller than they are because every function can silently acquire the service.

Do not replace every injected reference with a global accessor just to shorten parameter lists. Those parameters explain what the operation needs. Likewise, do not introduce an interface for every tiny value. TicketSource is justified in the lab by a concrete testing requirement: a consumer should work with independent counters as well as the shared production service.

For concurrency, one mutex protects only the state consistently accessed under it. If a future peek method reads next_ without locking, take’s lock does not make that new read safe. If two operations must form one transaction, locking each separately may still allow interleaving between them. Define the operation boundary first, then choose locking or an atomic design that preserves that boundary. Singleton answers where the object comes from; it does not answer every question about its correct use.

11. Controlled construction and global access are two decisions
Mechanism in C++

SAY
TicketDispenser controls how ordinary code obtains an instance. Its constructor is private, so clients cannot create a second dispenser directly. Copy construction and copy assignment are deleted, so they cannot duplicate the existing one by copying. A static member function named instance provides the access point and returns TicketDispenser&. That reference lends the service; the caller does not become its owner and must not delete it. The class also has a private destructor. These C++ access rules are checked during compilation. Together with the function-local static object, they establish this program's controlled instance. They do not automatically make the service persistent, globally unique across processes, or safe for every concurrent operation.

12. The word static has two meanings in this small block
Mechanism in C++

SAY
The static before instance says this member function belongs to the class interface and does not need an existing dispenser object. It has no this pointer. The static inside the function describes the storage and lifetime of a different thing: the local dispenser variable. That object is initialized the first time execution reaches its declaration, then reused on later calls. Since C++11, concurrent first callers do not each build their own copy; initialization is guarded. If construction throws, a later call can try initialization again. This once-only guarantee is useful, but it concerns construction. It does not wrap future calls to take in an invisible lock.

13. Protect the check and the increment as one operation
Mechanism in C++

SAY
A mutex is a lock that participating threads use to take turns accessing shared state. lock_guard acquires the mutex when the guard is constructed and releases it when the guard leaves scope. The chapter keeps both the exhaustion check and next_++ inside that guarded region. If they were protected separately, another call could slip between the check and update and break the operation's meaning. If take throws because tickets are exhausted, stack cleanup still destroys the guard and releases the lock. This is resource management tied to object lifetime, often called RAII. The code does not promise fairness or which caller gets the first ticket. It promises the guarded transition stays consistent.

14. A race has no promised output to memorize
Mechanism in C++

SAY
It is tempting to say two unsynchronized increments merely lose one ticket. In C++, conflicting unsynchronized accesses to an ordinary shared integer can form a data race, which gives the program undefined behavior. There is no reliable output sequence to teach for that broken program. We therefore discuss the failure without running a racy demonstration. The actual chapter uses a mutex to protect the transition. Its sequential main checks identity, numbering, and repeated exhaustion; those are valuable checks but not a stress test of many threads. If a future peek method reads next_, it must follow the same synchronization policy. Locking writes alone does not make an unlocked read safe.

45. Decide whether global access is worth its cost
Recall and transfer

SAY
A process-wide service can be a valid design choice when its lifetime, initialization, and shutdown are clear. It is less suitable when an application may host two sessions, use different test settings, or need controlled restarts. The short call to instance can hide a large dependency: any function can reach and alter the same state. A parameter makes that relationship visible. Do not add interfaces for every tiny value, but do not remove useful parameters merely to shorten signatures either. Choose the service boundary from the required operations and lifetimes. Then decide who owns the instance, how callers reach it, and what synchronization protects its state.

46. Remember three separate questions, not one magic object
Recall and transfer

SAY
Reconstruct Singleton by answering three questions. Identity asks whether callers reach the same service or different ones. Lifetime asks when the service is constructed, how long borrowed references remain valid, and when it is destroyed. Synchronization asks how concurrent operations preserve the state rules. The pattern's accessor and local static address the first two questions in this example; the mutex guards the complete take transition for the third. Tests and injection address the cost of shared history. Now apply these questions to a cache or configuration service. One global object alone is never a full answer. A clear design says what it guarantees, what it borrows, and where its guarantees stop.
