1. An event is not permission
Problem and first design

SAY
Imagine a small import session with a Begin button and a Finish button. Pressing Finish before Begin must not claim that an import completed. The same button therefore has different meaning at different times. We need a record of the current mode and rules for changing it. A finite-state machine is a system with a fixed set of named modes and permitted changes. In this chapter the modes are idle, active, and done. The session remains the same public object while its behavior changes. Our first job is to state which events are allowed. Choosing classes comes later, after we can explain what the program must preserve.

2. Write the complete transition contract
Problem and first design

SAY
Three modes and three event values produce nine possible pairs. Only three pairs are accepted. The six rejected pairs are real requirements, not unfinished branches. A rejection returns false and preserves the current mode. An accepted event returns true and moves to the stated destination. This distinction gives us two things to verify after each event: the result and the mode. Checking only a true result could miss a transition to the wrong destination. The sample is a model of import control. It does not read a file or start a worker. If real work arrives later, its completion and failure events will need rules of their own.

4. A convenient shortcut changes the protocol
Problem and first design

SAY
Here is a tempting maintenance shortcut: let Reset always return the session to idle. That sounds helpful, but our contract permits Reset only from done. The demonstration starts in active and compares the shortcut with the required rule. Both functions compile, and neither uses invalid memory. 5. The contract we must preserve
Requirements and mechanism

SAY
A session with three permitted transitions. Each state returns a proposed next state. Session owns the current state and commits the replacement after the call completes. Returning no pointer is an ordinary rejected event.

Start idle; accept begin only from idle. Accept finish only from active and reset only from done. Reject other state/event pairs without mutation. Replace old state objects only after their handlers return.

Session owns exactly one live state during public calls. Rejected events preserve the current state. A state handler cannot destroy its own receiver through Session. Only declared transitions are accepted. These are the rules that define a correct extension, even if it has the right C++ types. An enum and switch are likely simpler for this exact three-state example. A table works especially well when transitions are data and behavior is small. State objects earn their cost when several state-specific operations or resources would otherwise be scattered.

6. The problem: one session, different rules at different times
Requirements and mechanism

SAY
A local data-import session begins idle. A begin event makes it active. A finish event is accepted only while active and moves it to done. A reset event is accepted only while done and returns it to idle. Every other event is rejected without changing the session. These rules form a finite-state machine: a system with a limited set of named states and permitted changes between them. A state is the current mode; a transition is an allowed change of mode in response to an event.

The simplest implementation uses an enum for the current mode and a switch for each event. That is a good choice for this three-state machine if behavior stays small. The difficulty appears when each state gains different begin, finish, status, timeout, and cleanup behavior, and those decisions spread across many switches. A maintainer can update one switch but forget another. Grouping behavior by state becomes useful when the behavior that belongs together is easier to review in one place. The object-based solution here shows that growth path without claiming it is the shortest solution to three transitions.

7. A state object supplies behavior for the current mode
Requirements and mechanism

SAY
State declares two operations: name and next. name describes the current mode. next receives an Event and returns either an owned proposed next state or no state for rejection. Idle, Active, and Done each implement this interface. Each class therefore gathers the rules for events received while that state is current. The Session context owns exactly one State through unique_ptr and delegates event decisions to it.

enum class Event creates named event values whose type stays distinct from ordinary integers. Event::begin uses the scope operator to select one name from that enum. A unique_ptr<State> return value expresses exclusive ownership of a proposed state. Returning nullptr means no proposed object and therefore no accepted transition. This is a contract chosen for this example. Another design could return an explicit result with accepted, rejected, or accepted-without-change cases when internal actions need to succeed without leaving a state.

8. Understand the two times when choices are made
Requirements and mechanism

SAY
The compiler checks that each concrete state supplies compatible name and next overrides. The class declarations can announce functions before their complete definitions appear. Definitions such as Active::next use the scope operator to identify the class whose member is being defined. Defining the transition functions after all three classes are complete lets make_unique construct their destination types. Forward declarations alone would not provide enough information to allocate a complete object.

During execution, state_->next uses virtual dispatch to call the current object’s implementation. If that object is Active, the event is compared with Event::finish. A match constructs Done; a different event returns no object. make_unique creates the destination and returns its owning pointer. The proposed pointer remains local to send until the operation decides whether to commit. If allocation throws, the old state still exists and Session has not changed its pointer. That failure differs from a rejected event, which returns false normally.

9. Do not destroy the state while its method is still running
Requirements and mechanism

SAY
A dangerous implementation lets a state call a context setter that immediately deletes the current state. That setter may delete the very object whose member function is still executing. Some carefully restricted cases can avoid further access, but it is a fragile rule to maintain: adding a log that reads a member afterward can use a dead object. This design avoids the entire hazard. next only returns a proposal. Session waits for the virtual call to finish and then replaces state_.

The assignment state_ = std::move(proposed) transfers ownership of the new state into Session and destroys the previously owned state. std::move does not itself move bytes or call a transition; it enables the unique pointer’s move assignment. The old handler has already returned at this point. If there is no proposal, send returns false without changing state_. Session deletes copying and assignment and provides no move operation, keeping the non-null state invariant straightforward. A movable Session would need a documented rule for its moved-from state or a safe reinitialization strategy.

10. Rejected events are part of the model
Requirements and mechanism

SAY
There are three states and three event values, so the primary behavior table has nine state-event combinations. Only three are accepted. The other six are not omissions; they are defined rejections. main checks all nine combinations while moving through the normal cycle. In idle, finish and reset are false. In active, begin and reset are false. In done, begin and finish are false. Each accepted event is followed by a state-name check, so a return value alone cannot hide a wrong destination.

This model does not perform a real import, start a thread, or wait for a file. It isolates transition logic for study. A real asynchronous import needs a rule for who sends finish and how a late completion is handled after cancellation. A generation identifier can distinguish a completion from the current run and one from an old run. Adding that protection requires a concrete asynchronous requirement; it should not be implied by a state diagram that only contains begin and finish arrows.

11. State and Strategy solve different change problems
Requirements and mechanism

SAY
A strategy is a selected way to perform a task, such as choosing a sorting or compression rule. It is normally selected because a caller wants a different algorithm. State represents a mode governed by the object’s history and permitted events. Their class shapes can look alike because both delegate through an interface. Their contracts differ: selecting any next strategy may be acceptable, while jumping from idle to done without begin and finish would violate this session’s protocol.

For a tiny stable machine, a transition table or switch remains easier to scan than several classes and heap allocations. Choose State when state-specific behavior grows enough to justify grouping it, or when ownership of mode-specific data becomes important. The lab adds cancel only from active to idle. The key work is not adding one enum word; it is preserving the existing transitions, rejecting cancel from idle and done, and documenting what cancellation means. Testing the full expanded table reveals accidental new transitions that a single happy-path test would miss.

12. Group the rules that change together
Mechanism in C++

SAY
The context is the object that holds the changing mode. Here it is Session. It owns one State object and sends each event to that object. Idle, Active, and Done are concrete states: classes that supply the actual behavior for a mode. The shared State interface promises a name operation and a next operation. 13. A proposal is not yet a committed transition
Mechanism in C++

SAY
A unique_ptr is a handle that owns one object and destroys it when that ownership ends. next returns a unique_ptr<State> containing a proposed destination, or nullptr, an empty pointer, for rejection. That meaning is a rule chosen by this example. It does not mean that every state system must use a pointer to report success. Session first keeps the proposal in a local variable. If it is empty, send returns false and the current owner stays untouched. If it is present, Session may commit it. A system with accepted events that stay in the same mode would need a richer result, because empty currently means rejected.

14. Two choices happen at different times
Mechanism in C++

SAY
The compiler checks that the declared overrides match State's functions. A missing const or a wrong return type can be caught before the program runs. 15. Let the old handler finish before destruction
Mechanism in C++

SAY
The most important line order is call first, replace second. While Active::next executes, Session still owns Active. The returned proposal is stored locally. Only after that call has returned does state_ = std::move(proposed) transfer the destination into Session and destroy the old state. std::move permits a move operation; it does not itself run the state transition. A risky design lets Active call a setter that deletes Active during its own member function. A later debug message that reads a member could then access an object whose lifetime ended. The chapter avoids that maintenance trap by keeping replacement outside the running handler entirely.

16. Distinguish rejection from failure to allocate
Mechanism in C++

SAY
Two outcomes may leave the session unchanged, but they mean different things. If no transition is permitted, next returns an empty pointer and send returns false normally. If a permitted destination cannot be constructed, construction may throw an exception. The assignment has not happened, so the old state remains owned. The caller can distinguish these outcomes by the return path and exception path. This guarantee covers the shown transition logic. It does not roll back an external file write or protect two threads that call send at once. When extending the model into a real import service, define those additional failure and timing rules explicitly.

46. Diagnose the lost current state
Recall and transfer

SAY
Suppose a review finds state_ = state_->next(event) in send. It looks compact, but it erases the rejection check. Finish in idle returns an empty owner. The assignment destroys Idle and leaves state_ empty. A later name call attempts to reach a missing object, which has undefined behavior. We should not run that invalid access merely to see what happens. We can diagnose it by following ownership and repair it by keeping the proposal local, checking it, then committing. A useful regression test first rejects finish and then checks that name still says idle. That test links an error path to later normal usability.
