4. The build stages fail for different reasons
Problem and first experiment

SAY
Saving source creates text, not an executable. Preprocessing can fail because a header is missing. Compilation can reject an incompatible type or invalid language construct. The assembler encodes target instructions and produces a relocatable object with symbols and relocation records. Linking then resolves references against definitions in other objects and libraries. A missing checksum_update definition belongs at the link boundary, not inside the byte loop. Keep artifacts in a known build directory and inspect the stage that failed. Running an older executable after a failed build can otherwise produce convincing output from code you did not just compile.

10. Source Code → Compiler
Systems mechanisms and source lecture

SAY
Source code describes behavior under a language standard. Declarations establish types and interfaces; definitions provide objects and function bodies. The preprocessor handles includes and macros before the compiler’s language analysis. The compiler must reason about the program’s allowed behavior, including integer rules, object lifetime, aliasing, and observable effects. A pointer-and-length interface carries preconditions even when its machine representation is only two integer-like values. Invalid source-level behavior is not repaired by the fact that the target CPU can execute some corresponding instruction sequence. [ R1 , R8 ]

12. Assembly → Object Code
Systems mechanisms and source lecture

SAY
The assembler encodes instructions and data into a relocatable object file. 13. Object Code → Linker
Systems mechanisms and source lecture

SAY
The linker combines object files and resolves symbols against other objects and libraries. It lays out the resulting program according to the executable format and link options. Missing definitions, incompatible interfaces, and duplicate definitions appear at this boundary. The C declaration and definition must agree. A successful link does not prove that a mismatched manually declared ABI is correct, and linking a library does not prove that its runtime dependencies will be available. Build correctness includes the intended headers, object versions, options, and target architecture. [ R1 , R37 ]

14. Executable → Loader
Systems mechanisms and source lecture

SAY
Execution asks the operating system to replace a process image with the executable. The kernel validates and interprets the executable format and establishes the initial execution environment. Dynamically linked programs also involve a runtime linker or loader according to the platform’s format and configuration. main is not normally the very first instruction executed. Startup code establishes language-runtime state before calling it. Understanding this explains why a program can fail before reaching the first source line of main , for example when a required dynamic library cannot be loaded. [ R16 ]

15. Loader → Virtual Address Space
Systems mechanisms and source lecture

SAY
The executable’s loadable segments become virtual mappings with appropriate permissions and backing. Code, initialized data, zero-filled storage, stack, and libraries occupy regions of the process’s address space. The loader need not eagerly copy every executable byte into physical memory before execution begins. File-backed demand paging and shared mappings allow work to occur as pages are used. The address-space layout is therefore a mapping plan, not simply a complete physical-memory photograph. [ R10 , R14 ]

In plain English: Think of an address written on a note: the note can tell you where to look, but it does not prove the thing is still there or that you are allowed to use it.

Systems mechanisms and source lecture

17. CPU → Registers and Caches
Systems mechanisms and source lecture

SAY
The byte-sum loop uses registers for pointers, counters, and partial results where the compiler chooses. Loads obtain input bytes through the cache hierarchy. Several adjacent bytes can share a fetched line, giving spatial locality. Calling the update function may require arguments in the ABI’s designated registers and preservation of callee-saved state. Inlining can remove that call boundary but not the source-level requirement to read only valid input bytes. Machine optimization and memory safety remain separate obligations.

In plain English: A cache is like keeping the things you use most often on your desk instead of walking to a storage room every time.

19. Program → System Call
Systems mechanisms and source lecture

SAY
The program calls read to obtain input and write to emit its result. Library wrappers marshal arguments into the operating-system ABI and translate return conventions into the documented C interface. Every positive read result supplies an exact valid extent for the next checksum update. The program must not process the entire 4096-byte buffer when only 100 bytes were returned. This is where an I/O return value becomes a memory-safety boundary. [ R11 , R12 , R46 ]

20. System Call → Kernel
Systems mechanisms and source lecture

SAY
The kernel resolves the descriptor, checks the request, and performs or waits for the relevant operation. Standard input may be a regular file, pipe, terminal, or another endpoint, so the same user code can trigger different kernel paths. A blocking read may let another task run, while a read satisfied from available data may return without switching processes. Kernel entry, blocking, and context switching are separate events. Error and short-progress results return responsibility to the program’s control flow.

21. Kernel → Hardware
Systems mechanisms and source lecture

SAY
When necessary, kernel subsystems and drivers coordinate with storage or network hardware. Interrupts, DMA, device queues, and memory-management policy can participate below the user-visible read interface. A cached read need not reach a device at all. Conversely, a device operation can complete before the waiting application is scheduled again. The end-to-end result is produced by several cooperating layers whose internal timings differ. Measure at the boundary relevant to the application’s requirement rather than attributing every delay to the CPU instruction loop.

Reason about the implementation

SAY

30. One load crosses distinct translation and storage mechanisms
Reason about the implementation

SAY
The checksum loop reads through a pointer, but the processor and memory system perform several different jobs below that expression. Address translation finds the relevant mapping, often using cached translations in the TLB. Data caches supply nearby bytes when present. A data-cache miss may fetch from another cache or memory without a page fault. A page fault involves the operating system because the access needs mapping or residency handling, or is invalid. Sequential traversal can exploit spatial locality because adjacent bytes share cache lines. Keep these events separate when explaining why a loop waits; they suggest different evidence and remedies.

31. A read result becomes the next memory-safety boundary
Reason about the implementation

SAY
The source utility uses a buffer that can hold four thousand ninety-six bytes, but read may return any positive count up to the requested size. If it returns one hundred, only those one hundred bytes are the newly supplied input for the next checksum update. Processing the full capacity would include unrelated or stale bytes. A zero result has EOF meaning for this stream workflow, while an error requires its own handling. This is a crucial cross-layer connection: an operating-system return value becomes a language-level valid range. Passing that exact count keeps the computation independent of whether input came from a file or pipe.

47. Kernel entry, blocking, and context switching are separate
Recall and transfer

SAY
A write wrapper arranges arguments according to the operating-system interface and enters the kernel. That entry is not automatically a switch to another process. The kernel may complete the request immediately, or block while waiting and let another task run. Similarly, a read may be satisfied from available cached data without asking a physical device to transfer anything new. Drivers, DMA, interrupts, and device queues can participate when needed, but their activity is not visible as one fixed sequence for every call. Diagnose the chosen input endpoint and return behavior before attributing all time to a CPU loop or disk.

48. Diagnose the earliest failed boundary in the end-to-end path
Recall and transfer

SAY
If the program prints the wrong total, first ask whether the built executable is current, whether read supplied the intended bytes, and whether the checksum saw the exact extent. If nothing prints, the error may instead be loading, an invalid descriptor, formatting, or incomplete output delivery. A correct arithmetic function cannot repair a broken surrounding pipeline. Record build commands, input bytes, exit status, standard error, and actual output so each boundary is reviewable.
