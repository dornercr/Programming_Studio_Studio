1. Atomic describes an operation, not an entire design
Problem and first experiment

SAY
An atomic operation is indivisible with respect to its defined observers, but that statement has a limited scope. An atomic counter can safely hand out positions without proving that the data at those positions is initialized. An atomic pointer can be read without tearing while its target has already been destroyed. We need to name the complete protocol: what value changes, what other data the change announces, and how long each object remains alive. This chapter adds tools for those questions. Start with the simplest default ordering, then choose weaker memory orders only when the reasoning and a measured need justify the added complexity.

2. The old value can identify a unique slot
Problem and first experiment

SAY
Suppose three tasks need distinct sequence positions starting at ten. fetch_add with an increment of one returns the previous value while updating the counter as one operation. The tasks therefore receive ten, eleven, and twelve in some order, and the next position becomes thirteen. A plain load followed by store cannot provide that guarantee under contention. The returned ticket identifies an allocation decision; it does not publish a payload automatically. Our fixed three-request example stays far from numeric limits. A long-lived service must define what happens at exhaustion or wraparound before treating ticket values as permanently unique identities.

4. A failed compare updates the expectation
Problem and first experiment

SAY

10. Atomic loads
Systems mechanisms and source lecture

SAY
An atomic load reads an atomic object’s value according to the selected memory order. It avoids a non-atomic conflicting access to that object. It does not automatically make unrelated ordinary memory safe to read. An acquire load can participate in publication when it observes the appropriate release operation or release sequence under the language rules. Without that relationship, attaching the word acquire to a load is not a general promise that every other thread’s latest writes become available.

In plain English: This is a coordination rule that helps multiple workers share information without stepping on each other's work.

11. Atomic stores
Systems mechanisms and source lecture

SAY
An atomic store updates one atomic object. A release store can publish earlier ordinary writes to a reader that acquires the corresponding publication. The order applies to the protocol, not to a physical instruction named “flush all memory.” A reusable flag needs more care than a one-shot flag. 12. Read-modify-write
Systems mechanisms and source lecture

SAY
An atomic read-modify-write operation reads and updates an object as one indivisible operation. Examples include fetch_add , exchange, and compare-and-swap. This avoids the lost-update problem of a separate load followed by store. The returned value and update rule matter. fetch_add returns the previous value, making it useful for allocating unique sequence positions within a bounded, overflow-aware design. It does not make the data stored at those positions automatically initialized or published.

14. Compare-and-swap
Systems mechanisms and source lecture

SAY
Compare-and-swap compares the atomic value with an expected value and conditionally replaces it with a desired value. In the C++ interface, failure updates the expected argument with the observed value. Weak forms can fail spuriously and are commonly used in retry loops. A bounded increment can repeatedly load a value, reject it when at the limit, and attempt to replace it with value plus one. The addition is safe only after proving the bound. CAS does not solve memory reclamation or the ABA problem by itself: a pointer can change away and back while the referenced object’s identity or lifetime changes. A simple default-order loop has this shape: The test expected < limit ensures expected + 1 cannot exceed the unsigned maximum when limit is representable. Explicit weaker memory orders require a separate proof, including valid success and failure order combinations.

15. Memory ordering
Systems mechanisms and source lecture

SAY
Relaxed ordering provides atomicity and the atomic object’s modification-order guarantees without using that operation to publish unrelated ordinary data. It is appropriate for some independent statistics and counters when no additional ordering is required. Release/acquire ordering supports directed publication. Sequential consistency adds a single total order for the relevant sequentially consistent operations, consistent with the standard’s constraints. It is a useful starting point but still does not repair an algorithm with the wrong atomic operation boundaries. Do not translate memory orders into folklore such as “always use relaxed on x86” or “a compiler barrier is enough.” The C++ abstract machine, compiler transformations, and hardware ordering all participate. Begin with a simple correct protocol and weaken ordering only when the proof and measured need justify the complexity.

16. One-shot publication
Systems mechanisms and source lecture

SAY
A producer initializes a three-element payload and then publishes readiness with release ordering. The consumer waits with acquire ordering and reads the payload before joining the producer. That ordering relationship, not the later join, protects the payload read. Companion listing: ch46/publication.cpp The expected result is 21. The acquire load that observes true synchronizes with the release publication, making the prior payload initialization available to the consumer under the language model. The payload is never modified again, and all objects remain alive through the join. The spin/yield loop is deliberately simple. For long waits, a blocking facility can avoid repeated polling. 23. Relaxed counting is not relaxed publication
Reason about the implementation

SAY
Our ticket counter can use relaxed ordering because its job is only to allocate distinct bounded integers; results are collected through joins. Change the counter's meaning to payload ready, and the proof changes. An observer that sees the flag needs a relationship to the producer's ordinary payload writes, not just an indivisible flag load. Replacing release and acquire with relaxed would remove that publication argument and can make ordinary accesses invalid. Do not run such a variant as a harmless performance comparison. The useful question is which data needs ordering and which operation supplies that edge, rather than a hardware slogan about one processor being strong enough.

24. Sequential consistency does not combine separate operations
Reason about the implementation

SAY
Suppose two workers each perform a default-order atomic load and later a default-order store of old plus one. Sequential consistency constrains the order of those atomic actions, but it still permits both loads before both stores. The final count can therefore lose an intended update even though there is no data race. Stronger ordering does not change the operation boundaries. fetch_add combines the read and update into one read-modify-write; a compare-and-swap loop conditionally combines a checked update. If the rule spans several related objects, one mutex may be easier to prove correct than a collection of atomic fields whose cross-field states remain inconsistent.

25. A reused flag needs a handoff protocol
Reason about the implementation

SAY
The one-shot source writes a payload once and never changes it after publication. Reusing the same buffer introduces a second question: when may the producer overwrite it? Resetting a Boolean flag does not by itself prove that the consumer has finished reading. A correct reusable protocol needs an acknowledgment, sequence scheme, ownership transfer, or a protected queue whose state machine covers both directions. The initial release/acquire pair can be correct while a later overwrite races with the reader. Trace the entire cycle, including who owns the buffer after consumption. A small first example should establish one guarantee clearly rather than imply it solves every repeated exchange.

42. Atomic is not a performance promise
Recall and transfer

SAY
The type std::atomic does not guarantee that every operation uses one instruction or avoids internal locks. The implementation and target platform determine lock-free properties. Even a lock-free counter may scale poorly when many cores repeatedly request exclusive access to the same cache line. Our three-ticket demonstration is far too small to measure that cost. If contention matters, compare designs with per-worker batches or private accumulation while preserving the allocation contract. Performance work needs a workload, measurement method, and correctness baseline.
