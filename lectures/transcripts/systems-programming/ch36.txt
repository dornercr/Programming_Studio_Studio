1. Mapping gives bytes an address, with a bounded lifetime
Problem and first experiment

SAY
A file parser can repeatedly call read, or it can ask the operating system to make a file region accessible through memory addresses. The second option is memory mapping. It changes how the program reaches bytes; it does not remove file size, permission, and lifetime rules. A pointer into the region is valid only inside the mapped extent while that mapping remains alive. Pages may need operating-system work when first touched, so a successful mmap is not proof that every later access is immediate. We will use controlled temporary files and bounded accesses to study the mechanism without touching device registers or existing documents.

Problem and first experiment

SAY

3. Mapping offsets have alignment rules
Problem and first experiment

SAY
A record beginning at byte nine thousand is not necessarily a legal mapping offset. With an illustrative page size of four thousand ninety-six, the aligned base is eight thousand one hundred ninety-two and the internal displacement is eight hundred eight. To access one hundred record bytes, the requested region must cover at least nine hundred eight bytes from that base. This arithmetic is about mapping extent, not record interpretation. Query the actual platform requirements rather than assuming the illustrative page size. Also check that displacement plus requested length fits the addressable size and remains within the stable file region before constructing pointers.

4. Private writes are not file updates
Problem and first experiment

SAY

10. mmap
Systems mechanisms and source lecture

SAY
mmap requests a mapping with a length, protection flags, sharing mode, descriptor, and offset. Failure is reported as MAP_FAILED , not as a null pointer. A zero-length mapping is not a valid substitute for handling an empty file. The offset must satisfy the platform’s alignment requirements, normally a multiple of the relevant page size. Mapping an arbitrary record offset often requires rounding the mapping base down to a page boundary and retaining an internal displacement, with overflow checks on the total mapped length.

11. Address mappings
Systems mechanisms and source lecture

SAY
The returned address identifies the beginning of the mapping in the process’s virtual space. Its validity lasts until the mapping is removed or otherwise changed. Closing the original descriptor does not by itself remove an established mapping on Linux. Pointers into the region become invalid after munmap . A function borrowing the mapping must not retain those pointers beyond the owner’s lifetime. Mapping ownership deserves the same discipline as allocation ownership: one clear owner, explicit extent, and structured cleanup.

In plain English: Think of an address written on a note: the note can tell you where to look, but it does not prove the thing is still there or that you are allowed to use it.

12. File-backed pages
Systems mechanisms and source lecture

SAY
File-backed pages associate virtual regions with file contents. A shared writable mapping can propagate modifications to the underlying file according to synchronization and filesystem rules. A private mapping provides private modification semantics instead of updating the file with those writes. Mapping flags are not a complete interprocess synchronization protocol. Multiple writers need an agreed layout and synchronization mechanism. Data-race rules still apply to threads in one process, and process-shared synchronization requires facilities designed for that purpose.

In plain English: The program uses a map of memory addresses. The operating system translates that map to where the data is actually stored.

13. Page faults
Systems mechanisms and source lecture

SAY
The first access to a mapped page may fault so that the kernel can establish backing. Later accesses can still fault under memory-management activity. A mapping therefore does not promise that every load has register-like or even DRAM-like cost. Concurrent file truncation is a serious hazard. Accessing a mapped region whose backing has been removed can generate SIGBUS on Linux. Checking file size before mapping is not enough when another actor can shrink the file afterward. The example below requires a stable regular file throughout the mapping’s lifetime.

In plain English: The program uses a map of memory addresses. The operating system translates that map to where the data is actually stored.

14. Mapping permissions
Systems mechanisms and source lecture

SAY
Protection flags specify permitted reads, writes, and instruction execution. They must be compatible with the mapping and descriptor’s access rights. A read-only mapping is appropriate for a checksum or parser that does not need to modify the file. Use the least authority required. Do not request writable executable memory merely because it seems convenient. For writable shared file mappings, msync can request synchronization under its documented semantics, while a complete durable-update protocol may require additional filesystem operations. 15. Memory-mapped I/O
Systems mechanisms and source lecture

SAY
The phrase memory-mapped I/O also describes device registers placed in an address map. A volatile pointer alone does not provide every device-ordering or synchronization guarantee. 22. Failure is MAP_FAILED; empty input is its own case
Reason about the implementation

SAY
An allocation-style habit can be misleading here: mmap reports failure with MAP_FAILED, not a null pointer. A check written as if not region does not implement that contract. An empty file also needs a direct path because a zero-length mapping is not the right way to represent an empty region. For a checksum, the empty result can be returned without constructing a mapping. Before mapping nonempty data, check that the file length fits the program's size type and that the object has the expected capabilities. These guards make later pointer arithmetic meaningful. The compiler accepts pointer syntax without proving the external mapped extent.

23. A page fault is deferred work, not always a bug
Reason about the implementation

SAY
Accessing a mapped address can trigger a page fault so the kernel establishes the page needed for that virtual address. That is often normal deferred work, not a crash. But an address being inside the originally mapped length is not enough if another actor truncates the backing file. On Linux, touching missing backing can produce SIGBUS. The source therefore requires a stable regular file throughout its read-only checksum operation. Checking size once does not lock the file forever. Keep that stability assumption in the API contract, especially if a later maintenance change allows another component to resize the same file while the mapping is borrowed.

24. Permissions and sharing answer different questions
Reason about the implementation

SAY
A writable private mapping and a read-only shared mapping answer different combinations of questions. Protection says what access this process may perform. Sharing says how modifications relate to backing and other mappings. Neither is a lock. Two threads concurrently changing shared mapped data still need synchronization under the language rules, and separate processes need facilities designed for shared-process use. Use only the authority needed: a parser that never edits data should normally request read-only access. Adding write or execute permission for convenience increases the set of mistakes that can affect the region without helping the parsing requirement.

25. Device mappings are a different contract
Reason about the implementation

SAY
The phrase memory-mapped I/O can refer to device registers as well as ordinary file data. A device read might acknowledge an event, and a write might start hardware work. Access width, order, and cacheability can therefore be part of correctness. A plain file parser's habit of reading bytes freely is not a valid device protocol. Marking a pointer volatile does not automatically provide every hardware ordering or interthread synchronization guarantee. Follow the operating system's driver interface and the device's documented rules. Our user-space temporary-file programs deliberately make no claim about physical device access; they teach file mapping only.

41. Choose mapping for a real access pattern
Recall and transfer

SAY
Memory mapping may be convenient when many bounded reads revisit a stable file and ordinary address-based access simplifies the algorithm. Buffered or positional reads can be simpler when work is sequential, windows are short-lived, or the program wants explicit transfer results at each step. Neither option eliminates error handling. Mapping shifts some work to later page accesses and makes pointer lifetime central. Reads return counts that the application must process correctly. Compare the actual workload and failure model before choosing. A small file parser does not become more correct merely because it uses mmap, and a mapping-based parser should not retain dangling views after its owner unmaps.

42. Recall address, extent, backing, and owner
Recall and transfer

SAY
