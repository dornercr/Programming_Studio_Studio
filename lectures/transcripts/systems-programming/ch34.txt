1. A descriptor integer is a table index, not the whole resource
Problem and first experiment

SAY
A descriptor such as three names an entry in the current process's descriptor table. It is not the file contents, and it is not a C++ object whose lifetime follows an integer variable. Assigning that number to another int only creates an alias for the same table entry. Closing the entry invalidates both copied numbers as handles. dup is different: it asks the kernel for another entry that refers to the same open object. A function must therefore say whether it borrows a descriptor or owns a reference that it must close. The type int alone does not communicate that contract.

Contrast a copied number with a duplicated descriptor.

2. Two descriptors can consume one shared position
Problem and first experiment

SAY
This real POSIX example creates a temporary file holding XYZ, flushes its output, and moves the position to zero. It duplicates the descriptor, then reads one byte through the original and one through the duplicate. The results are X and Y because both descriptors refer to one open file description with one current offset. Querying that offset returns two. Closing the duplicate does not close the original entry, so the stream can still be closed normally afterward. The program checks operations and never prints descriptor numbers, which can vary between runs. The stable output demonstrates a relationship, not a particular allocation of table slots.

3. The standard streams describe roles, not devices
Problem and first experiment

SAY
A program reading standard input must not assume a keyboard. Descriptor zero may refer to a file or a pipe. Likewise, standard output might feed another program, so a progress message inserted into a binary result can corrupt that next program's input. Standard error gives diagnostics a separate role, though a shell can redirect both outputs to the same destination. These conventions help small utilities compose. They also mean output failure is part of program failure: a correct calculation whose result could not be written is not automatically a successful command. Preserve the useful result stream and report setup or transfer problems through the intended diagnostic path.

4. An error after progress does not remove the prefix
Problem and first experiment

SAY
The model sends ABC before a simulated interruption in the larger operation. The destination already contains those bytes. Restarting the entire string appends ABCDEF again, producing ABCABCDEF. Resuming from the recorded offset three appends only DEF and produces ABCDEF. The program prints both outcomes so the duplication is visible. This is a deterministic model of partial progress, not an actual system call failure injected into a file. A real helper must distinguish positive write counts, interruptions with their documented effects, and failures after prior calls. Its reported result should preserve how much progress the caller can safely rely on.

8. Chapter 34 — File Descriptors
Systems mechanisms and source lecture

SAY
A file descriptor is a small nonnegative integer that indexes a process’s descriptor table. It can refer to a regular file, pipe, socket, or other supported object. The descriptor number is meaningful only while that table entry remains open; after closure, the same number can be reused for an unrelated object. The central programming rule is simple: interpret the documented return value of every operation. A request for a certain byte count is not a guarantee that exactly that many bytes moved. Error handling, partial progress, and cleanup are part of the operation’s semantics, not optional additions. [ R11 , R12 , R13 , R47 ]

10. Descriptor tables
Systems mechanisms and source lecture

SAY
A descriptor-table entry refers to an open file description or another kernel-managed open object. Descriptor flags such as close-on-exec belong to the descriptor, while file status flags and the current offset have their own sharing rules. Treat ownership explicitly. A function that borrows a descriptor must not close it unless the contract transfers ownership. A function that returns a newly opened descriptor must document who closes it. Copying the integer does not create a new kernel reference; dup does.

11. Standard input
Systems mechanisms and source lecture

SAY
Descriptor 0 conventionally represents standard input, accessed through STDIN_FILENO . It may be a terminal, file, pipe, or another redirected source. A program should not assume keyboard input merely because it reads descriptor 0. Reading standard input until end of file makes a utility composable. The same implementation can then process an interactive stream, a redirected file, or a pipeline without knowing which source supplied the bytes.

12. Standard output
Systems mechanisms and source lecture

SAY
Descriptor 1 conventionally represents standard output. Machine-readable results should normally go there, while diagnostics go elsewhere. Mixing progress messages into a binary or structured output stream can corrupt downstream processing. A write to standard output can fail or complete partially. Redirection to a full filesystem, a broken pipe, or another failing endpoint changes the result even when the program’s internal calculation succeeded. Output completion is part of overall success.

14. open
Systems mechanisms and source lecture

SAY
open resolves a pathname and requests access with specified flags. It returns a descriptor on success and -1 on failure. Creation flags require a permission mode, which is affected by the process’s file-creation mask and other applicable policy. [ R47 ] Choose destructive behavior deliberately. O_TRUNC can discard existing contents; O_EXCL with creation can require that a new name be created. O_CLOEXEC establishes close-on-exec atomically with opening on the reference platform, avoiding a separate setup window in multithreaded code.

15. read
Systems mechanisms and source lecture

SAY
read(fd, buffer, count) returns a nonnegative byte count or -1 on error. A positive result smaller than count is a successful short read. For a positive requested count, zero indicates end of file for the stream-oriented uses considered here. [ R11 ] On EINTR , retry when the operation’s contract and cancellation policy call for it. On a nonblocking descriptor, EAGAIN or EWOULDBLOCK means that readiness must be awaited; a tight retry loop merely wastes CPU. Never process bytes beyond the returned count.

17. close
Systems mechanisms and source lecture

SAY
close releases a descriptor reference and can report errors associated with outstanding I/O. On Linux, do not blindly retry close after an error: the descriptor number may already have been released and reused. A retry could close an unrelated resource. [ R13 ] This is a documented portability boundary. POSIX.1-2024 specifies different EINTR behavior from Linux’s established behavior. The examples in this book use the Linux rule explicitly rather than presenting one retry pattern as universal. Closing also does not by itself establish durable storage.

18. lseek
Systems mechanisms and source lecture

SAY
lseek changes or queries the current offset of a seekable open file description. Its return type is off_t , and failure is indicated by (off_t)-1 . Pipes and sockets are not ordinary seekable files. Changing a shared offset affects other descriptors referring to the same open file description. When independent operations must not interfere through the current position, consider positional I/O or separate open descriptions instead of surrounding every operation with fragile seek/read sequences.

25. Read only the bytes the call reports
Reason about the implementation

SAY
A read into a four-kilobyte buffer can return seven bytes. Only those seven bytes belong to this result; the rest of the array may hold old data or uninitialized storage. Processing all four kilobytes would manufacture input the endpoint never supplied. A zero result for a positive request indicates end of file for the stream uses in this chapter. A negative result reports failure and requires inspecting the error. EINTR and nonblocking EAGAIN do not mean the same thing: one may call for retry under the cancellation policy, while the other calls for waiting for readiness rather than a tight CPU-consuming loop.

26. Write loops need a progress invariant
Reason about the implementation

SAY
A complete-transfer loop keeps two quantities aligned: bytes already sent and bytes remaining. If a five-byte request writes two, the next call begins two bytes later and asks for three. Reusing the original pointer duplicates data; reducing the count without advancing the pointer loses the tail. For the small blocking transfers in the source, a zero-byte result with work still pending is treated as a no-progress failure. Production helpers must also respect supported request-size limits and cancellation policy. The invariant is simple enough to state in a test: completed plus remaining equals the original length, and completed identifies the next unsent byte.

27. Opening a destination can already change it
Reason about the implementation

SAY
Opening is not always a harmless lookup. With truncation requested, an existing file's contents can be discarded as part of setup. A safe tool chooses those flags based on the user's operation rather than copying a familiar example blindly. Creation also needs a permission mode interpreted with the process's mask and other applicable rules. A returned minus one means failure, not a descriptor to pass onward. On the reference platform, opening with close-on-exec avoids a separate flag-setting window in multithreaded launch code. Review setup and cleanup as one ownership path: every successful acquired entry needs a clear release, including later failure branches.

28. Closing follows a platform contract, not a blind retry rule
Reason about the implementation

SAY
A descriptor number can be reused after its entry is released. On Linux, blindly retrying close after an error can therefore close an unrelated resource that has since received the same number. The source explicitly teaches the Linux rule and notes that portability specifications differ for interruption behavior. Do not turn a read retry loop into a universal cleanup pattern. Ownership should end once according to the selected platform contract, while any reported output error is preserved for the caller. Closing also does not establish the same promise as a durable-update protocol. Releasing access and guaranteeing persistence are separate responsibilities with different operations and tests.

45. Recall the resource, the count, and the owner
Recall and transfer

SAY
The central habit is to read each operation's contract literally. open acquires an entry or reports failure. read and write report actual byte counts, not a promise that the requested amount moved. dup acquires another entry while retaining shared underlying state. close releases according to the platform's rules. Place those facts beside the code so a future helper does not confuse borrowed and owned handles or restart a partially completed transfer. Standard input and output make a program composable only when bytes remain exact and failure remains visible. The same discipline will support pipes and child-process redirection in later chapters.

DO
Ask learners to write a one-sentence contract for a borrowed copy source.
