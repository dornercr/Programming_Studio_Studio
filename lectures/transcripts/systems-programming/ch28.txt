1. Use the bytes you bring close
Problem and first experiment

SAY
A cache commonly brings in a whole line even when a program asks for one small value. Spatial locality means nearby bytes are likely to be useful too. Temporal locality means a recently used value will be needed again before competing work pushes it away. These ideas explain why layout and order matter without requiring a particular cache size. Reuse after a million unrelated accesses may be too late, even if it occurs quickly in clock time. We will count useful bytes and distinct model lines, then verify that two real traversals compute the same answer. Neither step alone is a hardware timing measurement.

3. A working set belongs to a phase
Problem and first experiment

SAY
A program may own a large dataset while using only one tile at a time. Its active working set during that tile can be small. Conversely, an index, pointer graph, code, and thread stacks may add substantial pressure beyond the obvious input array. Choose an interval such as one request, one loop, or one batch, then ask which values are reused within it. This makes working-set reasoning useful for maintenance: adding a small lookup structure to every record may expand the hot footprint enough to change behavior. Total allocated bytes and useful hot bytes answer related but different questions.

8. Chapter 28 — Locality
Systems mechanisms and source lecture

SAY
Locality is a pattern of reuse. Temporal locality concerns returning to the same information, while spatial locality concerns accessing nearby information. Hardware caches and software buffers exploit these patterns by retaining recently useful data and moving adjacent bytes together. Locality is not a property of a data structure in isolation. It depends on the traversal and workload. The same matrix can be accessed in a cache-friendly or cache-hostile order, and the same linked structure can behave differently when nodes are allocated compactly rather than scattered.

10. Temporal locality
Systems mechanisms and source lecture

SAY
Temporal locality occurs when an item used now is likely to be used again soon. A loop repeatedly updating a small set of accumulators exhibits it. Retaining those values in registers or cache avoids repeated access to slower levels. “Soon” must be interpreted relative to competing accesses and capacity. Reusing an item after touching millions of unrelated bytes may be too late for a small cache. Reuse distance—the intervening distinct data relevant to a cache model—is often more informative than elapsed time alone.

11. Spatial locality
Systems mechanisms and source lecture

SAY
Spatial locality occurs when an access predicts accesses to nearby bytes. A sequential array traversal typically uses several elements from each fetched cache line. Fetching an entire line is valuable when the remaining bytes are consumed before eviction. Spatial proximity is not automatically useful. A structure containing many rarely used fields can force frequently used fields to share lines with irrelevant data. A layout that groups the fields used together may reduce transferred bytes without changing the logical records.

12. Working sets
Systems mechanisms and source lecture

SAY
A working set is the collection of data and instructions actively used during a relevant phase or interval. Its size and access order determine pressure on caches, TLBs, and physical memory. Different phases of one program can have different working sets. A useful analysis chooses a time scale: one inner loop, one request, one batch, or a steady-state interval. Counting every allocation in the process may overestimate the hot working set, while counting only explicit input arrays may omit indexes, metadata, code, and thread stacks.

13. Sequential access
Systems mechanisms and source lecture

SAY
Sequential access follows adjacent locations in a predictable order. It can use most bytes of each cache line and allow hardware prefetching to anticipate future accesses. It also often reduces translation pressure by consuming many bytes within each page. The benefit depends on actual use. Reading a large array once still incurs compulsory traffic. Sequential order makes that traffic efficient; it does not make the bytes free. Streaming too much unrelated data can also evict useful cached state.

14. Strided access
Systems mechanisms and source lecture

SAY
Strided access advances by a fixed distance between elements. Small strides may retain useful spatial locality; large strides may touch a new line or page for every item. Particular stride patterns can also interact poorly with cache-set indexing. When analyzing a stride, express it in bytes. A stride of 16 elements means 64 bytes for four-byte elements but 128 bytes for eight-byte elements. Element count without element size does not determine cache-line use.

15. Random access
Systems mechanisms and source lecture

SAY
Random access uses an order that is difficult to predict from recent addresses. It can reduce prefetch usefulness and increase the number of distinct lines or pages needed for a small amount of useful data. Randomness should be defined carefully: a random permutation of a compact array differs from pointers distributed across a much larger heap. A benchmark should generate its access order outside the timed region when the goal is to measure memory traversal rather than random-number generation. It should also preserve dependencies intentionally: independent random loads and dependent pointer chasing test different limits.

16. Row-major versus column-major traversal
Systems mechanisms and source lecture

SAY
Assume a row-major 64 × 64 matrix of eight-byte elements and 64-byte cache lines. A row contains 512 bytes, or eight lines. Traversing a row consecutively uses eight elements from each line before moving on. A column traversal advances by 512 bytes between successive elements. It touches one element in each of 64 different rows before returning to the next element of the first row. If the relevant cache cannot retain those lines, much of each fetched line is wasted before reuse. If it can retain them, the difference may be smaller. Capacity and associativity determine the result; “column traversal always misses” is too strong. A blocked traversal processes a smaller rectangle before moving elsewhere. For example, an 8 × 8 tile contains 512 bytes of element data. In a transpose or matrix operation, choosing tiles whose active input and output regions fit the useful cache budget can preserve reuse. Include all simultaneously active arrays and temporary storage when estimating the budget.

17. Temporal locality in a counter
Systems mechanisms and source lecture

SAY
A loop that increments count every iteration repeatedly accesses the same small piece of state, demonstrating temporal locality. Once its cache line is loaded, many subsequent updates can hit in cache. If the loop instead touches a fresh random page each iteration, reuse falls dramatically and translation/cache misses become more frequent.

18. Stride and cache lines
Systems mechanisms and source lecture

SAY
For 64-byte cache lines and 8-byte elements, sequentially reading doubles uses eight neighboring elements per fetched line. Reading every eighth double touches one element per line. Reading every sixteenth skips a full line between accesses. Larger strides therefore waste more fetched bytes and reduce spatial locality.

In plain English: A cache is like keeping the things you use most often on your desk instead of walking to a storage room every time.

22. Row-major is a layout fact, not a loop-name preference
Reason about the implementation

SAY
In our flat three-by-four array, row one begins at element four because each earlier row contains four elements. Incrementing the column then advances one element at a time. Incrementing the row while holding column fixed advances four elements. That arithmetic, not the names row and column, explains the locality difference. A column-major representation would favor a different order, and a vector of separately allocated rows has additional layout details. Before rewriting loops, verify the actual representation and dependencies. A visually familiar matrix expression is not enough to prove which objects sit next to each other in memory.

23. Packing hot fields can reduce unused traffic
Reason about the implementation

SAY
Suppose each record occupies sixty-four bytes, but a repeated analysis reads only a four-byte score. A record-at-a-time layout may fetch many unused bytes with each score. A separate compact score array can place sixteen scores in the space formerly occupied by one whole record. This is a potential traffic improvement, not an automatic recommendation: other operations may need complete records, and keeping parallel arrays synchronized adds maintenance obligations. Identify which phase dominates and preserve the correspondence between fields. A locality change is worthwhile when it improves the measured workload without making the data model unreliable.

24. Randomness and dependence are separate properties
Reason about the implementation

SAY
Calling a benchmark random does not describe its whole memory behavior. A shuffled order over a compact array may reuse a small number of pages, while pointers scattered across a large heap may touch many. Independent random loads can overlap; a dependent linked chain may wait for each previous result. Generating random numbers inside the timed region adds another workload entirely. Define the distribution, size, dependency pattern, and setup boundary before interpreting a result. Otherwise a supposed memory test may mostly measure random-number generation or a different working set from the real application.

25. The one-resident-line model has a narrow claim
Reason about the implementation

SAY
The chapter’s compact model reports four misses for row-first traversal and sixteen for column-first traversal of its four-by-four example. Those counts follow its one-resident-line rule. A real cache has more entries, associativity, replacement behavior, and often prefetching, so the same tiny matrix may fit entirely after initial loading. The model remains useful because it shows how visit order changes reuse opportunities under a stated capacity. Do not repeat its numbers as measured performance. When changing the model, record line size, capacity, starting state, and access order together so the reason for a changed count stays visible.

41. Optimize only after preserving the computation
Recall and transfer

SAY
Reordering independent additions over our small integers preserves sixty-six. That does not mean every loop can be rearranged freely. A loop may depend on a value updated in the previous iteration, or floating-point rounding may make different summation orders produce different results. A cache-friendly rewrite must preserve the required computational contract, not just the set of addresses touched. Start with correctness checks, then measure the effect under a controlled workload. If the application permits a different numeric approximation, state that as a changed requirement. Otherwise an apparently faster result may simply be doing a different job.
