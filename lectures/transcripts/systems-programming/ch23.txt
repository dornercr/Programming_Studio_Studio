1. Pages organize storage; objects organize meaning
Problem and first experiment

SAY
A page is a fixed-size region of virtual address space. A C++ object is a language-level value with a type, lifetime, and bounds. These units need not line up. A large vector can span several pages, and a single page can hold several unrelated allocations. This matters when discussing safety: a hardware check may permit an address even though it lies beyond the array you are allowed to access. Conversely, crossing a page boundary is normal when the allocation and mappings cover both pages. We will use tiny page sizes in arithmetic demonstrations so every boundary is visible without pretending those sizes describe actual hardware.

2. A three-byte span can need two mappings
Problem and first experiment

SAY
The modeled span begins at virtual address seven and covers three bytes. With eight-byte pages, seven is page zero at offset seven. Eight is page one at offset zero, and nine is page one at offset one. We map page zero to frame three and page one to frame nine, producing physical addresses thirty-one, seventy-two, and seventy-three. The large jump comes from the frame mapping, not from skipped virtual bytes. These are integer calculations in an explicit model, not accesses to real physical memory. The output shows why checking only the first byte of a multi-byte operation cannot establish permissions for the whole span.

3. A frame is the physical partner of a page
Problem and first experiment

SAY
If page five maps to frame two, the number five does not become part of the offset. The mapping replaces the page-number portion while retaining the byte’s position within the page. For a frame size of four thousand ninety-six bytes, frame two begins at eight thousand one hundred ninety-two. Adding offset nine gives eight thousand two hundred one. Adjacent virtual pages can select distant frames while still presenting a contiguous virtual array. That flexibility supports allocation and isolation. A device that requires physically contiguous storage needs a stronger platform mechanism; an ordinary contiguous C++ container only promises contiguity in its own address space.

4. Count a partial last page without overflowing first
Problem and first experiment

SAY
The model uses eight-byte pages and sizes zero, one, eight, and nine. Dividing by eight alone gives zero, zero, one, and one, which undercounts one byte and nine bytes. The corrected calculation adds one when a remainder exists, giving zero, one, one, and two. The plus-one is applied to the quotient rather than forming size plus seven first. That avoids overflow in a common rounding-up expression for very large sizes. This example counts storage for a region beginning at a page boundary; an unaligned start would also affect the number of pages touched. State that assumption before applying the formula to an arbitrary pointer range.

8. Chapter 23 — Paging
Systems mechanisms and source lecture

SAY
Paging divides virtual address spaces and physical storage into fixed-size units. This simplifies placement: a virtual page can be backed by any suitable physical frame of the corresponding size. It also makes translation arithmetic systematic. The system trades fine-grained flexibility against page-table overhead, internal waste, and translation-cache coverage. [ R10 ]

10. Pages
Systems mechanisms and source lecture

SAY
A page is a fixed-size unit in the virtual address space. A mapping associates a virtual page with backing storage and permissions. Pages should not be confused with C objects: a page can contain many objects, part of one object, or bytes that no live language object currently occupies. A large allocation can span many pages. Crossing its internal page boundaries is valid when the allocation and mappings permit it. Conversely, staying within one page does not prove an array index is valid. Object-level bounds and page-level mapping boundaries solve different problems.

In plain English: The program uses a map of memory addresses. The operating system translates that map to where the data is actually stored.

11. Frames
Systems mechanisms and source lecture

SAY
A frame is a page-sized unit of physical storage. The kernel tracks which frames are free, in use, shared, or involved in other memory-management activity. A virtual page number and a physical frame number need not be equal. The distinction makes noncontiguous physical placement possible. Three adjacent virtual pages can be backed by frames 5, 200, and 9 while still appearing contiguous to the application. Device operations requiring particular physical arrangements need additional platform mechanisms; virtual contiguity alone is not a guarantee of physical contiguity.

12. Page size
Systems mechanisms and source lecture

SAY
For the following calculations, the page size is 4 KiB, or 4096 bytes. This is a teaching assumption, not a claim that every mapping on every system uses that size. Systems can support multiple page sizes, and applications should query the relevant platform interface where a runtime page size matters. Larger pages increase the amount of memory covered by one translation entry and reduce some table overhead. They can also waste more space for small or sparsely touched regions and complicate allocation or migration. The best size depends on workload and system policy, not merely on choosing the largest supported number.

In plain English: The program uses a map of memory addresses. The operating system translates that map to where the data is actually stored.

13. Page offset
Systems mechanisms and source lecture

SAY
For a page size of 2^p bytes, the low p address bits form the page offset. With 4096-byte pages, p = 12 . The offset is address mod 4096 , or equivalently address & 0xFFF for the nonnegative integer model. Translation preserves these low bits when mapping a page to an equal-sized frame. Only the page-number portion changes. This separation makes the final physical-address calculation straightforward and explains why correctly aligned page bases have zeroes in the offset positions.

In plain English: The program uses a map of memory addresses. The operating system translates that map to where the data is actually stored.

14. Virtual page number
Systems mechanisms and source lecture

SAY
The virtual page number is the address divided by page size, rounded down. In the bit model, it is address >> p . It identifies which page-table mapping applies, potentially through several levels of indexing. The number of bits available for the virtual page number depends on the virtual-address model. In a 32-bit model with 4-KiB pages, there are 20 virtual-page-number bits and 12 offset bits. Do not transfer those counts unchanged to a different address width or page size.

In plain English: The program uses a map of memory addresses. The operating system translates that map to where the data is actually stored.

15. Physical page number
Systems mechanisms and source lecture

SAY
The physical page number, also called a frame number in this discussion, identifies the selected frame. If the frame number is f , its base address is f * page_size . Add the original offset to obtain the final physical address. A page-table entry contains more than a frame number, so real software cannot treat every bit of an entry as an address. Flag bits and architecture-specific encodings must be interpreted correctly. The arithmetic below deliberately uses a dictionary of already-decoded frame numbers to isolate the translation concept.

In plain English: The program uses a map of memory addresses. The operating system translates that map to where the data is actually stored.

22. The low bits describe the byte within the page
Reason about the implementation

SAY
For four-kibibyte pages, the offset ranges from zero through four thousand ninety-five. Twelve bits can represent exactly that many choices. In an unsigned integer model, address modulo four thousand ninety-six agrees with masking by hexadecimal FFF, and dividing agrees with shifting right twelve bits. These equivalences depend on the stated power-of-two page size. A generic arithmetic model with a positive size of ten would still support division and remainder, but the same mask would be wrong. In source maintenance, keep geometry in one named place and test both the final byte of a page and the first byte of the next page.

23. Page size is a policy tradeoff, not a free upgrade
Reason about the implementation

SAY
A translation entry covers more bytes when the page size grows. That can reduce translation pressure for a large densely used region. But a larger page can also bring in or reserve storage that a sparse workload barely touches. Allocation, migration, and protection granularity change too. The chapter uses four-kibibyte pages for calculation, not as a universal constant for every machine and mapping. If a program needs the operating system’s actual page size, obtain it through the relevant platform interface. A classroom bit diagram is useful only when its page size and address width are written beside it.

24. A missing mapping is a distinct result
Reason about the implementation

SAY
Frame zero is a legitimate number in a simplified translation model. If zero is also used as a lookup-failed marker, a valid mapping can be mistaken for failure. The source lab uses optional to distinguish no translation from a translated numeric address. A caller tests presence before dereferencing the optional. This is ordinary model-level error reporting, not a simulated hardware fault handler. A real operating system may recover a legitimate absent mapping through demand paging or reject an invalid request. The translation helper intentionally does less: it returns no value when its table cannot supply a safe result.

25. Check multiplication before constructing an address
Reason about the implementation

SAY
An unsigned type has a largest representable value. Multiplying an arbitrary frame number by page size can wrap, producing a small number that looks like a valid address. The lab checks whether frame exceeds maximum minus offset, divided by page size, before performing the multiplication. Its page size is nonzero and the offset is bounded, so the guard itself is meaningful. This is a proof obligation in the integer model, not a claim that arbitrary frame numbers are legal hardware mappings. A compiler can accept overflowing unsigned arithmetic because wraparound is defined; tests still need to reject a wrapped result when it violates the translation contract.

41. A multi-page request needs a range contract
Recall and transfer

SAY
Consider copying twelve bytes beginning four bytes before a page boundary. The first four bytes use one translation; the remaining eight use another. A successful first-byte check proves neither that the second page exists nor that the whole destination object has enough space. A robust range operation checks its length arithmetic, object bounds, and relevant mapping permissions at the correct layer. In normal application code, prefer established buffer APIs and lengths rather than inventing a userspace page-permission check as a substitute for object safety. Our tiny span trace is useful because it makes the otherwise hidden boundary crossing explicit.
