1. A full cache must forget something
Problem and first experiment

SAY
A three-slot cache holds A, B, and C when D arrives. The access is a miss, but that fact alone does not tell us which resident to remove. Replacement is the rule that makes that choice. A direct-mapped cache may have only one eligible slot, while a fully associative model lets every resident compete. In this chapter we keep the trace and capacity explicit so we can compare policies fairly. The goal is not to guess a particular processor's undocumented behavior. It is to explain how retained history influences the next choice, and what that choice costs when a block is needed again.

2. FIFO remembers arrival, not affection
Problem and first experiment

SAY
First in, first out, or FIFO, remembers when each resident arrived. Suppose A entered before B and C, and ten later accesses all hit A. FIFO still removes A when the set next needs space. That may feel surprising because recent usefulness and insertion age are different measurements. A hit must leave the insertion queue alone. Moving A to the back would silently change the policy toward recency. When reviewing a simulator, therefore inspect the hit branch as carefully as the miss branch. The compiler can check vector operations, but it cannot know that this particular order is supposed to represent arrival history.

3. More FIFO capacity can still mean more misses
Problem and first experiment

SAY
Run this portable model with the same twelve requests and two capacities. It prints nine misses for three slots and ten for four slots. A larger FIFO cache does not always contain everything the smaller FIFO cache would contain at the same point, so the extra slot can change later victims in an unhelpful way. This result is called an anomaly of FIFO replacement. It is not a timing measurement and does not mean extra memory usually harms applications. It refutes one universal claim: FIFO miss counts cannot be assumed to decrease for every trace when capacity increases. Trace resident order to explain the result.

4. Recent use is evidence, not knowledge of the future
Problem and first experiment

SAY
Least recently used, or LRU, treats recent access as a clue that a block may be used again. If A and B are resident and A is touched, B becomes the least recent resident. That differs from FIFO even if both policies use a container ordered from oldest to newest. The word oldest means different things in the two implementations. LRU tracks last touch, not first arrival. This extra information has a maintenance cost because hits update policy state too. Hardware may approximate it. Before declaring LRU better, ask whether the workload actually repeats a hot subset or instead cycles through more distinct blocks than fit.

8. Chapter 31 — Cache Replacement
Systems mechanisms and source lecture

SAY
When a set is full and a new block must be installed, the cache chooses a resident victim. Replacement policy attempts to retain blocks that will be useful again. Because future accesses are usually unknown, practical policies use limited history and inexpensive approximations. The policies in this chapter apply to abstract caches and also illuminate software caches, page replacement, and bounded object stores. Actual processor caches need not implement exact LRU. The best policy depends on the workload, implementation cost, and information available. [ R3 ]

10. FIFO
Systems mechanisms and source lecture

SAY
First in, first out evicts the block that entered earliest among the eligible residents. Hits do not refresh its position. FIFO is simple because insertion age, rather than every access, determines replacement order. Insertion age can be a poor predictor of future use. A frequently accessed old block may be evicted while a newer block that will never be reused remains. FIFO also lacks the general stack property associated with exact LRU, so increasing capacity does not guarantee fewer misses for every trace.

11. LRU
Systems mechanisms and source lecture

SAY
Least recently used evicts the block whose most recent access is oldest. Hits refresh recency. It exploits the assumption that recently used blocks are more likely to be used again soon. Exact LRU requires tracking access order, which has a cost. Hardware often uses approximations or other policies. LRU can also perform poorly on cyclic scans slightly larger than capacity: every returning block may have just been evicted.

12. Optimal replacement
Systems mechanisms and source lecture

SAY
Optimal replacement evicts the block whose next use lies farthest in the future, or that will never be used again. With a fully known trace, it provides a lower bound on misses for the stated cache model. It is not generally implementable online because future accesses are unknown. Its purpose is comparison: it separates unavoidable misses under the model from misses caused by a practical policy’s limited information. Calling a policy “optimal” requires specifying the objective and assumptions.

13. Eviction
Systems mechanisms and source lecture

SAY
Eviction removes a resident block to make space or satisfy another policy. Its cost depends on the block’s state. A clean copy can often be discarded; a modified copy may require propagation before its only current contents are lost. Eviction can also disrupt future locality. A streaming workload may evict a small hot set and then immediately require that set again. Software techniques such as separating phases or limiting batch size can sometimes reduce this interference.

14. Dirty blocks
Systems mechanisms and source lecture

SAY
A dirty block contains modifications not yet reflected in the next level according to a write-back policy. Evicting it requires preserving those modifications through the appropriate writeback path. Dirty state therefore adds work beyond fetching the incoming block. Dirty does not mean corrupted. It means newer than the backing copy at the relevant level. The term applies similarly to file-cache pages whose updates have not yet been written according to the filesystem’s policy.

15. Clean blocks
Systems mechanisms and source lecture

SAY
A clean block matches the relevant backing copy under the cache’s protocol. It can be discarded without losing unique modifications. A later access may fetch it again if needed. Cleanliness and usefulness are different properties. A clean block may be extremely valuable to retain because it will be reused immediately, while a dirty block may never be referenced again. Replacement policy must balance future usefulness, writeback cost, and implementation constraints.

16. FIFO and LRU choose different victims
Systems mechanisms and source lecture

SAY
Use a fully associative three-line cache and the block trace: After loading A, B, and C, both caches are full. The next A is a hit. FIFO retains insertion order A, B, C ; LRU updates recency to B, C, A , from oldest to newest. When D arrives, FIFO evicts A, while LRU evicts B. The final A therefore misses under FIFO and hits under LRU. FIFO has five misses and one hit; LRU has four misses and two hits. This trace demonstrates a difference, not a proof that LRU wins on every trace. Another workload can favor a different policy. Now mark A dirty before D arrives. FIFO’s eviction requires writeback of A in a write-back model; LRU’s eviction of clean B does not. The event counts alone still do not yield time: the model must say whether writeback overlaps other work and how much each operation costs.

18. Dirty versus clean eviction
Systems mechanisms and source lecture

SAY

22. A scan just beyond capacity can miss every time
Reason about the implementation

SAY
The program runs LRU on A, B, C, D, then repeats those four blocks. The capacity is three. When D first arrives, A is least recent and leaves. The next request is A, so it misses and evicts B, which is requested next. This pattern continues, producing zero hits and eight misses. The code is a safe deterministic simulation, not a claim about actual CPU counters. Its lesson is that a policy can follow its rules perfectly and still fit the workload poorly. Improving locality may require changing the active batch or access order rather than repairing a replacement algorithm that is already correct.

23. Optimal replacement has information an online cache lacks
Reason about the implementation

SAY
If we knew every future request, we could evict the resident whose next use is farthest away, or never occurs again. This optimal policy gives a useful comparison point for miss count in the chosen cache model. For residents A and B, with future requests A, C, A, B, keeping A is sensible because B is needed later. A running general-purpose cache usually does not have that complete future list. Comparing it with an offline optimum therefore measures the price of missing information as well as policy choice. Optimal also needs an objective: minimizing misses is not automatically the same as minimizing writeback traffic or elapsed time.

24. Dirty means newer, not damaged
Reason about the implementation

SAY
A cache line is dirty when it contains changes not yet reflected in the relevant backing level. It is not corrupted. If dirty A contains the only current value, eviction needs a writeback path before that value is lost. A clean B matches its backing copy and can be discarded without preserving unique changes. But cleanliness does not predict reuse: B may be requested immediately afterward. This is why choosing the cheapest immediate eviction can increase later misses. Keep two questions separate in a review: how expensive is removing this line, and how likely is retaining it to save future work? Both depend on the stated cache protocol.

25. Policy state needs its own invariants
Reason about the implementation

SAY
A simulator can print plausible totals while its internal state is wrong. Check that each resident appears only once, that the number of residents stays within capacity, and that a hit changes order only when the policy requires it. For LRU, moving a hit requires removing its old position before appending it. Forgetting the erase creates duplicates and makes the cache seem larger or smaller than intended. In C++, erase also invalidates relevant vector positions, so do not continue using the erased iterator. Store the block value independently before mutation. The same discipline matters in a software cache whose bookkeeping determines which owned object is destroyed.

41. Separate a correct policy from a good workload fit
Recall and transfer

SAY
When a cache disappoints, begin with a tiny trace whose expected victims you can explain. That distinguishes an implementation bug from a workload that offers little reuse. Then compare representative traces with consistent capacity, initial state, and placement rules. If one policy has fewer misses, do not immediately translate that percentage into program speedup. Dirty evictions, overlapping transfers, and policy overhead still matter. A useful report names the model, counts misses and writebacks, and separately reports any real measured timing. This gives maintainers enough evidence to decide whether to change replacement, resize a cache, or reorganize the work that feeds it.
