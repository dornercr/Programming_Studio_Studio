1. A failure needs a postcondition, not only an error message
Problem and first experiment

SAY
A function returning failure does not always mean that nothing happened. A write may have transferred a prefix. A renamed file may already be visible even if a later durability step fails. A remote operation may complete before its acknowledgment is lost. Robustness starts by defining the state left after each failure, then choosing a retry or recovery rule that fits it. This chapter connects return values, parsing, assertions, cleanup, and persistence. The goal is not to keep running at any cost, but to leave a known safe state and enough evidence to diagnose the failed boundary.

Problem and first experiment

SAY

4. Use the failure indicator that belongs to the interface
Problem and first experiment

SAY
Different system interfaces have different failure conventions. A descriptor-returning call can use minus one. A mapping operation uses MAP_FAILED rather than a generic null test. Many POSIX thread interfaces return an error number directly instead of asking the caller to read errno. A wrapper that forces all of these into one guessed convention can report stale errors or treat failure as success. Read the documented result before inspecting any secondary status. Then preserve enough safe context to identify the operation and resource involved. Consistent application-level error types are useful only after the wrapper has respected the underlying interface.

8. Chapter 59 — System Robustness
Systems mechanisms and source lecture

SAY
Robustness is the ability to behave predictably when inputs are invalid, resources are unavailable, operations make partial progress, or dependencies fail. It requires explicit failure contracts and cleanup paths. A robust system does not have to succeed at every request; it must avoid turning a failed request into corruption, leakage, or an unexplained hang. Correctness on the normal path is only the beginning. Examine each resource acquisition and each externally visible update: what can fail before it, what can fail after it, and what state remains when that happens?

10. Defensive programming
Systems mechanisms and source lecture

SAY
Defensive programming validates assumptions at trust boundaries and makes internal invariants explicit. Validate external lengths, indexes, versions, and resource requests before using them. Keep validated values in a representation that will not silently change during later conversion. Avoid indiscriminate checks that conceal programming errors or continue with fabricated defaults. A failed invariant inside a component may require stopping that operation rather than proceeding with a “best guess” pointer or size. The response should preserve safety and make diagnosis possible.

11. Error handling
Systems mechanisms and source lecture

SAY
Error handling must define the operation’s postcondition after failure. Did nothing happen, did some bytes transfer, or did the update commit but its acknowledgment fail? These are different states with different retry rules. Design for idempotence where retries are expected. Repeating a read is different from repeating a money transfer or appending a record. An error does not necessarily mean that the remote side performed no work. Protocols need identifiers, transactions, or explicit reconciliation when duplicate effects would be harmful.

13. errno
Systems mechanisms and source lecture

SAY
errno is meaningful when an interface documents that its failure result sets it. A successful call need not clear an old error value. Inspecting errno after success can therefore diagnose a failure that never occurred. Save the error code before cleanup or logging that could change it. Report the failed operation and relevant safe context, not just an unexplained number. In multithreaded POSIX environments, errno access is thread-specific, but that does not make stale values meaningful. [ R54 ]

14. Assertions
Systems mechanisms and source lecture

SAY
Assertions document and test internal invariants. They are not a substitute for validating untrusted input because ordinary C/C++ assertion checks can be disabled in builds defining NDEBUG . Do not place required side effects inside an assertion. assert(close(fd) == 0) can remove the close operation when assertions are disabled. Perform the operation explicitly, handle its result, and use assertions only for checks whose removal does not change required behavior.

15. Sanitizers
Systems mechanisms and source lecture

SAY
AddressSanitizer, UndefinedBehaviorSanitizer, and ThreadSanitizer instrument different classes of behavior. Their availability, compatible combinations, and runtime requirements differ. Address and undefined-behavior checks are commonly combined; thread-race checking should normally use a separate build. [ R5 , R6 , R53 ] A clean run means that the enabled instrumentation reported no covered failure during that execution. It does not prove memory safety, race freedom, or correct recovery on unexecuted paths. Keep compiler warnings, static analysis, boundary tests, and design review alongside instrumentation.

16. Resource cleanup
Systems mechanisms and source lecture

SAY
Cleanup releases every owned resource exactly once: memory, descriptors, mappings, threads, temporary files, and permits. RAII in C++ and structured cleanup paths in C make the ownership visible during both normal returns and failures. Destructors should not casually throw during stack unwinding. Operations whose completion can fail meaningfully, such as flushing durable output, often need an explicit checked completion method before fallback destruction. Cleanup that merely prevents leaks is not the same as successful commit.

17. Failure recovery
Systems mechanisms and source lecture

SAY
Recovery establishes a known consistent state after failure. Common techniques include constructing a new result before replacing the old one, writing temporary files before rename, logging transactions, and restarting isolated workers. Atomic visibility and durable persistence are different guarantees. A rename can make a new pathname visible atomically under filesystem rules, while durable recovery after power loss can require synchronizing the file and containing directory. The exact guarantee also depends on filesystem and hardware behavior. [ R33 ]

Reason about the implementation

SAY

25. Required work must not hide inside assert
Reason about the implementation

SAY
An assertion is useful for an internal condition that should already be true, but ordinary C and C++ assertions can disappear when NDEBUG is defined. If assert contains close(fd), that build may remove the close itself and leak the descriptor. Likewise, untrusted lengths cannot be accepted merely because a debug assertion checked them during development. Perform required operations and boundary validation explicitly, handle their failure according to the contract, and use assertions for additional internal evidence. Tests should include the release configuration when changing error handling so behavior does not accidentally depend on debug-only evaluation.

43. Sanitizers cover different failure classes and executed paths
Recall and transfer

SAY
AddressSanitizer can expose certain memory-access and lifetime errors. UndefinedBehaviorSanitizer covers selected undefined operations. ThreadSanitizer targets data races through separate instrumentation with its own runtime requirements. These tools are not interchangeable and some combinations are inappropriate. A clean execution means the enabled checks reported no covered defect on the paths that ran; it does not prove every future input is safe or every failure path is correct. Retain warnings, boundary tests, invariant review, and controlled failure injection. If the environment cannot run a tool, report that limitation rather than silently treating the check as passed.

44. Recovery should leave a known state and a reviewable story
Recall and transfer

SAY
A robust operation can be described as a sequence of ownership and state transitions. After acquiring a descriptor, who owns it? After allocating a buffer, which failure path releases it? Before commit, can the old state remain valid? After commit, what does a lost acknowledgment mean? Design tests that fail after each meaningful boundary and inspect both resources and user-visible state. Cleanup can prevent leaks without proving that output was flushed successfully. The goal is a clear postcondition, not merely a catch block. That clarity lets maintainers change implementation details without accidentally changing the meaning of failure.

DO
Ask learners to predict the answer and state their assumptions.
Reveal the answer, then identify which program boundary establishes it.
