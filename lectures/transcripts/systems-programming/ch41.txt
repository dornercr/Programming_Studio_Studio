1. Signals: an interruption is not an ordinary call
Problem and first experiment

SAY
Suppose a process is formatting a status line when a shutdown request arrives. The request did not wait for the formatting library to finish updating its private buffers. That is the central signal problem: the handler can run at an inconvenient point inside ordinary work. A signal is an event notification delivered under operating-system rules. It may request termination, report child changes, or reflect a fault. We must distinguish a routine request from a fault caused by an invalid instruction or memory access. Catching a fault does not establish that the interrupted program is healthy enough to continue. Begin with a minimal notification contract, not a large handler.

2. Choose the promise: request noticed, not events counted
Problem and first experiment

SAY
A pending notification is not necessarily an exact event count. If several standard signals of the same kind arrive while blocked, they can be represented by one pending instance. A flag set to one therefore means inspect the underlying state, not process exactly one request. For child changes, ordinary code should collect all available child statuses instead of assuming one status for each signal delivery. If every event must carry data and be counted, a queue or another explicit communication mechanism may be needed. The choice comes from the requirement. Replacing a flag with an ordinary increment inside a handler does not create a reliable general event queue.

10. Asynchronous events
Systems mechanisms and source lecture

SAY
An asynchronous signal can arrive independently of the interrupted statement’s purpose. The program may be halfway through updating a data structure or holding a library’s internal lock. Handler code must not assume a clean application boundary. Synchronous fault signals have a different relationship to execution: they result from an instruction’s behavior. Catching such a signal does not automatically make corrupted state recoverable. Treat routine notifications and invalid-memory faults as different design problems.

11. Signal delivery
Systems mechanisms and source lecture

SAY
Signal disposition defines whether a signal is handled, ignored, or given its default action, subject to signals that cannot be caught or ignored. Signal masks control which signals are blocked for a thread. In a multithreaded process, dispositions and per-thread masks have different scopes. Process-directed signals can be delivered to an eligible thread under the platform’s rules. A design that depends on one particular worker receiving a signal should use a deliberate masking and signal-consumption strategy instead of leaving delivery accidental.

12. kill
Systems mechanisms and source lecture

SAY
Despite its name, kill sends a signal; the chosen signal’s disposition determines the effect. It can request termination, notify, or test certain existence/permission conditions with signal number zero under documented rules. A PID is a reusable identifier, not an eternal object reference. Long-lived supervisors must account for lifecycle and identity races. This book’s simple examples use freshly created children or the current process rather than treating an old stored PID as permanently trustworthy.

15. Blocking signals
Systems mechanisms and source lecture

SAY
Blocking delays delivery; it does not necessarily discard the event. A critical setup sequence can block a signal, install state, and then unblock it at a controlled point. In multithreaded programs, use the appropriate thread-aware mask interfaces and establish masks before creating workers when that is part of the design. Blocking is also needed to close a check-then-sleep race. The signal must not slip between observing a flag and entering a wait that would then have no future notification to wake it.

16. Pending signals
Systems mechanisms and source lecture

SAY
A blocked signal can become pending. Standard signals generally do not queue one distinct instance for every repeated occurrence; multiple occurrences can coalesce. Real-time signals provide different queuing semantics under their documented limits. Consequently, a handler flag is usually a request to inspect state, not an exact count of events. A SIGCHLD notification should trigger collection of all available child statuses, not one wait per presumed signal instance.

17. Signal safety
Systems mechanisms and source lecture

SAY
Signal safety concerns reentrancy and permitted operations at an asynchronous interruption point. It is not the same as ordinary thread safety. A function protected by an internal mutex can be thread-safe yet deadlock when called from a handler that interrupted a thread holding that mutex. A handler using an async-signal-safe function that can affect errno should save and restore errno when necessary. A self-pipe pattern can notify an event loop with a small write, but it must handle a full nonblocking pipe without blocking inside the handler.

18. Signal races
Systems mechanisms and source lecture

SAY
A race occurs when correctness depends on the timing of delivery relative to ordinary state changes. Installing a handler after enabling an event source can miss the intended handling window. Updating shared bookkeeping without a masking plan can expose inconsistent state. Design the state transition and notification together. The signal says that something may have changed; protected ordinary code determines exactly what changed and performs the required work. This parallels condition-variable design in Part XI.

Systems mechanisms and source lecture

SAY

Making the flag volatile does not make those two operations atomic. sigsuspend temporarily installs a signal mask and waits as one coordinated operation. 26. Masks and dispositions answer different questions
Reason about the implementation

SAY
A disposition answers what action a signal should cause. A mask answers whether delivery is currently allowed for a thread. These are different pieces of state, with different scopes in a multithreaded process. Imagine installing a shutdown handler while workers are being created. If masking is part of the plan, establish the intended mask before worker creation and deliberately select who consumes notifications. Otherwise a process-directed signal may reach an eligible worker rather than the thread whose state machine expected it. Blocking an event during setup can preserve it as pending; it does not necessarily throw it away. Describe this lifecycle before adding calls that enable the event source.

27. sigsuspend links checking with eligibility to wake
Reason about the implementation

SAY
The correct waiting shape begins by blocking the relevant signal while checking the flag. If work is still absent, sigsuspend temporarily changes the mask and waits in one coordinated operation. A signal already pending can then be delivered without falling into a gap between checking and sleeping. When control returns, the earlier mask is restored and normal code checks the predicate again. A return does not necessarily mean the particular work we want is ready, because another handled signal may be involved. This resembles a condition-variable predicate loop, although its mechanism is a signal mask rather than a mutex. The predicate remains the source of truth.

28. Thread-safe is weaker than signal-safe here
Reason about the implementation

SAY
Consider a library routine that locks its private mutex before changing a buffer. Two normal threads can call it safely because one waits for the other. Now imagine a handler interrupts the owning thread and calls that same routine. It waits for a mutex that the interrupted work cannot release until the handler returns. That is why ordinary thread safety does not imply asynchronous signal safety. Keep complex work in normal flow. A self-pipe can bridge a handler to an event loop using a carefully bounded notification write, but a full pipe must not make the handler block. Even a small bridge has a capacity and failure policy.

29. Restart policy does not erase I/O contracts
Reason about the implementation

SAY
Installing a handler includes a choice of flags. SA_RESTART can restart some interrupted operations, but it does not promise that every blocking interface behaves as though no signal occurred. I/O code must still examine return values, byte counts, and documented interruption behavior. If a handler calls a permitted operation that may change errno, it may need to save and restore the interrupted value so ordinary error reporting remains meaningful. Keep the roles separate: the handler requests work, the normal operation reports its own progress, and the caller decides whether retrying is valid. Blindly retrying an operation with side effects can be as wrong as blindly treating interruption as fatal.

45. Debug a shutdown that is asleep forever
Recall and transfer

SAY
A process that stops responding during shutdown may have received the only notification before it actually began waiting. Adding a longer delay can change the symptom without closing the race. Record the sequence instead: when was the flag checked, when was the signal blocked, when did it become pending, and when was delivery enabled? Our safe model gives one concrete failing order. The repair must remove that order from the allowed protocol, not make it unlikely. Also check whether complex handler work is blocked on a library lock. A trace of state and ownership is more useful than a claim that the problem disappeared during ten quiet test runs.

46. Carry the notification pattern into larger systems
Recall and transfer

SAY
A reusable signal component needs more than a successful one-shot example. It must define installation, mask ownership, pending work, restoration of earlier dispositions, and shutdown while other threads still exist. The key lesson transfers to queues and condition variables: a notification says inspect state, while the state records what work remains. If a supervisor needs ten distinct messages, use a protocol that preserves ten messages rather than a flag that merely says yes. If it needs only a shutdown request, the simpler flag may be appropriate. State exactly what the component promises, then test notification before waiting, during waiting, repeated notification, and teardown under that promise.
