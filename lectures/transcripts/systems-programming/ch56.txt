Problem and first experiment

SAY

2. Speeding up a small phase has a limited whole-job effect
Problem and first experiment

SAY
The supplied cost model gives computation twenty of the original one hundred time units. Doubling only that phase reduces twenty to ten while the other eighty stay unchanged. Total time becomes ninety, and the whole-job speedup is one hundred divided by ninety, about one point one one. The program prints these modeled values with two decimal places. It does not time a program. This calculation can save wasted work: if most of the user's wait lies outside arithmetic, even a large local improvement has a modest total effect. The model assumes the workload and the other costs truly stay fixed.

3. More workers can lose after coordination cost is included
Problem and first experiment

SAY
This deliberately simple model includes a cost that the ideal formula leaves out. Twenty-five units remain serial, seventy-five divide across workers, and every extra worker adds five units of overhead. Two workers reduce time to sixty-seven point five. Four improve it further to fifty-eight point seventy-five. Eight worsen it to sixty-nine point thirty-eight after rounding because added coordination exceeds the remaining parallel benefit. These numbers are assumptions calculated by the program, not a forecast for a particular processor. The useful question is what real measurements could estimate or disprove each modeled component.

4. Read Amdahl’s equation as a time accounting statement
Problem and first experiment

SAY
The expression s plus one minus s divided by p describes normalized new time under ideal parallelization of a fixed workload. If s is one fifth and p is four, the unchanged part takes point two and the parallel part takes point two, for point four total. Inverting gives a speedup of two point five. With indefinitely many ideal workers, the remaining serial fraction limits speedup to one over s, which is five here. The arithmetic is not the uncertain part. The uncertain assumptions are whether the fraction stays fixed, overhead is negligible, and enough independent work exists to keep workers useful.

10. Identifying bottlenecks
Systems mechanisms and source lecture

SAY
A bottleneck is a stage or resource that constrains the chosen performance objective. Removing one bottleneck can expose another. The limiting factor can also change with input size, concurrency, and cache state. Form a testable hypothesis: “This phase is limited by repeated allocation,” or “These workers wait on one mutex.” Then collect evidence that could disprove it. A profile showing time inside a function does not by itself identify whether the cause is computation, cache misses, or waiting inside that function.

11. CPU-bound workloads
Systems mechanisms and source lecture

SAY
A CPU-bound workload spends its critical time performing computation rather than waiting on external I/O. It may still be limited by instruction dependencies, branch behavior, vectorization, or execution-resource throughput. Reducing instruction count can help, but not every instruction has equal cost and not every removed instruction lies on the critical path. Independent work can overlap, while a short dependency chain can dominate latency. Inspect the hot generated code only after establishing that it matters.

12. Memory-bound workloads
Systems mechanisms and source lecture

SAY
A memory-bound workload is constrained by data access, such as bandwidth or dependent-load latency. Reducing arithmetic may have little effect when the processor already waits for data. Improving locality or reducing transferred bytes can be more valuable. A simple bandwidth roof illustrates the limit. At arithmetic intensity 0.125 operations per byte and available bandwidth 40 GB/s, the bandwidth-limited rate is 5 billion operations per second under the model. A processor capable of much more arithmetic cannot exceed that rate for the same required traffic without changing the access pattern or reuse.

13. I/O-bound workloads
Systems mechanisms and source lecture

SAY
An I/O-bound workload waits on storage, network, or another external service. Useful changes include batching, caching, reducing requests, overlapping independent operations, and improving the protocol. Adding threads can hide some waits but can also overload the downstream system and increase queueing. Distinguish service time from waiting time. When the dependency is saturated, more concurrent demand may worsen latency without increasing completed throughput.

In plain English: The program asks the operating system to move bytes to or from a resource, much like using a numbered ticket to ask a clerk for the right item.

14. Profiling
Systems mechanisms and source lecture

SAY
Profiling attributes time or events to code paths. Sampling profiles estimate where execution spends time; instrumentation records chosen events more directly but can perturb behavior. Hardware counters provide additional evidence subject to event definitions and access permissions. A Linux starting point can be perf stat with a small set of understood events, followed by a sampling profile when available. Container, kernel, and administrative policy may restrict access. 15. Scaling
Systems mechanisms and source lecture

SAY
Strong scaling holds total problem size fixed while increasing resources. Weak scaling grows the problem with the resource count. They answer different questions and should not be compared without stating which workload changed. Synchronization, communication, memory bandwidth, load imbalance, and serial setup limit scaling. Measure useful throughput and latency alongside CPU use. A program using all cores at high utilization can still scale poorly if much of that activity is contention or redundant work.

17. Quantify the improvement ceiling
Systems mechanisms and source lecture

SAY
With serial fraction 0.20 and four workers, the normalized time is 0.20 + 0.80/4 = 0.40 , so speedup is 2.5. With infinitely many ideal workers, speedup cannot exceed 5 unless the serial portion is changed. Now add overhead equal to 0.05 of the original runtime at four workers. Normalized time becomes 0.45 and speedup falls to approximately 2.222. This explains why “80% parallelizable” is not a sufficient performance forecast without a communication and synchronization model. Companion listing: ch56/amdahl.py The output is ideal=2.500 with_overhead=2.222 . A model can also guide priorities: reducing the serial fraction from 0.20 to 0.10 may be more valuable than adding workers beyond the point of diminishing returns. Confirm that the measured serial component is truly independent of worker count before applying the formula mechanically.

23. CPU-bound does not mean every instruction matters equally
Reason about the implementation

SAY
A computation can be limited by arithmetic while still responding differently to two instruction reductions. Removing an instruction off the critical path may change little if other work overlaps it. Shortening a dependent chain can reduce latency more directly because each step waits for the previous result. Branch behavior, vectorization, and execution-unit capacity add other limits. Establish that the phase is actually compute-bound before studying the generated instructions in detail. Otherwise a beautiful arithmetic rewrite may leave the program waiting on the same memory access or remote service as before.

24. A memory ceiling connects useful work to required bytes
Reason about the implementation

SAY
A memory-bound workload waits for data access rather than available arithmetic capacity. The source's roof model uses one eighth of an operation per transferred byte and forty billion bytes per second of bandwidth. Multiplying yields five billion operations per second under those assumptions. A processor capable of far more arithmetic cannot exceed that rate without reducing required traffic or improving reuse. Dependent-load latency is another possible limit that a bandwidth number alone may miss. Measure the actual access pattern and working set, then consider compact data, blocking, or fewer pointer traversals instead of only reducing arithmetic instructions.

25. Waiting on I/O changes the useful optimization choices
Reason about the implementation

SAY
If the critical path waits for a storage device or service, adding arithmetic throughput may have little effect. Batching can reduce fixed per-request cost, caching can avoid requests, and independent work can overlap waiting. But a saturated dependency has finite capacity. Sending more concurrent requests can increase queueing and tail latency without improving completions. Separate the service's work time from time spent waiting in front of it. A useful experiment changes one source of demand and measures both throughput and latency, rather than declaring more threads successful because all of them are busy or blocked.

26. Profiles and counters are evidence with definitions
Reason about the implementation

SAY
A sampling profile estimates where execution was observed; it does not automatically measure every call exactly. Instrumentation records selected events more directly but adds work that can change the behavior being studied. Hardware counters can help distinguish misses, branches, and instructions, but their definitions, multiplexing, and permissions matter. In restricted environments, perf access may be unavailable. Report that limitation rather than filling the gap with invented counts. Connect each tool result to a hypothesis and a completion metric. A lower cache-miss count can explain a change, but the application still has to finish the required work correctly and usefully.

42. Strong and weak scaling ask different questions
Recall and transfer

SAY
Strong scaling asks how quickly the same fixed job can finish with more resources. Weak scaling asks whether resources can handle a proportionally larger job at a similar per-resource load. A graph that changes both input size and workers without saying so can make results hard to interpret. Load imbalance, synchronization, memory bandwidth, and setup costs affect both experiments differently. Keep the sequential result or another trusted reference for correctness. Report useful throughput and latency alongside CPU use, and avoid interpreting high utilization as evidence that scaling is efficient when workers may be contending or repeating work.

43. Use a ceiling to prioritize, then verify the revised system
Recall and transfer

SAY
A ceiling is valuable even when it is not a precise prediction. If a phase takes only five percent of total time, eliminating it entirely cannot save more than that fraction under the fixed-cost model. That may guide effort toward a larger wait or repeated allocation. After the change, measure again: removing one constraint can expose another, and the old fractions may no longer apply. Retain the workload, output check, build configuration, and uncertainty report so the comparison is reviewable. Performance analysis is an iterative explanation of observed limits, not a single formula that stays true after every architecture change.
