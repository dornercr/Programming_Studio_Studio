2. Separate writing data from executing code
Problem and first experiment

SAY
This permission model uses three Boolean capabilities: read, write, and execute. A data region allows reading and writing but not execution. A code region allows reading and execution but not writing. A region requesting both writing and execution fails the chosen least-permission policy, so the output is data-ok one, code-ok one, and writable-code-ok zero. No mapping or processor permission is changed by this program. In a real system, page mappings and the operating system enforce permissions. The model helps state the intended policy before inspecting whether the built program and runtime actually request it.

Problem and first experiment

SAY

Problem and first experiment

SAY
A stack protector can arrange for a guard value to be saved and checked on selected function paths. If certain overwrites cross that guard, a mismatch can stop a normal return. But a guard comparison proves only whether the saved guard matches the expected value at the check. Systems mechanisms and source lecture

SAY
Mitigations reduce the consequences or feasibility of exploiting certain bugs. They are defense in depth, not substitutes for memory safety. A program can contain a serious vulnerability even when it is compiled with hardening flags, uses randomized addresses, and has non-executable data pages. Treat mitigation status as a property to inspect in the actual build and deployment. 10. Stack canaries
Systems mechanisms and source lecture

SAY
Stack-protector instrumentation places a check value in selected stack frames and verifies it before returning through the protected path. Some overwrites can then be detected before corrupted state is used in a normal return sequence. Coverage depends on compiler options and generated code. A canary does not prevent the original out-of-bounds write, protect every object, or guarantee detection of every corruption pattern. It is a detection barrier for a subset of consequences.

11. Non-executable memory
Systems mechanisms and source lecture

SAY
Non-executable permissions prevent instruction fetches from designated data regions. Separating executable code from writable data reduces one class of attack opportunity. The processor and operating system must support and enforce the mapping policy. Non-executable data does not prevent all control-flow misuse or data-only corruption. An attacker does not necessarily need to introduce new executable bytes to cause harm. The underlying invalid write, stale pointer, or authorization error still requires repair.

12. Address-space randomization
Systems mechanisms and source lecture

SAY
Address-space randomization varies locations of mapped regions to make useful addresses less predictable. Position-independent executables and libraries support relocation under the relevant loader model. Randomization is not confidentiality by itself. Information disclosure can reveal addresses, and entropy varies with architecture and configuration. Do not disable randomization to make an application appear more stable; investigate invalid address assumptions instead.

In plain English: Think of an address written on a note: the note can tell you where to look, but it does not prove the thing is still there or that you are allowed to use it.

13. Memory permissions
Systems mechanisms and source lecture

SAY
Memory permissions restrict reading, writing, and execution at mapping granularity. A least-permission design avoids writable executable regions and removes unneeded access. Read-only mappings can protect immutable tables from accidental modification. Changing permissions is a privileged service request and may require translation invalidation. Permissions still do not distinguish two objects inside one writable page. They reinforce region-level boundaries while language and application rules govern object-level behavior.

14. Privilege separation
Systems mechanisms and source lecture

SAY
Privilege separation divides a system so that components handling untrusted input possess only the authority they need. A small privileged component can perform narrow validated operations for a less-privileged parser or worker. The communication interface becomes a security boundary and must validate message type, size, identity, and requested action. Splitting into processes without reducing authority or validating requests merely relocates the same risk. Failure recovery should also specify what happens when one component exits midway through an operation.

21. Non-executable data closes one route, not every misuse
Reason about the implementation

SAY
Preventing execution from a data mapping reduces one way invalid input could be turned into instructions. It does not stop an out-of-bounds write from changing a permission flag, a length, or another ordinary data value. Nor does it prove that every future control transfer reaches only an intended function. The useful claim is narrower: designated mappings cannot be used for instruction fetch under the enforced policy. That barrier belongs alongside memory-safe operations and authorization checks. Avoid describing it as a general proof that injected or corrupted input cannot harm the application; different failures cross different boundaries.

22. Randomized placement depends on relocatable code and secrecy limits
Reason about the implementation

SAY
Address-space layout randomization changes where relevant regions are mapped, making addresses less predictable. A position-independent executable supports relocating its code under the platform's loader model. Inspecting that the executable is position independent is useful evidence, but it is not the same as proving every runtime mapping is randomized effectively. The amount of uncertainty varies, and a separate information disclosure can reveal addresses. Do not make a faulty pointer program appear stable by disabling randomization; that hides an invalid assumption. Repair the address and lifetime logic while keeping the protection enabled where the deployment supports it.

23. Page permissions reinforce regions, not object boundaries
Reason about the implementation

SAY
Memory permissions act at mapping or page granularity. A read-only table can be protected against writes, and code can be kept nonwritable. But two small objects inside one writable page do not receive separate array bounds from that page permission. An incorrect index may cross from one into the other while the hardware still sees an allowed page access. That is why object-level bounds and lifetime rules remain necessary. A least-permission design asks which whole regions need reading, writing, or execution, then uses language and application contracts for finer-grained access within those regions.

40. Privilege separation makes the message interface a trust boundary
Recall and transfer

SAY
A small trusted helper can perform a narrow operation for a less-privileged worker. The helper must still validate what it receives: message type, size, identity, and requested action. An interface that accepts an arbitrary command or path with unrestricted authority can undo the intended separation. Recovery matters too. If the worker exits after the helper commits an operation but before receiving the reply, repeating the request may duplicate effects. Keep the helper's contract small enough to test and reason about, and use identifiers or reconciliation when the operation's retry meaning requires them.
