1. Serving concurrently creates budgets before it creates speed
Problem and first experiment

SAY
A thread per connection makes a blocking conversation easy to follow, but it does not make resources unlimited. Each admitted client may need a descriptor, stack reservation, request buffer, output buffer, and access to shared services. Those threads share the process's memory, so a cache or counter remains shared even if each thread has its own request object. Start by writing a budget and naming the resource that enforces it. A listening backlog does not cap active clients or worker memory. Concurrency is useful only when the accepted workload can make progress without overwhelming these shared limits.

2. Two separate checks can oversubscribe one remaining slot
Problem and first experiment

SAY
The gate has capacity two and already holds one client. We model two arrivals by making both decisions before either increment. Each sees one active client and says yes. Applying both approvals increases active to three, violating the cap. This program is deliberately single-threaded and contains no data race; it models the logical interleaving of an incorrectly split check and update. A real unsynchronized shared integer would additionally have undefined behavior in C++. Protecting each increment alone is insufficient. The capacity check and the reservation must be one critical section so later arrivals see the earlier reservation.

3. An admitted request needs one release on every exit
Problem and first experiment

SAY
This complete example adds lifetime management to a mutex-protected gate. Permit asks the gate to reserve a slot and remembers whether it succeeded. When the scope ends, its destructor releases only a slot it actually owns. The request body deliberately throws after admission. Stack unwinding destroys the permit, and the catch reports the failure. A second permit can then acquire the same capacity, so the output ends with reusable equals one. The permit is not copied because two copied owners could release one reservation twice. This mechanism bounds admitted work; it does not automatically bound every buffer or downstream request.

4. Use the smallest applicable resource ceiling
Problem and first experiment

SAY
Suppose descriptor accounting permits nine hundred sixty clients, while a memory model permits thirteen hundred sixty-five. The arithmetic ceiling is the smaller number, not their average. The source then chooses an operational cap of two hundred fifty-six to preserve headroom. Those numbers are modeled assumptions, not measurements of this machine. A defensible budget lists what it includes, what it omits, and which measured workload could force a lower limit.

10. Thread-per-connection
Systems mechanisms and source lecture

SAY
A thread-per-connection design assigns a worker to each accepted client. Blocking I/O becomes straightforward because one slow connection blocks its own worker rather than the entire server loop. The control flow resembles a sequential protocol handler. The cost grows with active connections: thread stacks, scheduler state, per-connection buffers, and synchronization overhead accumulate. An unbounded thread-per-connection loop can exhaust resources before useful work completes. Bound admission and ensure every thread is joined or otherwise owned through shutdown.

In plain English: Imagine several people editing the same whiteboard. If they do not coordinate, the final answer can depend on who writes at exactly the wrong moment.

11. Connection state
Systems mechanisms and source lecture

SAY
Connection state includes protocol progress, input and output buffers, authentication or session information, deadlines, and lifecycle status. A connection may be reading a prefix, reading a body, computing a response, writing a partial response, or closing. Make state transitions explicit. “Socket exists” is not enough to determine which operation is valid next. A half-closed connection can still have data to drain or a response to send, depending on the protocol. Cleanup should occur only when no worker or event handler can still reference the connection object.

12. Shared resources
Systems mechanisms and source lecture

SAY
Connections compete for descriptors, memory, CPU, downstream services, caches, and application data. Per-connection limits do not replace global limits. A thousand individually acceptable requests can collectively overwhelm a shared database or work queue. Define budgets at each stage. An accepted socket may count against a connection limit, a parsed request against a queued-work limit, and an executing task against a worker limit. Transfer the corresponding ownership credits when work moves between stages, and release them on every failure path.

13. Synchronization
Systems mechanisms and source lecture

SAY
Shared application state requires the same synchronization rules developed in Parts X and XI. A server should avoid holding global locks while waiting for a client or downstream service. Slow external activity inside a critical section can stall otherwise independent clients. Use snapshots, immutable request objects, and bounded queues to separate I/O from protected updates. A worker pool limits simultaneously executing handlers, but an unbounded queue in front of it can still consume unlimited memory and produce extreme waiting times.

14. Resource exhaustion
Systems mechanisms and source lecture

SAY
Exhaustion occurs when demand exceeds a resource limit. Symptoms include failed thread creation, descriptor exhaustion, allocation failure, long queues, and timeout cascades. Rejecting or deferring work deliberately is often safer than accepting everything and failing unpredictably later. A robust policy specifies admission limits, maximum frame sizes, idle and whole-request deadlines, output-buffer limits, and shutdown behavior. Per-operation socket timeouts alone do not defeat a client that makes tiny amounts of progress just before each timeout; a whole-request deadline bounds the complete transaction.

15. Derive an admission budget
Systems mechanisms and source lecture

SAY
Assume a hypothetical service budget , not a measurement of the host system: The descriptor bound is 1024 - 64 = 960 clients when each client uses one descriptor. The modeled per-client memory is 72 KiB. The remaining memory is 96 MiB, which permits floor(96 × 1024 / 72) = 1365 clients under those assumptions. The combined arithmetic ceiling is therefore 960. Choosing an operational cap of 256 leaves headroom. Its modeled client memory is 256 × 72 KiB = 18 MiB ; adding the 32-MiB base gives 50 MiB. This does not include every possible kernel buffer or thread reservation. The assumptions must be replaced with measurements and explicit accounting before using the number as a deployment limit. 21. Per-connection state should stay with its connection
Reason about the implementation

SAY
Two clients can each have half of a header buffered at the same time. Putting both fragments into one global scratch buffer mixes unrelated conversations even if individual writes are locked. Keep framing state, output offsets, deadline information, and the descriptor together in a connection object. That object needs a clear owner, while callbacks and workers may borrow it under a lifetime rule. Closing a descriptor from another thread is not a universal cancellation mechanism, and the integer may later be reused. A stale callback that recognizes only the integer can act on the wrong connection after reuse.

22. Choose a lock boundary around a complete shared operation
Reason about the implementation

SAY
A server cache often needs a compound operation: find a key, decide whether it exists, and possibly install a value. Locking only individual map methods can leave a gap between the decision and the update. Conversely, holding one global lock while writing a slow client's response blocks unrelated clients. A useful design protects the shared data operation, obtains a result with a clear lifetime, and releases the lock before slow I/O when the contract allows it. Returning a borrowed reference into a cache that another thread can erase requires more than simply unlocking quickly.

23. Backpressure is a policy, not a full queue accident
Reason about the implementation

SAY
When capacity is full, the server must choose what the next request experiences. It can reject promptly, wait within a bounded queue, or apply a documented shedding policy. An unlimited waiting queue only moves resource exhaustion from active workers to queued requests. A bounded queue also needs a waiting deadline or cancellation rule when clients disappear. Distinguish overload from a bad request so callers can respond appropriately, but do not encourage unbounded immediate retries. Admission, queueing, execution, and response delivery are separate stages; each should have a budget and an owner for abandoned work.

24. Creation failure is part of concurrency setup
Reason about the implementation

SAY
Imagine that a server successfully starts three workers but fails to create the fourth. Returning immediately can leave the first three using queues or buffers that are being destroyed. Setup is therefore a sequence of resource acquisitions, not an all-or-nothing magic operation. Record each successful creation, publish shutdown if setup cannot continue, and collect the workers already created before destroying their shared state. Scope-based thread owners can help, but their joins must not wait on work that will never be signaled. The shutdown protocol and lifetime order need to be designed together.

40. Test the admission invariant under overlap and failure
Recall and transfer

SAY
A good gate test checks more than one happy admission. Fill the budget, verify the next request is rejected, release one permit, and verify reuse. Test a zero limit and error paths after successful admission. For actual concurrent tests, collect results after joining and verify the maximum protected active count never exceeded the limit. Do not infer correctness only because one run happened to finish. The logical split-check model shows why the invariant must be justified by the critical section. Leak checks and shutdown tests then cover lifetime obligations that the count alone cannot prove.

Recall and transfer

SAY
A few long, simple conversations may justify one thread each. A bounded worker pool fits tasks that can be handed off without leaving a thread attached to every idle client. An event loop can service many connections by acting when I/O is ready, but requires explicit partial-operation state. None eliminates framing, ownership, resource bounds, or shutdown. Compare the number of active versus idle clients, work per request, downstream limits, and implementation complexity. The next chapter changes how waiting is organized; it does not remove the shared-resource contracts established here.
