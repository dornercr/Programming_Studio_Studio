1. One call produces two continuations on success
Problem and first experiment

SAY
fork creates a child process, and a successful call is followed by execution in both processes. They continue after the call; the child does not restart main. The return value tells each branch its role. The parent receives the child's positive process ID, the child receives zero, and failure gives the caller minus one with no new child. Treat all three cases explicitly. A branch written for every nonzero value can accidentally treat failure as a created child. The program also needs a lifecycle plan: who waits, who closes inherited endpoints, and where the child ends if it is not meant to continue the parent's normal workflow.

3. Private memory does not imply private everything
Problem and first experiment

SAY
The array experiment can create a misleading generalization: all child changes are private. Kernel-managed resources follow their own sharing rules. If a file was opened before fork, the inherited descriptor in the child can refer to the same open file description as the parent's descriptor. That object holds the current offset. A child read can therefore change where the parent's next read begins. Closing the child's entry releases its reference without closing the parent's separate entry. Keep two diagrams in mind: private address-space values and references to shared kernel objects. Confusing them causes both missing data and leaked communication endpoints.

8. Chapter 37 — Process Creation
Systems mechanisms and source lecture

SAY
Process creation separates an execution environment into independently scheduled participants. On POSIX systems, fork creates a child whose initial state resembles the parent’s at the call boundary, but the two processes receive different return values and can immediately follow different paths. The resemblance must be interpreted carefully. Private memory has independent modification semantics, while inherited descriptors can reference the same underlying open objects. Treating everything as either “fully copied” or “fully shared” produces errors. [ R15 ]

10. fork
Systems mechanisms and source lecture

SAY
fork returns once in the parent and once in the child after successful creation. In the parent it returns the child’s process ID; in the child it returns zero. On failure, the parent receives -1 and no child is created. The child begins after the call, not at the beginning of main . Every branch must therefore be explicit about which process owns which cleanup and continuation responsibilities. A child intended to execute a new program should not accidentally fall through into the parent’s main loop when execution fails.

11. Parent process
Systems mechanisms and source lecture

SAY
The parent retains its identity and receives a handle-like process ID for the child. It must decide whether to wait immediately, continue concurrently, or supervise several children. It also remains responsible for closing inherited communication endpoints it does not use. A parent cannot assume that it executes first after the fork. Scheduling can run the child before the parent reaches its next statement. Any ordering requirement must be established through waiting or communication, not inferred from source order in the parent’s branch.

12. Child process
Systems mechanisms and source lecture

SAY
The child has its own process identity and private execution state. It can modify ordinary private variables without changing the parent’s copies. It may execute a new program, perform bounded work, or participate in a pipeline. After a fork from a multithreaded process, only the calling thread appears in the child, while copied library and mutex state can reflect locks held by threads that no longer exist there. Until a successful exec, the child must obey the applicable async-signal-safe restrictions. The examples here create children from single-threaded programs. [ R15 , R20 ]

14. Address-space duplication
Systems mechanisms and source lecture

SAY
The child receives an address space with corresponding mappings according to the interface’s rules. Ordinary private memory initially contains the same values, but later modifications are logically independent. Shared mappings remain shared according to their mapping semantics. User-space I/O buffers are also memory. If buffered output exists before a fork and both processes later perform normal stream flushing, the same buffered bytes can be emitted twice. Flush deliberately before forking when appropriate, or ensure that an exec-bound child’s failure path uses _exit rather than normal buffered cleanup.

In plain English: Think of an address written on a note: the note can tell you where to look, but it does not prove the thing is still there or that you are allowed to use it.

15. File-descriptor inheritance
Systems mechanisms and source lecture

SAY
The child’s inherited descriptors refer to the same open file descriptions as the corresponding parent descriptors. They can share current offsets and file status flags. Closing the child’s descriptor releases its reference without closing the parent’s separate descriptor-table entry. This sharing is useful for pipelines and redirection but can also cause surprises. A child’s read can advance the offset subsequently observed by the parent. An accidentally retained pipe write end can prevent another process from seeing end of file.

In plain English: The program asks the operating system to move bytes to or from a resource, much like using a numbered ticket to ask a clerk for the right item.

16. Copy-on-write
Systems mechanisms and source lecture

SAY
Copy-on-write can avoid physically copying all private pages immediately. Parent and child initially share backing while hardware permissions trigger separation when a private write requires it. The interface promises the observable private-memory behavior, not an eager byte-for-byte copy at the instant of creation. The amount of memory actually duplicated depends on later writes, mappings, allocator activity, and kernel policy. Forking a large process is therefore not automatically equivalent to immediately allocating another complete physical copy, but it is also not free.

23. Scheduling order must be established, not imagined
Reason about the implementation

SAY
Writing the parent branch first on the page does not cause the parent to run first. After fork, either process may be scheduled before the other's next statement. If both print, their observed order may vary even though each branch follows its own local sequence. A requirement such as read after the child finishes must be encoded with waiting or a communication protocol. Tests should avoid declaring one accidental print order a guarantee. In our demos, child work is reported through status and the parent prints afterward. That preserves deterministic evidence without concealing the fact that concurrent execution order before the wait is unspecified.

24. Copy-on-write is an implementation mechanism for private behavior
Reason about the implementation

SAY
Copy-on-write can let parent and child initially refer to shared physical backing for private pages. When a private write occurs, the system can create the separation needed to preserve independent values. This avoids eagerly copying every byte merely because fork returned. It does not make process creation free, and later allocator activity or writes may still cause substantial work. The array demo proves neither the number of copied pages nor their timing. It proves the behavior the program depends on. Keep implementation explanations and observable guarantees distinct when estimating memory use, especially when forking a large process whose later writes may be far broader than the small explicit assignment.

25. Copied output buffers can print the same bytes twice
Reason about the implementation

SAY
If a library output buffer contains unflushed text before fork, both processes inherit a copy of that buffer state. If both later perform normal flushing, the same text can appear twice. The extra output did not come from the file descriptor magically copying already-written bytes; it came from two user-space copies of bytes not yet sent. Flush deliberately before creation when that is appropriate. An exec-bound child generally uses _exit on failure so it does not run the parent's buffered cleanup. That choice needs deliberate lifecycle design, because _exit also bypasses ordinary user-space cleanup that a different kind of child might actually need.

26. A multithreaded parent creates a stricter child boundary
Reason about the implementation

SAY
The demos fork from a single-threaded program. A multithreaded parent has a harder problem: only the calling thread is present in the child, while copied mutex and library state can reflect locks held by other threads before the fork. Those missing threads cannot later release their locks in the child. This is why the child must obey the applicable async-signal-safe restrictions until exec. A convenient allocator or formatting call may not be appropriate in that narrow interval. Do not generalize the single-threaded examples into an unrestricted child setup routine for a large threaded application. Choose launch facilities and setup operations that match that environment.

42. Creation includes cleanup and reaping obligations
Recall and transfer

SAY
A correct launch path is more than a successful fork. On failure, no child exists, so the caller must clean up prepared resources without waiting for an invented process. On success, each process must close inherited communication ends it does not need. The parent must then follow a clear policy for collecting child status. A forgotten pipe writer can block another process's EOF long after the useful writer exits, and an unreaped child leaves termination bookkeeping behind. Review every branch with an ownership table: resource, parent use, child use, and release point. That table is often more revealing than the successful output alone.
