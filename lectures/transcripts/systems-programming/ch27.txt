1. One memory number hides several different limits
Problem and first experiment

SAY
A request can finish quickly in isolation while a busy system completes few requests per second, or a system can complete many overlapping requests while each waits a long time. Latency and throughput describe different boundaries. Capacity adds another question: can the useful working set remain in a fast level? The memory hierarchy balances these concerns across registers, caches, main memory, and persistent storage. A single phrase such as memory speed is too vague for a diagnosis. 2. Overlap changes completion time without shortening service time
Problem and first experiment

SAY
This deterministic scheduling model submits three identical requests at time zero. One service lane would complete them at times five, ten, and fifteen. With two lanes, the first two run together and finish at five, then the third finishes at ten. The printed service time remains five in both arrangements. The improvement comes from overlap, not a faster individual operation. These numbers are invented model units, not measured nanoseconds or a claim that two CPU threads double memory bandwidth. Real overlap is limited by dependencies, queues, and shared resources. The example forces us to distinguish per-operation service time from the batch’s final completion time.

3. Registers are a compiler allocation choice
Problem and first experiment

SAY
Writing int sum in source does not force a memory load and store for every update. The compiler may keep sum in a register, combine operations, or remove the entire calculation if its result has no observable effect. Therefore, timing a loop that computes an unused answer can measure little or none of the work you intended. Registers also obey instruction constraints and calling conventions, so register pressure may cause values to spill to memory. When investigating one compiled program, inspect the generated instructions and preserve meaningful observable results. Do not infer the hierarchy level of every operation from source variable names alone.

8. Chapter 27 — Memory Hierarchy
Systems mechanisms and source lecture

SAY
A computer does not store every useful byte in one uniformly fast place. It uses a hierarchy of storage technologies and structures with different capacities, access costs, and management rules. Programs perform well when frequently needed information remains in the levels that can serve it efficiently. This chapter uses qualitative relationships rather than a table of supposedly universal nanosecond values. Actual latency and bandwidth depend on the processor, memory configuration, access pattern, contention, power state, and measurement method. Treat hardware specifications and local measurements as evidence for a particular machine, not as constants of the language. [ R3 , R30 ]

10. Registers
Systems mechanisms and source lecture

SAY
Registers hold operands and execution state directly used by instructions. The compiler allocates many frequently used values to registers, subject to instruction constraints and calling conventions. Values that cannot remain in registers may be spilled to memory. A source-level local variable is not automatically a stack slot. It can live in a register, be folded into another expression, or disappear when it has no observable effect. Looking at generated assembly is the appropriate way to investigate a particular compiled implementation.

11. L1 cache
Systems mechanisms and source lecture

SAY
An L1 cache is a small, fast cache close to an execution core. Processors commonly distinguish instruction and data L1 caches, although exact organizations vary. Its limited capacity favors compact working sets and repeated access to nearby data. The cost of an L1 hit is not simply the cost of a complete source statement. Dependencies, execution ports, translation, and instruction scheduling also affect progress. A chain of dependent loads behaves differently from many independent loads that hardware can overlap.

In plain English: A cache is like keeping the things you use most often on your desk instead of walking to a storage room every time.

12. L2 cache
Systems mechanisms and source lecture

SAY
L2 provides additional capacity beyond L1 at a different access cost. It can satisfy requests for lines absent from L1 without requiring a trip to main memory. Whether an L2 is private to a core or shared is a hardware design choice. A working set too large for L1 can still perform well when it fits in L2 and has predictable access. Performance often changes gradually or in steps as working-set size crosses hierarchy boundaries, rather than following a single universal “memory access” time.

In plain English: A cache is like keeping the things you use most often on your desk instead of walking to a storage room every time.

13. L3 cache
Systems mechanisms and source lecture

SAY
An L3 or last-level cache often provides larger shared capacity, but names and sharing arrangements are not universal. Shared caches allow data to serve multiple cores while also creating competition for capacity and bandwidth. Cache inclusion policies vary. Do not assume that every line in a private cache must also exist in the last-level cache, or that evicting a line has identical consequences on all processors. For application design, focus first on working-set size, sharing patterns, and measured behavior.

In plain English: A cache is like keeping the things you use most often on your desk instead of walking to a storage room every time.

14. DRAM
Systems mechanisms and source lecture

SAY
DRAM supplies main-memory capacity beyond the processor caches. Access cost depends on more than a single chip latency: memory controllers, channels, banks, row state, access concurrency, and NUMA placement can all matter. Bandwidth and latency limits are distinct. A workload with many independent sequential accesses may approach a bandwidth limit, while a dependent pointer-chasing workload may be limited by the latency of each next address. The same number of bytes can therefore take different times under different dependency patterns.

15. SSD
Systems mechanisms and source lecture

SAY
An SSD is persistent storage accessed through a device and operating-system stack rather than as ordinary CPU cacheable DRAM. Its behavior depends on request size, queue depth, write patterns, device state, and filesystem policy. A file read that returns quickly may have been served from the operating system’s page cache without reaching the SSD. Distinguish cached file-access measurements from device measurements. Similarly, successful buffered writes do not by themselves prove that data has reached durable media.

16. Persistent storage
Systems mechanisms and source lecture

SAY
Persistent storage is intended to retain data across power loss or restart under specified guarantees. The complete durability story involves hardware behavior, filesystem semantics, and explicit synchronization operations. Persistence is a property to request and verify at the appropriate layer, not a synonym for “the write function returned.” A robust design distinguishes data in an application buffer, data accepted by the kernel, and data committed according to the required durability contract. Chapters 35 and 59 revisit this distinction when discussing buffering and recovery. [ R33 ]

17. Latency
Systems mechanisms and source lecture

SAY
Latency is the time required for one operation or dependency to complete. A dependent chain exposes latency because later work cannot begin until earlier results are available. For example, following linked-list pointers often prevents the next address from being known in advance. Report the operation being measured. Cache-hit load latency, end-to-end request latency, and storage-read latency describe different boundaries. A number without its start event, end event, and conditions is difficult to interpret.

18. Throughput
Systems mechanisms and source lecture

SAY
Throughput is completed work per unit time. A system can have high throughput while individual requests experience substantial latency, especially when many operations overlap. Conversely, a fast isolated operation can yield poor aggregate throughput when shared resources serialize it. Useful units include bytes per second, records per second, and requests per second. Choose a unit tied to completed useful work, not merely to internal activity. Counting retries or duplicated work as successful throughput can conceal a broken design.

19. Capacity
Systems mechanisms and source lecture

SAY
Capacity is the amount of information a level can hold. Larger capacity can reduce misses, but only for data that remains useful before eviction. A cache filled with streaming data that will never be reused may displace a smaller, more valuable working set. Working-set analysis asks how much data is actively needed over a relevant interval. Total dataset size alone does not answer that question. A terabyte dataset processed in small independent tiles can have a modest active working set.

20. Cost
Systems mechanisms and source lecture

SAY
Cost includes hardware expense, energy, area, management overhead, and opportunity cost. Faster storage structures are constrained by more than purchase price. A design that used the fastest possible storage for every byte would face physical and economic limitations. The hierarchy is therefore a resource-allocation strategy. Software participates by making reuse visible, avoiding unnecessary movement, and organizing work so that scarce fast capacity holds valuable information. Optimization is often about moving fewer bytes rather than executing a cleverer arithmetic instruction.

23. Why capacity increases down the hierarchy
Systems mechanisms and source lecture

SAY
Registers are fastest but scarce; caches are larger and slower; DRAM is much larger; persistent storage is larger again. If every byte could economically have register latency and SSD capacity, a hierarchy would be unnecessary. Engineering trades latency, cost, power, and capacity at each level.

27. A cache miss does not name its final destination
Reason about the implementation

SAY
A value absent from the first-level cache may still be available in a larger cache close to the processor. Calling that event a trip to main memory skips important levels. Likewise, the names L2 and L3 do not establish the same sharing or inclusion policy on every processor. For a software discussion, say which level missed and where the request was satisfied if that evidence is available. A working set larger than L1 may still perform well when it fits in L2 and its accesses are predictable. The hierarchy is a set of tradeoffs, not a rule that every miss pays one universal penalty.

28. Dependencies distinguish latency limits from bandwidth limits
Reason about the implementation

SAY
In a linked structure, the next address may be stored inside the value just loaded. The program cannot request that next location until the earlier load finishes, so the chain exposes latency. In a sequential array, several upcoming addresses are already known, allowing hardware to overlap requests and approach a bandwidth limit. Both traversals might read the same number of useful bytes while taking different times. Our two-lane model illustrates overlap only; it does not model every dependency or queue inside a processor. A benchmark must preserve the dependency pattern it claims to measure and generate unrelated setup outside the measured region.

29. Persistent is a durability promise, not a buffer location
Reason about the implementation

SAY
Suppose a write copies data into the operating system’s page cache and returns successfully. That proves the request reached a particular interface boundary; it does not by itself prove the data will survive power loss. A durability requirement needs the filesystem and platform’s appropriate synchronization protocol. Similarly, a quick file read may come from cached memory rather than the SSD. When discussing the hierarchy, distinguish where bytes are currently held from what failures they are promised to survive. This prevents a performance test of cached reads from being mislabeled as a device benchmark, and prevents a successful return code from becoming an unsupported persistence claim.

30. Working-set capacity is about active reuse
Reason about the implementation

SAY
A terabyte dataset does not require a terabyte of fast cache if each phase works on a small independent tile. The relevant working set is the data and instructions reused during that phase. Conversely, a modest allocation can perform poorly if its access order repeatedly displaces values before reuse. A streaming pass that never returns to its data may fill cache with little future value and evict a smaller hot set. Capacity is therefore meaningful only with an interval and access pattern. Before increasing data structures or buffer sizes, ask which bytes must remain useful together and what other work competes for that level.

46. Compare useful work with the same units and boundary
Recall and transfer

SAY
An optimization report can look better simply because it counts internal activity rather than useful completed work. Retrying a request twice is not twice the successful throughput. Comparing a buffered write with a durable write without naming their different guarantees is similarly misleading. Establish the same work unit, input, and completion boundary before comparing designs. Then distinguish setup costs from repeated costs. Batching can reduce repeated setup latency, but it can also increase waiting time for the first item. SAY
A convincing performance investigation begins with a hypothesis. If dependent loads are the limit, a test that removes dependencies no longer measures the same thing. If bandwidth is the limit, tiny isolated transfers may mostly measure fixed overhead. If cache capacity is the limit, vary the active working set while preserving useful computation and examine changes. Our executable models let you practice arithmetic without scheduling noise, but their output cannot validate real machine timings.
