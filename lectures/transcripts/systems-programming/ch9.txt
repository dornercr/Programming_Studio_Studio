Chapter 9: Dynamic Memory: ownership, growth, and failure cleanup
Dr. Charles Dorner

1. Allocation creates a cleanup obligation
Problem and first experiment

SAY
Dynamically created storage can outlive the function that first requested it, which is useful only if the program keeps a clear cleanup plan. Ownership names the component responsible for destruction and release. A borrowed pointer may use the object without taking that responsibility. Unique ownership has one responsible owner; shared ownership coordinates several owners and carries additional cost and rules. Choosing shared ownership merely to avoid deciding who owns the data can create cycles and confusing lifetimes. The chapter's practical goal is to match ownership to the required lifetime graph. Once that graph is clear, containers and smart pointers can enforce much of the cleanup automatically.

2. Storage acquisition and object construction are different work
Problem and first experiment

SAY
A raw storage request answers where bytes can be placed. A complete C++ object also has initialization and destruction rules. A new expression combines storage acquisition with object initialization, while an allocation function alone is not the whole construction operation. malloc does not run a C++ class constructor, and zeroing bytes with calloc is not a general replacement for object semantics. Containers and make_unique usually let the caller request the object or sequence it needs while keeping cleanup attached to an owner. Low-level storage operations still matter inside such abstractions, but every application call site should not need to rebuild their failure and lifetime rules.

10. Heap allocation
Systems mechanisms and source lecture

SAY
A heap allocation requests a region large enough and suitably aligned for a purpose. The allocator may satisfy the request from existing free space or obtain more backing storage. Allocation can fail because of size limits, fragmentation, policy, or resource exhaustion. A successful request for raw storage does not necessarily mean every page has already been physically committed or touched. Nor does it initialize arbitrary C++ objects by itself. Separate storage acquisition, object initialization, use, destruction, and storage release. This sequence helps explain both raw allocation APIs and higher-level containers.

11. malloc
Systems mechanisms and source lecture

SAY
malloc(n) requests at least n bytes of storage and returns a suitably aligned pointer for the supported ordinary object alignments, or a null pointer on failure. The returned bytes are not initialized. In C, assignment through an appropriately typed pointer can establish the intended object use within the language’s effective-type rules. Compute n safely before calling. Use sizeof *pointer rather than repeating a type name when it reduces maintenance risk. A zero-size request has special behavior that should not be used as an application control signal. Handle an empty collection explicitly so the ownership rules do not depend on a zero-size allocation convention. [ R39 ]

12. calloc
Systems mechanisms and source lecture

SAY
calloc(count, size) requests storage for an array and zeroes the allocated bytes. Its separate count and size arguments allow the implementation to detect multiplication overflow. The application still needs semantic bounds, because a representable request may be far larger than policy permits. All-zero bytes are not a universal initializer for every possible object representation. On the reference platform they represent zero for ordinary integer storage, but portable C does not equate zero bytes with every null pointer or floating-point zero representation. In C++, use constructors and value initialization for objects rather than treating calloc as a replacement for object semantics.

13. realloc
Systems mechanisms and source lecture

SAY
realloc changes the size of a previously allocated block while preserving the common prefix of the old and new sizes. It may move the block. For a nonzero requested size, failure leaves the original allocation available. Success ends the old allocation’s role and returns the pointer to use afterward. Store the result in a temporary pointer. Assigning directly to the only owning pointer can lose the original allocation on failure. After success, old aliases must not be used, even if the returned numeric address happens to match. Avoid realloc(p, 0) in portable application logic because its historical and language-version semantics are troublesome; use an explicit free-and-empty path instead.

14. free
Systems mechanisms and source lecture

SAY
free releases a block obtained through the matching allocation family. Passing a null pointer has no effect. Passing an interior pointer, a pointer to automatic storage, or an already freed pointer violates the contract. The allocator needs the original allocation identity, not merely an address somewhere inside its payload. Freeing storage does not guarantee that its bytes are erased or that the operating system immediately reclaims its pages. Do not use free as a data-sanitization operation. More importantly, do not read the bytes after release merely because a debugger still shows the old contents. The lifetime boundary is semantic, not a visible overwrite event.

15. new
Systems mechanisms and source lecture

SAY
A C++ new expression obtains storage and initializes an object. Ordinary allocation failure throws std::bad_alloc ; a nothrow form can return null. If construction throws after storage acquisition, the language arranges the matching cleanup for that failed construction path. Prefer std::make_unique for unique dynamic ownership and containers for collections. A raw new is sometimes needed inside a low-level abstraction, but it should not force every caller to reason about cleanup. The distinction between an allocation function named operator new and a complete new expression also matters: the former obtains storage, while the latter includes object initialization.

16. delete
Systems mechanisms and source lecture

SAY
A delete expression destroys the object and releases its storage through the matching mechanism. Scalar new matches scalar delete ; array new[] matches delete[] . Mixing allocation families, such as malloc with delete , is invalid. Deleting through a base-class pointer requires appropriate polymorphic destruction when the dynamic object is derived. A base intended for such ownership generally needs a virtual destructor. Resource ownership through a pointer is therefore a type-design issue as well as an allocator issue. A correct address with the wrong destruction interface is still unsafe.

17. Allocation lifetime
Systems mechanisms and source lecture

SAY
An allocation’s lifetime must cover every use of its storage. Borrowed pointers into a resizable allocation have especially fragile lifetimes because growth can move the block. A function that returns an interior pointer should document which operations invalidate it. Group objects with the same lifetime when that simplifies ownership. A request-scoped arena can release many short-lived allocations together. A vector can own a sequence whose elements move as one resource. Avoid creating a separate ownership obligation for every small object unless independent lifetimes are actually needed.

18. Ownership
Systems mechanisms and source lecture

SAY
Ownership identifies the component responsible for destruction and release. Unique ownership has one responsible owner. Shared ownership coordinates several owners, commonly with reference counting. Borrowing grants access without release responsibility. Shared ownership is not free and does not automatically make the object thread-safe. A reference count protects lifetime, not arbitrary member updates. Cycles can also prevent reclamation unless broken by weak references or another policy. Choose the simplest ownership model that matches the required lifetime graph; do not use shared ownership merely to avoid deciding who owns a resource.

25. Check the request before asking for storage
Reason about the implementation

SAY
An allocator cannot repair a byte count that was already computed incorrectly. If count times element size wraps before the request, the allocator may successfully return a smaller block than the program intended. Use a checked size calculation and a domain limit before calling. A representable request can still be far too large for the application. Empty collections also deserve an explicit policy, because zero-size allocation conventions are not a useful general signal for success or failure. A high-level container often handles empty state more clearly. When raw storage is necessary, keep the count, capacity, ownership, and allowed failure state together so later code does not reconstruct them from guesses.

26. Match the acquisition and release mechanisms
Reason about the implementation

SAY
A resource must be released through the mechanism that matches how it was acquired. Storage from malloc belongs with free. A scalar new expression pairs with scalar delete, and array new pairs with delete[]. Mixing them is invalid even if the pointer's numeric address looks correct. C++ object destruction adds another requirement: deleting a derived object through a base pointer needs an appropriate polymorphic destruction interface, normally a virtual destructor for that owning base use. Smart pointers help only when their deleter and pointed-to type express the right contract. They cannot turn a mismatched raw acquisition into correct cleanup merely by wrapping the address.

27. Successful growth ends the old borrowing arrangement
Reason about the implementation

SAY
A successful realloc preserves the common prefix of the old and new byte counts, but it may move the allocation. The pointer it returns is the one to use afterward. Old aliases must not be kept in circulation based on a guess that the allocator probably grew in place. Even an equal displayed numeric address does not justify using the old allocation's stale access values. A similar rule appears when vector reallocation invalidates element pointers. Design callers to keep an index or another stable logical identifier where appropriate, then reacquire a bounded view after growth. A buffer API that retains hidden interior pointers makes this transition much harder to maintain.

28. Release does not promise erasure or immediate page return
Reason about the implementation

SAY
After free or object destruction, the program must stop using the old allocation even if a debugger still displays familiar bytes. Lifetime ends by the language and allocator contract, not by the memory being visibly overwritten. Release also does not promise that sensitive contents were securely erased or that pages were immediately returned to the operating system. Those are separate requirements with separate mechanisms. In normal code, the immediate task is to end all unsupported borrowing and prevent a second release. In diagnostics, do not read freed storage to verify cleanup. Inspect ownership behavior or use appropriate tools rather than adding another invalid access to investigate the first.

44. Shared ownership solves a lifetime relation, not every dependency
Recall and transfer

SAY
A tree of request-owned objects often needs one clear root owner and borrowed access below it. Giving every link shared ownership can make cleanup less obvious, particularly when objects point back to one another. Reference counts may never reach zero in a cycle. A weak reference can express a link that should observe an object without extending its lifetime, but it must be checked when converted to usable access. Do not introduce this machinery without a need for independently lasting owners. The smallest ownership model that matches the real lifetime graph is usually easier to reason about, test, and change when a new component is added.

45. Test cleanup on the path that fails halfway
Recall and transfer

SAY
A resource test should cover the moment after one acquisition succeeded but a later operation failed. Our tracked-object demonstration shows that the owner releases the earlier object during exception cleanup. The growth demonstration shows a different guarantee: rejection leaves the existing buffer available rather than releasing it. Both are correct because their contracts differ. State the expected remaining ownership explicitly before writing tests. Also test normal exit, repeated operations, empty states, and the boundary that rejects more growth. A maintainable abstraction lets callers trust these outcomes without duplicating cleanup logic at every error return.
