1. A crash is often the last event, not the first
Problem and first experiment

SAY
A service crashes while following a pointer, but the pointer was damaged by an earlier write beyond an unrelated buffer. Debugging only the final instruction can therefore explain the symptom without finding the cause. We need a vocabulary that separates four questions. Is the index inside the object? Is that object still alive? Was the value initialized before it was read? Who is responsible for releasing it? A mapped page answers none of these questions completely. The operating system may permit access to that page while C++ still forbids access outside a particular array. Start your investigation with the first broken promise.

2. One owner can move without duplicating a resource
Problem and first experiment

SAY
This program uses a live-object count so we can observe ownership without printing addresses. Construction raises the count to one. Moving first into second transfers the unique owner, leaving first empty while the same Resource remains alive. That is why the middle output says first is false and second is true, with one live object rather than two. Leaving the scope destroys second and its Resource, so the final count is zero. This is a small example of resource acquisition is initialization, often called RAII: an object's lifetime carries its cleanup duty. It avoids inventing two independent deletion paths.

3. A size check can overflow before it protects anything
Problem and first experiment

SAY
A guard can be wrong even when it looks like a bounds check. The demonstration sets offset near the largest size_t value and length to five. Their unsigned sum wraps to two, so the naive comparison wrongly accepts an eight-byte region. The guarded version first rejects an offset beyond the extent, and only then subtracts to find remaining room. It prints naive true and guarded false. These are numeric checks only; the program deliberately forms no out-of-range pointer. This isolates the logic flaw safely. A real copy also needs valid live source and destination ranges and an explicit overlap policy.

4. Reserve the terminator before copying text
Problem and first experiment

SAY
An array of eight chars has eight elements, numbered zero through seven. If it must hold a C string, one element is reserved for the terminating zero byte. An eight-character payload therefore does not fit even though eight sounds like the right capacity. The chapter's copy exercise checks the request before touching the destination, which gives a useful failure guarantee: rejected input leaves existing bytes unchanged. Do not confuse a counted byte range with a zero-terminated string. They have different contracts. When maintaining a parser, specify whether the size includes the terminator and use one convention consistently at every call boundary.

10. Buffer overflow
Systems mechanisms and source lecture

SAY
A buffer overflow writes more data than a buffer can hold. The relevant bound is the actual destination capacity, not a claimed input length. A safe copy needs agreement among source availability, destination capacity, and requested count. String operations add another requirement: space for the terminator when the result must be a C string. A ten-character payload needs eleven bytes in that representation. Prefer length-aware interfaces and verify arithmetic before allocation. A bounded function can still be misused if the supplied bound describes the source instead of the destination.

11. Out-of-bounds access
Systems mechanisms and source lecture

SAY
An out-of-bounds read or write accesses outside an object’s permitted range. Reads matter as much as writes: they can disclose data, fault, or influence control flow using unrelated bytes. A read that remains within a mapped page can still violate the language’s rules. Check indices before forming an invalid pointer. For a region described by offset and length, use the guarded subtraction pattern from Chapter 4. In multidimensional code, validate every dimension and stride relationship. A valid row index does not rescue an invalid column index that happens to land inside neighboring storage.

12. Memory leaks
Systems mechanisms and source lecture

SAY
A leak occurs when storage remains allocated without a reachable ownership path that will release it when required. Losing a pointer is a common cause, but a reachable container that grows forever can also create a practical retention problem even when a leak detector sees it as reachable memory. Distinguish accidental leaks from intentional caches and from unbounded retention. Measure live object counts and ownership paths, not only process resident size. A cache needs a limit and eviction policy. An ownership cycle needs a way to break the cycle. “The operating system frees it at exit” does not justify unbounded growth in a long-running service.

13. Double free
Systems mechanisms and source lecture

SAY
A double free releases the same allocation more than once. It often arises when two components both believe they own a raw pointer, or when a cleanup path runs after an earlier release without updating ownership state. The repair is a single ownership protocol, not merely adding scattered null checks. After ownership transfer, the previous owner must no longer release. In C++, move-only resource wrappers make this rule visible in the type system. In C, document transfer and reset the owning state in a disciplined way while remembering that unrelated aliases remain unchanged.

14. Invalid free
Systems mechanisms and source lecture

SAY
An invalid free passes a pointer that is not a currently releasable allocation from the matching family. Interior pointers, stack addresses, and pointers from a different allocator are common examples. The allocator’s metadata lookup can be corrupted or confused by such inputs. A function returning a borrowed interior pointer should not expose an interface that suggests ownership. Name and document it as a view. Where several allocators exist, keep the release operation with the owner or use a deleter that records the matching mechanism. Allocation provenance is part of the resource contract.

15. Use-after-free
Systems mechanisms and source lecture

SAY
Use-after-free accesses storage after its allocation has been released. The storage may retain old bytes, be reused for a different object, or become inaccessible. None of those physical outcomes restores the old access’s validity. Concurrent use-after-free is especially subtle. One thread can validate a pointer while another releases the target before the first dereferences it. Protect the lifetime across the entire access interval with ownership, locking, or a carefully designed reclamation scheme. Atomic pointer loads alone do not keep the pointed-to object alive.

16. Dangling pointers
Systems mechanisms and source lecture

SAY
A dangling pointer or reference outlives the object it designates. It can result from returning a local address, destroying an owner, reallocating a vector, or resetting an arena. The pointer variable itself may remain perfectly intact. Track invalidation events in interface documentation and code review. A function that returns a view into a container should specify which mutations invalidate it. Avoid storing borrowed views in long-lived objects unless the owner’s lifetime relationship is explicit and enforceable. Lifetime bugs become easier to prevent when the design limits how far a borrow can travel.

In plain English: Think of an address written on a note: the note can tell you where to look, but it does not prove the thing is still there or that you are allowed to use it.

17. Uninitialized memory
Systems mechanisms and source lecture

SAY
Raw allocation does not initialize its payload, and many automatic scalar declarations do not establish a usable value. Reading an indeterminate scalar value is generally invalid in the language modes used here, with narrow special rules that are not a basis for ordinary application logic. Initialize before use, but do not confuse initialization with semantic validation. A zeroed length can be a valid default while a zeroed state tag may still be invalid for the protocol. Tools for uninitialized-value tracking complement address sanitizers because staying within allocated storage does not guarantee that the bytes have been meaningfully initialized.

18. Undefined behavior
Systems mechanisms and source lecture

SAY
Undefined behavior means the language imposes no requirements on the program’s behavior for the offending execution. It is not a promise to wrap, crash, throw, or continue with a random value. Optimizations can rely on the assumption that valid programs do not perform the invalid operation. This is why an apparently harmless out-of-bounds access can change unrelated-looking code after optimization. The right response is to remove the invalid operation, not to demand that the compiler preserve one observed accident. Debug and release builds are different experiments; both must implement a program whose source-level behavior is defined.

19. Sanitizers
Systems mechanisms and source lecture

SAY
AddressSanitizer instruments memory accesses and allocation boundaries to detect classes such as heap and stack out-of-bounds access and use-after-free. UndefinedBehaviorSanitizer targets selected language violations. ThreadSanitizer tracks data races. Their coverage and limitations differ, and some configurations cannot be combined. [ R5 , R6 ] A clean sanitizer run covers only executed paths and the checks enabled in that build. Some lifetime, intra-object, protocol, and logical errors remain outside a tool’s detection. Use sanitizers alongside warnings, tests, fuzzing of parsers, ownership design, and review. Instrumented performance is not production performance.

26. Nulling one variable does not erase every alias
Reason about the implementation

SAY
Suppose two pointer variables refer to one allocation. Releasing through the owner and then setting that owner variable to null does not change the other variable's stored bits. The second variable is now a dangling pointer: its object has died even if those bits still name mapped memory. We do not dereference such a pointer to learn what it happens to print, because the language makes no promise for that access. The design repair is to bound the borrowing interval or give readers an ownership mechanism that keeps the object alive. A null check alone cannot protect an interval during which another thread may release the object.

27. Pair allocation and release through one contract
Reason about the implementation

SAY
A function may return a pointer to the middle of a larger buffer. That pointer can be a useful view while the buffer remains alive, but it is not a new allocation that the caller may free. Similarly, storage obtained from one allocation family must be released through the matching family. The numeric address alone does not carry this history, which is why raw-pointer interfaces need clear ownership documentation. A C++ owner can keep a custom deleter with the resource when a library supplies a special release function. Centralizing that pairing is safer than making every caller remember a cleanup rule from a comment elsewhere.

28. Initialized does not mean meaningful
Reason about the implementation

SAY
Initializing a length to zero avoids reading an indeterminate scalar, but a zero state tag may still be invalid for an application protocol. These are separate obligations: the language needs a value that may be read, and the program needs a value with an accepted meaning. Consider a packet with a valid length field but an unknown operation code. No out-of-bounds access is required for the packet to be rejected. This distinction also explains tool coverage. A memory access can stay inside allocated storage while reading bytes that were never established for the intended use. Choose tests and tools based on the violated contract, not just the presence of a crash.

29. Leaks and unbounded retention need different evidence
Reason about the implementation

SAY
A leak detector may report an allocation as reachable because a global vector still points to it. That does not prove the service can run indefinitely: the vector may retain every request ever seen. Conversely, a deliberate bounded cache can retain memory without being a bug. Investigate whether the program has a release path and whether its retention policy has a justified limit. The live counter in our first demonstration proves a small scope cleans up, but it says nothing about a cache that never leaves scope. For a long-running service, test repeated operations and measure live ownership, not only one successful request or the memory reclaimed at process exit.

SAY
The guard avoids computing source.size()+1, which could overflow at the type boundary. The caller must supply a live writable range of capacity bytes when capacity is nonzero. 45. Treat sanitizer results as evidence about executed paths
Recall and transfer

SAY
Sanitizers add checks to an instrumented build. Address checks can detect many boundary and lifetime failures; undefined-behavior checks and race checks cover other classes. They do not all provide the same guarantees, and some configurations are separate builds. A clean test run tells us that enabled checks did not find a defect on the executed paths. It does not cover an untested error branch or prove a logical bound was correct. Keep warnings, targeted tests, and ownership review alongside these tools. Also keep instrumented timing separate from production timing, because added checks change the work the program performs.

46. Build a diagnosis from four questions
Recall and transfer

SAY
Take the original copy failure and explain it without the vague phrase bad memory. Name the destination object, its capacity, the requested payload and terminator, and the guarantee that failure leaves it unchanged. Then explain the ownership of that destination for the entire call. These details distinguish a capacity defect from a dangling pointer passed with a perfectly accurate size. During maintenance, preserve both kinds of test: boundary inputs for arithmetic and scope changes for lifetime.
