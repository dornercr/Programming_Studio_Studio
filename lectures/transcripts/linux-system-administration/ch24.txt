1. Kernel and Hardware Administration

Applications depend on a kernel, drivers, and hardware that must be understood as a layered system. HarborWorks does not need a custom kernel to serve a page, but its administrators need to identify the running kernel, investigate device failures, and change low-level settings without confusing temporary experiments with persistent policy.

2. Separate installed and running kernel state

The installed kernel is not necessarily the running kernel. Record the actual runtime and preserve a bootable recovery choice. A kernel package update is assumed to change the running kernel without reboot.

4. 24.1 Kernel Architecture

The Linux kernel manages execution, memory, devices, filesystems, and networking, and exposes interfaces used by user-space programs. Drivers and many other facilities can be built into the kernel or supplied as loadable modules. A userspace service and a kernel component operate with different boundaries and failure consequences.

A system call is an application request to the kernel for a protected operation, such as opening a file or creating a process. A hardware interrupt signals an event requiring attention. You do not need to write kernel code to administer a server, but knowing which layer handles an operation helps locate failures. (R01)

Avoid interpreting every application crash as a kernel fault. A segmentation fault in one process usually calls first for that application’s diagnostics; a kernel panic or widespread device errors suggests a different scope.

6. 24.2 Kernel Versions

uname -r reports the running kernel release. Installed packages can include other kernels that will not become active until a selected boot. The distribution’s package build and support policy matter because vendors can backport changes.

The command line can reveal boot parameters relevant to a problem; review it before sharing because environments may include sensitive details. Record architecture and package provenance as well as the release string.

Do not decide vulnerability status by comparing only a vendor kernel’s visible version with an upstream announcement. Use the applicable distribution advisory and installed package build. Keep old recovery kernels according to a controlled retention policy rather than removing every alternative immediately after an update.

9. 24.3 Kernel Modules

A module adds kernel functionality at runtime when supported. Storage, network, filesystem, and virtualization features may use modules. Their dependencies, signatures, version compatibility, and configuration determine whether they load correctly.

A loaded module executes with kernel privilege, so its provenance matters. Prefer supported distribution packages and approved vendor drivers. Copying a module from a different kernel build can fail or create an unsupported environment.

Modules built into the kernel do not appear as ordinary loaded modules. Absence from lsmod therefore does not prove a feature is unavailable. Inspect kernel configuration and device binding through appropriate tools before concluding that a driver is missing.

11. 24.4 lsmod

lsmod displays loaded modules, sizes, and usage relationships derived from the running system. A usage count is useful context, not permission to remove a module. A device may be essential even when a superficial display appears quiet.

Filter only after viewing the relevant context. Similar driver names can refer to different components, and a broad text match may miss the actual device binding. Combine module output with lspci -k, logs, and the device’s sysfs information.

Treat this as observation. Do not append removal commands to an inventory script. A script called “hardware report” must not change the kernel simply because it encountered an unfamiliar module.

14. 24.5 modprobe

modprobe loads or removes modules while accounting for dependencies and configuration. modinfo MODULE reports metadata where available. Loading is a privileged change; removal can disconnect storage or networking and must not be used casually on a running service.

These examples inspect the common loop-device facility. Confirm the installed tool’s options and distinguish metadata inspection from actually loading a module. Configuration under /etc/modprobe.d can affect parameters and aliases.

A blacklist entry is not always a complete prohibition under every loading path. For a security or hardware policy, follow the distribution’s documented controls and regenerate any relevant initramfs only when required. Test the result after a planned reboot with console recovery. (R53)

17. 24.6 Kernel Parameters

Kernel parameters can come from the boot command line or runtime interfaces. Some take effect only at boot; others change live behavior. The presence of a similarly named sysctl does not make the two mechanisms interchangeable.

Before changing a parameter, record its purpose, current value, scope, supported values, workload effect, and rollback. An option copied from a low-latency trading system can be inappropriate for a general-purpose VM.

Use an experiment with a measurable outcome. “Increase performance” is too vague. “Reduce a measured queue bottleneck without raising error rate or resource use beyond agreed limits” provides something to test.

19. 24.7 sysctl

sysctl reads and writes runtime kernel settings exposed through supported interfaces, commonly represented under /proc/sys. A read does not imply that changing the value is safe.

Use individual keys for focused investigation. A blanket sysctl -a can produce large output, permission warnings, and irrelevant information. Persistent settings normally belong in a reviewed file under /etc/sysctl.d, subject to precedence and the system’s loader.

A runtime write and persistent configuration must be verified separately. sysctl --system can apply many configured settings, not just the one you edited. For a bounded change, understand exactly which keys your chosen application command will touch. (R53)

22. 24.8 /proc/sys

Paths under /proc/sys expose tunable kernel state. Dots in a sysctl key commonly correspond to path separators: net.ipv4.ip_forward maps to /proc/sys/net/ipv4/ip_forward. These are live interfaces, not persistent configuration files.

Writing the correct value to the wrong host or namespace can have unexpected scope. Containers and network namespaces may expose different views or limit which settings are namespaced. Establish where a command runs before interpreting it as a host-wide change.

Never restore an old recursive copy of /proc/sys as a recovery method. Rebuild the intended policy from reviewed configuration, then verify the installed kernel’s supported values. (R53)

24. 24.9 Hardware Discovery

Hardware discovery creates an inventory connecting a physical or virtual device to its bus address, driver, firmware, operating-system name, and role. A drive name such as /dev/sdb is not a sufficient asset identity, especially after reordering or replacement.

Use lsblk for block-device relationships, lspci for PCI devices, lsusb for USB devices, and lscpu for CPU topology. Some information requires elevated access. Firmware tools can expose serial numbers and other identifiers that should be protected when sharing reports.

Compare the expected inventory with what the running system sees. A missing device may be disabled in firmware, detached from a VM, unsupported by a driver, or failed physically. Those possibilities precede filesystem-level repair.

26. 24.10 lspci

lspci lists PCI devices. With suitable options it can show the driver currently bound to a device and candidate modules. This helps connect a network or storage error to the relevant hardware path.

Numeric identifiers help avoid ambiguity in marketing names. Driver binding is more informative than merely having a matching module installed. In a virtual machine, the device can be a virtual adapter rather than the host’s physical hardware.

Do not assume that a new hardware ID requires an unsupported driver download. Check the distribution’s supported kernel, firmware package, and vendor guidance first.

29. 24.11 lsusb

lsusb inventories USB devices; a tree view can show hub relationships and negotiated connections. USB storage or network devices can share a bus and power boundary even when they have separate names.

Disconnects can be caused by power, cabling, hubs, firmware, or device faults. Correlate inventory changes with kernel messages. Repeatedly reconnecting a device with active writes can damage application state.

Treat removable media as a trust boundary. Do not automatically execute content or mount unknown filesystems with excessive privileges simply to identify a device. Follow the organization’s removable-media policy for real systems.

32. 24.12 CPU Information

lscpu reports architecture and topology such as sockets, cores, threads, and NUMA nodes. A virtual CPU count is not a direct guarantee of dedicated physical cores. CPU features exposed to a guest depend on the hypervisor and migration policy.

Use topology to interpret per-core performance and placement, not as a reason to pin every service arbitrarily. Pinning can reduce scheduler flexibility and create contention. Chapter 30 considers NUMA and high-performance tradeoffs.

Record whether the workload uses a single thread, several workers, or vector instructions. Adding CPUs does not make serial work parallel. A correct capacity plan connects the program’s concurrency to the available execution resources.

What to check: Available logical CPUs do not imply exclusive physical-core ownership.

34. 24.13 Memory Information

Memory information includes total capacity, available capacity, topology, and hardware error evidence. /proc/meminfo describes the kernel’s view; firmware inventory tools can describe installed modules when the platform exposes that information.

A difference between installed and usable memory can result from hardware reservations, virtualization, kernel settings, or faults. Do not infer failure solely from a rounded number. Compare exact units and the platform’s expected reservations.

Where supported, hardware error logs and vendor management interfaces can help investigate corrected and uncorrected memory errors. Replacement decisions need the platform’s service procedure and evidence, not a generic “memory is high” alert.

36. 24.14 Device Problems

Start with the device’s role and failure scope. An application timeout may result from link loss, driver resets, media errors, path failover, or power. Correlate the kernel log with storage or network metrics and any hardware-management records.

Protect data before invasive tests. A full-disk stress test on a suspect production drive can worsen a fragile situation and affect users. Read-only diagnostics can still impose load; schedule them with the device owner.

When replacing hardware, verify stable identities and mappings before bringing services back. The replacement may enumerate under a different name. A previously correct /dev/sdX assumption is not a safe provisioning contract.

38. 24.15 Kernel Updates

Treat a kernel update as a change that requires installed-package validation, boot selection, driver compatibility, and a planned restart unless a supported live-patching mechanism covers the exact issue. Live patching is not a blanket replacement for all kernel maintenance.

Confirm backups, console access, known-good boot entries, and application acceptance tests before the window. Account for externally built modules, Secure Boot requirements, and storage drivers needed during early boot.

After restart, record uname -r, failed units, storage, networking, and the real application test. A successful package-manager transaction before reboot is not evidence that the new kernel booted or that the service works under it.

What to check: Preserve a tested recovery kernel and console path before applying a reviewed kernel update.

40. 24.16 Kernel Troubleshooting

Collect a bounded kernel-journal window and the system’s exact context:

Permissions and persistent-journal configuration affect visibility. For intermittent panics, establish the distribution’s supported crash-dump arrangement before the next event. Crash artifacts can contain sensitive memory and need restricted handling.

Escalate with observations, reproduction conditions, and recent changes. Avoid inventing a hardware diagnosis from an isolated warning. A good report distinguishes the first abnormal event from the downstream failures it triggered.

43. Requirement

Determine whether a proposed kernel-setting change is justified without applying it yet. HarborWorks has received advice to enable IP forwarding on its web server “for better networking.” The server is not intended to route traffic between networks.

The naive implementation writes net.ipv4.ip_forward=1 and adds it to a configuration file. Its limitation is that it changes the host’s routing role without a requirement or a performance mechanism.

44. Evidence and decision

Record whether the host is meant to forward traffic, which interfaces exist, and what firewall policy assumes. Serving a local web socket does not require acting as a router. In this scenario the correct administrative action is to reject the unrelated change and preserve the observed baseline.

For a separate disposable router lab, define two isolated networks, explicit forwarding and firewall requirements, approved test traffic, and console recovery. Only then plan a temporary change, a discriminating connectivity test, restoration of the original value, and a persistent configuration if the design is accepted.

46. Practice and implementation lab

Check your understanding. Does a runtime sysctl write necessarily persist after reboot? No. Does lsmod list built-in drivers? Not as ordinary loaded modules. Is a newer upstream version string sufficient to evaluate a vendor security fix? No.
