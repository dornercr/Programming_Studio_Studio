Users, Groups, and Identity

1. Users, Groups, and Identity

A new service runs successfully when an administrator launches it, but fails when systemd starts it. The files are identical. The difference is identity: the interactive process and the service have different credentials. Linux permission decisions are about those credentials, not about who remembers installing the software.

Identity administration therefore covers more than adding login names. You must understand numeric ownership, group membership, authentication, authorization, account lifetime, and the difference between a human account and a service identity.

4. 4.1 Linux User Accounts

A user account associates a name with identity information such as a numeric user ID, primary group, home directory, and login shell. Accounts can represent people or services. An account does not necessarily permit interactive login.

Authentication answers “How was this identity established?” Authorization answers “What is this identity allowed to do?” A valid SSH key can authenticate a user who still lacks permission to write a particular directory. Conversely, a service with no password can run locally under a restricted account through a supervisor.

Inspect the account as the system resolves it:

getent consults configured name services rather than reading only a local file. The distinction becomes important when accounts come from a directory service.

7. 4.2 UID and GID Values

The kernel normally uses numeric user IDs (UIDs) and group IDs (GIDs) for ownership and permission checks. Human-readable names are mappings supplied by user-space identity services. If a name disappears, the stored numeric ownership can remain.

An account has a primary group and may belong to supplementary groups. A process inherits a credential set at creation; changing a directory-service or local group record does not retroactively update every running process.

This matters when sharing files between hosts. The name deploy can map to different UIDs on two machines. NFS and restored archives may therefore show surprising ownership unless identity mapping is coordinated. Do not solve the problem by making the files world-writable. Establish consistent identity or a supported mapping mechanism. (R07)

9. 4.3 /etc/passwd

/etc/passwd contains local account records with colon-separated fields: name, password placeholder, UID, GID, descriptive information, home directory, and shell. On conventional shadow-password systems, the password field contains a marker such as x, while password hashes reside in /etc/shadow.

The file is usually readable by ordinary users because many programs need account names and home directories. Its name is historical; it should not contain plaintext login passwords.

Do not casually edit it with a generic text replacement. Account-management utilities maintain related state and apply locking. When manual recovery requires editing, use the appropriate protected tools such as vipw, understand the record format, and preserve a recovery path.

12. 4.4 /etc/shadow

/etc/shadow stores local password-hash and password-aging information. Hashes are not plaintext passwords, but exposure still enables offline guessing attacks. Restrict access and protect backups containing the file.

Fields can encode the last password change, minimum and maximum age, warning period, inactivity period, and account expiration. Special values can indicate a locked password or an account without a usable password hash. Interpret them with the installed shadow(5) manual rather than guessing from one character.

Locking password authentication is not equivalent to revoking every way to access an account. Public-key authentication, existing sessions, service execution, and other authentication mechanisms may remain possible. Offboarding must address the full access path, not just one field.

14. 4.5 /etc/group

/etc/group stores local group names, numeric GIDs, and supplementary member lists. A user’s primary group is recorded in the passwd entry, so the absence of a username from a group’s visible member list does not prove the user lacks that group.

Use id username to ask how the account resolves now, and plain id inside a session to inspect that session’s actual credentials. These can differ after a membership change.

Choose groups according to responsibilities: deployment, log review, or application-data access. One giant group with every operational permission is difficult to audit and often grants more access than each task requires.

17. 4.6 Creating and Removing Users

On many systems, useradd is the low-level account-creation tool. Debian-family adduser can provide a friendlier policy-aware interface. Defaults differ, especially around home-directory creation, so use explicit options and validate the result.

Change — disposable lab VM.

The password is entered interactively, not placed in the command line. Check that the home directory and intended shell exist.

Removing an account requires a data-retention decision. userdel -r can remove its home and mail spool, but it does not discover every file, scheduled task, key, or service dependency elsewhere. Inventory those dependencies first. Disable or expire access when appropriate, retain required data, and only then remove the account according to policy. (R08)

20. 4.7 Modifying Accounts

usermod changes local account properties. Typical operations include changing a shell, moving a home directory, or adjusting group membership. A UID change is especially consequential because files can retain the previous numeric owner.

A common mistake is using usermod -G group user when the intention is to add one group. Without -a, the specified supplementary group list replaces the previous list. Use -aG when appending is the actual goal.

Before a change, record id user and getent passwd user. Afterward, verify the new records and test a fresh session. Existing sessions may continue with older credentials. A successful modification command does not prove that every dependent service or process has adopted the change.

22. 4.8 Managing Groups

Use groupadd, groupmod, and groupdel for local groups, and usermod -aG or gpasswd for membership changes. Group names should express a permission boundary, not merely an organizational label that changes frequently.

These commands assume the lab names do not already exist. In automation, inspect first or use a desired-state tool rather than treating an “already exists” error as a reason to keep running blindly.

A new group membership is ordinarily available to a new login session. newgrp can start a shell with a changed group context, but it is not the same as refreshing every existing process. Test the same execution path the application actually uses.

25. 4.9 Password Policies

Password policy includes length, resistance to common or compromised choices, storage, recovery, and protection against guessing. A policy is ineffective if administrators bypass it by sharing one privileged password or embedding credentials in scripts.

On Linux, password-quality checks may be implemented through PAM modules such as pam_pwquality; the exact package and configuration vary. Inspect the distribution’s supported mechanism. Do not copy a PAM stack from another distribution and assume its control flags are harmless.

Forced periodic changes are not a substitute for detecting compromise or using multifactor authentication where supported. Follow the organization’s reviewed policy and the applicable identity system. A local aging rule does not necessarily govern a centrally authenticated account.

27. 4.10 Account Expiration

Account expiration limits when an account may be used; password expiration limits the lifetime of a password. They are different controls. chage -l user displays local password-aging and expiration information.

An expiration date is useful for temporary contractors or lab accounts when paired with an owner and review process. It should not be applied blindly to a service account that must run unattended; doing so can create a delayed outage.

Offboarding also requires revoking keys, tokens, group memberships, active sessions, and access in external systems. An account marked expired in one host’s local database is not proof that all organizational access has ended. Verify each relevant authentication and authorization path.

30. 4.11 Service Accounts

A service account is an identity used by software rather than a person. Give each service only the files, directories, sockets, and capabilities it needs. A noninteractive shell such as /usr/sbin/nologin can prevent ordinary shell login, but it does not itself define all service permissions.

33. 4.12 Root

UID 0 is the traditional superuser identity. Its privileges can bypass many discretionary permission checks, although mandatory-access controls, namespaces, capabilities, and other boundaries can still matter.

Root is necessary for some administrative tasks, but a permanent root shell makes accidental changes easier and attribution weaker. Use named accounts and elevate for the specific operation. Before destructive work, verify the host and target again after elevation.

Do not confuse root with the directory /, the home /root, or ownership of every file. A file owned by root may be readable by ordinary users, and a root process can still fail because a filesystem is read-only or an SELinux policy denies an action. “I am root” is not a diagnosis.

35. 4.13 su

su starts a command or shell under another identity, subject to authentication and PAM policy. A login-style invocation such as su - user more closely establishes the target user’s login environment than a plain identity switch.

The environment matters. Retaining the previous user’s variables or working directory can make a test unlike the real login path. Use a fresh, clearly defined context when diagnosing a user’s environment.

For administrator-controlled testing, sudo -u user command often provides a more auditable and bounded way to run one command. Neither method recreates every property of an SSH session or systemd service. A service may have additional namespace restrictions, resource limits, and mandatory-access-control context.

37. 4.14 sudo

sudo applies a policy controlling which users may run which commands as another identity. Its value is not simply avoiding a root password; it can provide named accountability and scoped privilege.

Edit policy with visudo or a supported drop-in checked by visudo -cf. A syntax error can remove the access needed to fix itself. Keep an existing privileged session and a console recovery path while changing policy.

A rule that permits a command with arbitrary file arguments, shell escapes, or editable executable paths may grant much more power than it appears to. Allowing a text editor as root commonly permits arbitrary root-level changes. Design restrictions around actual command behavior, executable ownership, and argument validation. Avoid broad NOPASSWD: ALL merely for convenience. (R09)

A rule that permits a command with arbitrary file arguments, shell escapes, or editable executable paths may grant much more power than it appears to. Allowing a text editor as root commonly permits arbitrary root-level changes. Design restrictions around actual command behavior, executable ownership, and argument validation. Avoid broad NOPASSWD: ALL merely for convenience. (R09)

39. 4.15 PAM Fundamentals

Pluggable Authentication Modules, or PAM, lets applications use a configurable stack of authentication-related modules. Its responsibilities include authentication, account checks, password changes, and session setup. A login can succeed at one stage and fail at another.

PAM configuration typically lives under /etc/pam.d, but distributions may generate shared stacks through tools such as authselect or pam-auth-update. Understand the supported ownership model before editing generated files.

Control flags and module order influence the result. A seemingly small change can reject all logins or accidentally permit an unintended path. Test in a disposable VM with console access. For production, validate ordinary access, privileged access, failure behavior, and recovery—not just one successful authentication. (R10)

41. 4.16 Centralized Identity Concepts

Centralized identity services provide accounts and groups across machines. LDAP commonly supplies directory information; Kerberos can supply ticket-based authentication; SSSD can connect Linux systems to identity providers and cache selected information.

Name Service Switch, configured through /etc/nsswitch.conf, determines where many account and name lookups are obtained. This is why getent passwd user is preferable to assuming that every user must appear in /etc/passwd.

Centralization creates new dependencies: DNS, time synchronization, provider reachability, certificates, and cache behavior. A directory outage need not mean every existing process loses its identity immediately, but new logins may behave differently. Document supported offline behavior and a tightly controlled break-glass account before relying on centralized access.
