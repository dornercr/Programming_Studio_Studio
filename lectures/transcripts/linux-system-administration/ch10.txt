Logical Volume Management

1. Logical Volume Management

HarborWorks initially divides a disk into fixed partitions. The log area fills while another partition has unused capacity. Moving boundaries now requires awkward planning. Logical Volume Management introduces a pool-and-allocation layer so that storage can be assigned more flexibly.

LVM improves manageability, but it does not erase filesystem rules or physical failure modes. A logical volume is still backed by real storage, and resizing the block container is not the same operation as resizing the filesystem inside it.

4. 10.1 Why LVM Exists

LVM separates physical storage devices from the logical block devices presented to filesystems. You can combine approved storage into a pool and allocate named volumes according to workload requirements.

The benefit is operational flexibility: grow an application volume, add a device to a pool, or move allocated extents under supported conditions. The cost is another layer of metadata and another set of capacity boundaries to monitor.

Do not allocate every free extent on day one simply because the command allows it. Leaving reserve space can support growth, snapshots, or recovery. That reserve should be planned rather than treated as wasted capacity. LVM is a tool for managing uncertainty, not a guarantee against running out of space. (R24)

6. 10.2 Physical Volumes

A physical volume, or PV, is a block device prepared for LVM. It can be a whole approved device or a partition. PV metadata identifies the storage to LVM and describes its participation in a volume group.

This is an inspection command. pvcreate, by contrast, writes metadata and must only target verified disposable or approved storage. Existing use may be hidden behind encryption, RAID, or other mappings.

RHEL 9 can use an LVM devices file to control which devices LVM sees. A device absent from LVM output may therefore be filtered rather than empty. Do not disable production filters merely to make a lab command discover more devices.

9. 10.3 Volume Groups

A volume group, or VG, combines one or more PVs into an allocation pool. LVM divides space into extents, and logical volumes receive extents from the pool. The VG’s free capacity limits growth of ordinary logical volumes.

A volume group spanning several nonredundant devices can increase the failure domain. If an LV uses extents from a failed device, its data can become unavailable or corrupt even though other PVs remain healthy.

Adding a PV does not automatically redistribute existing data or make it redundant. Choose RAID or another supported redundancy mechanism when the requirement is device-failure tolerance. Pooling and redundancy solve different problems.

12. 10.4 Logical Volumes

A logical volume, or LV, is a block device allocated from a VG. A filesystem, swap area, or another supported consumer can use it much like a partition.

The devices field helps reveal physical placement. Names such as /dev/vgname/lvname are convenient interfaces, while device-mapper also exposes paths with encoded naming conventions. Avoid constructing those encoded names by guesswork.

An LV has a size independent of the filesystem inside it. If the LV is 10 GiB and the filesystem still describes 8 GiB, the application sees the filesystem’s capacity. If the LV is reduced below the filesystem’s needs, data can be destroyed.

15. 10.5 Creating LVM Storage

The creation sequence is PV, VG, LV, filesystem, and mount. Each step has a separate validation command. Stop when a layer does not match the intended design.

For a verified disposable lab device only, the conceptual sequence is pvcreate, vgcreate, lvcreate, the correct mkfs tool, and mount. Do not execute that sequence until the device’s hypervisor identity, size, serial, holders, partitions, and absence of needed data have been checked.

The worked example uses LAB_PV as an explicitly selected device and a dedicated hb_vg group. These names must not collide with existing storage. A production procedure needs an independent backup, change approval, and recovery plan in addition to the lab’s identity checks.

17. 10.6 Extending Logical Volumes

An ordinary LV can grow when its VG has available extents. lvextend -L +1G means add 1 GiB; lvextend -L 3G means request a total size of 3 GiB. Confusing relative and absolute size is a preventable error.

Inspect the current LV and VG sizes first. Then grow the intended LV and verify the new size before touching the filesystem. The -r option can coordinate filesystem resizing for supported combinations, but it does not make unsupported operations safe.

Avoid routinely consuming 100%FREE. A measured increment preserves reserve capacity and makes the intended result easier to review. Growth should be driven by demand, projected horizon, and the storage pool’s other obligations.

19. 10.7 Extending Filesystems

After an LV grows, the filesystem must recognize the added space. For ext4, use the supported resize2fs procedure against the block device. For XFS, use xfs_growfs against the mounted filesystem’s mount point.

These observations distinguish the container, mount, and application-visible capacity. The growth command itself appears in the worked example once the filesystem is established.

Verify more than size. Create and read a small test file through the application’s expected identity, inspect kernel logs for new errors, and ensure persistent references still match. A larger filesystem with broken ownership has not met the service’s requirement.

22. 10.8 Reducing Volumes Safely

Shrinking is more dangerous than growing because removing blocks can cut away live data. The order must preserve the invariant that the block container is never smaller than the filesystem requires.

For an ext4 filesystem that supports the planned reduction, the reviewed offline sequence is: back up and test restore, stop users, unmount, check the filesystem, shrink the filesystem to a conservative size, verify it, and only then reduce the LV without crossing the filesystem boundary. Units, metadata overhead, minimum-size estimates, and tool support must all be understood.

This book does not provide a blind one-line shrink command. For XFS on the RHEL 9 baseline, use a new smaller filesystem and a verified migration instead. A command’s confirmation prompt cannot compensate for a wrong model of what lies inside the LV. (R25)

24. 10.9 LVM Snapshots

A snapshot preserves a view of a volume at a point in time using the relevant snapshot implementation. Traditional copy-on-write snapshots track changed blocks and require sufficient snapshot capacity. Thin snapshots use thin-pool mechanisms with different accounting.

A block snapshot is not automatically an application-consistent backup. A database may need a supported backup mode, checkpoint, freeze coordination, or recovery procedure. A filesystem snapshot can preserve a state that still requires journal or application recovery.

Monitor snapshot usage and lifetime. A snapshot that exhausts its required storage can become unusable or disrupt operation according to the implementation. Keep snapshots short-lived when they are intended for a maintenance window, and retain independent backups for device loss and broader disasters.

26. 10.10 Thin Provisioning

Thin provisioning allows logical allocations to exceed immediately allocated physical space. Physical blocks are consumed as data is written. This can improve flexibility but creates an overcommitment risk.

A thin pool has both data and metadata capacity. Monitor both, plus growth rate, reserve extents, and the mechanism responsible for extension. A thin LV showing free filesystem capacity can still fail when its underlying pool fills.

The meaning and applicability of fields depend on the LV type. An alert must identify the pool and responsible owner, not simply report that one guest filesystem looks healthy. Do not oversubscribe a production pool without an explicit capacity and failure policy.

29. 10.11 Recovering LVM Configurations

LVM keeps metadata backups and archives, commonly under /etc/lvm/backup and /etc/lvm/archive. vgcfgbackup saves VG metadata; it does not back up the filesystem’s data blocks.

A metadata recovery must match the actual devices, UUIDs, and historical layout. Restoring the wrong mapping can point an LV at unrelated blocks. Preserve current evidence and make a recovery copy before attempting reconstruction.

Use the distribution’s documented vgcfgrestore and PV recovery procedures only after establishing the correct metadata version and device identities. A missing PV can reflect discovery filters, a disconnected device, or actual failure; these require different actions. Test complex recovery on cloned evidence where feasible, and escalate when the mapping is uncertain.

37. Verification and recovery

Write and read a small lab file, inspect the mount source, and record the before-and-after capacities. This exercise does not add an fstab entry; the mount is intentionally temporary.

For cleanup, stop all use and unmount /mnt/harbor-lvm. Verify the exact LV and VG again, then remove only the dedicated LV, VG, and PV metadata through the corresponding LVM tools. Because removal is destructive, use the VM snapshot or detach-and-recreate the dedicated virtual disk when that is the clearer lab reset. Never run generalized removal commands against every VG.

38. Practice and implementation lab

Draw the current allocation of hb_vg before and after growth. Explain which capacity changed at each command and why the filesystem did not grow merely because the VG had free extents.

Design, on paper, a migration from a 100 GiB XFS filesystem to a new 60 GiB filesystem containing 30 GiB of required data. Include application consistency, metadata preservation, validation, cutover, and rollback. Do not propose reducing the old LV beneath XFS.

Check your understanding. Is vgcfgbackup a backup of file contents? No. Does adding a PV create redundancy? Not by itself. What two thin-pool capacities need monitoring? Data and metadata, together with growth and extension headroom.

Chapter takeaway. LVM separates allocation from filesystems. Preserve that separation in every inspection, resize, and recovery plan.
