Building a Production Linux Server

1. Building a Production Linux Server

A production server is not finished when the installation completes or the website first appears. It is finished enough for release when its owner can explain the requirements, demonstrate the controls, recover the service, and support the people who depend on it. This chapter joins those responsibilities into one build-and-review sequence.

The capstone is a production-candidate lab, not a claim of production certification. HarborWorks will publish a small, static HarborStatus site over HTTPS on web1, using a separate client, admin1, for access tests. A second disposable server, web2, will prove recovery. The concrete server configuration uses the RHEL 9 family. Ubuntu differences are identified where they change a path, package, account group, or security mechanism. Do not combine both distributions’ instructions on one host.

4. 33.1 Requirements

Write the acceptance contract before installing anything. For this lab, the site must return the approved release marker at https://status.harbor.test/index.html, authenticate the server with a certificate that the test client explicitly trusts, allow administration through a verified named account, and prevent the web worker from modifying the deployed content. Logging, a bounded external check, a recoverable backup, and a tested rebuild procedure are required.

The teaching recovery objectives are a recovery point no older than 24 hours and recovery within 60 minutes of declaring a restore. These are exercises, not promises about an untested design. Decide what starts and stops each clock. A single web server has a single-server failure domain; nothing in this chapter turns it into a highly available service.

Record the service owner, approved client network, administrative source, data classification, expected requests, patch window, certificate owner, and alert recipient. Unknown values are unresolved requirements. An invented IP address in a worksheet is not authorization to use it on a real network.

10. 33.3 Storage Layout

For a small teaching VM, the operating system and site can share the system filesystem. Document the consequence: log growth and application data compete with the operating system for capacity. A separate data volume can isolate capacity and simplify certain recovery operations, but it also adds a required mount and its own failure cases. Choose deliberately rather than treating a diagram’s extra disks as automatic reliability.

Use /srv/harbor/site for deployed content and /var/log/nginx for service logs. Record the filesystem type, size, persistent identifier, mount options, free-block threshold, and free-inode threshold. Verify any required data mount before deployment; otherwise a missing mount can leave a deceptively writable directory on the root filesystem.

findmnt --target /srv identifies the filesystem containing that path. Compare its reported target and source with the design; it does not by itself prove that /srv is a separate mount. Do not partition or format the installed system disk during this capstone. Use Chapters 9 and 10 for separately identified disposable storage exercises.

13. 33.4 Network Configuration

Assign web1 an address that the isolated lab actually permits. This chapter continues the example address 192.168.56.20, but the address must be replaced when the lab differs. Verify the interface, connection profile, prefix, gateway, and resolver owner before changing persistent configuration. Apply remote network changes only with working console recovery.

Use the persistent NetworkManager procedure from Chapter 11 rather than adding a temporary address and assuming it will survive reboot. Register the name through the lab’s DNS service, or use a deliberate client /etc/hosts entry for the isolated exercise. Record which approach was used. A later curl --resolve test intentionally bypasses DNS, so it cannot substitute for a separate normal-name lookup test.

Decide whether the service supports IPv6. Configure and test its address, listener, routing, and firewall policy when it does. The IPv4-only examples below do not silently provide an IPv6 service or establish an IPv6 security policy. (R27, R31)

16. 33.5 Users and Administrative Access

Use a named administrator rather than a shared root login. On the RHEL-family lab, inspect the account’s group membership and effective sudo privileges. Membership in wheel is relevant only in conjunction with the host’s sudo policy; the equivalent common Ubuntu administrative group is sudo.

Keep the web worker separate from administration and deployment. The NGINX master may require startup privileges for its listening socket and protected key, while its worker identity should only read the static release. Inspect the packaged configuration and running processes rather than assuming a username. The worker does not need a human password, an administrative group, or ownership of the content directory.

Validate a second, fresh administrative login and a usable elevation path before closing the original session. Record recovery-account custody separately from everyday access. Never put a recovery password or private key into the build document.

25. 33.8 SELinux Configuration

Keep the RHEL-family server enforcing. The site needs a persistent label appropriate for static HTTP content, not a blanket permission for the web process to access arbitrary data. Chapter 18 establishes the mapping for /srv/harbor/site; inspect that mapping before adding it again.

After the directory exists, and only when no conflicting local mapping needs review, establish the intended rule if absent:

An existing rule calls for deliberate inspection and, when appropriate, modification with -m, not an ignored error from repeated -a. Standard certificate locations use the distribution’s policy mappings; inspect and restore their expected labels after creating files. The static site does not require a broad outbound-network Boolean merely to read local pages. Diagnose any denial through the actual process, object, and attempted operation. On Ubuntu, review the relevant AppArmor profile instead of assuming this SELinux procedure applies. (R39, R40)

29. 33.9 Application Deployment

Deploy a small, auditable release before adding moving parts. In the isolated lab, create the site directory and a single HTML file. These commands intentionally publish release 1; on an existing installation, preserve the approved previous release first.

The root-owned deployment prevents an ordinary web worker from rewriting the served page. It does not by itself protect every parent directory, service configuration, or privileged deployment tool. Inspect those paths as a chain. Record a content checksum and the release identifier so a successful request can be compared with the intended artifact.

Promote a reviewed release, not an uncontrolled working directory. Larger sites may use versioned release directories and an atomic link switch, but that design must also address permissions, labels, caching, and rollback. The simple single-file release keeps this capstone’s acceptance test inspectable.

Include commands with real environment values only in the controlled local runbook; keep public teaching examples free of secrets. Record the date of each test and the person responsible for the next review.

A diagram should show actual dependencies: client resolver, network policy, HTTPS listener, certificate and key, content filesystem, logs, observer, and independent backup. Explicitly mark the single-server failure boundary. Documentation that hides it makes an unsafe promise.

58. 33.20 Production Readiness Review

The final review is a decision supported by evidence, not a ceremonial checklist. For each requirement, link the artifact or observation that demonstrates it. Anything not tested remains unverified. The following worksheet deliberately contains no prefilled passes.

Review area | Evidence required before approval
Service contract | Correct named HTTPS response and exact release marker from the intended client path
Administration | Fresh approved login, tested elevation, and protected console recovery
Storage and access | Verified mounts, capacity thresholds, ownership, and mandatory-access-control state
Operations | Delivered test alert, usable logs, defined patch/restart process, and assigned owners
Recovery | Independent backup restored onto a separate host within the declared objectives
Security | Allowed and rejected paths tested; key access and relevant exceptions reviewed
Change and handover | Versioned configuration, rollback evidence, and an independently usable runbook

A reviewer can approve, approve with explicitly owned limits, or withhold release pending a failed requirement. A single-server lab may be adequate for a low-criticality internal exercise while failing a requirement for continuous availability. The answer depends on the contract, not on how many commands were entered.

61. Trace the evidence chain

The administrator begins on a fresh web2, follows the runbook, and records each unresolved assumption. The client first confirms that the original server is not supplying the test response. It then targets the recovery address while preserving the service name and explicit lab certificate trust. The response must contain HarborStatus release 1: operational.

Next, the administrator requests an absent page, confirms the expected failure, and finds the event in the correct site’s access log. This verifies that the evidence is associated with the tested service rather than a different default site. The monitoring owner triggers a bounded check failure and confirms that the intended recipient receives it.

63. Interpret and recover

A certificate mismatch is a failed identity test, not a reason to turn verification off. A correct page from the wrong host is a failed recovery-routing test. A successful restore requiring an undocumented private key is an incomplete recovery procedure. Each failure identifies a specific remaining requirement.

After the rehearsal, restore the lab’s normal routing, remove temporary firewall exceptions and client overrides, and protect or remove recovered secret material according to the exercise plan. Preserve the test record without publishing sensitive data.

SOURCE: EPUB/text/ch035.xhtml — Interpret and recover

64. Practice and implementation lab

Build the service, produce the evidence packet, and ask a second person to perform the restore using only the runbook and authorized recovery material. Time the process. Document at least one assumption they had to resolve, then revise the runbook and repeat that part of the test.

Check your understanding. Does a certificate file with a future expiration date prove that clients receive it? No; test the served certificate. Does a successful local probe prove the external network path works? No. Does a restorable snapshot on the lost storage provide an independent backup? No. Does this single-server build guarantee high availability? No.

Chapter takeaway. A production-ready decision connects a stated requirement to repeatable evidence and a demonstrated recovery path. Linux commands implement that decision; they do not replace it.
