4. 28.1 Linux as the Cloud Operating System

Cloud platforms provide virtual compute environments on which Linux runs ordinary services, packages, processes, and filesystems. The provider manages selected infrastructure layers; the customer remains responsible for the guest and workload according to the chosen service model.

Do not transfer responsibilities from a managed database service to a self-managed database on a VM. Both may be “in the cloud,” but patching, backups, availability, and administrative access can belong to different parties.

Write the boundary explicitly: provider-managed resources, guest-managed configuration, application-managed state, and organization-managed identity. Unowned responsibilities often emerge only during an outage.

6. 28.2 Cloud Virtual Machines

A cloud instance combines an image, machine size, storage, network interfaces, identity, and startup configuration. Machine size describes allocated capabilities, not a guaranteed application response time under every workload.

Understand stop, restart, suspend, and terminate semantics for the selected provider and resource. Attached disk persistence, local temporary storage, and public address behavior can differ. Do not assume “stop” means “no further cost” or “terminate” means “every disk was deleted.” Verify the exact policy before creation and removal.

This chapter does not prescribe a priced deployment. Run provider exercises only in an authorized sandbox with quotas, cost alerts, and a cleanup inventory. A guest command cannot reveal every billable resource left behind in the control plane.

8. 28.3 Images

An image supplies the starting disk and operating-system configuration. Select a trusted publisher, supported release, architecture, and update policy. Record the exact image identifier, not merely a moving “latest” label.

A golden image can standardize packages and agents, but baked-in secrets, stale host identities, and outdated configuration create risk. Use supported image-generalization procedures and inject instance-specific values through a controlled provisioning process.

Keep an image manifest with source, build revision, installed components, test evidence, and retirement date. Rebuilding an image does not automatically update existing instances; the rollout strategy must address both new and already-running servers.

10. 28.4 Cloud-init

Cloud-init initializes supported cloud instances using platform data and user-supplied configuration. It can create users, configure networking, write files, and run selected commands according to its stages and module frequencies. It is not a continuous desired-state manager.

Use this inside a supported guest to inspect initialization state. A login becoming available can precede completion of later initialization tasks. Inspect cloud-init logs and status rather than racing a package operation that provisioning is still using.

User data may be stored or exposed through platform and guest mechanisms. Do not place long-lived credentials there simply because the file is supplied at launch. Use an approved instance identity and secret retrieval path. The exact datasource and distribution integration determine behavior. (R59)

14. 28.5 SSH Access

Cloud SSH access depends on the guest account and daemon plus provider-side identity and network policy. The image’s initial username varies by publisher. Key injection, identity-based login services, and bastion arrangements are different access designs.

Verify the instance’s host identity through a trusted path. Reusing an address after replacing an instance can produce a legitimate host-key change, but legitimacy must be established rather than assumed.

Maintain a recovery route such as an authorized serial console or management service where supported. A security-group change and a broken guest sshd_config can look similar from outside, but require different repairs. Do not widen public SSH access as the first test.

16. 28.6 Block Storage

Cloud block storage appears to the guest as a block device that can be partitioned, formatted, and mounted according to its supported use. Growing the provider-side volume does not necessarily grow the partition, logical volume, or filesystem automatically.

Identify the volume through stable metadata and the guest’s actual mapping. Device names requested in the control plane may not match the final Linux enumeration. Reuse Chapter 9’s layered growth and validation method.

Snapshots have consistency and retention rules. An application writing across several volumes may need coordinated capture. Also verify whether the volume survives instance deletion and who can delete its snapshots. “Durable service” is not a substitute for a workload-specific backup plan.

18. 28.7 Object Storage

Object storage manages named objects through an API rather than presenting ordinary local block-device semantics. Buckets, object keys, versions, lifecycle policies, and access rules are part of its administrative model.

A filesystem adapter can expose object storage through paths, but that does not automatically provide the locking, rename, latency, or write semantics an application expects from a local filesystem. Evaluate the adapter and workload contract before using it as a database or shared application directory.

For backups, verify version retention, deletion protection, encryption keys, retrieval permissions, and recovery time. Upload success and list permission do not necessarily prove that recovery credentials can retrieve every required version.

20. 28.8 Virtual Networks

Cloud virtual networks contain subnets, routes, interfaces, and associated policy. A “private” subnet designation is shorthand for a particular routing design, not proof that every service is inaccessible from untrusted sources.

Draw ingress and egress separately. An instance may reach repositories through a NAT service without accepting inbound Internet connections. Private endpoints, peering, VPNs, and interconnects add paths that the guest route table cannot fully explain.

When troubleshooting, inspect both the control-plane association and the guest’s effective route and address. A resource existing in the right region is not sufficient; it must be attached to the intended network and policy.

22. 28.9 Security Groups

Providers expose network-policy constructs with different names and semantics. AWS security groups, Azure network security groups, and Google Cloud firewall policies are not interchangeable command syntaxes or identical rule-processing models.

Translate intent: permitted source, destination, protocol, port, direction, and administrative owner. Verify where the rule attaches and how other controls interact. Host firewalls remain a separate layer.

A rule allowing TCP 443 does not install a certificate or start a listener. Conversely, a listening guest socket does not prove the provider allows its path. Test from the intended client network and preserve the administration route during changes.

What to check: A permitted guest firewall rule does not override a restrictive cloud security group.

24. 28.10 Identity and Access Management

Cloud identity and access management governs API operations and access to platform resources. Linux UIDs and sudo govern guest operations. These domains interact but are not the same identity system.

Prefer scoped instance or workload identities over embedding long-lived API keys in the guest. Limit what the instance can read or change. A web application vulnerability can become a control-plane incident if the machine’s identity has broad permissions.

Metadata services can expose instance information and, under configured identity arrangements, temporary credentials. Protect them using provider-supported controls and application defenses. AWS’s instance metadata service includes distinct access-version and configuration controls; follow the specific EC2 documentation rather than treating a link-local address as inherently trusted. (R60)

26. 28.11 Load Balancing

A load balancer distributes requests across backends and can perform health checks or TLS handling depending on the product and configuration. It introduces another endpoint, policy layer, and logging location.

Health checks should reflect readiness without becoming expensive or destructive. A backend can answer a trivial check while failing real authenticated requests. Conversely, making every check depend on one unstable shared component can remove all backends at once.

Trace forwarded client identity, TLS termination, backend encryption, timeouts, and connection draining. A load balancer does not remove the need to manage application state or compatible versions across backends.

28. 28.12 Autoscaling Concepts

Autoscaling changes capacity in response to policy and measurements. It works best when new instances can initialize predictably and service state does not exist only on one disappearing machine.

Include startup time, health-check delay, scaling limits, quotas, and downstream capacity. A response to CPU alone may not help a service blocked on its database. Aggressive scale-out can amplify the dependency’s overload.

Test scale-in as carefully as scale-out. Drain connections and finish or safely reassign work before removing capacity. Do not assume that an instance termination notice guarantees an application has enough time to commit every task.

30. 28.13 Linux Administration in AWS, Azure, and GCP

The guest fundamentals remain familiar: supported packages, systemd, logs, storage, networking, identity, and backups. The provider-specific work concerns resource identities, image conventions, bootstrap services, access methods, network constructs, and recovery tooling.

For AWS EC2, inspect the selected image, instance profile, metadata controls, volume lifecycle, and network associations. For Azure, distinguish cloud-init-supported image provisioning from other guest-agent responsibilities. For Google Compute Engine, establish whether access uses metadata-managed keys, OS Login, or another approved path. These are separate documented systems, not a single generic “cloud SSH” setting. (R60, R61, R62)

Maintain provider-specific runbooks and test them in the actual account or project. Screens and defaults change; use current official documentation for control-plane actions instead of relying on an old screenshot.

32. 28.14 Cloud Troubleshooting

Investigate guest and platform together. Collect instance state, startup status, console output, network associations, disk health, quotas, and the failing application’s logs. A provider operation reporting success may mean the resource was created, not that initialization and health checks completed.

When SSH fails, separate the route and firewall path, host identity, user authorization, and guest daemon. Provider diagnostics can help, but understand whether a repair feature modifies guest keys or configuration before using it.

Preserve recovery disks and snapshots deliberately. Attaching a failed instance’s disk to a rescue host changes its exposure and can create identity or mount ambiguity. Identify the disk before any write and keep a record of repairs.
