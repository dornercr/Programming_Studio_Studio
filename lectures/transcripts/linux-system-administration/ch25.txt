4. 25.1 Virtualization Concepts

A virtual machine, or VM, presents virtual hardware on which a guest operating system runs its own kernel. The host supplies the underlying resources and virtualization mechanisms. This differs from a conventional Linux container, whose processes normally share the host kernel.

Virtualization can improve isolation and reproducibility, but the VM’s security boundary depends on the hypervisor, configuration, host administration, and exposed devices. Shared folders, device passthrough, and privileged management access create additional trust relationships.

For a lab, keep guest data disposable and maintain a console recovery path. A snapshot before an experiment saves time, but it is not independent protection against losing the host’s only storage device.

6. 25.2 Hypervisors

A hypervisor manages virtual execution and access to resources. “Type 1” commonly describes a hypervisor operating directly in the platform’s virtualization layer, while “Type 2” describes a hosted arrangement. Real implementations can combine mechanisms in ways that make the labels less useful than their actual architecture.

For operations, ask who schedules virtual CPUs, owns device emulation, controls networking, and stores VM disks. Determine how the management plane is authenticated and backed up. A compromise of that plane can affect every guest it controls.

Do not assume a VM on a laptop and a managed cloud VM have identical recovery or networking behavior. They share concepts, but their available consoles, snapshots, storage guarantees, and support responsibilities differ.

8. 25.3 KVM

KVM provides Linux kernel facilities for hardware-assisted virtualization on supported platforms. User-space virtualization software uses those facilities while supplying other parts of a VM’s execution environment. Hardware support, firmware settings, modules, and permissions must align.

Inspect rather than assume:

An absent device can reflect unavailable virtualization support, a nested-virtualization restriction, or missing configuration. Its existence does not grant every user permission to use it. Check the platform’s supported setup before changing group membership or device modes.

A Linux server can host KVM guests and ordinary processes at the same time. Capacity planning must account for both, including the host’s own memory, storage, and control-plane needs. (R55)

11. 25.4 QEMU

QEMU supplies machine emulation and virtualization components. With an appropriate accelerator such as KVM, guest execution can use hardware-assisted virtualization; other modes can emulate different machine architectures. These are not interchangeable performance expectations.

QEMU device models, machine types, firmware, and disk formats become part of a VM’s compatibility contract. A migration or upgrade needs to preserve the guest’s expected environment, not simply copy a disk and hope its devices remain recognizable.

For routine administration, a management layer such as libvirt is usually easier to audit than many manually constructed QEMU command lines. Understand the underlying components so you can interpret errors without bypassing the established management system. (R55)

13. 25.5 libvirt

libvirt provides interfaces for managing virtual machines, networks, and storage. Its virsh command operates against a selected connection. System-wide and per-user sessions can show different guests and networks.

These are observations requiring suitable authorization. An empty list on qemu:///session does not prove the system-wide guests are gone. Record the connection URI in automation and incident notes.

libvirt calls a guest a domain. Domain XML describes its configuration. Active and persistent configuration can differ, so inspect the intended state before making changes and understand whether an operation affects the running VM, its next start, or both. (R54)

16. 25.6 Virtual Machines

A VM needs a guest definition, virtual storage, network attachment, firmware or boot arrangement, and an installation source or image. It also needs an owner, patch policy, backups, and lifecycle dates once it becomes more than an experiment.

Distinguish shutdown, destroy, and undefine in management tooling. A graceful shutdown requests guest cooperation. In libvirt, destroy stops the running guest forcefully; it does not mean “securely erase every associated file.” undefine removes persistent configuration, with additional flags capable of affecting associated state. Read the exact command before treating an alarming or reassuring name as a complete description.

Never practice removal commands on a guest discovered by fuzzy name matching. Use an explicitly named disposable guest and inspect all associated disks first.

18. 25.7 Virtual Networking

A NAT network commonly allows guests to make outbound connections through the host while limiting unsolicited inbound access. A bridge can attach guests to a Layer 2 network more directly. An isolated network can connect selected guests without ordinary external forwarding.

Choose a topology from the lab’s needs. Package downloads can use NAT; failure-injection and service tests can use an isolated network. Adding a bridged interface can expose a lab service to a real network even though the administrator still calls it “a VM.”

Inspect guest addresses, virtual interface attachment, host bridges, routes, and firewall policy when diagnosing connectivity. The guest’s ip route cannot reveal every host-side NAT or switch decision.

20. 25.8 Virtual Storage

Virtual disks can use raw block devices, files such as qcow2 images, or managed storage backends. Thin allocation can make the apparent guest capacity larger than current physical consumption. That saves space only while the host pool retains enough real capacity.

A guest’s filesystem free space and the host’s backing-store free space are separate measurements. Either can exhaust first. Monitor snapshots and backing chains because they can increase host consumption independently of what the guest sees.

Do not modify an active disk image with offline tools unless the tool explicitly supports the operation and ownership is coordinated. Concurrent writers can corrupt the image. Inspect a verified offline teaching image with qemu-img info before experimenting with its format or chain.

22. 25.9 Snapshots

VM snapshots may include disk state, memory state, or a combination depending on the platform and operation. An external disk snapshot can create a new overlay while retaining a backing file. Losing an essential backing file can make the apparent newest image unusable.

Application consistency still matters. Capturing memory and disks does not excuse ignoring external databases or services that are not part of the snapshot. A resumed guest may also encounter changed networks, expired credentials, or time-dependent application state.

Document what the snapshot includes, which files it depends on, and how it is removed or consolidated. Test restoration on disposable workloads before relying on it during an upgrade. (R54)

24. 25.10 Cloning

Cloning creates another machine from a template or existing guest. A correct clone receives appropriate unique identities: hostname, machine identity, network address, SSH host keys, and application identifiers as required. Some identifiers must be preserved for a replacement; others must change for a simultaneous additional server.

Prepare templates using the distribution and provisioning tool’s supported cleanup process. Do not indiscriminately delete identity files on a live production guest. A template should not contain long-lived credentials or private customer data.

After cloning, verify connectivity and host identity from the management client. Two guests with the same address or host key can create confusing failures and weaken trust, even when both boot successfully.

26. 25.11 Resource Allocation

Allocate virtual CPUs, memory, and storage based on measured workload and host capacity. Overcommit means promising more logical resources than are physically available at once. It can be useful for workloads whose peaks differ, but correlated peaks and failure recovery can invalidate that assumption.

Leave host headroom. Memory ballooning, CPU scheduling, and storage caching do not create resources without limits. A guest that appears slow may be competing with a backup or another VM at the host layer.

For high availability, calculate remaining capacity after a host failure. A cluster able to run its guests only while every host is healthy has insufficient failover reserve. Chapter 29 connects this to service-level requirements.

Linux example — 25.11

Read a lab VM's CPU and memory allocation.

What to check: Guest allocation competes with host capacity; more assigned CPUs may not improve performance.

28. 25.12 Troubleshooting Virtual Machines

Separate guest, hypervisor, storage, and network evidence. If a guest cannot boot, use its console and inspect firmware and disk attachment before repairing its filesystem. If all guests slow together, investigate shared host resources before modifying every guest.

The guest name must be verified. These commands describe configuration, not application health. Correlate guest logs with host events using synchronized clocks and preserve both sides of a storage or scheduling incident.

Avoid deleting snapshots, forcing shutdown, or changing network attachments as the first diagnostic step. Those changes can destroy evidence or affect dependencies beyond the guest being examined.

35. Practice and implementation lab

Create a two-guest dependency diagram showing shared host, storage, switch, and power boundaries. Explain why two VMs on one laptop are not two independent availability zones. Document which identities must change when cloning a guest for simultaneous use.

Check your understanding. Does free guest disk space prove the host pool has room? No. Does a snapshot necessarily include external dependencies? No. Can two libvirt connection URIs show different guest inventories? Yes.

Chapter takeaway. Virtualization separates environments, but dependable operations still require exact resource mappings and tested recovery.
