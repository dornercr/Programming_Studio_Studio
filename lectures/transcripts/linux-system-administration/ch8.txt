4. 8.1 The Linux Boot Process

A conventional boot progresses through firmware, a boot manager or loader, the kernel, early user space, the real root filesystem, and the system’s main init process. Details vary with architecture, encryption, cloud images, and distribution tooling.

Each stage has different evidence. Firmware may fail before the kernel produces any log. An initramfs problem may prevent the real root filesystem from mounting. A systemd service failure occurs later, after the kernel and substantial user space are already working.

When diagnosing a boot failure, identify the last successful stage. “The server does not boot” is too broad to select a repair. A photo or console transcript of the exact error is often more useful than repeatedly power-cycling the machine.

6. 8.2 BIOS and UEFI

BIOS and UEFI are firmware interfaces that initialize hardware and select how to launch the operating system. UEFI commonly uses an EFI System Partition containing boot applications. Secure Boot can verify trusted components in that chain, subject to platform and distribution configuration.

A useful inspection is whether /sys/firmware/efi exists on a normally booted machine. This can help identify the current boot mode, but recovery procedures must still account for the installed bootloader and actual disk layout.

Do not switch firmware mode casually after installation. A system installed for one mode may not have the required files or boot entries for the other. Firmware settings, boot entries, and encryption recovery keys belong in the recovery plan, not only inside the guest’s filesystem backup.

8. 8.3 GRUB

GRUB is a commonly used bootloader that can select a kernel and supply its command line. Distribution tools often generate its configuration from templates and scripts. Editing the generated file directly can be overwritten by later updates.

Debian-family and RHEL-family systems differ in helper commands, configuration locations, and use of Boot Loader Specification entries. Follow the procedure for the installed release and boot mode rather than copying a generic grub-install command.

A temporary boot-menu edit can help test a kernel parameter without immediately making it persistent. Record exactly what changed and whether the next ordinary boot should retain it. A one-time rescue change is not a complete permanent fix.

10. 8.4 Kernel Initialization

After loading, the kernel initializes core subsystems, discovers available hardware, and prepares to start user space. Its command line can influence root-device selection, logging, drivers, and other behavior.

These inspect the running kernel’s state. The command line may contain infrastructure details, so review before sharing. Kernel messages can reveal missing devices or driver failures, but the earliest output may only be visible on the console if persistent logging never started.

A kernel panic is different from a later service failure. Preserve the error, kernel version, and recent changes. Booting a known-good installed kernel can be a recovery option when the distribution’s boot configuration and storage remain intact.

13. 8.5 Initramfs

An initramfs is an initial filesystem used during early boot. It can contain drivers and tools needed to locate, unlock, assemble, and mount the real root filesystem. Encrypted storage, LVM, RAID, and network-root setups may depend on it.

If a required storage driver or configuration is missing, the kernel may run but never reach the installed system. Rebuilding an initramfs can be appropriate after a verified cause, using tools such as dracut on RHEL-family systems or update-initramfs on Debian-family systems.

Do not rebuild blindly from an incorrectly mounted rescue environment. Confirm the target root, boot filesystem, kernel version, and required modules first. Otherwise you can create an image for the wrong system while believing the repair succeeded.

15. 8.6 PID 1

PID 1 is the initial process in the system’s PID namespace. On the reference full-server installations, systemd normally occupies that role. It participates in process lifecycle management and system startup.

Inside a container, PID 1 may instead be an application or small init wrapper. That process has responsibilities around signal handling and reaping adopted children. This is one reason an application that behaves normally in a shell can behave unexpectedly as a container entrypoint.

Do not assume that the presence of the systemctl executable means a systemd manager is running and reachable. Identify the execution environment before using service-management procedures.

18. 8.7 systemd Architecture

systemd represents managed resources as units and resolves activation relationships among them. It supervises processes through service units and cgroups, integrates logging with the journal, and supports sockets, mounts, timers, and targets.

The system manager is distinct from a per-user manager. systemctl ordinarily addresses system units; systemctl --user addresses the current user’s manager. Configuration paths, permissions, and startup lifetime differ.

A useful mental model is desired lifecycle plus observed state. Unit files describe how a resource should be managed; systemctl asks the manager to act or report; logs explain what happened. Editing a unit file does not automatically start the service or reload its application configuration. (R17)

20. 8.8 Units

A unit is a named object managed by systemd. The suffix identifies its type: .service, .socket, .timer, .mount, .target, and others. Different unit types describe different responsibilities.

Vendor units commonly live under /usr/lib/systemd/system or a distribution-equivalent path. Local system overrides belong under /etc/systemd/system. Use systemctl cat name.service to see the main file and drop-ins rather than assuming one visible file contains the complete effective configuration.

Prefer a drop-in for a narrow override. Replacing the entire vendor unit can prevent future package improvements from taking effect. Some list-valued settings require an empty assignment before replacement, so consult the setting’s documented merge behavior.

22. 8.9 Services

A service unit defines a process lifecycle: how to start, under which identity, with what environment and limits, and how to stop or restart. The Type= setting determines how systemd interprets startup.

Type=simple considers startup early in the launch process. Type=exec waits until the executable is invoked successfully, but still does not prove application readiness. Type=notify lets a cooperating program announce readiness. Type=oneshot is useful for a task that completes rather than running continuously.

A successful oneshot unit may become inactive after completion unless configured otherwise. That is not automatically failure. Select the service type that matches the actual program rather than forcing every task to look like a permanently running daemon. (R18)

24. 8.10 Targets

A target groups units and expresses a synchronization or activation point. multi-user.target commonly represents a non-graphical multiuser system, while graphical.target adds graphical-session requirements.

Targets are not simply old-style numeric runlevels with new names. Their relationships form a dependency graph, and multiple targets can be active at once.

Changing the default target affects future startup. Isolating a target can stop units not required by the new target and may disrupt access immediately. Do not test target isolation over your only remote session.

27. 8.11 Dependencies

Requirement dependencies and ordering dependencies are different. Wants= requests activation without the same failure coupling as Requires=. After= specifies ordering when relevant units are started; it does not by itself request their activation.

After=network.target does not mean the internet, DNS, or a remote database is reachable. network-online.target depends on the configured wait-online implementation and still is not a guarantee that a particular external service will remain available.

Applications need timeouts and retries for runtime dependencies. A correct boot order cannot prevent a database from failing later. Express necessary local mounts with supported dependency settings, and make application readiness explicit where the program provides a mechanism.

29. 8.12 systemctl

systemctl manages and inspects units. Start with observation:

The first gives a human-oriented summary; the next two ask different state questions. A service can be active but disabled, or enabled but failed. Scripts should use machine-oriented status properties or documented exit statuses rather than parse decorative terminal output.

start, stop, restart, and reload have different meanings. Reload requires application support. Restart usually interrupts the process lifecycle. daemon-reload asks systemd to reread unit definitions; it does not reload the application’s own configuration automatically.

32. 8.13 Enabling and Disabling Services

Enabling a unit generally creates activation links based on its [Install] section. It does not necessarily start the unit now. Starting a unit does not necessarily enable future automatic activation.

This combines enablement and immediate startup. Use it only when both are intended. disable --now similarly combines future disablement with a current stop.

Disabling does not prevent all possible activation: another unit, socket, or manual request may start the service. Masking prevents ordinary activation by replacing the unit’s load path with a mask, but it can break dependencies. Use masks deliberately and document why a simple disable is insufficient.

35. 8.14 Creating Custom Services

A custom service should specify an absolute executable path, an appropriate identity, a lifecycle type, restart behavior, and necessary directories or limits. Do not depend on a personal shell’s aliases, current directory, or exported variables.

systemd does not interpret ExecStart= as an ordinary shell command line. Pipes, redirections, and shell built-ins require a deliberately invoked shell or, preferably, a separate reviewed script. Environment handling also differs from interactive Bash.

Validate with systemd-analyze verify and test actual startup. Hardening settings such as NoNewPrivileges=, PrivateTmp=, and ProtectSystem= can reduce access, but they can also expose undeclared application write requirements. Add restrictions with tests rather than copying the largest possible list. (R19)

37. 8.15 Boot Targets

The default target determines the normal activation goal at startup. Inspect it before changing it. A headless server often uses multi-user.target, but graphical or specialized systems can have other intentional arrangements.

Use systemctl list-dependencies to inspect relationships, recognizing that a textual listing is not a complete timing trace. systemd-analyze critical-chain can help explain startup ordering and delays, but parallel activity and service-readiness semantics still require interpretation.

A long boot can result from a missing mount, a device timeout, network wait-online behavior, or an application startup timeout. Reducing a timeout may hide a required dependency rather than solve the underlying problem. Identify what the system is waiting for.

39. 8.16 Emergency and Rescue Modes

Rescue and emergency environments provide reduced operation for recovery. Available services, mount state, authentication, and networking depend on the distribution and boot path. Do not assume remote SSH will remain available.

Use the hypervisor or physical console, and know where encryption and administrative recovery credentials are stored. A recovery shell may have the root filesystem mounted read-only. Remounting it writable is a deliberate step that should follow inspection of storage health.

Keep recovery activity minimal and recorded. A rescue environment is not an excuse to disable every protection permanently. Repair the identified configuration, validate it, and return through the normal boot path to prove that the repair is complete.

Use the hypervisor or physical console, and know where encryption and administrative recovery credentials are stored. A recovery shell may have the root filesystem mounted read-only. Remounting it writable is a deliberate step that should follow inspection of storage health.

Keep recovery activity minimal and recorded. A rescue environment is not an excuse to disable every protection permanently. Repair the identified configuration, validate it, and return through the normal boot path to prove that the repair is complete.

41. 8.17 Diagnosing Boot Failures

Identify the failing stage, collect console output, and compare with the last known-good state. Once the installed system is reachable, inspect failed units and boot-scoped logs:

The previous-boot query requires retained journal data. Its absence does not prove the previous boot had no errors. Also inspect /etc/fstab, root-device identity, recent kernel changes, and disk health when the evidence points there.

Do not reinstall a bootloader simply because a late service failed. Match the intervention to the stage. After repair, perform a controlled reboot and verify the actual service, not only the login prompt.

50. Evidence, failure injection, and recovery

In the disposable VM, signal this teaching service with systemctl kill --signal=SIGKILL harbor-heartbeat.service. Inspect the journal and NRestarts property afterward. The unexpected termination should trigger the configured restart, subject to rate limiting. This is a controlled demonstration, not a recommended way to stop a real service.

For normal cleanup, use disable --now, remove only the dedicated unit and executable, and run daemon-reload. Do not repeatedly trigger failures until rate limiting obscures the first error. A restart loop is evidence requiring diagnosis, not a self-healing success story.

52. Practice and implementation lab

Compare the active and enabled states of three installed units. Find an example where the states differ and explain why the result is valid. Then add a harmless description-only drop-in to the teaching unit and inspect it with systemctl cat.

Reboot the lab VM while the heartbeat is enabled. Verify that it starts without an interactive login and that journal entries identify the new boot. Stop the unit normally and explain why Restart=on-failure does not mean “restart after every administrator-requested stop.”

Check your understanding. Does After= activate its named dependency? Not by itself. Does daemon-reload reload NGINX’s configuration? No. Does Type=exec guarantee an application is ready for traffic? No; it improves launch detection, not application-level readiness.

Chapter takeaway. Describe the lifecycle explicitly, separate activation from readiness, and verify normal startup, failure handling, and controlled shutdown.
