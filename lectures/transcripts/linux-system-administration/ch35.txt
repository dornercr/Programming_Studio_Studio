4. Read-only host report

Save this as scripts/host-report.sh. It prints UTC observation time, host identity, running kernel, uptime, memory, local filesystem capacity, and visible network addresses and routes. It does not upload data or elevate privileges. The --local option avoids deliberately traversing every network-mounted filesystem for the capacity report, but a diagnostic can still have environment-specific costs.

The report attempts each named observation and returns a nonzero overall status when a required command is missing or an observation fails. Partial output is therefore not silently presented as a complete inventory. Review output before sharing: network addresses and host names may be sensitive.

6. Bounded HTTP content check

Save the following as scripts/check-http.sh. The contract is an HTTP status of exactly 200 plus a literal marker in the body. Redirects do not count as success and are not followed. HTTPS retains normal certificate and name verification. An optional third argument selects a readable CA file for an explicit trust arrangement, including the isolated Chapter 33 lab.

The connection and total-request timeouts limit waiting. The requested response-size limit is one MiB; behavior on unknown-length transfers depends on the installed curl version, so do not treat this sample as a hardened download service. It writes the response to a private temporary file and removes it on exit. Do not place credentials in a URL or use the script as a generic secret-bearing probe.

From a client with the lab’s name-resolution and certificate trust prepared, a teaching invocation is:

Use the exact client trust arrangement established in Chapter 33. This program does not add DNS records, distribute trust, schedule itself, store history, or deliver alerts. Those responsibilities remain part of monitoring operations.

11. Verification record and limits · 1/2

The companion test runner was executed as the unprivileged nobody account in the preparation container. Fifteen Python unittest cases passed, with no skips, after Bash syntax checks passed for all four scripts and the shell test runner.

The cases covered new/unchanged status rendering, all supported states, invalid input preserving prior output, spaces in paths, symlink rejection, missing or nonregular targets, successful HTTP content checks, wrong content, missing resources, redirects, invalid schemes, empty markers, and a tar archive/restore fixture. One integrated NGINX case also checked a staged HTTPS configuration, the expected served content, rejection of the wrong hostname, rejection of an untrusted certificate, and a missing resource.

The NGINX fixture substituted a random unprivileged loopback port and temporary paths for production paths. Its body/proxy/FastCGI/uWSGI/SCGI temporary directories were explicitly redirected inside the fixture because the installed NGINX build uses privileged absolute defaults. These are test-harness adaptations, not changes applied to a production server.

Fifteen fixture test cases passed in the preparation environment, with no skips. Bash syntax checks passed for the four scripts and shell test runner. The executable versions and captured test output are recorded in the companion package.

12. Verification record and limits · 2/2

These checks do not establish a full two-distribution integration result. No privileged storage, LVM, boot, network, SSH-policy, firewall, SELinux/AppArmor, or cloud workflow was applied to target infrastructure. Systemd boot behavior, Ansible execution, container builds, and fleet convergence require the reader’s own lab tests. Example outputs elsewhere remain illustrative unless explicitly identified as captured fixture results.

The EPUB was assembled as reflowable text with chapter and section navigation. The assembly check verifies package structure, parseable XML, manifest/spine references, internal links, and the presence of all 33 chapters and 490 numbered sections. That is not a claim of an EPUBCheck pass or proof of identical rendering in every reading application.

Before operational use, validate the installed versions, security policy, target identifiers, restore access, and actual application behavior. The most important test remains the one that demonstrates the requirement on the environment that will carry the responsibility.
