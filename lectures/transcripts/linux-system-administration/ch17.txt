1. Linux Security

Security is the set of controls that preserves intended access and limits unintended consequences. HarborWorks needs a server that serves approved content, rejects unauthorized access, survives ordinary mistakes, and produces evidence when something goes wrong. No single setting delivers all of those outcomes.

4. 17.1 Defense in Depth

Defense in depth uses several independent controls so one failure does not grant unlimited access. For HarborStatus, these include authenticated administration, limited service identity, read-only content, network policy, mandatory access control, updates, backups, and monitoring.

Independence matters. Two controls that rely on the same compromised account may fail together. A backup accessible for deletion with the production server’s credentials is not an independent recovery boundary. Draw the trust relationships and ask what remains protected after each component fails.

6. 17.2 Least Privilege

Least privilege grants only the access needed for a defined task. A web worker reading static content should not own the operating system’s configuration or write the site’s release files. A monitoring account that reads a health endpoint does not need interactive root access.

Start with the required operation and resources, then grant narrowly. Do not infer that a failed operation needs “more privilege” before checking its path, identity, and configuration. An incorrect filename can produce a permission-like symptom that no sensible privilege policy should accommodate.

8. 17.3 System Hardening

Hardening reduces unnecessary exposure and makes approved behavior explicit. Remove or disable unneeded services, restrict administration, protect configuration, apply supported updates, and validate the workload under the resulting policy.

A hardening change needs a rollback and a functional test. Disabling a service because its name is unfamiliar can break time synchronization or identity. Use a baseline appropriate to the distribution release and server role, document exceptions, and test changes in a representative environment before fleet deployment.

10. 17.4 Account Security

Use named accounts, deliberate group membership, controlled administrative elevation, and prompt offboarding. Inventory service accounts separately from people. Review dormant accounts and authorized keys without assuming that a locked password disables every authentication method.

Recovery accounts need protection and testing. A break-glass account that nobody can use during an identity outage is not a recovery control; an unmonitored permanent root credential is also not an acceptable substitute. Define approval, storage, access logging, and post-use rotation.

14. 17.6 File Permissions

Permissions should reflect who must read, write, and traverse each path. Directory execute permission permits traversal; file execute permission permits execution. World-writable directories and overly broad recursive changes expand the set of people who can replace trusted content.

Configuration and executable files loaded by privileged services should not be writable by less-trusted users. A root-owned service unit pointing to a user-writable script still gives that user influence over privileged execution. Inspect the complete chain of files and parent directories, not only the unit file’s mode.

What to check: Review writable parent directories as well as the file.

16. 17.7 Linux Capabilities

Linux divides some traditional root powers into capabilities. A process may receive a particular privilege without receiving every root capability. This can reduce exposure when the capability is genuinely narrower than full root.

Capabilities are still powerful and interact with namespaces, executable file attributes, and process state. Inspect with tools such as getcap where installed, and avoid granting broad capabilities merely to silence a failure. CAP_SYS_ADMIN encompasses many operations and should not be treated as a harmless convenience. Service-specific capability bounding can be part of a reviewed systemd policy. (R41)

Inspect process and executable capabilities when libcap tools are installed.

What to check: A missing file capability can be normal; avoid granting broad capabilities to arbitrary binaries.

18. 17.8 Firewalls

A firewall evaluates traffic against policy. Decide which sources may reach which destinations, protocols, and ports, then implement that intent at the appropriate host and network boundaries. An allowed inbound port does not create a listening application.

State tracking commonly permits replies to established connections, but the exact policy depends on implementation. IPv4 and IPv6 both need consideration. Preserve management access and console recovery before changing host policy, and test from outside the host; local loopback traffic may follow different paths.

20. 17.9 firewalld

firewalld manages host policy through concepts such as zones, services, ports, and runtime versus permanent configuration. Start with firewall-cmd --get-active-zones and inspect the zone attached to the actual interface or source.

A runtime change affects current policy; a permanent change affects what is restored later. They can differ. Do not assume that a permanent addition immediately opens a port, or that a temporary runtime rule survives reload. For an isolated lab, timed runtime changes can reduce forgotten exposure, but they do not replace a verified rollback. (R37)

22. 17.10 nftables

nftables provides the packet-filtering framework and nft command. Rules live in tables and chains attached to specific hooks and priorities. A ruleset’s behavior depends on ordering and other managers, not merely one visually reassuring accept rule.

Use sudo nft list ruleset to inspect effective state. Validate a candidate file with nft -c -f FILE where appropriate before applying it. Do not flush a production ruleset to start a tutorial. On a firewalld-managed system, avoid simultaneously managing the same policy through independent raw nftables commands unless the interaction is deliberately designed. (R38)

24. 17.11 SELinux

SELinux adds mandatory access control based on policy and labels. It can restrict a service even when ordinary user/group permissions would permit access. This creates a separate boundary against mistakes and compromised processes.

A denial is evidence about an attempted operation. It may reveal a mislabeled file, unsupported path, wrong port, or an action the service should not perform. Identify the intended behavior before changing policy. Chapter 18 works through a static web-content example with enforcing mode preserved. (R39)

26. 17.12 SELinux Modes

Enforcing mode applies policy and records denials. Permissive mode records many would-be denials without enforcing them. Disabled mode removes SELinux enforcement and changes what policy evidence and labels can be relied on.

getenforce reports the current mode. A runtime mode change and a persistent boot configuration are different operations. Broadly switching a production host to permissive removes a protection boundary for more than the one failing service. Prefer targeted diagnosis and correct labeling; any temporary diagnostic relaxation needs authorization and a confirmed restoration.

Linux example — 17.12

Inspect configured and current SELinux modes.

What to check: Current runtime mode can differ from next-boot configuration; do not disable enforcement to hide a denial.

28. 17.13 Security Contexts

An SELinux context commonly contains user, role, type, and level fields. For many service investigations, the process domain and object type are the most immediately useful parts. ls -Z shows file contexts, while process inspection can show domains.

Ordinary ownership and SELinux labeling are independent. A file owned by the web worker can still be denied by policy, while a correctly labeled file can still fail Unix permission checks. Test both layers and ensure persistent label mappings match the intended paths.

30. 17.14 AppArmor

AppArmor is another Linux mandatory-access-control system, using profiles that commonly express access in terms of paths and application behavior. Ubuntu frequently uses AppArmor, but the actual enabled profiles depend on installed packages and configuration.

Inspect status with aa-status when available and read relevant denial messages. Enforce mode blocks prohibited behavior; complain mode is used for observation during policy development and does not provide the same restriction. Moving an application or changing its resource paths may require a reviewed profile adjustment, not disabling all profiles. (R40)

32. 17.15 Security Updates

Security maintenance requires supported repositories, advisories, testing, rollout, and verification that affected processes use the corrected code. Installing a library update does not necessarily replace an already-running process’s mapped copy. A kernel update normally requires booting into the new kernel unless an applicable supported live-patching arrangement addresses the issue.

Prioritize using actual exposure and vendor guidance, not only version-string comparisons. Enterprise vendors backport fixes. Keep records of exceptions, reboot needs, service restarts, and the exact package build installed. Chapter 6’s safe patching sequence remains the foundation.

34. 17.16 Auditing with auditd

The Linux audit subsystem can record selected security-relevant events with identity and operation details. auditd handles collection and storage in common enterprise configurations. Rules should answer specific questions rather than indiscriminately logging every syscall.

High-volume audit rules can consume storage and affect operations. Define retention, forwarding, rule ownership, and response to a full audit filesystem. Inspect existing policy before adding a teaching rule. An audit record’s presence helps establish an event; interpreting its security meaning still requires context and authorized investigation. (R41)

36. 17.17 CIS Benchmarks

CIS Benchmarks provide consensus configuration recommendations for particular products and versions. They are useful baselines, not a universal executable recipe. Select the correct distribution release and profile, understand each control’s rationale, and record justified exceptions.

A benchmark score does not prove application security or operational readiness. Some controls can conflict with a workload or recovery design when applied without adaptation. Treat remediation as a change process with test evidence rather than automatically enforcing every finding across production. (R42)

38. 17.18 Detecting Suspicious Activity

Look for deviations connected to risk: unexpected administrative access, new listening services, unauthorized configuration changes, unusual outbound connections, and unexplained persistence. Compare against a known baseline and approved change records.

A strange process name alone is not proof of compromise, and a familiar name is not proof of safety. Preserve executable paths, ownership, package provenance, process relationships, and timestamps. Do not run a suspicious binary just to see what it does. Escalate through the incident process when evidence supports concern.

40. 17.19 Incident Response Fundamentals

Incident response balances containment, evidence preservation, service impact, and communication. Identify the incident owner, record the initial facts, preserve relevant logs and volatile evidence as authorized, and choose containment that limits harm without destroying the investigation.

Do not immediately wipe or reboot every suspicious host. Those actions can remove useful evidence and may not remove stolen credentials or external access. Recovery often includes rebuilding from trusted sources, revoking affected credentials, closing the entry path, and verifying that monitoring works. Follow organizational and professional incident-response procedures for real events.

49. Practice and implementation lab

Write a least-privilege statement for the web worker, deployment identity, and monitoring identity. Identify which files each needs to read or write. Inspect current firewall and mandatory-access-control state without changing either.

Check your understanding. Is a world-writable application directory repaired by enabling SELinux alone? No; both controls matter. Does an installed security update prove every running process uses it? No. Is a benchmark score a guarantee of security? No.

Chapter takeaway. Security controls should enforce explicit access requirements and remain testable during normal operations and recovery.
