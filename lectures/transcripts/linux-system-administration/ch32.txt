1. The Administrator’s Troubleshooting Lab

This chapter is an assessment, not a collection of commands to run against a live server. Use disposable VMs with console access and verified snapshots. Cases involving boot, storage, identity, or policy must never be injected into production. The case observations below are invented teaching fixtures unless you reproduce them in your own lab.

For every case, submit a record containing the symptom, affected path, initial evidence, at least two hypotheses, a discriminating test, the smallest justified repair, verification, and prevention. A correct guess without evidence is not a completed exercise. Several cases deliberately share symptoms so that memorizing a favorite fix is insufficient.

4. 32.1 Server Will Not Boot

Case. After a maintenance restart, the VM reaches firmware but never displays a kernel boot message. The operator says “Linux is broken.” A second possibility is that firmware cannot find the intended boot device; a third is that the bootloader or its configuration is unavailable.

Use the hypervisor console to record the last visible stage and the exact error. Compare disk attachment and firmware mode with the pre-change inventory from Chapter 25. Do not run a filesystem repair merely because boot failed: at this stage you may not have evidence that the filesystem was reached.

Recovery. Restore the documented disk attachment or boot selection when that mismatch is established. If bootloader repair is required, use the distribution’s recovery procedure for the installed firmware mode and identified root and boot filesystems. Verify a complete boot, network access, mounts, and the HarborStatus request.

Prevention. Include console and boot-device evidence in the change record. A successful package transaction is not a boot test.

What to check: Rescue environments may not expose the installed host's journal automatically; mount and inspect it deliberately.

6. 32.2 Service Will Not Start

Case. NGINX reports failure after a configuration edit. In an isolated lab, save the current configuration, create a candidate copy with a deliberately missing semicolon, and validate the candidate in its proper full-configuration context. You need not replace the active configuration or stop a healthy service to learn from a parser error.

Inspect systemctl status nginx, the recent journal, and nginx -t. Compare the error’s file and line with the actual included file. A missing semicolon, occupied listener, missing certificate, and denied key file produce different evidence.

Recovery. Restore or correct the exact configuration, validate it, then start or reload according to the service’s current state. Test the named endpoint and its content. Do not repeatedly reset the service’s failed state without fixing the parser or runtime problem.

Prevention. Validate the complete assembled configuration before deployment and preserve the previous working revision.

Inspect the failing lab service.

What to check: Select the actual failing unit; repair the first meaningful configuration or execution error.

8. 32.3 Filesystem Is Full

Case. The application cannot write a report. The root filesystem has free space, but /var is a separate filesystem at its capacity limit. A competing hypothesis is a quota or read-only mount, so the phrase “disk full” is not yet enough.

Inspect errors from du and account for its scope. Identify growth and retained deleted files before deleting anything. Do not intentionally fill the VM’s root filesystem. A reproducible capacity-injection exercise belongs only on the separately identified tiny loop filesystem from Chapter 9, with a strict byte bound and no live application data.

Recovery. Stop the unintended producer, archive required evidence, and reclaim only known disposable data or extend the correct storage layers under the approved plan. Confirm a real application write and stable growth afterward.

Prevention. Add headroom and growth-rate alerts plus a retention owner; a static percentage alone may warn too late.

Distinguish bytes, inodes, and open deleted files.

What to check: Deleting unrelated files may not free the space held by an open deleted file.

11. 32.4 Application Cannot Write to a Directory

Case. The administrator can create a file with sudo, but a supervised application receives Permission denied. Candidate causes include ordinary ownership, ACLs, mandatory access control, a read-only mount, or systemd’s filesystem sandbox.

Inspect the unit’s runtime user and group, namei -l on the path, getfacl, findmnt, and relevant security logs. On SELinux systems, inspect process and file contexts. Reproducing access as the service’s Unix user is useful, but does not necessarily reproduce its SELinux domain or unit sandbox.

Recovery. Grant the legitimate write only in a dedicated state directory. Keep executable and release paths read-only to the worker. If the unit’s ReadWritePaths needs adjustment, document the reason and verify that unrelated paths remain protected.

Prevention. Declare required write paths before adding sandbox restrictions, and test them using the real supervised process.

Linux example — 32.4

Trace the application's intended writable directory.

What to check: Static content may intentionally be read-only to the service; verify the actual write requirement.

13. 32.5 SSH Connection Is Refused

Case. A client reaches the lab server’s address but SSH reports a refused connection. In a disposable VM, stopping the SSH service from a working console can reproduce one cause. Do not do this over the only management session.

Confirm the destination address and port. Inspect the guest listener, service state, and host firewall. A deliberate firewall reject can resemble an absent listener, so do not equate the client’s text with a unique root cause.

Recovery. Start the intended daemon only after its configuration passes validation, or restore the narrowly required policy when rejection is established. Test a new connection from the original client and preserve host-key verification.

Prevention. Monitor the supported administration path and retain an independently authenticated console route. Do not expose SSH to every source merely to avoid maintaining a source-specific rule.

Inspect SSH's listener and installed service unit.

What to check: Refusal usually occurs before authentication; also check destination, route, and firewall policy.

15. 32.6 SSH Authentication Fails

Case. The transport and host-key checks succeed, but the user’s key is rejected. The correct public key may be missing, the wrong private key may be selected, directory permissions may be unsuitable, or effective server policy may reject the account.

Use an explicit selected identity with ssh -i and bounded verbose diagnostics. Compare server authentication records with the user’s account state, authorized-key path, and sshd -T -C output for the actual connection context. Keep any working session open.

Recovery. Repair the specific account or key-path configuration, validate server syntax if changed, and test a new login plus sudo as required. A locked password does not necessarily block public-key authentication; conversely, some account restrictions apply beyond passwords.

Prevention. Provision named access through a controlled process and test offboarding across all authentication methods rather than only the password field.

What to check: Correlate with the server's authentication log; never send the private key as troubleshooting evidence.

17. 32.7 Server Cannot Resolve DNS

Case. An application reports an unknown hostname. A direct query to the intended resolver succeeds, but getent hosts fails. That comparison suggests the host’s resolver integration or name-service path rather than a nonexistent DNS record.

Inspect the active network and resolver manager, search domains, and query type. On systems using systemd-resolved, resolvectl status can add per-link context. Do not assume the command exists or controls every distribution.

Recovery. Correct the owning configuration and retest the application’s lookup path, not only dig. Avoid replacing managed resolver files with public DNS as a shortcut.

Prevention. Monitor internal resolution from the actual client context and document which service owns resolver configuration.

20. 32.8 Server Cannot Reach the Internet

Case. Internal hosts are reachable, but repository downloads fail. Possibilities include no default route, blocked egress, proxy requirements, DNS failure, TLS trust failure, or the remote repository’s own problem.

Inspect address and route state, then test the intended repository by name and protocol. A successful route lookup does not prove packet delivery. A failed ping to a public host does not prove HTTPS is impossible because ICMP policy can differ.

Recovery. Correct the established layer: route, approved proxy, egress policy, resolver, or trust configuration. Use the network manager for persistent state and preserve console recovery before changing a management interface.

Prevention. Document repository dependencies and proxy trust. Do not grant broad outbound access to resolve a specific missing repository path without an approved requirement.

Inspect local routes and test a bounded approved request.

What to check: Separate name resolution, route selection, transport, and TLS failures.

25. 32.10 Memory Is Exhausted

Case. An application is terminated while the host still reports available memory. Its unit has a memory maximum, and its cgroup records an out-of-memory event. This is different from global host exhaustion.

Inspect the service’s effective memory settings, restart history, kernel messages, and workload size. Do not deliberately exhaust the host for practice. Use this case card or a separately engineered small cgroup-limited lab with an automatic time bound and no production processes.

Recovery. Determine whether the limit is wrong, the input exceeds the supported size, concurrency is excessive, or the program leaks memory. A reviewed temporary increase can restore service, but record why it is safe and how host headroom remains protected.

Prevention. Test worst-case supported inputs and failure handling. A restart policy should not turn an OOM event into an unlimited rapid failure cycle.

Read memory accounting and kernel OOM evidence.

What to check: Also inspect the application's cgroup limit; the whole host may still have available memory.

27. 32.11 Disk I/O Is Saturated

Case. A backup and the application’s latency spike overlap. CPU is mostly idle, device latency increases, and blocked tasks rise. This supports investigating I/O contention, but it does not rule out device errors or an unrelated storage-path problem.

Map the application and backup paths to actual underlying devices, then inspect aligned iostat, pidstat, and kernel-log observations. A filesystem on a different pathname can still share the same storage backend.

Recovery. In an approved test, reduce or reschedule the competing workload and verify both service latency and backup completion requirements. If errors indicate failing hardware, follow the storage recovery process instead of tuning around retries.

Prevention. Include backup activity in capacity tests. A server sized only for interactive traffic may fail its operating contract during its own maintenance.

29. 32.12 Broken Package Update

Case. A package transaction was interrupted. Some packages are present, but a service’s dependency configuration is incomplete. Another possible cause is a repository or signature failure before installation, so start with the exact transaction log.

Inspect the package manager’s state and history. On Debian-family systems, dpkg --audit can help identify incomplete package states. On RHEL-family systems, DNF history and package verification can help reconstruct what occurred. Do not bypass signature checks or remove a lock owned by an active process.

Recovery. Follow the distribution-supported recovery for the actual partial state, using an approved repository set and a known recovery point. Retest dependent services and any required reboot. A transaction rollback may not undo application data migrations.

Prevention. Separate package rollout from irreversible data changes and maintain tested recovery artifacts rather than assuming package history is a complete backup.

Linux example — 32.12

Inspect package consistency on the matching host family.

What to check: Review the failed transaction before running any automatic repair or forced downgrade.

31. 32.13 Incorrect /etc/fstab Entry

Case. A wrong UUID in a required mount delays or interrupts boot. Diagnose the file before reboot whenever possible. Copy /etc/fstab to an ordinary lab file, add an invented entry there, and inspect it without replacing the live file:

Use the installed tool’s validation output and compare with blkid and lsblk -f. A syntax-valid entry can still refer to the wrong device or an unavailable network service.

Recovery. From the verified rescue environment or console, restore the intended UUID and mount options in the installed system’s file. Validate, test the specific mount, and then perform a planned reboot. Do not add nofail to every required filesystem just to hide the error.

Prevention. Test mount identity and boot behavior as part of every persistent-storage change.

43. 32.18 Production Service Becomes Intermittent

Case. Roughly some, but not all, requests fail after a rollout. Avoid assuming the fraction proves a particular architecture. Inventory DNS answers, backends, IPv4 and IPv6 paths, and deployment revisions.

Test each approved backend with the intended hostname using curl --resolve, while retaining TLS verification. Record backend identity, marker, latency, and errors. A fresh connection and a reused connection can follow different behaviors, so document the client method.

Prevention. Add per-backend readiness and release checks. The fleet’s aggregate success rate can hide one consistently incorrect node.

45. 32.19 Recovering from Administrative Mistakes

Case. An operator changes ownership recursively on the wrong lab directory. The temptation is another broad recursive command intended to reverse it. Without a known previous state, that can compound the damage.

Stop further mutation, preserve the command and target evidence, identify affected files, and consult trusted configuration, package metadata, backups, and application ownership requirements. A terminal history is helpful but not complete proof of every effect.

Recovery. Restore known state from an appropriate source or rebuild a disposable machine. For real data, involve the responsible owner and recovery process. Do not claim that one guessed chown can recover every original owner, ACL, or label.

Prevention. Use explicit target validation, dry runs where meaningful, limited privileges, and staged changes. A command’s convenience should not hide its blast radius.

47. 32.20 Performing a Complete Root-Cause Analysis

Case synthesis. Use the intermittent-service case. The fictional evidence shows that one backend serves the previous certificate after a renewal deployment, while the other presents the intended certificate. The renewal job completed, but only one daemon reloaded. The monitor checked local files rather than the endpoint-presented identity.

Write the causal chain without inventing missing events: deployment created the new file; reload coverage was incomplete; one backend continued using old in-memory state; client selection exposed intermittent certificate failure; the monitor missed it because it checked the wrong object. State any uncertainty about why reload coverage was incomplete until logs or reproduction resolve it.

Record impact with the actual measurement window and population. Do not convert a small sample into a precise percentage of all users. Document restoration by draining and repairing the affected backend, then verified endpoint tests across all backends.

Corrective actions should have owners and tests: make reload results explicit per host, fail the rollout on incomplete coverage, verify the presented certificate, and rehearse rollback. “Remember to reload” alone leaves the process dependent on memory.
