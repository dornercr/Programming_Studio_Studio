The Linux Filesystem

1. The Linux Filesystem

An administrator sees /var in a path and assumes it is a separate disk. Another deletes a large log but discovers that free space has not increased. Both mistakes come from treating a pathname as if it completely described the object underneath it. Linux storage presents one directory tree, but that tree can combine several filesystems, virtual interfaces, and names for the same data.

This chapter develops a precise model: directories map names to filesystem objects; mounts connect filesystems to the visible tree; processes can keep objects open after a name disappears. That model explains many seemingly contradictory storage observations.

2. Resolve names to filesystem objects

A hard link names an existing inode; a symbolic link stores a path. Removing one name need not release an open object. A deleted log still consumes space because a process retains its descriptor.

4. 3.1 The Filesystem Hierarchy Standard

The Filesystem Hierarchy Standard, or FHS, describes conventional locations for system files. Its purpose is predictability: an operator should have a reasonable place to look for configuration, logs, installed programs, and service data. It is a convention and specification, not a guarantee that every application follows it perfectly.

The major distinction is between kinds of data. /etc contains host configuration, /var contains changing state, and /usr contains installed software and shared resources. An application that stores important database files in /tmp violates the lifetime expectations of that location even if it works today.

Modern distributions can use a merged /usr layout in which paths such as /bin are symbolic links into /usr. Read the actual layout with ls -ld /bin /sbin /lib; do not assume every conventional directory is physically separate. (R02)

6. 3.2 Understanding /

The single slash / is the root of the visible directory tree. It is not the root user’s home directory. Every absolute pathname begins there, but the objects below it can live on different devices or be generated by the kernel.

A filesystem mounted at / is the root filesystem. Other filesystems may be attached at paths such as /boot, /home, or /var/lib/data. These are mount points, not separate drive letters. A directory’s name alone cannot tell you whether it is a mount point.

The first inspects the root mount; the second identifies the filesystem containing /var. If both show the same source, /var is not on a separate filesystem in that configuration. This distinction matters before making capacity or isolation claims.

9. 3.3 /etc — System Configuration

/etc holds host-specific configuration. A package may install defaults there, and administrators may override or extend them through documented drop-in directories. Prefer a supported drop-in mechanism over editing a vendor-supplied file in a package directory.

Configuration is not automatically active configuration. A daemon may read a file only at startup or reload. Some tools generate files from another source, so editing the generated output may be temporary. Determine which component owns each file and how it is applied.

Before editing, preserve a copy with metadata, record its purpose, validate the proposed syntax, and identify the reload or restart needed. Do not back up secrets into a world-readable directory. A copy of an authentication configuration or private key deserves at least the protection of the original.

11. 3.4 /var — Variable Data

/var contains data expected to change during operation. Important subdirectories include /var/log for logs, /var/lib for persistent application state, /var/cache for generally reconstructible caches, and /var/spool for queued work.

These categories have different recovery value. A package cache can often be downloaded again; a database cannot necessarily be reconstructed. Do not delete an entire changing-data directory merely because it is large. Identify its owner and data semantics first.

Separating selected /var workloads onto their own filesystems can prevent one growth pattern from filling the root filesystem. It also creates additional mount and backup obligations. The best layout follows failure containment and recovery requirements, not a rule that every conventional directory needs its own partition.

13. 3.5 /home and /root

/home commonly contains ordinary users’ home directories. /root is commonly the root account’s home. Homes contain personal files and per-user configuration, including potentially sensitive SSH material. They are not ideal places for production service code that should outlive one administrator’s account.

A service launched from /home/alex/project can accidentally depend on Alex’s permissions, shell settings, or account lifetime. Move system-managed software and state into deliberate service locations with documented ownership.

Home-directory removal is therefore more than housekeeping. Before removing a user, find owned service files, scheduled tasks, keys, and operational dependencies. An account may look inactive while an unattended job still depends on its home directory.

15. 3.6 /usr and /opt

/usr contains much of the installed user-space software. /usr/bin holds many commands; /usr/lib holds libraries and related components; /usr/share holds architecture-independent resources. /usr/local is conventionally reserved for locally administered software outside the distribution’s normal package ownership.

/opt is commonly used for self-contained add-on applications. It can be useful for versioned vendor or internal software, but it is not exempt from inventory, permissions, updates, or backups.

Avoid overwriting a packaged executable with a manually compiled one under the same path. The package manager may replace it later, and verification becomes confusing. Use an explicit local prefix, a package built for the distribution, or a versioned application directory with a documented deployment method.

17. 3.7 /tmp and /run

/tmp holds temporary files and may be cleaned automatically or backed by memory. Never assume its contents survive reboot. /run holds runtime state such as PID files, sockets, and service-created working directories; it is normally recreated during boot.

Use mktemp for unpredictable temporary names rather than guessing a filename in a shared directory. A predictable root-written temporary file can create a security problem when another user can create or replace the path first.

For services, systemd’s RuntimeDirectory= can create and manage an appropriately owned directory under /run. Persistent application data belongs elsewhere, such as /var/lib. A program that cannot distinguish runtime state from durable state will be difficult to recover correctly.

19. 3.8 /proc and /sys

/proc and /sys are virtual filesystems exposing kernel and process information. Their contents are not ordinary files stored on the root disk. /proc includes process-specific directories and system interfaces; /sys organizes devices, drivers, and kernel objects.

Reading an interface can provide a live view; writing to some interfaces can change kernel behavior. Treat a writable virtual file as a control surface, not as a harmless text file. Its semantics come from the kernel documentation.

Do not recursively back up /proc or /sys as ordinary data. Some entries change during the scan, expose sensitive state, or have unusual read behavior. Recovery requires recreating the operating environment, not restoring a stale copy of these live interfaces. (R01)

22. 3.9 Absolute and Relative Paths

An absolute path begins at /; a relative path begins at the current working directory. Programs also interpret relative paths in configuration according to their own rules, which may differ from your interactive shell’s location.

For example, a service using data/report.txt might interpret it relative to its WorkingDirectory=, or relative to another application-defined base. A script that works from its source folder may fail when a scheduler starts it from a different directory.

Use absolute paths for critical operational files unless a deliberate relocatable design establishes a trusted base directory. Test a script from outside its own directory. That simple test exposes hidden working-directory assumptions before the script runs unattended.

24. 3.10 Inodes

An inode stores metadata describing a filesystem object, including ownership, permissions, size, timestamps, and information needed to locate its data. A directory entry associates a name with an inode. The name is not simply a field inside the file’s inode.

An inode number is meaningful within its filesystem, not globally across every mounted filesystem. A device or filesystem identity plus inode number is more useful than an inode number alone when comparing objects.

This separation explains why a file can have several names and why deleting a name does not always release storage. Space can remain allocated while another hard link exists or a process still holds the object open. It also explains why filesystem capacity can be exhausted by many tiny files even when few data bytes are stored. (R06)

27. 3.11 Hard Links

A hard link is another directory entry referring to the same inode. Neither name is inherently the “real” file. Changing the content through one name changes the object visible through the other. Removing one name decreases the link count but leaves the other name valid.

Hard links normally cannot cross filesystem boundaries because an inode belongs to a particular filesystem. Ordinary users cannot use them to create arbitrary directory cycles. These restrictions preserve a manageable directory structure.

Hard links are useful for understanding deduplication-like backup layouts, but they are not independent copies. Editing a shared object changes every linked name. A backup design using hard links must create a new inode when updating content rather than modifying a shared inode in place.

29. 3.12 Symbolic Links

A symbolic link, or symlink, is a separate object containing a target pathname. The target can be on another filesystem and can be absent. Such a link is then called dangling. A relative symlink target is resolved relative to the symlink’s containing directory, not your current shell directory.

A symlink can be convenient for pointing current at a versioned application release. Replacing the link changes future pathname resolution, but processes that already opened old files may continue using them. The deployment still needs an application-specific reload strategy.

Be careful when privileged tools follow symlinks through untrusted directories. The object reached can differ from the object you inspected earlier. Secure automation controls directory ownership and avoids treating pathname checks as perfect protection against concurrent replacement.

32. 3.13 File Types

Linux exposes regular files, directories, symbolic links, block devices, character devices, sockets, and named pipes. The first character of ls -l often indicates the type: - for a regular file, d for a directory, l for a symlink, b or c for devices, s for a socket, and p for a named pipe.

A socket or named pipe can look like a path while representing communication rather than stored document content. Copying it like a regular file does not recreate the running service behind it.

Use file and stat to inspect unfamiliar objects. A filename extension is only a convention. Linux does not require a shell script to end in .sh, nor does a .txt suffix guarantee that a file contains readable text.

34. 3.14 Mount Points

A mount point is a directory where another filesystem is attached to the visible tree. If the directory already contains files, mounting over it hides those files without deleting them. They reappear when the mounted filesystem is detached.

This behavior causes a common backup failure. A backup disk fails to mount, but the job writes into the ordinary directory underneath. The root filesystem fills, and the supposed remote backup is actually local.

Before writing to an expected mount, verify its source and filesystem with findmnt -T /path or a precise mountpoint check. Checking that the directory exists is insufficient. An application requiring a mount should also express that dependency through its service configuration and monitor the expected storage identity.

36. 3.15 Filesystem Troubleshooting

Start by identifying the path, object type, containing filesystem, and caller identity. Then ask whether the problem is capacity, inodes, permissions, a read-only mount, a missing mount, or an open-but-deleted file. Similar error messages can arise at different layers.

df -i checks inode availability. namei -l displays permissions along a path. If a filesystem has become read-only after errors, do not immediately force it writable. Preserve evidence, inspect kernel logs, and follow the filesystem-specific recovery procedure.

A useful diagnosis states both the observation and its scope: “The filesystem containing /var/log has free blocks but no free inodes” is stronger than “the disk is broken.”

38. 3.15 Filesystem Troubleshooting · example 2

Start by identifying the path, object type, containing filesystem, and caller identity. Then ask whether the problem is capacity, inodes, permissions, a read-only mount, a missing mount, or an open-but-deleted file. Similar error messages can arise at different layers.

df -i checks inode availability. namei -l displays permissions along a path. If a filesystem has become read-only after errors, do not immediately force it writable. Preserve evidence, inspect kernel logs, and follow the filesystem-specific recovery procedure.

A useful diagnosis states both the observation and its scope: “The filesystem containing /var/log has free blocks but no free inodes” is stronger than “the disk is broken.”

Check your understanding. Can two files on different filesystems have the same inode number? Yes. Does mounting over a nonempty directory delete its files? No; it hides them. Why can deletion fail to free blocks immediately? Other hard links or open file descriptors can retain the object.
