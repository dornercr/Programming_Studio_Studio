4. 5.1 Linux Ownership

A filesystem object has an owner UID and group GID. Traditional permissions define access for the owner, the owning group, and everyone else. These are classes selected by credential matching, not permissions that are simply added together.

If a process matches the file owner, the owner permissions are used even when its group membership would otherwise offer different rights. ACLs add more entries, but the principle remains that the access algorithm selects and evaluates applicable rules.

ls -n shows numeric identities, useful when name mapping is unavailable. Verify the process identity with id or the service configuration rather than assuming it matches the user who installed the application. (R06, R07)

7. 5.2 Read, Write, and Execute

For a regular file, read permits reading content, write permits modifying content, and execute permits attempting execution. Execution still depends on a valid format or interpreter and other policy. A text file with an execute bit is not automatically a valid program.

For a directory, the meanings differ. Read permits listing entry names; execute permits searching or traversing the directory; write permits creating, removing, or renaming entries, normally in combination with execute. Deleting a file primarily depends on its parent directory’s permissions, not the file’s write bit.

This explains why a read-only file can sometimes be deleted by someone who controls its directory, and why a readable file can still be inaccessible when a parent directory lacks execute permission. Inspect the entire path, not only its final component.

9. 5.3 Numeric Permissions

Numeric modes use three ordinary digits for owner, group, and others. Read contributes 4, write 2, and execute 1. Add the desired bits within each class: 7 means read/write/execute; 6 means read/write; 5 means read/execute.

640 means owner read/write, group read, and no ordinary access for others. 750 on a directory allows the owner full directory control, the group listing and traversal, and others no access through that directory.

A leading digit can encode special bits, such as 2750 for a set-group-ID directory. Do not memorize modes without their intended object and role. 644 is common for public data files but inappropriate for private keys; 755 is common for directories or public executables but grants more visibility than many service-state directories need.

11. 5.4 Symbolic Permissions

Symbolic modes name the classes and changes directly. u, g, and o mean user, group, and others; a means all. + adds bits, - removes them, and = sets the specified class to an explicit selection.

The first command specifies an exact ordinary policy. The second modifies one part while retaining other existing bits. That distinction matters in repeatable administration: “add group write” is not the same desired state as “set this complete mode.”

The special symbol X grants execute to directories and to files that already have an execute bit. It can help with reviewed recursive adjustments, but it is not permission to apply an unexamined recursive change to a mixed tree.

14. 5.5 chmod

chmod changes mode bits. The owner or an appropriately privileged process can ordinarily change a file’s permissions. Some filesystems or mount options provide different behavior, so a successful-looking command should still be verified where portability matters.

Before changing a tree, separate directories, ordinary data files, executable files, and secrets. Applying one mode recursively can make private material readable or make directories impossible to traverse.

These inspection commands establish categories; they do not change them. When a service fails, identify the smallest required permission instead of widening everything. A write failure in one state directory does not justify write access to service code, configuration, and logs.

17. 5.6 chown and chgrp

chown changes ownership, optionally including the group, while chgrp changes the group. Changing owner generally requires privilege. The ability to change a file’s group is constrained by ownership, membership, and system rules.

These example commands assume an intentionally created lab path and group. Do not apply them to an arbitrary existing production directory.

Recursive ownership changes are risky across symlinks, mount boundaries, and mixed workloads. They can also alter security-relevant metadata or executable privilege bits. Inventory first, use the tool’s documented traversal behavior, and verify both ownership and application behavior afterward. Owning a directory does not automatically imply ownership of every file beneath it.

20. 5.7 umask

A umask removes permission bits from the mode requested when a new object is created. It is not decimal subtraction and does not retroactively change existing files. Ordinary programs commonly request 666 for data files and 777 for directories, after which the mask removes selected bits.

With umask 027, a normally requested data file becomes 640 and a directory becomes 750. Execute permission is not added to ordinary files because it was not requested in the first place. Default ACLs can change the creation calculation, so inspect actual results rather than relying only on the mask.

The parentheses create a subshell, keeping the temporary mask from altering the parent shell. Service-specific UMask= settings can make creation policy explicit without depending on an administrator’s login environment.

What to check: Typical results are 600 and 700; the parent shell's umask remains unchanged.

23. 5.8 SUID

The set-user-ID (SUID) bit on an executable can cause it to run with an effective UID derived from the file owner. It exists for narrowly designed privileged operations, not as a general solution for permission problems.

Its behavior is affected by execution context, mount flags such as nosuid, and security controls. Linux does not generally honor SUID on ordinary interpreter scripts in the same way as on suitable executable binaries.

Do not add SUID to an arbitrary utility or shell. A program designed for ordinary use may expose unrestricted privileged actions through arguments, environment variables, plugins, or shell escapes. Prefer a reviewed sudo policy, a purpose-built service, or a narrowly assigned capability when appropriate. Audit unexpected SUID changes against a known baseline.

Inspect an existing SUID program without creating one.

What to check: A leading mode digit of 4 indicates SUID. Avoid adding this privilege to arbitrary executables.

25. 5.9 SGID

The set-group-ID (SGID) bit on an executable has a group-related privilege meaning. On a directory, its common administrative use is group inheritance: newly created entries generally inherit the directory’s group, and new subdirectories can inherit the SGID bit.

This is useful for a collaboration directory owned by a deployment group. It does not by itself guarantee group write permission; the creation mode, umask, and default ACL still matter.

For example, a 2770 directory gives owner and group directory access, denies others, and requests group inheritance. Pair the mode with an intentional file-creation policy. Otherwise members can create files that carry the correct group but still cannot be edited by their colleagues.

27. 5.10 Sticky Bit

On a shared writable directory, the sticky bit restricts who may remove or rename entries. Typically the entry owner, directory owner, or a suitably privileged process can do so. /tmp commonly uses this behavior.

The sticky bit does not prevent users from reading or modifying content when the file’s own permissions allow it. It controls directory-entry operations, not every operation on the file.

A mode such as 1777 can be appropriate for a deliberately shared temporary directory, but it is not a general policy for production application state. If only one service should write, give that identity ownership and restrict access rather than creating a public scratch area.

29. 5.11 Access Control Lists

An access control list, or ACL, adds permissions for named users and groups beyond the basic owner/group/other entries. getfacl displays ACLs; setfacl changes them. Install the distribution’s ACL tools package when needed.

The ACL mask limits the effective rights of named users, named groups, and the owning-group entry. An entry displaying rwx may therefore provide less effective access. getfacl shows this distinction.

A directory can also carry default ACLs used when creating new children. These are inheritance rules, not permissions on every existing descendant. Record and test both access and default entries. Also remember that a later chmod can change the mask and therefore alter effective ACL access. (R11)

32. 5.12 Extended Attributes

Extended attributes, or xattrs, attach additional name/value metadata to a filesystem object. They can store application metadata, security labels, or capabilities. They are separate from ordinary file content and mode bits.

Tools such as getfattr and setfattr inspect or modify appropriate attributes, while specialized tools manage particular namespaces. SELinux labels and Linux file capabilities should normally be handled through their dedicated tools rather than arbitrary byte edits.

A copy or archive that preserves file content but omits xattrs can change security behavior after restoration. Chapter 21 therefore treats permissions, ownership, ACLs, xattrs, and labels as part of recovery requirements. Always verify that the selected filesystem and backup method support the metadata you depend on.

34. 5.13 Diagnosing Permission Problems

Begin with the exact operation and effective service identity. Inspect every parent directory with namei -l, the final object’s ownership and mode, ACLs, mount options, and mandatory-access-control evidence. A read-only filesystem or systemd sandbox can block a write even when ordinary permissions look correct.

A root-run test can hide the failure experienced by the service. Run the smallest relevant test as the service identity, then test through the real service because it may have additional restrictions.

Avoid chmod 777 as a diagnostic switch. It destroys information about which ordinary permission was missing and may introduce a second problem. Narrow tests preserve both security and the evidence needed to identify the actual cause.

41. Evidence and limitations

Verify that the file belongs to hb-deploy, is accessible to the intended group, and does not grant others access. Then inspect a newly created subdirectory separately. Do not assume that testing one regular file proves directory inheritance behavior.

For a production deployment, group-writable release code may itself be too broad. A stronger design gives deployment automation permission to create immutable versioned releases while the running service has read-only access. This lab teaches collaboration, not the final trust model for executable application code.

43. Practice and implementation lab

Create a readable file inside a directory without traversal permission for a second lab user. Predict the failure, then confirm it. Restore the directory permission and explain why the file’s own mode never needed to change.

Compare file creation under umasks 022 and 027, first without a default ACL and then with one. Record actual modes and effective ACL permissions rather than assuming that the mask alone decides the outcome.

Check your understanding. Which permissions usually control file deletion? The parent directory’s permissions, with sticky-bit and other policy considerations. Does SGID guarantee group write? No. Why can an ACL entry appear generous while effective access is smaller? The ACL mask limits the group-class entries.

Chapter takeaway. Grant the smallest permission needed to the actual execution identity, and verify the full path and every relevant policy layer.
