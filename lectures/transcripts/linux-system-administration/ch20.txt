1. File Sharing and Network Storage

A local pathname can hide a remote dependency. HarborWorks wants a shared directory for approved reports, but the reports must not become writable by every machine that can reach the server. This chapter connects file sharing to identity, availability, and recovery rather than treating a successful mount as the end of the task.

4. 20.1 Network Filesystems

A network filesystem lets a client access remote files through filesystem operations. The application may use familiar paths while every lookup, read, or write depends on a network and another host. Local-looking behavior does not imply local latency or failure semantics.

Define the workload before selecting a share. Does it require several writers, locking, stable identity, low latency, encryption, or operation during disconnection? A deployment artifact repository, a user home directory, and a database data directory impose different requirements. Do not put a database on a generic share without the database vendor’s supported storage contract.

Document the server, exported path, client mount point, protocol, security mode, and owner. Test server loss as well as normal operation. A process blocked in a remote filesystem operation may not respond immediately to the signals an operator expects.

6. 20.2 NFS

NFS is a common network filesystem protocol in Unix-like environments. Version and security flavor matter. An NFSv4 deployment is not operationally identical to an older configuration with additional RPC services and ports. Establish the negotiated protocol instead of assuming the package name determines it.

With traditional AUTH_SYS, client-provided numeric identity is part of the trust model. Restricting access to a subnet does not turn it into strong per-user authentication. For stronger identity and integrity or privacy requirements, evaluate a properly configured Kerberos-based security flavor, such as krb5p, within the organization’s identity infrastructure. (R46)

For the introductory lab, use a read-only export between isolated, administrator-controlled machines. That constrains the exercise without implying it is an enterprise identity design.

An export specifies a server directory, allowed clients, and options. On common Linux servers, /etc/exports and included export files define the persistent intent. exportfs -v shows the active interpretation; it is more useful than assuming that an edited file has already taken effect.

An illustrative isolated-network entry is:

The address must be the verified client, not a guessed network. There must be no space between the client expression and its parenthesized options. ro makes the export read-only. root_squash maps requests claiming client root to an anonymous identity rather than trusting client root as server root. 12. 20.4 NFS Clients

A client needs the distribution’s NFS utilities, a dedicated mount point, network access, and compatible export permissions. Ubuntu commonly uses nfs-common; RHEL-family systems use nfs-utils. Mounting requires administrative permission even when later file access uses an ordinary account.

These observations help establish the actual mounts and options. Verify file access as the intended user, not only as root. A mount that root can list may still reject application access because identity or directory permissions differ.

Avoid changing from the default hard-retry behavior to a soft mount merely to stop a process from waiting. Soft timeout behavior can expose applications to I/O errors and data-integrity risks they were not designed to handle. Select options from workload requirements and current protocol documentation, not impatience during an outage. (R46)

15. 20.5 Samba

Samba provides SMB services on Linux and can participate in several identity roles. A simple standalone share, a domain member, and a domain controller are different designs. This chapter’s example is a standalone file-sharing lab, not instructions for replacing an organization’s identity service.

Samba access depends on both its share policy and the underlying filesystem. Granting access in smb.conf does not bypass Unix permissions or mandatory access control. Conversely, permissive filesystem modes do not necessarily grant access through the share.

Validate a candidate configuration with testparm and inspect the service names supplied by the distribution. On common systems they differ between families. Keep protocol security and supported defaults under review; do not re-enable obsolete SMB versions to accommodate an unexplained client failure. (R47)

18. 20.6 SMB/CIFS

SMB is the protocol family; CIFS is a historical name still present in Linux mount tooling such as mount.cifs. A command containing cifs does not by itself identify the negotiated SMB dialect. Inspect the client’s capabilities and the server’s effective policy.

Credentials supplied directly in a shell command can leak into history or process inspection. A root-owned, mode-0600 credentials file is safer for a narrow lab, while production should use an approved credential-management and authentication design. Protect that file in backup and configuration management as a secret.

Do not confuse client display mappings such as uid= with changing the server’s authorization decisions. Depending on negotiated Unix extensions and server configuration, ownership presentation can differ from server-side identity. Test permitted reads, writes, creates, renames, and deletes through the actual client application.

21. 20.7 Automounting

Automounting activates a mount when its path is accessed rather than necessarily establishing it during boot. This can reduce boot dependencies for optional shares and release idle mounts. It does not make an unavailable server available, nor does it remove application delays on first access.

An automount path should have a clear owner and purpose. Avoid ordinary tools that recursively traverse every mount while diagnosing an unrelated local problem. Such commands can trigger remote mounts or wait on failed servers.

systemd can create automount units from suitable /etc/fstab options, while autofs offers map-based management. Choose one manager for a particular mount point. Two managers trying to control the same directory create confusing ownership of state.

23. 20.8 autofs

autofs uses a master map to associate mount locations with subordinate maps. An indirect map places named shares under a managed parent; a direct map specifies complete mount points. Exact configuration paths and defaults depend on packaging.

For example, a reviewed indirect map might associate /shares with /etc/auto.harbor; that file could name a reports key pointing to the approved server export. This is a relationship to design, not a universal configuration to paste over an existing master map.

After validation and service activation, access the specific path, inspect findmnt, and test idle expiry without leaving shells inside the mounted directory. Record how to diagnose map lookup failures separately from NFS authentication, server availability, and file permission failures. (R48)

26. 20.9 Network Storage Permissions

Trace access through client identity, protocol authentication, share policy, server filesystem permissions, ACLs, and mandatory access control. A failure at any layer can appear to an application as denied access. Identify which layer rejected the operation before expanding privileges.

Numeric UID and GID consistency is especially important for traditional Unix identity sharing. A user called analyst with UID 1100 on one host is not automatically the same identity as analyst with UID 1500 on another. Central identity and tested mapping prevent local naming conventions from becoming an accidental access policy.

For a writeable team share, test inheritance and the lifecycle of a file: creation, editing by another approved user, rename, and removal. Directory permissions control some operations that file modes do not. Never use chmod -R 777 as a substitute for identifying the intended collaborators.

28. 20.10 Troubleshooting Shared Storage

Start by determining whether the expected remote filesystem is actually mounted. A missing mount can leave an ordinary local directory at the same path. An application then writes to the system disk while operators believe it is using network storage.

findmnt --target reports the filesystem containing a path; it does not alone prove that path is the expected mount point. Compare source, type, target, and options. Check name resolution and connectivity to the server, then export/share policy and identity. Use bounded inspection and avoid repeatedly probing a failing mount from many terminals.

A “stale file handle” concerns the client’s reference to an object the server no longer recognizes, not simply an incorrect password. Investigate export changes, replacement filesystems, and recovery events. Remounting may be part of recovery after clients are safely quiesced, but preserve evidence and understand active applications first.

38. Recovery and cleanup

Leave the mounted directory in all shells, stop any consumers, and unmount the exact client path. Remove only the teaching export, reapply exports, and restore the prior firewall configuration. Do not force-unmount a busy production share because the lab used a short cleanup sequence.

For a stronger continuation, arrange central identity and an authenticated NFS security flavor, then repeat access tests with authorized and unauthorized users. That is a separate identity project, not an option that can be enabled without prerequisites.

39. Practice and implementation lab

Write a dependency contract for a report-generating application whose output directory is a network mount. Specify how it detects the wrong mount, what it does during an outage, and how it avoids filling the local root filesystem. Contrast that design with a local spool followed by a separately monitored transfer.

Check your understanding. Is a directory’s existence proof that its share is mounted? No. Does root on a client automatically deserve root access on a server? No. Does automounting remove the need for outage testing? No.

Chapter takeaway. Shared storage is a contract involving identity, remote availability, and file semantics, not just a pathname.
