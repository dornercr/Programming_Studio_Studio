1. Scheduling and Automation

A recurring task is not reliable merely because someone wrote down a time. HarborWorks needs to know which identity runs it, what happens after a missed execution, whether two copies can overlap, and how a failure reaches a person. Scheduling chooses when to start; the program still has to produce a trustworthy result.

4. 15.1 Why Administrators Automate

Automation makes a defined procedure repeatable. It removes forgotten steps and enables review of the exact action. It also repeats mistakes faster than a person, so begin with a bounded, verified manual procedure before giving it a schedule.

Good candidates have clear inputs and outcomes: produce an inventory, check certificate lifetime, or create and verify a backup. “Clean the server” is not a safe requirement because it does not define what may be removed. Specify the permitted target, expected result, failure signal, and rollback before choosing a scheduler.

6. 15.2 Cron

Cron evaluates time expressions and launches commands under the selected account. User crontabs are commonly edited with crontab -e and inspected with crontab -l. Those commands operate on the current user’s table unless an authorized administrator explicitly selects another user.

A cron job does not inherit your interactive terminal’s complete environment. Its shell, PATH, working directory, and available credentials may differ. Use a real script with an explicit interpreter and controlled dependencies rather than a long fragile line. A job working in a terminal is a starting test, not evidence that it works under cron. (R35)

8. 15.3 Crontab Syntax

The usual user-crontab format has five time fields followed by the command: minute, hour, day of month, month, and day of week. 15 3 * * * /absolute/path/report.sh requests a daily run at 03:15 in the scheduler’s effective time zone.

A step is evaluated within its field. */35 * * * * means minute 0 and minute 35 of every hour, not one execution every 35 minutes. In common cron implementations, restricting both day-of-month and day-of-week gives matching behavior that surprises people expecting a simple AND. Percent signs in the command have special meaning unless escaped. Keep complicated date formatting inside the script and consult the installed cron manual. (R35)

10. 15.4 System Cron Jobs

/etc/crontab and files under /etc/cron.d commonly include an additional username field. Copying a user crontab line into a system table without accounting for that field can silently change how the rest of the line is interpreted.

System jobs belong to the configuration-management process. Keep files root-owned and not writable by untrusted users, and observe the implementation’s filename and format rules. Distribution-provided daily or weekly directories may be driven by cron, anacron, or another integration. Inspect the actual scheduling chain before adding a second copy of an existing maintenance job.

12. 15.5 at

at schedules a one-time job where the service is installed and permitted. atq lists queued jobs and atrm JOB_ID removes an identified queued job. This can be useful for a controlled deferred task, but it is not automatically installed on minimal servers.

Document the captured environment and execution identity. A one-time job scheduled after a maintenance window is easy to forget. For a safety rollback, test that the scheduler and recovery command actually function; a queued but unexecutable command is false reassurance. Do not rely on an untested at job as the only protection against remote lockout.

14. 15.6 systemd Timers

A timer activates another unit, usually a service with the same base name. Calendar timers express wall-clock schedules; monotonic timers express intervals relative to events such as boot or a service’s last completion. The service describes the work separately from the timing.

For calendar timers, Persistent=true can trigger an execution after an inactive period when a scheduled event was missed; it does not replay every missed run as a historical queue. RandomizedDelaySec can spread fleet load. A timer does not start another instance of its already-active target service, so do not use RemainAfterExit=yes for a repeating oneshot that should run again. (R35)

17. 15.7 Choosing Cron vs. systemd Timers

Cron is compact and widely familiar. systemd timers integrate execution identity, dependencies, resource controls, journal logging, and service status with the supervisor already used by the teaching systems. Choose based on the operational requirements rather than declaring one tool universally superior.

A portable personal reminder may fit cron. A fleet maintenance task with a timeout, restricted identity, catch-up behavior, and a clear journal trail often fits a timer plus service. Neither scheduler makes the task idempotent or proves its output is valid. Those responsibilities remain in the program and its checks.

19. 15.8 Automating Maintenance

Bound maintenance by target, duration, and load. A log-retention task should operate on explicitly owned logs, not arbitrary files older than a date. A package task should follow repository and reboot policy, not surprise every server with a simultaneous restart.

Check preconditions immediately before doing work. A backup job should confirm the destination is the intended mounted storage, not merely that a directory exists. A job manipulating shared output needs a concurrency design, such as a lock or a transaction. Schedule choice does not solve overlap from manual invocations or a second scheduler.

21. 15.9 Handling Failures

A task needs meaningful exit statuses and a failure path. Retrying a transient network read can help; retrying an invalid configuration indefinitely hides a permanent fault. Use bounded retries with delays, report the final failure, and prevent a fast retry loop from overloading a dependency.

Decide whether a missed successful run is more important than a single failed attempt. A backup may tolerate one retry but not 24 hours without a verified artifact. Alert on the age of the latest successful result, not only the scheduler’s last launch. An OnFailure unit can assist with notification, but only if that notification path is itself implemented and tested.

23. 15.10 Logging Automated Tasks

Log start, end, outcome, and a nonsecret identifier connecting the run to its output. Keep standard error for diagnostic failures and preserve the exit status. Avoid redirecting everything to /dev/null merely to stop unwanted mail.

Cron’s output mail requires a functioning mail arrangement. systemd service output normally reaches the journal, but journal retention and access still matter. Test a deliberate harmless failure and confirm that the intended operator can see it. Automation without observable failure converts a visible chore into a hidden liability.

25. Requirement and simplest approach

Produce a periodic inventory without elevated privileges or writable system state. The companion’s host-report.sh prints identity, kernel, uptime, filesystem capacity, and available network observations. It does not upload anything. Review the report for sensitive host information before sharing it.

A cron line that assumes the author’s PATH and home directory is the simplest approach, but it fails when deployed under a different account. A dedicated service specifies the execution environment more clearly.

31. Verification and recovery

Confirm a scheduled execution appears after the next timer event. To stop scheduling, disable and stop the timer, not just the service. Remove the two dedicated unit files only after stopping the timer, then reload the manager. The task’s logs can remain under normal retention.

32. Practice and implementation lab

Translate a requirement for “one run at 03:15 local time each day” into both cron and timer forms. Explain how daylight-saving changes and missed runs affect the requirement; consult the installed implementation instead of assuming every scheduler behaves identically.

Check your understanding. Does an active timer prove its last job succeeded? No. Does a completed oneshot need to remain active? No. Does */35 mean a fixed 35-minute interval? No.

Chapter takeaway. A scheduled task needs an execution contract, not just a clock expression.
