SLIDE 1: Chapter 45 — Race Conditions

LECTURE NARRATION
A race condition is a logical dependence on timing that violates the intended result. A data race has a specific C++ memory-model meaning involving conflicting accesses without the required ordering, with at least one access non-atomic. Data races cause undefined behavior; logical races can also occur in programs that use atomics and contain no data race. [ R22 ]

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. When this topic appears in real systems code, separate what the language guarantees from what a compiler, operating system, ABI, ISA, or particular machine happens to do. Then identify the evidence you would inspect to test the claim without overgeneralizing from a single successful run.

SLIDE 4: 45.1 Shared state

LECTURE NARRATION
Shared state is information accessible to multiple activities. Mutable shared state requires a policy: one owner, a lock, atomic operations, or another proven protocol. The policy should cover related fields together when their relationship forms an invariant. A common design improvement is to reduce sharing. Give each worker a private accumulator, use immutable messages, or transfer ownership through a queue. Eliminating a shared write is often simpler than coordinating it correctly.

SLIDE 6: 45.2 Conflicting accesses

LECTURE NARRATION
Two accesses conflict when they target overlapping memory in a way relevant to the language rules and at least one modifies state or affects object lifetime. Two ordinary reads can coexist when the object is safely initialized and remains alive. Different source-level variables can still interact through aliasing or overlapping storage. Conversely, distinct non-bit-field array elements are separate memory locations for ordinary concurrent-access reasoning. Hardware cache-line sharing is a performance concern distinct from language-level location identity.

SLIDE 8: 45.3 Race conditions

LECTURE NARRATION
A check-then-act sequence can race even when each individual check and update is atomic. Two customers may both observe the last item as available and each reserve it unless the combined transaction is coordinated. Define the intended indivisible operation. Is it one counter increment, a transfer between two accounts, or removal of one queue item together with count adjustment? Synchronization must protect that semantic unit, not merely surround an arbitrary convenient statement.

SLIDE 10: 45.4 Data races

LECTURE NARRATION
In C++, conflicting accesses in different threads require the appropriate happens-before relationship unless the accesses are covered by the atomic rules. A non-atomic shared counter increment without synchronization is not merely allowed to lose updates; the program has undefined behavior. Do not use a run that “usually prints the expected number” as evidence of correctness. Compiler transformations and hardware execution are constrained by the language’s defined programs, not by a programmer’s preferred interleaving of an undefined one. ThreadSanitizer can help detect observed races but cannot prove their absence on every path. [ R6 ]

SLIDE 12: 45.5 Atomicity

LECTURE NARRATION
Atomicity means that an operation is indivisible with respect to the relevant observers and model. An atomic load and an atomic store are individually indivisible, but the pair is not automatically one atomic read-modify-write transaction. Atomicity also has scope. An atomic integer operation does not make a neighboring ordinary structure update safe. A transaction spanning several objects generally needs a broader synchronization protocol or carefully designed multi-object algorithm.

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. SLIDE 14: 45.6 Critical sections

LECTURE NARRATION
A critical section is code that accesses state under an exclusion or coordination rule. Its boundaries should preserve the state invariant: acquire the protection, inspect and update related fields, restore a consistent state, then release. Keep blocking I/O and unknown callbacks outside a lock when possible, but do not shorten the section by moving required validation outside and reintroducing a race. Performance changes must preserve the same indivisible logical operation.

The second phase uses fetch_add , which performs one atomic read-modify-write per increment. Companion listing: ch45/logical_race.cpp The expected output is load/store=1 fetch_add=2 . Every counter access is atomic, so the first phase has no C++ data race. It is still the wrong implementation of “count two increments.” Strong default memory ordering does not combine separate operations into a transaction. The barrier makes the failure deterministic and inspectable. This is preferable to a demonstration that runs undefined code repeatedly and hopes to display a surprising number.

SLIDE 18: Worked example — Lost update race

LECTURE NARRATION
Two threads both execute counter++ on an ordinary shared integer initially zero. Each increment conceptually reads, adds one, and writes. If both read zero before either writes, both can store one, so the final value is one rather than two. The operation is not atomic merely because it appears as one source expression.

SLIDE 20: Worked example — Critical-section repair

LECTURE NARRATION
Protecting the increment with the same mutex makes the read-modify-write sequence mutually exclusive. Thread A locks, reads zero, stores one, unlocks; only then can thread B enter and produce two. The lock protects the invariant that no two threads update the counter simultaneously.
