SLIDE 1: Chapter 9 — Dynamic Memory

LECTURE NARRATION
Dynamic storage is useful when size or lifetime cannot be fixed at a local scope boundary. It also introduces an explicit responsibility: somebody must keep the storage alive while it is used and release it exactly once afterward. The allocation function is only the beginning of that responsibility.

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. SLIDE 4: 9.1 Heap allocation

LECTURE NARRATION
A heap allocation requests a region large enough and suitably aligned for a purpose. The allocator may satisfy the request from existing free space or obtain more backing storage. Allocation can fail because of size limits, fragmentation, policy, or resource exhaustion. A successful request for raw storage does not necessarily mean every page has already been physically committed or touched. Nor does it initialize arbitrary C++ objects by itself. Separate storage acquisition, object initialization, use, destruction, and storage release. This sequence helps explain both raw allocation APIs and higher-level containers.

SLIDE 6: 9.2 malloc

LECTURE NARRATION
malloc(n) requests at least n bytes of storage and returns a suitably aligned pointer for the supported ordinary object alignments, or a null pointer on failure. The returned bytes are not initialized. In C, assignment through an appropriately typed pointer can establish the intended object use within the language’s effective-type rules. Compute n safely before calling. Use sizeof *pointer rather than repeating a type name when it reduces maintenance risk. A zero-size request has special behavior that should not be used as an application control signal. Handle an empty collection explicitly so the ownership rules do not depend on a zero-size allocation convention. [ R39 ]

SLIDE 8: 9.3 calloc

LECTURE NARRATION
calloc(count, size) requests storage for an array and zeroes the allocated bytes. Its separate count and size arguments allow the implementation to detect multiplication overflow. The application still needs semantic bounds, because a representable request may be far larger than policy permits. All-zero bytes are not a universal initializer for every possible object representation. On the reference platform they represent zero for ordinary integer storage, but portable C does not equate zero bytes with every null pointer or floating-point zero representation. In C++, use constructors and value initialization for objects rather than treating calloc as a replacement for object semantics.

SLIDE 10: 9.4 realloc

LECTURE NARRATION
realloc changes the size of a previously allocated block while preserving the common prefix of the old and new sizes. It may move the block. For a nonzero requested size, failure leaves the original allocation available. Success ends the old allocation’s role and returns the pointer to use afterward. Store the result in a temporary pointer. Assigning directly to the only owning pointer can lose the original allocation on failure. After success, old aliases must not be used, even if the returned numeric address happens to match. Avoid realloc(p, 0) in portable application logic because its historical and language-version semantics are troublesome; use an explicit free-and-empty path instead.

SLIDE 12: 9.5 free

LECTURE NARRATION
free releases a block obtained through the matching allocation family. Passing a null pointer has no effect. Passing an interior pointer, a pointer to automatic storage, or an already freed pointer violates the contract. The allocator needs the original allocation identity, not merely an address somewhere inside its payload. Freeing storage does not guarantee that its bytes are erased or that the operating system immediately reclaims its pages. Do not use free as a data-sanitization operation. More importantly, do not read the bytes after release merely because a debugger still shows the old contents. The lifetime boundary is semantic, not a visible overwrite event.

SLIDE 14: 9.6 new

LECTURE NARRATION
A C++ new expression obtains storage and initializes an object. Ordinary allocation failure throws std::bad_alloc ; a nothrow form can return null. If construction throws after storage acquisition, the language arranges the matching cleanup for that failed construction path. Prefer std::make_unique for unique dynamic ownership and containers for collections. A raw new is sometimes needed inside a low-level abstraction, but it should not force every caller to reason about cleanup. The distinction between an allocation function named operator new and a complete new expression also matters: the former obtains storage, while the latter includes object initialization.

SLIDE 16: 9.7 delete

LECTURE NARRATION
A delete expression destroys the object and releases its storage through the matching mechanism. Scalar new matches scalar delete ; array new[] matches delete[] . Mixing allocation families, such as malloc with delete , is invalid. Deleting through a base-class pointer requires appropriate polymorphic destruction when the dynamic object is derived. A base intended for such ownership generally needs a virtual destructor. Resource ownership through a pointer is therefore a type-design issue as well as an allocator issue. A correct address with the wrong destruction interface is still unsafe.

SLIDE 18: 9.8 Allocation lifetime

LECTURE NARRATION
An allocation’s lifetime must cover every use of its storage. Borrowed pointers into a resizable allocation have especially fragile lifetimes because growth can move the block. A function that returns an interior pointer should document which operations invalidate it. Group objects with the same lifetime when that simplifies ownership. A request-scoped arena can release many short-lived allocations together. A vector can own a sequence whose elements move as one resource. Avoid creating a separate ownership obligation for every small object unless independent lifetimes are actually needed.

SLIDE 20: 9.9 Ownership

LECTURE NARRATION
Ownership identifies the component responsible for destruction and release. Unique ownership has one responsible owner. Shared ownership coordinates several owners, commonly with reference counting. Borrowing grants access without release responsibility. Shared ownership is not free and does not automatically make the object thread-safe. A reference count protects lifetime, not arbitrary member updates. Cycles can also prevent reclamation unless broken by weak references or another policy. Choose the simplest ownership model that matches the required lifetime graph; do not use shared ownership merely to avoid deciding who owns a resource.

SLIDE 22: Worked example — Growing a C buffer without losing ownership

LECTURE NARRATION
The requirement is to grow a four-integer allocation to eight integers. If growth fails, the original allocation must remain releasable. The program uses fixed small sizes so the example can focus on ownership rather than input parsing. Companion listing: ch09/grow.c Before growth, four initialized elements exist. On success, the first four values are preserved, but the new suffix is not initialized by realloc ; the program initializes it before reading. Only after that does it update the logical count. The sum is 1+2+3+4+5+6+7+8 = 36 . The failure branch releases the original pointer. The success branch adopts the returned pointer and never compares or uses stale aliases. A production growable buffer would also check multiplication, enforce a capacity limit, and avoid updating its public state until all required initialization succeeds.

SLIDE 24: Worked example — Growing a dynamic array safely

LECTURE NARRATION
If p owns a malloc allocation, do not write p = realloc(p,new_size) unless losing the old block on failure is acceptable. Use tmp = realloc(p,new_size) . If tmp is non-null, assign p=tmp ; otherwise p still owns the original allocation. The temporary preserves ownership across the failure path.

SLIDE 26: Worked example — Matching allocation families

LECTURE NARRATION
Memory obtained with malloc must be released with free ; an object created with new T must be released with delete ; an array created with new T[n] requires delete[] . Mixing families bypasses the assumptions each runtime uses for metadata and object destruction. In modern C++, prefer RAII containers and smart pointers so matching happens structurally.
