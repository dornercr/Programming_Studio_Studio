SLIDE 1: Chapter 52 — Concurrent Servers

LECTURE NARRATION
A concurrent server handles overlapping client lifecycles while sharing finite resources. The architecture must balance simplicity, throughput, latency, isolation, and failure containment. The most important scaling question is not “How many threads can I create?” but “What resources does one admitted connection consume, and what happens when the budget is exhausted?”

SLIDE 4: 52.1 Thread-per-connection

LECTURE NARRATION
A thread-per-connection design assigns a worker to each accepted client. Blocking I/O becomes straightforward because one slow connection blocks its own worker rather than the entire server loop. The control flow resembles a sequential protocol handler. The cost grows with active connections: thread stacks, scheduler state, per-connection buffers, and synchronization overhead accumulate. An unbounded thread-per-connection loop can exhaust resources before useful work completes. Bound admission and ensure every thread is joined or otherwise owned through shutdown.

SLIDE 6: 52.2 Connection state

LECTURE NARRATION
Connection state includes protocol progress, input and output buffers, authentication or session information, deadlines, and lifecycle status. A connection may be reading a prefix, reading a body, computing a response, writing a partial response, or closing. Make state transitions explicit. “Socket exists” is not enough to determine which operation is valid next. A half-closed connection can still have data to drain or a response to send, depending on the protocol. Cleanup should occur only when no worker or event handler can still reference the connection object.

SLIDE 8: 52.3 Shared resources

LECTURE NARRATION
Connections compete for descriptors, memory, CPU, downstream services, caches, and application data. Per-connection limits do not replace global limits. A thousand individually acceptable requests can collectively overwhelm a shared database or work queue. Define budgets at each stage. An accepted socket may count against a connection limit, a parsed request against a queued-work limit, and an executing task against a worker limit. Transfer the corresponding ownership credits when work moves between stages, and release them on every failure path.

SLIDE 10: 52.4 Synchronization

LECTURE NARRATION
Shared application state requires the same synchronization rules developed in Parts X and XI. A server should avoid holding global locks while waiting for a client or downstream service. Slow external activity inside a critical section can stall otherwise independent clients. Use snapshots, immutable request objects, and bounded queues to separate I/O from protected updates. A worker pool limits simultaneously executing handlers, but an unbounded queue in front of it can still consume unlimited memory and produce extreme waiting times.

SLIDE 12: 52.5 Resource exhaustion

LECTURE NARRATION
Exhaustion occurs when demand exceeds a resource limit. Symptoms include failed thread creation, descriptor exhaustion, allocation failure, long queues, and timeout cascades. Rejecting or deferring work deliberately is often safer than accepting everything and failing unpredictably later. A robust policy specifies admission limits, maximum frame sizes, idle and whole-request deadlines, output-buffer limits, and shutdown behavior. Per-operation socket timeouts alone do not defeat a client that makes tiny amounts of progress just before each timeout; a whole-request deadline bounds the complete transaction.

SLIDE 14: Worked example — Derive an admission budget

LECTURE NARRATION
Assume a hypothetical service budget , not a measurement of the host system: The descriptor bound is 1024 - 64 = 960 clients when each client uses one descriptor. The modeled per-client memory is 72 KiB. The remaining memory is 96 MiB, which permits floor(96 × 1024 / 72) = 1365 clients under those assumptions. The combined arithmetic ceiling is therefore 960. Choosing an operational cap of 256 leaves headroom. Its modeled client memory is 256 × 72 KiB = 18 MiB ; adding the 32-MiB base gives 50 MiB. This does not include every possible kernel buffer or thread reservation. The assumptions must be replaced with measurements and explicit accounting before using the number as a deployment limit. The code verifies the budget calculation, not a claim that 960 live threads or clients are safe on the current machine. Real thread stack reservation and committed use are distinct quantities, and downstream capacity may impose a much lower cap.

SLIDE 16: Worked example — Thread-per-connection budget

LECTURE NARRATION
If each connection thread reserves an 8 MiB stack, 1,000 concurrent connections can imply roughly 8 GiB of virtual stack reservation before application buffers and kernel state. Even when pages are demand allocated, this architecture has scaling costs. Admission limits and smaller controlled stacks can matter as much as CPU throughput.

SLIDE 18: Worked example — Shared cache synchronization

LECTURE NARRATION
A concurrent server may let every connection consult a shared in-memory cache. Reads and updates need a synchronization strategy: a mutex, reader-writer scheme, sharding, or another concurrency-safe design. Per-connection threading does not make shared application state private.
