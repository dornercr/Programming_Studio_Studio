SLIDE 1: Chapter 11 — Memory Errors

LECTURE NARRATION
Memory errors are violations of object boundaries, lifetime, initialization, or ownership. Their visible symptoms can occur far from their cause. A write beyond one buffer may corrupt a pointer that fails minutes later. The most effective debugging approach identifies the first invalid operation rather than explaining only the final crash.

SLIDE 4: 11.1 Buffer overflow

LECTURE NARRATION
A buffer overflow writes more data than a buffer can hold. The relevant bound is the actual destination capacity, not a claimed input length. A safe copy needs agreement among source availability, destination capacity, and requested count. String operations add another requirement: space for the terminator when the result must be a C string. A ten-character payload needs eleven bytes in that representation. Prefer length-aware interfaces and verify arithmetic before allocation. A bounded function can still be misused if the supplied bound describes the source instead of the destination.

SLIDE 6: 11.2 Out-of-bounds access

LECTURE NARRATION
An out-of-bounds read or write accesses outside an object’s permitted range. Reads matter as much as writes: they can disclose data, fault, or influence control flow using unrelated bytes. A read that remains within a mapped page can still violate the language’s rules. Check indices before forming an invalid pointer. For a region described by offset and length, use the guarded subtraction pattern from Chapter 4. In multidimensional code, validate every dimension and stride relationship. A valid row index does not rescue an invalid column index that happens to land inside neighboring storage.

SLIDE 8: 11.3 Memory leaks

LECTURE NARRATION
A leak occurs when storage remains allocated without a reachable ownership path that will release it when required. Losing a pointer is a common cause, but a reachable container that grows forever can also create a practical retention problem even when a leak detector sees it as reachable memory. Distinguish accidental leaks from intentional caches and from unbounded retention. Measure live object counts and ownership paths, not only process resident size. A cache needs a limit and eviction policy. An ownership cycle needs a way to break the cycle. “The operating system frees it at exit” does not justify unbounded growth in a long-running service.

SLIDE 10: 11.4 Double free

LECTURE NARRATION
A double free releases the same allocation more than once. It often arises when two components both believe they own a raw pointer, or when a cleanup path runs after an earlier release without updating ownership state. The repair is a single ownership protocol, not merely adding scattered null checks. After ownership transfer, the previous owner must no longer release. In C++, move-only resource wrappers make this rule visible in the type system. In C, document transfer and reset the owning state in a disciplined way while remembering that unrelated aliases remain unchanged.

SLIDE 12: 11.5 Invalid free

LECTURE NARRATION
An invalid free passes a pointer that is not a currently releasable allocation from the matching family. Interior pointers, stack addresses, and pointers from a different allocator are common examples. The allocator’s metadata lookup can be corrupted or confused by such inputs. A function returning a borrowed interior pointer should not expose an interface that suggests ownership. Name and document it as a view. Where several allocators exist, keep the release operation with the owner or use a deleter that records the matching mechanism. Allocation provenance is part of the resource contract.

SLIDE 14: 11.6 Use-after-free

LECTURE NARRATION
Use-after-free accesses storage after its allocation has been released. The storage may retain old bytes, be reused for a different object, or become inaccessible. None of those physical outcomes restores the old access’s validity. Concurrent use-after-free is especially subtle. One thread can validate a pointer while another releases the target before the first dereferences it. Protect the lifetime across the entire access interval with ownership, locking, or a carefully designed reclamation scheme. Atomic pointer loads alone do not keep the pointed-to object alive.

SLIDE 16: 11.7 Dangling pointers

LECTURE NARRATION
A dangling pointer or reference outlives the object it designates. It can result from returning a local address, destroying an owner, reallocating a vector, or resetting an arena. The pointer variable itself may remain perfectly intact. Track invalidation events in interface documentation and code review. A function that returns a view into a container should specify which mutations invalidate it. Avoid storing borrowed views in long-lived objects unless the owner’s lifetime relationship is explicit and enforceable. Lifetime bugs become easier to prevent when the design limits how far a borrow can travel.

SLIDE 18: 11.8 Uninitialized memory

LECTURE NARRATION
Raw allocation does not initialize its payload, and many automatic scalar declarations do not establish a usable value. Reading an indeterminate scalar value is generally invalid in the language modes used here, with narrow special rules that are not a basis for ordinary application logic. Initialize before use, but do not confuse initialization with semantic validation. A zeroed length can be a valid default while a zeroed state tag may still be invalid for the protocol. Tools for uninitialized-value tracking complement address sanitizers because staying within allocated storage does not guarantee that the bytes have been meaningfully initialized.

SLIDE 20: 11.9 Undefined behavior

LECTURE NARRATION
Undefined behavior means the language imposes no requirements on the program’s behavior for the offending execution. It is not a promise to wrap, crash, throw, or continue with a random value. Optimizations can rely on the assumption that valid programs do not perform the invalid operation. This is why an apparently harmless out-of-bounds access can change unrelated-looking code after optimization. The right response is to remove the invalid operation, not to demand that the compiler preserve one observed accident. Debug and release builds are different experiments; both must implement a program whose source-level behavior is defined.

SLIDE 22: 11.10 Sanitizers

LECTURE NARRATION
AddressSanitizer instruments memory accesses and allocation boundaries to detect classes such as heap and stack out-of-bounds access and use-after-free. UndefinedBehaviorSanitizer targets selected language violations. ThreadSanitizer tracks data races. Their coverage and limitations differ, and some configurations cannot be combined. [ R5 , R6 ] A clean sanitizer run covers only executed paths and the checks enabled in that build. Some lifetime, intra-object, protocol, and logical errors remain outside a tool’s detection. Use sanitizers alongside warnings, tests, fuzzing of parsers, ownership design, and review. Instrumented performance is not production performance.

SLIDE 24: Worked example — Replacing an unchecked copy contract

LECTURE NARRATION
The requirement is to copy exactly the available source bytes into a destination only when the destination is large enough. Failure must leave the destination unchanged. A bounded range interface makes both extents explicit. Companion listing: ch11/bounded_copy.cpp The three-byte source cannot fit in the two-byte destination. The function rejects the request before writing anything. The exact-size destination succeeds, and every byte is compared against the source. The interface explicitly requires nonoverlapping ranges; supporting overlap would call for a different copy contract, such as an appropriately bounded memmove operation. This example addresses one class of failure without claiming to validate arbitrary pointers. The spans must already describe live accessible objects. A size check cannot repair a dangling span. Safety comes from combining ownership, valid range construction, and local bounds checks.
