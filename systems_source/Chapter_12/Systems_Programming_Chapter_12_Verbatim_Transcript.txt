SLIDE 1: Chapter 12 — Instruction Set Architecture

LECTURE NARRATION
The instruction set is the boundary between software’s requested operations and a processor’s implementation. It describes registers, instructions, address calculations, and architectural effects. It does not specify that every instruction takes one cycle or that internal work occurs in source order. Reading assembly well requires keeping the architectural result separate from the microarchitectural method.

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. When this topic appears in real systems code, separate what the language guarantees from what a compiler, operating system, ABI, ISA, or particular machine happens to do. Then identify the evidence you would inspect to test the claim without overgeneralizing from a single successful run.

SLIDE 4: 12.1 Machine instructions

LECTURE NARRATION
A machine instruction is an encoded operation the processor recognizes. It identifies an operation and, explicitly or implicitly, its operands. Instructions can move data, perform arithmetic, change control flow, or request privileged behavior. On x86-64, instructions have variable-length encodings rather than one fixed size. The visible instruction sequence is not necessarily the processor’s internal execution sequence. A processor may decode instructions into smaller operations, overlap independent work, and speculate past branches. Architectural rules determine what results may become visible. An assembly listing is therefore a semantic description and an input to performance analysis, not a cycle-by-cycle hardware trace.

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. SLIDE 6: 12.2 Registers

LECTURE NARRATION
Registers are named architectural storage locations used directly by instructions. General-purpose registers hold integer values and addresses. Other register classes support vector, floating-point, control, and status operations. Keeping a value in a register can avoid a memory access, but the number and use of registers are constrained by the ISA and ABI. Architectural register names need not correspond one-to-one with fixed physical storage inside a modern processor. Register renaming can map successive architectural values to different physical registers. This helps remove false dependencies while preserving the program’s required register behavior. Source-level programmers normally need the architectural model first and the renaming model only for deeper performance work.

SLIDE 8: 12.3 Memory

LECTURE NARRATION
Instructions access memory through effective addresses computed from available operands. A load brings a value into a register or another destination; a store writes a value to memory. Some x86 instructions combine memory access with arithmetic, but that does not eliminate the underlying data movement. A memory operand can involve address translation, cache lookup, coherence, and fault checks. Two instructions with similar arithmetic can have very different costs if one waits for a cache miss. Count memory traffic and dependencies, not just mnemonics, when estimating performance.

SLIDE 10: 12.4 Program counter

LECTURE NARRATION
The program counter identifies the instruction position used for control flow. On x86-64 the architectural instruction pointer is %rip . Sequential execution advances to the next instruction; branches, calls, returns, and exceptions change the flow according to their rules. For RIP-relative addressing, the displacement is interpreted relative to the next instruction’s address. This detail matters when manually calculating a target from disassembly. The value displayed beside an instruction is usually its own starting address, not necessarily the base used in that instruction’s relative-address computation.

SLIDE 12: 12.5 Processor state

LECTURE NARRATION
Processor state includes more than general-purpose registers. It can include condition flags, vector registers, floating-point control state, stack state, privilege state, and address-translation configuration. The exact state relevant to an operation depends on the architecture and execution context. A context switch must preserve enough state for a thread to resume as though its execution had been paused. A normal function call has a narrower contract: the calling convention specifies which registers the caller or callee must preserve. Confusing a context switch with a function call leads to incorrect assumptions about who saves what.

SLIDE 14: 12.6 ISA versus microarchitecture

LECTURE NARRATION
The ISA specifies architectural behavior. The microarchitecture is the implementation: pipelines, execution units, caches, predictors, queues, and scheduling logic. Different processors can execute the same binary while exhibiting different latency, throughput, and energy behavior. An optimization based on a particular instruction cost may not transfer to another processor implementing the same ISA. The portable part of the reasoning is the algorithm and architectural semantics; the measured part belongs to a specific machine and workload. The Intel architecture manuals separate instruction behavior from implementation-oriented performance guidance. [ R3 ]

SLIDE 16: Worked example — Tracing a tiny abstract machine

LECTURE NARRATION
Use a deliberately simplified machine with one accumulator, a program counter, and four instructions: load immediate, add immediate, multiply immediate, and halt. This is a teaching model, not x86 assembly. Companion listing: ch12/machine.py The trace is (1,6) , (2,10) , and (3,30) . Each pair records the next instruction index and accumulator after one operation. The halt instruction leaves the final pair unchanged. The model makes control and data state explicit, but it intentionally omits fixed-width overflow, memory, interrupts, and timing. Now imagine an implementation that computes the addition and multiplication through several internal steps. As long as the architectural result at each required boundary is preserved, those internal steps need not resemble this simple interpreter. That is the distinction between an ISA-level explanation and an implementation-level explanation.

SLIDE 18: Worked example — Separating ISA from implementation

LECTURE NARRATION
Two processors can both implement x86-64 and execute the same architectural instruction stream while using different pipelines, cache sizes, branch predictors, and execution widths internally. The ISA specifies programmer-visible behavior; the microarchitecture determines how a particular implementation achieves it. Performance differences therefore do not imply different source-level semantics.

SLIDE 20: Worked example — Updating architectural state

LECTURE NARRATION
For an instruction conceptually equivalent to RAX = RAX + RBX , the visible result is a new RAX and updated condition flags according to the instruction definition. Internally the processor may rename registers and execute out of order, but retirement preserves the architectural effect as though the instruction completed in program order, subject to the machine’s defined memory model.
