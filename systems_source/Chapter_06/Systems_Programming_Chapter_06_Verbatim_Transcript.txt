SLIDE 1: Chapter 6 — Memory Layout

LECTURE NARRATION
Layout translates logical objects into byte positions. It determines array strides, structure offsets, alignment requirements, and how a binary dump appears. Layout also affects performance, but its first obligation is correctness: every access must refer to the intended live object with a suitable type and alignment.

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. SLIDE 4: 6.1 Arrays

LECTURE NARRATION
Array elements occupy adjacent storage with no extra gap between complete elements beyond each element’s own size. If the element type includes padding, that padding is included in the stride. An array of structures therefore repeats the full structure size, not just the sum of useful field bytes. Contiguity supports efficient traversal and simple address calculations. It also means one out-of-bounds write can reach a neighboring element or another object. The fact that a numeric address lies near valid storage does not make it part of the array. Bounds come from the object, not from what the surrounding memory happens to contain. The element size is sizeof(element_type) . In int a[10] on a platform with four-byte int , the array occupies 40 bytes. In struct Record a[10] , each step uses sizeof(struct Record) , including any tail padding needed to align the next record. A pointer alone does not retain the number of elements. Keep count and capacity with the allocation, or use a container or span. When reading a file of fixed-size records, check both that the total byte count fits and that any required record-size divisibility holds. A leftover partial record is a format error, not an invitation to read beyond the buffer. For a one-dimensional array, address(a[i]) = base + i*sizeof(T) . This is a mathematical address model; source-level pointer arithmetic still requires i to identify an element or the permitted one-past position. To access an element, require i < count . Suppose the base is 0x2000 and each element is eight bytes. Element 5 begins at 0x2028 , because 5 × 8 = 40 = 0x28 . This simple calculation recurs in assembly scaled indexing, structure arrays, file offsets, and cache-line analysis. Always state whether the index counts elements or bytes. A built-in C or C++ array such as int a[3][4] is an array of three arrays, each containing four integers. Its rows are contiguous, and elements within a row are contiguous. With four-byte integers, the address of a[r][c] is modeled as base + (r*4 + c)*4 for valid indices. This is not the same representation as int** , which points to pointers and may describe separately allocated rows. Do not cast between them as a shortcut. For generic matrix interfaces, pass dimensions and strides explicitly or use a suitable multidimensional view. A stride describes layout; it does not itself establish ownership or bounds.

SLIDE 6: 6.2 Structures

LECTURE NARRATION
Structures place members in an implementation-defined layout subject to language constraints. In ordinary C structures, members follow declaration order with possible padding. C++ standard-layout types provide the predictable subset needed for facilities such as offsetof ; inheritance, virtual functions, and other class features add additional rules. Use offsetof and sizeof when inspecting a supported type rather than guessing from field names. A debugger’s display can show logical members without exposing all padding. When interfacing with hardware or a file format, prefer an explicitly decoded representation over assuming that an ordinary structure matches the external bytes. A type’s alignment constrains the addresses at which its objects may be placed. If a four-byte-aligned member follows a one-byte member, the implementation may insert three padding bytes before it. The enclosing structure’s alignment generally accommodates its most demanding member on the reference ABI. Alignment is both a language validity requirement and an implementation consideration. An x86 instruction’s ability to load an unaligned address does not make an improperly aligned C++ T* access valid. Use byte copying to an aligned object when decoding data at arbitrary byte offsets. Internal padding lies between members; tail padding follows the final member so array elements begin at suitable alignments. Padding bytes do not necessarily have stable values. Comparing whole object representations with memcmp can therefore disagree with memberwise equality. Padding also matters at trust boundaries. Sending an uninitialized structure’s full storage can disclose residual bytes even when every named field has been assigned. Zeroing storage is not a substitute for a stable external format, but explicit field encoding avoids both the layout dependency and accidental padding disclosure.

SLIDE 8: 6.3 Unions

LECTURE NARRATION
Union members overlap. Only enough storage for the largest and most aligned alternative is needed, subject to padding. A tagged union pairs that storage with a discriminator indicating which alternative is active. The discriminator and active object must agree at every interface boundary. Changing the tag without constructing or assigning the appropriate alternative can leave a logically impossible state. In C++, nontrivial member lifetimes make manual unions especially delicate. std::variant packages the tag and lifetime management when its cost and behavior fit the requirement. A union does not create several independent values in the same bytes. It supplies alternative interpretations subject to language rules. Reading a member different from the one most recently established is not a general portable way to reinterpret arbitrary C++ objects. For a representation copy between suitable trivially copyable types of equal size, C++20 provides std::bit_cast ; memcpy is also useful for byte transport. These operations still require valid representations for the intended use. No copying technique can turn arbitrary untrusted bits into a valid pointer or a well-formed complex object merely by avoiding an aliasing violation.

SLIDE 10: 6.4 Endianness

LECTURE NARRATION
In little-endian storage, the least significant byte of a multi-byte value is at the lowest address. A 32-bit value 0x12345678 appears in increasing addresses as 78 56 34 12 . The reference x86-64 platform uses this ordering for ordinary integer storage. The numeral 0x12345678 itself has not changed. Endianness describes the mapping between the value’s bytes and memory addresses, not the written order of digits in a debugger’s integer display. Inspect bytes explicitly when diagnosing a format mismatch. In big-endian storage, the most significant byte is at the lowest address. The same 32-bit value appears as 12 34 56 78 . Many network protocol fields use a specified big-endian order, often called network byte order. A format can also choose little endian or define fields byte by byte. The important property is agreement, not that one order is inherently more correct. Convert at the boundary and keep internal computation in the language’s ordinary value types whenever possible. A portable decoder assembles a value from explicitly ordered bytes. For a four-byte big-endian field, the value is (b0<<24) | (b1<<16) | (b2<<8) | b3 , with each byte converted to a sufficiently wide unsigned type before shifting. The widening is essential. A small byte can undergo signed integer promotion, and shifting into an unsuitable signed range can be invalid in some language modes. A clear decoder validates that four bytes are present, widens them, combines them, and then checks the resulting semantic value. That sequence keeps bounds, representation, and meaning separate.

SLIDE 12: 6.5 Alignment

LECTURE NARRATION
“Natural alignment” usually refers to an alignment convenient for a type’s ordinary machine accesses, often related to its width. It is not one universal language rule saying every n -byte type must be aligned to n bytes. Query the implementation with _Alignof in C or alignof in C++. Over-aligned objects require allocation that honors their larger alignment. Ordinary raw byte buffers or a custom allocator may not suffice. A placement construction does not repair an unsuitable address. The storage provider and object constructor must agree on both size and alignment. To round an offset upward to alignment a , a general mathematical expression is ceil(offset/a)*a . For a power-of-two alignment, (offset + a - 1) & ~(a - 1) is a common bitwise form, but the addition must be checked for overflow and a must be nonzero and a power of two. An allocator must account for both the alignment gap and the payload size before returning storage. Rounding first and checking only the payload can miss an overflow or exceed the arena. Chapter 10 develops this as an allocator invariant rather than treating alignment as a cosmetic adjustment. Aligned accesses can reduce the chance of crossing cache-line or page boundaries and may be required by particular instructions. Unaligned accesses on x86-64 are often supported, but their cost depends on width, boundaries, cache state, and instruction choice. “Unaligned is always slow” is too broad, while “x86 allows it, so it is free” is equally misleading. Layout also affects useful bytes per cache line. Reordering members can reduce padding, but changing a public structure can break an ABI or file format. Measure the internal performance benefit and identify every external consumer before changing layout. Correctness and compatibility are constraints on optimization.

SLIDE 14: Worked example — Accounting for every byte

LECTURE NARRATION
Consider a reference-platform structure containing a one-byte kind, a four-byte length aligned to four bytes, and a two-byte flags field aligned to two bytes. The kind begins at offset 0. Offsets 1 through 3 are padding. The length begins at 4 and occupies four bytes. Flags begins at 8 and occupies two bytes. Two tail-padding bytes make the total size 12 and keep an array’s next element four-byte aligned. Companion listing: ch06/layout.c On the stated reference layout, the output is size=12 align=4 and kind=0 length=4 flags=8 . The program reports actual implementation values rather than forcing those expectations on every C implementation. Reordering the fields as length, flags, kind commonly reduces the size to eight bytes on this ABI: four bytes, then two, then one, then one tail-padding byte. An array of one million records would then use about four million fewer bytes. That is a derived storage saving, not a measured speedup. The changed member offsets also mean the two structures are not binary-compatible layouts.

SLIDE 16: Worked example — Computing an array address

LECTURE NARRATION
If an array of 32-bit integers begins at address 0x1000 , element 7 begins at 0x1000 + 7 × 4 = 0x101C . The multiplication by element size is implicit in C and C++ pointer arithmetic: &a[7] equals a + 7 . This scaling is why adding one to an int* advances by sizeof(int) , not one byte.
