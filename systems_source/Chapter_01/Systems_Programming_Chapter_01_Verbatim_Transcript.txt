Section: CHAPTER 1 · GRADUATE LECTURE
Source mapping: original slide(s) 1.

Graduate lecture narration
A useful systems explanation is more precise than saying that the computer runs the code. We want to identify which component translates a representation, which component owns a resource, and which interface guarantees a particular result. Chapter 1 gives us the mental model for doing that. We will follow a small C program from source files to observable output, then ask what build success, a successful launch, and a successful test actually establish. These are different claims.

A program is not just a list of commands. Many parts work together, and each part has rules the others must follow.

03. Turn a claim into a testable argument
Section: GRADUATE METHOD
Source mapping: original slide(s) 2, 5, 19.
Graduate extension: added analysis, teaching model, diagnostic method, or exercise.

Graduate lecture narration
Consider the statement that our program printed 42. It reports an observation, but it does not specify the input domain, the compiler assumptions, or whether an invalid memory access occurred on the way to that output. A stronger argument separates a contract, assumptions, and evidence. The contract says what counts as correct. Assumptions identify the conditions under which the reasoning applies. Evidence is what we inspected or measured.

These categories prevent two common mistakes. First, a useful test result is not a universal proof. Second, a documented guarantee is not a measured performance result. During the lecture, attach each conclusion to its boundary: language, binary interface, operating system, or hardware. If the observation conflicts with the prediction, revise the model or inspect a lower-level artifact rather than inventing a promise that the interface never made. This framework is an instructional elaboration of the original chapter's contract model.

Sixth-grade explanation
Do not stop at “it worked.” Say what you expected, what had to be true, and what you checked.

Discussion / pause
What is missing from the claim “the executable ran successfully”?

Expected response: The success criterion, input domain, environmental assumptions, and evidence beyond that one run.

04. Hardware: compute, state, and movement
Section: 1.1.1 · HARDWARE & SOFTWARE
Source mapping: original slide(s) 3.

Graduate lecture narration
The original chapter begins with a deliberately simplified CPU-memory-I/O model. CPU cores execute instructions, registers hold working state, memory holds addressable instructions and data, and controllers connect devices to the rest of the machine. Storage and peripherals have different purposes and access mechanisms from registers. Buses and interconnects carry requests and data among these components.

Use this picture to ask three questions: where does a value currently exist, which component initiates its movement, and what event tells another component that progress occurred? The picture is not a claim that contemporary processors execute one instruction at a time or that all transfers pass through one physical wire. It is a model of responsibilities. The software side supplies instructions and data, while the language, executable format, operating system, and device interface assign meaning to particular encodings. A sequence of bits does not identify its own type or purpose.

Sixth-grade explanation
The processor does the work. Registers and memory hold information. Controllers help the computer talk to storage and other devices.

Discussion / pause
Does a byte sequence tell you whether it is an instruction, an integer, or text?

Expected response: No. Its interpretation depends on the surrounding interface, representation, and execution context.

05. Follow the value—not just the statement
Section: 1.1.1 · CPU, REGISTERS & MEMORY
Source mapping: original slide(s) 3, 18.

Graduate lecture narration
Suppose a source expression adds three to a value. Before discussing the addition, ask how the value became available to the executing instruction. It might arrive in an argument register, come from a prior calculation, or require a load. The result might remain in a register, be used immediately, or be stored. This is why a source variable should not automatically be imagined as a permanently assigned RAM slot.

The instruction stream also has to be fetched. Therefore, saying that an addition needs no data-memory access is not the same as saying that the processor uses no memory-related machinery. The original chapter makes this distinction in its expression example. Our register-workbench analogy explains placement, not exact timing or physical implementation. At this stage, track architectural inputs and outputs and leave detailed cache behavior and processor scheduling to later chapters.

Sixth-grade explanation
Think of registers as a tiny workbench and memory as a larger set of shelves. A value may already be on the workbench when it is needed.

Discussion / pause
Can the addition itself avoid a data-memory load?

Expected response: Yes, when the needed operand is already in a register or the compiler can otherwise supply it without a load.

Transition: Controllers and interrupts coordinate I/O.

06. Controllers and interrupts coordinate I/O
Section: 1.1.1 · STORAGE & PERIPHERALS
Source mapping: original slide(s) 3, 12.
Graduate extension: added analysis, teaching model, diagnostic method, or exercise.

Graduate lecture narration
I/O introduces a boundary between requesting work and completing work. A controller supplies a device-facing interface. Systems software translates a higher-level request into actions the device supports. An interrupt is one mechanism by which the system can learn that an event needs attention; it should not be mistaken for the application itself performing the hardware operation.

A useful explanation identifies the requester, the component doing the transfer, and the component reporting completion. Do not silently assume that a library call corresponds to one device command or that returning from a high-level call means durable storage has been achieved. Those are separate contracts. The source deck names controllers and interrupts; this slide makes the request/completion distinction explicit without prescribing one device protocol. We will revisit the same distinction when we discuss buffered output and partial failures.

Sixth-grade explanation
A device does not always finish right away. The program asks for work, the device does it, and the system reports what happened.

Transition: Software role is not execution privilege.

07. Software role is not execution privilege
Section: 1.1.2–1.1.3 · SOFTWARE CATEGORIES
Source mapping: original slide(s) 4.

Graduate lecture narration
The chapter classifies systems software by role: kernels control resources, compilers translate, linkers connect compiled units, runtime libraries supply startup and shared operations, and drivers handle device-specific interactions. Application software performs tasks for users or services. The distinction is useful, but not absolute. A database application may contain its own allocator, scheduler, or storage engine.

Execution privilege is a different axis. A compiler is systems software that normally executes as an ordinary user process. A server may manage important information without becoming kernel code. Conversely, a particular driver architecture can place components on either side of a privilege boundary. Avoid using the labels low-level, systems, and privileged as synonyms. For diagnosis, ask what a component is responsible for and what operations it is authorized to perform. These questions may have different answers.

Sixth-grade explanation
Some programs help the computer run other programs. That does not mean they all get special permission to control the machine.

Discussion / pause
Why does a compiler not need kernel privilege just because it is systems software?

Expected response: Translation is its role; the OS can provide ordinary process permissions sufficient to read inputs and write outputs.

Transition: An abstraction is a smaller contract.

08. An abstraction is a smaller contract
Section: 1.1.4 · ABSTRACTION LAYERS
Source mapping: original slide(s) 5.
Graduate extension: added analysis, teaching model, diagnostic method, or exercise.

Graduate lecture narration
The original slide describes an abstraction as hiding detail while preserving a contract. For example, a file descriptor lets a caller request byte-oriented I/O without manipulating a storage controller. A vector presents a sequence while hiding many allocation decisions. Hidden details continue to exist; they are simply not all part of the caller's interface.

At graduate level, describe a contract using preconditions, permitted effects, postconditions, and failure behavior. Preconditions tell the caller what must already hold. Postconditions constrain the result when the operation succeeds. Failure behavior says what may have changed and what remains valid. This is a reasoning framework, not a claim that every real interface documents all of these perfectly. A missing or ambiguous guarantee is something to investigate, not permission to assume convenient behavior. Abstraction succeeds when the smaller contract is sufficient for the caller's reasoning.

Sixth-grade explanation
A button can be easy to use even when the machine behind it is complicated. You still need to know what pressing the button promises.

Transition: Guaranteed, customary, or measured?.

09. Guaranteed, customary, or measured?
Section: 1.1.4 · DO NOT INVENT GUARANTEES
Source mapping: original slide(s) 5, 15, 19.

Graduate lecture narration
Separate what an interface promises from what an implementation commonly does and from what you observed on a particular run. This distinction appears explicitly in the source chapter. Suppose an output operation reports that it accepted some number of bytes. The count is part of that operation's result. Whether all bytes were accepted at once, when physical storage was updated, and how long the operation took are different questions.

The vector example has the same structure: a sequence interface need not expose every allocation decision. A caller who relies on an undocumented growth choice turns an implementation detail into a hidden dependency. When presenting evidence, use precise wording. Say that a run took a measured amount of time under a stated setup, not that the API promises that latency. Say that a platform documents a behavior when it actually does. The method is to classify a claim before relying on it.

Sixth-grade explanation
A rule, a habit, and something you saw once are different. A program should not treat them as the same thing.

Transition: API, ABI, and ISA answer different questions.

10. API, ABI, and ISA answer different questions
Section: 1.1.5 · HARDWARE / SOFTWARE INTERFACES
Source mapping: original slide(s) 6.

Graduate lecture narration
An API is a source-facing interface: names, operations, argument meanings, and behavioral contracts. An ABI governs compiled interoperability: calling conventions, register use, data layout, and other binary rules. An ISA describes machine operations and software-visible architectural state. These boundaries answer different questions even when one program crosses all three in a few instructions.

Use a function call as the running example. Its source declaration tells the compiler how the call is written and typed. Binary conventions tell caller and callee where to put arguments and results. The selected machine instructions must then be valid for the target architecture. Matching at one boundary does not imply matching at the others. The original chapter's three warnings remain important: identical APIs do not imply binary compatibility; a shared ISA does not imply a shared ABI; and a shared ISA does not imply identical microarchitecture or speed.

Sixth-grade explanation
The API says what you can ask for. The ABI says how compiled parts pass things. The ISA says which machine commands the processor understands.

Transition: One ISA can support different calling conventions.

11. One ISA can support different calling conventions
Section: 1.1.5 · ABI CASE STUDY
Source mapping: original slide(s) 6.
Graduate extension: added analysis, teaching model, diagnostic method, or exercise.

Graduate lecture narration
Here is a concrete graduate extension of the chapter's ABI distinction. For an ordinary function taking two int parameters, a System V AMD64 caller uses the integer argument-register convention associated with RDI and RSI, with the int values in their 32-bit portions. The usual Microsoft x64 convention uses RCX and RDX for those positions instead. For the int return in this example, EAX is used in both conventions.

This is a deliberately narrow example. Real ABIs also define stack rules, preserved registers, alignment, aggregate classification, and other details. Do not extend this two-int table to every type or every function. It is enough to demonstrate the logical point: a machine can implement the x86-64 ISA while binary components disagree about how a function is called. Source-level similarity is not evidence that independently built objects can be combined safely.

Sixth-grade explanation
Two people can speak the same language but use different handoff rules. Compiled functions also need to agree on where each value goes.

Discussion / pause
Would matching instruction sets make these two calling conventions interchangeable?

Expected response: No. Caller and callee must also agree on argument locations and the rest of the binary contract.

12. Architecture is a promise; implementation is a choice
Section: 1.1.5 · ISA VS. MICROARCHITECTURE
Source mapping: original slide(s) 3, 6, 18, 19.

Graduate lecture narration
The chapter warns that an ISA and a microarchitecture are not the same thing. The ISA defines the software-visible operations and state that an implementation must honor. Microarchitecture concerns how a particular implementation realizes that behavior. The existence of the same instruction in two systems does not establish the same latency, throughput, cache behavior, or resource contention.

Keep two explanations separate. A functional explanation asks which architectural result an instruction produces under its specified conditions. A performance explanation asks how long a workload takes on a particular implementation and why. A correct functional trace does not provide enough information to derive whole-program timing. Conversely, a favorable benchmark cannot excuse an invalid instruction assumption or a violated language rule. This distinction prepares the performance discussion without turning Chapter 1 into a processor-design course.

Sixth-grade explanation
Two cars can follow the same road rules but have different engines. Two processors can run the same commands at different speeds.

Transition: Locate the boundary before proposing a fix.

13. Locate the boundary before proposing a fix
Section: 1.1 · INTERFACE REASONING CHECK
Source mapping: original slide(s) 6, 11, 12, 21.
Graduate extension: added analysis, teaching model, diagnostic method, or exercise.

Graduate lecture narration
A systems failure is easier to investigate when the symptom is attached to a boundary. A missing source declaration is not the same problem as a missing compiled definition. A binary that requires a different instruction set has a different issue from a program that lacks access to a file. The table gives initial hypotheses, not a complete diagnostic decision tree.

The graduate task is to state the evidence that would discriminate among plausible explanations. For a binary-interface concern, examine build settings and the ABI of both components. For a runtime file error, inspect the operation's returned status and the relevant environment. For a performance discrepancy, record the workload and implementation. Avoid responding to every symptom by recompiling everything or increasing privileges. Those actions may hide the mismatch instead of explaining it. Later slides make the build-stage examples concrete.

Sixth-grade explanation
When something breaks, first find which handoff went wrong. Fixing the wrong part wastes time.

14. Seven stages, seven different questions
Section: 1.2 · FROM SOURCE TO EXECUTION
Source mapping: original slide(s) 7.

Graduate lecture narration
The source chapter presents a seven-stage model: source, preprocessing, compilation, assembly, linking, loading, and execution. The model separates responsibilities; it does not require every implementation to launch a separate operating-system process for every stage. Compiler drivers often orchestrate several stages in a single command.

Each stage changes what kind of evidence is available. Source text exposes the programmer's operations and obligations. Preprocessed text exposes the translation unit after directives and macros. Assembly exposes symbolic target operations. An object file exposes encoded data, symbols, and relocation requirements. A linked executable describes a loadable program, while loading and runtime establish and exercise the process environment. Notice that passing an earlier stage does not guarantee passing later stages. Successful compilation does not supply an omitted definition, and successful loading does not guarantee that a runtime resource will be available.

Sixth-grade explanation
The program goes through several stations before and while it runs. Each station has a different job and can find a different kind of problem.

Transition: Source code describes an abstract computation.

15. Source code describes an abstract computation
Section: 1.2.1 · SOURCE-LEVEL CONTRACT
Source mapping: original slide(s) 8.

Graduate lecture narration
Before imagining instructions, identify the source-level semantics. The original chapter lists types, expressions, statements, lifetimes, synchronization rules, and observable behavior. These constrain the abstract computation, but source order is not a literal physical schedule. A correct implementation may transform the computation while preserving the behavior required by the language and the implementation's documented guarantees.

For a pointer access, ask whether the object exists, whether the access is in range, and whether its lifetime and synchronization obligations hold. For arithmetic, ask whether the result is representable under the relevant rules. These are not optional details to check after performance tuning. They define the domain in which the rest of the explanation is valid. The public C committee draft provides a reference for abstract-machine reasoning; the lab retains the source deck's C17 compilation mode.

Sixth-grade explanation
Code has rules about what values mean and when they may be used. The computer may organize the work differently while keeping the promised result.

16. Not all language uncertainty is undefined behavior
Section: 1.2.1 · CLASSIFY THE RULE
Source mapping: original slide(s) 8, 19, 21.
Graduate extension: added analysis, teaching model, diagnostic method, or exercise.

Graduate lecture narration
This classification extends the original instruction to check defined behavior first. Some behavior is directly constrained by the language rules. Other matters permit an implementation-defined choice that the implementation documents, or an unspecified choice among permitted alternatives. Undefined behavior is different: it does not provide an ordinary language-level guarantee for the erroneous execution.

For the chapter's systems model, the practical point is not memorizing labels. It is choosing the right evidence. Documentation is relevant to an implementation-defined property. A program should not depend on a particular unspecified choice unless its specification tolerates all allowed choices. An out-of-bounds access cannot be justified by reporting that a test happened to print the expected number. Be careful with scope: the labels attach to specific rules and operations, not to the vague claim that an entire compiler is unpredictable.

Sixth-grade explanation
Sometimes a rule allows a choice. Sometimes the maker must explain the choice. Breaking a rule is different from either kind of choice.

Transition: Preprocessing works on directives and tokens.

17. Preprocessing works on directives and tokens
Section: 1.2.2 · HEADERS, MACROS & CONDITIONALS
Source mapping: original slide(s) 9.

Graduate lecture narration
The original preprocessing example contains a standard header, a macro constant, and a platform conditional. Include processing makes header content available to the translation unit; it does not automatically cause an external function implementation to be linked into the final program. Conditional inclusion is a translation-time decision. It is not a runtime test executed each time the program runs.

Macros operate on preprocessing tokens. They are not typed runtime variables or ordinary function calls. That distinction matters when an argument contains an operation with a side effect, as the next slide demonstrates. Use the preprocessed file as evidence when a macro or a conditional produces surprising source code. This is a more direct method than guessing at what the compiler saw. The platform symbol in this example is explicitly environment-specific, which also connects preprocessing to portability assumptions.

Before normal compilation, the preprocessor follows special instructions, brings in header text, and replaces chosen words or symbols.

18. A macro can duplicate an operation
Section: 1.2.2 · PREPROCESSOR COUNTEREXAMPLE
Source mapping: original slide(s) 9.
Graduate extension: added analysis, teaching model, diagnostic method, or exercise.

Graduate lecture narration
This is a deliberately invalid example for analysis, not a program to use as a numerical experiment. The SQUARE macro replaces its parameter in two positions. Giving it i++ expands the increment expression twice. In C, the two modifications shown in the multiplication expression are unsequenced relative to one another, so the example has undefined behavior. There is no correct portable numeric answer to predict.

Parentheses are still useful in macros because they prevent some precedence surprises, but they do not make repeated evaluation safe. A function that receives an already computed value separates the caller's side effect from the body calculation. Even then, arithmetic range requirements remain: replacing the macro with a function does not make arbitrary signed multiplication overflow valid. This extension turns the source deck's warning about duplicated side effects into a concrete contract failure.

Sixth-grade explanation
A macro can copy your instruction more than once. Asking it to “use the number and then increase it” can accidentally copy the increase too.

Discussion / pause
What portable value should we predict for y?

Expected response: None. The shown expanded expression violates C sequencing rules.

19. Declarations enable checking; definitions supply entities
Section: 1.2.2 · TRANSLATION UNITS
Source mapping: original slide(s) 9, 16.
Graduate extension: added analysis, teaching model, diagnostic method, or exercise.

Graduate lecture narration
In the chapter's two-file program, sum.h declares add, sum.c defines it, and main.c calls it. The declaration lets each translation unit check source-level uses. The compiled caller can still depend on a definition that will be supplied later. That is the central reason a program may compile and then fail at the link stage.

The graduate nuance is that a header is not intrinsically declaration-only. Headers can also contain definitions, subject to language and linkage rules. Our teaching layout places this externally linked function's declaration in the header and its definition in one source file. The include guard in the companion lab is an added organizational aid. Distinguish a file's conventional role from a language restriction. Also remember that consistent declarations across translation units are a programmer and build-system responsibility; a conventional linker is not a complete source-level type checker.

Sixth-grade explanation
A declaration says that a function exists and how to call it. A definition contains the actual function body.

20. The compiler transforms meaning into a target program
Section: 1.2.3 · COMPILATION
Source mapping: original slide(s) 10.

Graduate lecture narration
The original chapter separates compiler work from assembler work. The compiler parses a translation unit, checks language constraints, creates intermediate representations, transforms the computation, and selects target instructions. These phases need not appear as separate user-visible files. An intermediate representation is useful because the compiler can reason about operations and dependencies before choosing their final encoding.

Successful compilation establishes only what that compilation checked. It does not prove a whole-program specification or show that every runtime input is safe. A declaration can permit a source call even when its definition is missing from the eventual link. A path can contain a memory error that the compiler does not diagnose. For investigation, ask what assumptions a transformation uses and what observable behavior it must preserve. The next slide examines why optimized output need not resemble the source statement by statement.

Sixth-grade explanation
The compiler checks the code and turns its meaning into instructions for a chosen kind of processor.

21. Optimization does not preserve source appearance
Section: 1.2.3 · SEMANTICS VS. MACHINE SCHEDULE
Source mapping: original slide(s) 8, 10, 18.
Graduate extension: added analysis, teaching model, diagnostic method, or exercise.

Graduate lecture narration
Consider a function that adds three and returns the result. The source introduces y, but the implementation does not need to preserve a physical storage location named y. It can produce the result directly in a return register, use a target instruction that combines operations, or transform the surrounding caller when optimization permits. Source-level names are not a list of mandatory hardware objects.

The argument only applies within the function's valid domain. For int addition in this example, x must be at most INT_MAX minus three, and the source value must otherwise be valid. The actual emitted instructions depend on the target, compiler version, and options. For that reason, the slide does not promise a particular assembly listing. In the lab, compare generated assembly as an observation and record the build settings rather than treating one listing as the universal translation of C.

A compiler may take a shortcut that gives the same required result. It does not have to copy each written step into a separate machine command.

22. The assembler produces more than instruction bytes
Section: 1.2.4 · ASSEMBLY & OBJECT FILES
Source mapping: original slide(s) 10, 11.

Graduate lecture narration
Assembly output is not a uniform list of executable instructions. It can contain labels, directives, data, and symbolic references. Labels identify positions or symbols; directives tell the assembler how to organize material. The assembler encodes instructions and data and emits the additional object-file information required for later stages.

A relocatable object can contain a reference whose final address is not yet known. Keeping that information is not a failure to assemble the file. It is part of separate compilation. The chapter's caller can therefore assemble before the linker sees the definition of add. When reading assembly or disassembly, separate the actual instructions from organizational metadata. When examining an object, ask both what bytes it already contains and what obligations remain unresolved. This is the bridge between compiler output and linking.

Sixth-grade explanation
Assembly uses readable names for machine operations. The assembler makes the bytes and keeps information needed to connect unfinished references later.

23. Linking connects separate compiled responsibilities
Section: 1.2.5 · SYMBOLS, SECTIONS & LIBRARIES
Source mapping: original slide(s) 11, 16, 17.

Graduate lecture narration
The source chapter describes linking as combining object files and libraries, resolving symbol references, laying out sections, and applying relocations that can be handled at link time. In our example, main.o refers to add and sum.o provides the corresponding definition. The linker connects the reference using the applicable object format and binary conventions.

An undefined-reference diagnostic points us toward the link inputs, symbol names, and compatible definitions. It is not normally fixed by adding another source declaration to the caller. 27. Mapped memory is not necessarily resident memory
Section: 1.2.6 · DEMAND PAGING
Source mapping: original slide(s) 12.

The source chapter describes invalid input, unavailable resources, interruptions, and partial failures as conditions that should lead to controlled behavior. A robust specification explains the result, the state that remains, and the obligations still owned by the caller or callee.

For a failed operation, ask three practical questions. What changed before the failure was reported? Which resources are still valid and who owns them? Is retry safe, and from which point? These questions connect robustness to the invariants and ownership model rather than treating error handling as a message printed at the end. Returning an error code while leaving shared state inconsistent is not controlled failure. The next example shows why partial progress and total failure must be distinguished.

Sixth-grade explanation
A strong program plans for bad input and missing resources. When it fails, it should still leave things in a known, safe condition.

47. Partial success changes the retry position
Section: 1.3.5 · ROBUST I/O REASONING
Source mapping: original slide(s) 15.
Graduate extension: added analysis, teaching model, diagnostic method, or exercise.

Graduate lecture narration
Suppose a byte-output interface is asked to write ten bytes and returns a positive count of four. That count records progress. In this illustrative stream or ordinary file-output case, the next attempt to send the remaining data starts at buffer plus four and requests six bytes. Repeating the original request can duplicate the already completed prefix.

The Linux write interface documents partial writes and distinct failure conditions, but this slide is not a universal retry loop. A complete implementation must handle the actual interface's interruption, blocking, signal, and error rules, as well as its own cancellation or retry limits. Message-oriented protocols and non-idempotent operations may require different recovery logic. The arithmetic teaches a broader design principle from the chapter: define what remains true after failure, including partial effects, before deciding whether a retry is safe.

Sixth-grade explanation
If four of ten items were delivered, six are left. Sending all ten again may repeat the first four.

Discussion / pause
Why is retrying all ten bytes potentially wrong?

Expected response: The first four may already have taken effect, so repeating the entire request can duplicate them.

48. Portability has at least three separate targets
Section: 1.3.6 · PORTABILITY
Source mapping: original slide(s) 15.

Graduate lecture narration
The original chapter explicitly distinguishes source portability, binary compatibility, and performance portability. Source portability concerns whether the program can be translated appropriately for another supported environment. Binary compatibility concerns whether compiled components can interoperate or execute under the expected machine and runtime conventions. Performance portability concerns whether the implementation still meets the relevant performance goals across platforms.

These are related but independent claims. A portable source program may need rebuilding. A binary can require a particular ABI or shared library. A program that executes correctly may have different bottlenecks on a second implementation. Make each platform assumption visible and testable: representation, interfaces, resource limits, compiler options, and runtime dependencies. Do not call a design portable without specifying the supported environments and the level of portability being claimed.

Sixth-grade explanation
Code that can be rebuilt elsewhere, a file that runs elsewhere, and a program that stays fast elsewhere are three different achievements.

49. Serialize a value—not an accidental object layout
Section: 1.3.6 · EXPLICIT REPRESENTATION
Source mapping: original slide(s) 15.
Graduate extension: added analysis, teaching model, diagnostic method, or exercise.

Graduate lecture narration
Take the unsigned value 0x01020304 and assume an environment with eight-bit bytes and a 32-bit unsigned value representation for this example. Its four byte values can be ordered most-significant first or least-significant first. The table defines both sequences explicitly. A protocol that chooses most-significant byte first specifies the bytes independently of the sender's internal order.

This is an illustrative serialization design, not a universal rule that every protocol uses one byte order. A complete format also defines field widths, versioning where needed, and the meaning of the values. Copying an entire in-memory structure can accidentally export padding, alignment-dependent layout, or process-local addresses. The original chapter's instruction to serialize explicitly means that the external representation deserves its own contract. The receiver should not have to share an undocumented compiler or platform choice to interpret the data.

Sixth-grade explanation
When two computers share a number, they need the same packing rules. Agree on the order of the bytes instead of guessing from memory.

50. Faster invalid behavior is not a better implementation
Section: WORKED EXAMPLE · CORRECTNESS VS. PERFORMANCE
Source mapping: original slide(s) 19.

Graduate lecture narration
The original deck compares two checksum versions using twelve and eight milliseconds. Those numbers are an illustrative comparison in the supplied teaching material, not benchmark measurements collected for this revision. Version A produces the expected checksum and has no known contract violation under the stated test. Version B appears to produce the checksum but reads beyond its buffer.

The smaller timing does not repair Version B's invalid access. We should also avoid overstating the evidence for Version A: passing the stated check does not by itself prove correctness for every input. The appropriate conclusion is narrower. 60. Chapter 1: the system is a chain of contracts
Section: TAKEAWAYS & CHAPTER 2 PREVIEW
Source mapping: original slide(s) 22.

Graduate lecture narration
Return to the original chapter's takeaways. Computer systems are layered contracts, not one undifferentiated machine. API, ABI, and ISA describe different interfaces. Source passes through preprocessing, compilation, assembly, linking, loading, and runtime execution. Systems work makes representation, ownership, failure, and platform assumptions explicit. The graduate addition is a method for making these statements operational.
