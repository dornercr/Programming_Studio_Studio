SLIDE 1: Chapter 53 — Event-Driven I/O

LECTURE NARRATION
An event-driven server keeps many connection state machines in a smaller number of execution threads. Instead of blocking one thread per idle connection, it waits for readiness and advances the corresponding state only as far as current I/O permits. This trades simple sequential control flow for explicit state, buffers, and scheduling policy. Readiness is not completion. A readable socket may provide only part of a frame, and a writable socket may accept only part of a response. A correct event loop records partial progress and resumes later without losing ownership or duplicating bytes. [ R28 , R29 ]

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. SLIDE 4: 53.1 Blocking

LECTURE NARRATION
A blocking operation can suspend the calling thread until progress or failure occurs. In a one-thread event loop, an unexpected blocking call can stall every connection managed by that loop. Set nonblocking mode on all endpoints whose operations must never stall the reactor. On Linux, accepted sockets need their flags established explicitly; inheriting the listener’s intended behavior is not a portable assumption. Potentially blocking computation and filesystem operations also require architectural attention.

SLIDE 6: 53.2 Polling

LECTURE NARRATION
Polling can mean repeatedly checking state without sleeping, or using an interface named poll that waits for readiness. Distinguish the two. A tight loop around EAGAIN is busy polling; it consumes CPU without creating data or capacity. A readiness wait lets the kernel block the event-loop thread until an event or timeout is relevant. Some low-latency systems deliberately busy-poll under controlled budgets, but that is a specialized tradeoff, not a default error-handling loop.

SLIDE 8: 53.3 select

LECTURE NARRATION
select monitors descriptor sets for readiness. The caller prepares sets and a descriptor-range bound, then inspects the modified sets after return. The interface’s set representation imposes limits, including the fixed FD_SETSIZE constraint in common libc implementations. Do not place an arbitrary large descriptor into a fixed-size set. The highest descriptor number, not merely the count of active descriptors, matters. For larger or more dynamic sets, other interfaces often provide a more suitable representation. [ R41 ]

SLIDE 10: 53.4 poll

LECTURE NARRATION
poll uses an array of descriptor-event entries rather than fixed descriptor bit sets. It reports readiness and error conditions per entry. The array must still be scanned and maintained by the application. A readiness event can coexist with hangup or error indicators. Read buffered data before treating a hangup as proof that no data remains. The operation’s return value remains authoritative when attempted after readiness. [ R28 ]

SLIDE 12: 53.5 epoll

LECTURE NARRATION
Linux epoll maintains an interest set and returns ready events. It supports level-triggered and edge-triggered modes. Level-triggered behavior continues to report readiness while the condition remains; edge-triggered use requires carefully draining nonblocking operations until they would block. [ R29 ] Do not describe epoll as making every network operation universally constant-time. Registration changes, event delivery, application state lookup, and actual I/O still cost work. Its usefulness comes from avoiding repeated handling of large inactive descriptor sets in suitable workloads.

SLIDE 14: 53.6 Event loops

LECTURE NARRATION
An event loop waits, dispatches ready connections, performs bounded work, updates interest masks, and handles timers and shutdown. Each connection retains input progress, output progress, and protocol state between dispatches. Register write readiness only when output remains pending; an idle socket is often writable and can otherwise wake the loop continuously. For edge-triggered operation, stopping before EAGAIN for fairness requires an explicit rescheduling strategy so that remaining work is not forgotten while waiting for a new edge.

SLIDE 16: 53.7 Active connections

LECTURE NARRATION
Connection lifetime must outlast every queued event and task that refers to it. Descriptor numbers can be reused, so identifying a connection solely by an old integer in delayed work can target a new connection accidentally. Use ownership-aware objects, generation identifiers, or another strategy that validates event identity. Closing and deleting a connection is a state transition coordinated with the reactor, not an arbitrary action another thread should perform while callbacks still hold raw pointers.

SLIDE 18: 53.8 Scaling large numbers of connections

LECTURE NARRATION
Event-driven designs reduce thread-per-idle-connection overhead, but active work still consumes CPU, memory, and bandwidth. Bound input, output, queued tasks, and per-dispatch work. Backpressure is as important in an event loop as in a threaded server. A common architecture combines a small set of I/O reactors with a bounded worker pool for heavier computation. The handoff must preserve connection lifetime and return results through a safe queue. More architectural layers create more ownership transitions to test.

SLIDE 24: Worked example — Why nonblocking matters

LECTURE NARRATION
If an event-loop thread performs a blocking read on one client that has no complete request, the entire loop can stall and stop servicing other ready clients. Nonblocking descriptors let the loop attempt work, detect that an operation would block, and return to multiplexing other connections.
