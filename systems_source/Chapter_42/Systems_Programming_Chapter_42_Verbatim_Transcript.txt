SLIDE 1: Chapter 42 — Shell Architecture

LECTURE NARRATION
A shell is a process-control program with a language front end. It turns command syntax into a plan for programs, arguments, descriptors, process groups, and waiting. A small shell can demonstrate systems concepts, but a complete interactive shell also needs careful syntax, signal, terminal, and lifecycle handling. Separate parsing from execution. Parsing should produce a structured description without opening files or launching programs. Execution should consume that structure according to a documented policy. This separation makes malformed input testable without causing side effects.

SLIDE 4: 42.1 Parsing commands

LECTURE NARRATION
Parsing begins with lexical rules for words, quoting, escapes, and operators. A space inside quotes is data, while an unquoted pipe character may be syntax. A quoted "|" must not become a pipeline operator merely because its final text is a vertical bar. Represent token kind separately from token text. Then build an abstract command structure containing argument vectors, ordered redirections, pipeline stages, and background status. Reject incomplete constructs before launch, including unterminated quotes and a redirection without a destination.

SLIDE 6: 42.2 Creating processes

LECTURE NARRATION
The executor creates the required children and tracks each successful creation. Failure halfway through a pipeline requires cleanup of descriptors and already-created children. The plan must define what happens to partially started work. Built-in commands complicate the model. A command such as changing the shell’s current directory must affect the shell process itself in the appropriate context; executing it only in a child would leave the parent unchanged. Decide which operations are built-ins before applying a blanket fork-everything rule.

SLIDE 8: 42.3 Executing programs

LECTURE NARRATION
Each child prepares descriptors, signal state, process-group membership, and other required context before exec. The argument vector should preserve parsed word boundaries. Exec failure must end the child branch with an appropriate status rather than return to the interactive shell loop. A secure launcher also defines executable lookup and environment handling. A general shell intentionally supports broad user-controlled behavior; an application that merely needs to run one helper should prefer direct argument-vector execution instead of implementing or invoking unnecessary shell syntax.

SLIDE 10: 42.4 Redirection

LECTURE NARRATION
Redirection modifies a command’s descriptor relationships in the order specified by the language. Input files, output truncation, append mode, and descriptor duplication require distinct operations. Do not postpone error checking until after exec. If opening a required input fails, the command cannot run as requested. The shell should report the setup error and avoid silently falling back to its own input stream.

SLIDE 12: 42.5 Pipelines

LECTURE NARRATION
A pipeline is a group of connected stages, not a sequence of complete programs run one after another. Its data flow requires overlap when bounded pipes connect producers and consumers. Track pipe-end ownership explicitly. For an N-stage pipeline, there are N−1 connecting pipes, but each child needs only its relevant input and output roles. Extra inherited ends must be closed so that EOF and broken-pipe behavior reflect the intended graph.

SLIDE 14: 42.6 Foreground jobs

LECTURE NARRATION
A foreground job receives the terminal relationship intended for interactive input and terminal-generated signals. The shell normally waits for the job’s completion or stop state before resuming its prompt. Waiting for one PID is insufficient for a pipeline treated as one job. The shell must track all member processes and determine when the job as a whole is complete or stopped. Status reporting is therefore a job-level state machine.

SLIDE 16: 42.7 Background jobs

LECTURE NARRATION
A background job allows the shell to continue accepting commands while the job runs. The shell still owns bookkeeping and must reap child statuses. “Do not wait immediately” is not the same as “forget the child forever.” Background terminal access has special behavior under job-control rules. A robust interactive shell must manage notifications, stopped jobs, and later foregrounding rather than assume every background process can freely read from the terminal.

SLIDE 18: 42.8 Process groups

LECTURE NARRATION
A process group collects related processes, such as all stages of one pipeline, under a group identifier. It lets the shell and terminal mechanisms direct signals to the job as a unit. Group setup has races between parent and child execution. A carefully designed shell establishes membership on both relevant sides as appropriate and checks the documented errors. The exact implementation deserves dedicated testing; it is not replaced by storing several PIDs in a vector.

SLIDE 20: 42.9 Job control

LECTURE NARRATION
Job control combines process groups, terminal foreground ownership, signal dispositions, and wait-status tracking. Interfaces such as setpgid and tcsetpgrp participate in the POSIX model. The shell must regain the terminal after a foreground job stops or finishes and restore the appropriate state. [ R51 , R52 ] The fixed pipeline from Chapter 40 is not a job-control shell. It has no interactive terminal handoff, stopped-job management, expansion language, or background-job table. Those omissions are intentional so that its descriptor and process behavior remain inspectable. [ R17 , R21 ]

Terminal-generated signals such as an interactive interrupt can then target the whole job. The shell waits for or monitors the group rather than treating each pipeline process as an unrelated command.
