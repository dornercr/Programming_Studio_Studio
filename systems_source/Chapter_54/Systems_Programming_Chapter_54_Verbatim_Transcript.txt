SLIDE 1: Chapter 54 — Measuring Performance

LECTURE NARRATION
Performance engineering begins by defining the work and the measurement boundary. A number is meaningful only when it identifies what completed, under which conditions, and how the observation was made. Correctness checks belong in the experiment: a program that skips work can appear extraordinarily fast. This chapter distinguishes measured observations , analytical models , and illustrative assumptions . The companion benchmark reports local timings when run, but the book does not convert one container run into a universal hardware claim. Reproduce measurements on the machine and workload that matter. [ R30 , R42 ]

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. When this topic appears in real systems code, separate what the language guarantees from what a compiler, operating system, ABI, ISA, or particular machine happens to do. Then identify the evidence you would inspect to test the claim without overgeneralizing from a single successful run.

SLIDE 4: 54.1 Latency

LECTURE NARRATION
Latency measures elapsed time from a defined start event to a defined completion event. For a request, the boundary might include queueing, parsing, computation, and response delivery. For a kernel, it might include only the computation after inputs are prepared. Report a distribution when requests vary. A mean can hide a long tail, and a percentile requires enough samples and a clearly defined population. Do not compare one system’s median service time with another system’s end-to-end 99th percentile as though they were the same metric.

SLIDE 6: 54.2 Throughput

LECTURE NARRATION
Throughput measures completed useful work per unit time. It can be expressed as records, requests, or bytes per second. Define whether failed requests, retries, warmup work, and partial completions count. Throughput and latency interact through queueing. A system can increase completed work by admitting more concurrent requests while making each request wait longer. Evaluate the service objective rather than maximizing a single number without constraints.

SLIDE 8: 54.3 CPU time

LECTURE NARRATION
CPU time measures processor execution charged to a process or thread under the operating system’s accounting rules. It excludes many periods spent blocked or not scheduled. A multithreaded process can accumulate more total CPU time than elapsed wall time when several threads execute concurrently. CPU time helps distinguish computation from waiting, but it is not a complete explanation. Kernel activity, helper processes, and accounting boundaries may contribute differently. State whether the measurement covers one thread, the whole process, or a larger job.

SLIDE 10: 54.4 Wall-clock time

LECTURE NARRATION
Wall-clock elapsed time includes waiting, scheduling delays, and other activity between the chosen start and end. For duration measurements, use a monotonic clock such as std::chrono::steady_clock rather than a civil-time clock that can be adjusted. Clock resolution and call overhead matter for very small operations. Batch enough work to make the measured interval meaningful, while ensuring that the batch still represents the workload and does not change cache behavior beyond the intended experiment.

SLIDE 12: 54.5 Utilization

LECTURE NARRATION
Utilization describes the fraction of a resource’s capacity in use under a stated definition. CPU utilization, memory bandwidth utilization, and device busy time are different metrics. High CPU utilization does not prove that useful work is progressing efficiently; a spin loop can consume an entire core. Low utilization does not automatically mean spare end-to-end capacity. The bottleneck may be a serialized dependency, a lock, a downstream service, or a limit in another resource. Identify the constrained stage before adding more work.

SLIDE 14: 54.6 Benchmarking

LECTURE NARRATION
A benchmark should state input size and distribution, build configuration, machine context, warmup policy, repetition count, and correctness criteria. Keep setup outside the timed region when the goal excludes setup, and include it when evaluating end-to-end behavior. Preserve observable results so the compiler cannot legally discard the intended work as unused. Inspect generated code when a result seems implausible. Avoid volatile as a blanket benchmarking technique because it can change the workload being measured rather than merely prevent elimination.

SLIDE 16: 54.7 Measurement error

LECTURE NARRATION
Measurements vary because of scheduling, frequency changes, contention, cache state, page faults, thermal behavior, and instrumentation overhead. Repeated samples reveal variation but do not automatically remove bias. Change one factor at a time where practical and alternate comparison order to reduce drift effects. Report uncertainty honestly. A difference smaller than the experiment’s noise is not strong evidence of improvement, and a statistically clear difference may still be too small to matter operationally.

SLIDE 20: Worked example — Throughput and latency

LECTURE NARRATION
If a service completes 12,000 requests in 60 seconds, average throughput is 200 requests/s. That fact does not reveal individual latency: one request may complete in 2 ms while another waits 500 ms. Report throughput and latency distributions separately because batching and queueing can improve one while harming the other.
