SLIDE 1: Chapter 56 — Performance Analysis

LECTURE NARRATION
Performance analysis identifies the limiting resource or dependency and estimates how much improvement is possible. It combines observations, profiles, and models. The purpose is not to collect every available counter, but to explain which change could reduce the application’s completion time or increase useful throughput.

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. SLIDE 4: 56.1 Identifying bottlenecks

LECTURE NARRATION
A bottleneck is a stage or resource that constrains the chosen performance objective. Removing one bottleneck can expose another. The limiting factor can also change with input size, concurrency, and cache state. Form a testable hypothesis: “This phase is limited by repeated allocation,” or “These workers wait on one mutex.” Then collect evidence that could disprove it. A profile showing time inside a function does not by itself identify whether the cause is computation, cache misses, or waiting inside that function.

SLIDE 6: 56.2 CPU-bound workloads

LECTURE NARRATION
A CPU-bound workload spends its critical time performing computation rather than waiting on external I/O. It may still be limited by instruction dependencies, branch behavior, vectorization, or execution-resource throughput. Reducing instruction count can help, but not every instruction has equal cost and not every removed instruction lies on the critical path. Independent work can overlap, while a short dependency chain can dominate latency. Inspect the hot generated code only after establishing that it matters.

SLIDE 8: 56.3 Memory-bound workloads

LECTURE NARRATION
A memory-bound workload is constrained by data access, such as bandwidth or dependent-load latency. Reducing arithmetic may have little effect when the processor already waits for data. Improving locality or reducing transferred bytes can be more valuable. A simple bandwidth roof illustrates the limit. At arithmetic intensity 0.125 operations per byte and available bandwidth 40 GB/s, the bandwidth-limited rate is 5 billion operations per second under the model. A processor capable of much more arithmetic cannot exceed that rate for the same required traffic without changing the access pattern or reuse.

SLIDE 10: 56.4 I/O-bound workloads

LECTURE NARRATION
An I/O-bound workload waits on storage, network, or another external service. Useful changes include batching, caching, reducing requests, overlapping independent operations, and improving the protocol. Adding threads can hide some waits but can also overload the downstream system and increase queueing. Distinguish service time from waiting time. When the dependency is saturated, more concurrent demand may worsen latency without increasing completed throughput.

SLIDE 12: 56.5 Profiling

LECTURE NARRATION
Profiling attributes time or events to code paths. Sampling profiles estimate where execution spends time; instrumentation records chosen events more directly but can perturb behavior. Hardware counters provide additional evidence subject to event definitions and access permissions. A Linux starting point can be perf stat with a small set of understood events, followed by a sampling profile when available. Container, kernel, and administrative policy may restrict access. Record those limitations instead of inventing missing counter data. [ R30 ] The executable path is illustrative; use the actual path produced by the companion build script. A missing tool or denied counter is not a program correctness failure.

SLIDE 14: 56.6 Scaling

LECTURE NARRATION
Strong scaling holds total problem size fixed while increasing resources. Weak scaling grows the problem with the resource count. They answer different questions and should not be compared without stating which workload changed. Synchronization, communication, memory bandwidth, load imbalance, and serial setup limit scaling. Measure useful throughput and latency alongside CPU use. A program using all cores at high utilization can still scale poorly if much of that activity is contention or redundant work.

SLIDE 18: Worked example — Quantify the improvement ceiling

LECTURE NARRATION
With serial fraction 0.20 and four workers, the normalized time is 0.20 + 0.80/4 = 0.40 , so speedup is 2.5. With infinitely many ideal workers, speedup cannot exceed 5 unless the serial portion is changed. Now add overhead equal to 0.05 of the original runtime at four workers. Normalized time becomes 0.45 and speedup falls to approximately 2.222. This explains why “80% parallelizable” is not a sufficient performance forecast without a communication and synchronization model. A model can also guide priorities: reducing the serial fraction from 0.20 to 0.10 may be more valuable than adding workers beyond the point of diminishing returns. Confirm that the measured serial component is truly independent of worker count before applying the formula mechanically.

SLIDE 20: Worked example — Amdahl calculation

LECTURE NARRATION
If 80% of a program can be accelerated by a factor of 4 while 20% is unchanged, total speedup is 1 / (0.20 + 0.80/4) = 2.5 . Infinite acceleration of the parallel part would still cap speedup at 1/0.20 = 5 . The unchanged fraction sets a hard upper bound.

SLIDE 22: Worked example — Distinguishing CPU- and memory-bound behavior

LECTURE NARRATION
If profiling shows execution units frequently idle while the program waits on last-level cache misses, optimizing arithmetic instructions may have little effect. Improving locality, reducing the working set, or prefetching may matter more. A CPU-bound loop with high cache hit rates suggests a different optimization path. Profiling should classify the bottleneck before changes are chosen.
