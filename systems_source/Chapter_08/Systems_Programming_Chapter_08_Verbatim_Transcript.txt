SLIDE 1: Chapter 8 — Process Memory Layout

LECTURE NARRATION
A process sees a virtual address space containing mappings with different purposes and permissions. The familiar picture of code, data, heap, and stack is useful, but it is a conceptual map rather than a universal fixed arrangement. Shared libraries, thread stacks, mapped files, guard pages, and allocator regions make real layouts more complex.

SLIDE 4: 8.1 Code/text segment

LECTURE NARRATION
The text region contains executable instructions. In an ELF file, sections organize linking information while loadable segments describe mappings needed at execution time. Several sections can contribute to one segment. Do not confuse a linker section name with a complete runtime mapping. Executable mappings are commonly readable and executable but not writable. This limits accidental modification and supports security policy. A function’s instructions may be shared physically among processes running the same executable while each process retains its own virtual mappings and private writable state. The sharing is below the source-level function abstraction.

SLIDE 6: 8.2 Read-only data

LECTURE NARRATION
Read-only regions commonly hold constants, string literals, and tables that need not change. A string literal’s storage must not be modified through an ordinary program operation. In C, historical syntax may allow a pointer assignment that does not itself enforce that rule; the attempted modification is still invalid. A const object is not guaranteed to appear in a particular read-only section. It may be automatic, optimized away, embedded into instructions, or stored elsewhere according to its use. The language’s const qualification and the operating system’s page permissions are related design tools, not identical mechanisms.

SLIDE 8: 8.3 Initialized data

LECTURE NARRATION
Writable objects with static storage duration and explicit nonzero initial values commonly contribute to an initialized-data region. Their initial bytes are described by the executable or its loading process. Each process can then modify its private copy according to the mapping rules. A global counter initialized to seven is logically initialized before ordinary application use, but the exact startup work can differ for C++ objects requiring dynamic initialization. Separate the initial byte image from constructors and runtime initialization. A complex global object’s readiness may depend on code that runs before main .

SLIDE 10: 8.4 Uninitialized data

LECTURE NARRATION
The conventional BSS region represents static-duration storage that begins zero-initialized without requiring every zero byte to be stored literally in the executable file. “Uninitialized data” is therefore a misleading everyday label: these objects do receive the language’s required initial state. An automatic local integer without an initializer is different. Its value is not made zero merely because a global integer would be. The storage-duration distinction matters more than whether the source visibly contains = 0 . The loader and runtime can efficiently establish zero-filled pages for large static regions.

SLIDE 12: 8.5 Heap

LECTURE NARRATION
The heap is a conventional name for dynamically managed storage. A user-space allocator may obtain regions from the operating system through several mechanisms and divide them into allocations. Large allocations may use separate mappings rather than one continuously growing area. Calling malloc does not necessarily trigger a system call, and calling free does not necessarily return pages immediately to the operating system. The allocator can retain free blocks for reuse. Consequently, a process’s resident memory may remain high after application objects are released. Distinguish live allocations, allocator-retained storage, mapped address space, and resident physical pages.

SLIDE 14: 8.6 Stack

LECTURE NARRATION
A thread’s stack supports call state and automatic storage that the compiler chooses to place there. On the reference ABI it conventionally grows toward lower addresses. Optimized functions can omit frame pointers, keep values in registers, or use other layouts permitted by the ABI. Each thread needs its own execution stack. Stack capacity is finite, and guard mappings can detect some growth beyond its boundary. Large automatic arrays and deep recursion can exhaust it. A stack overflow is not reliably recoverable by ordinary code that needs the same exhausted stack to run its error path.

SLIDE 16: 8.7 Command-line arguments

LECTURE NARRATION
Program startup provides an argument count and an array of pointers to strings. In the usual main(int argc, char* argv[]) form, valid argument entries are argv[0] through argv[argc-1] , and argv[argc] is a null pointer. The first entry conventionally identifies the program, but applications should not treat it as a trusted executable path. Arguments are input, not authority. Parse numeric strings with range and syntax checks. A string that begins with a valid number but contains trailing junk should not silently become a valid count unless that grammar is intended. Never use an argument length or value directly in allocation arithmetic without validation.

SLIDE 18: 8.8 Environment

LECTURE NARRATION
The environment supplies named string values such as locale settings, search paths, and configuration. It is inherited and can be replaced when a new program image is executed. Environment values can affect library behavior before the application examines them. Treat environment data as untrusted configuration where appropriate, especially across privilege boundaries. Avoid printing the complete environment in diagnostics because it can contain secrets. Concurrent modification also complicates use: a pointer returned by an environment lookup should not be assumed permanently stable while other code changes the environment. Prefer capturing required configuration during controlled startup.

LECTURE NARRATION
Consider four objects: a global initialized integer, a global zero-initialized array, an automatic local integer, and an allocated integer. Their storage-duration categories are known from the source. Their exact addresses are runtime observations and may change between executions because of address-space randomization. Companion listing: ch08/regions.c The stable value output is values=7 0 11 13 . The pointer output is intentionally variable. Predict categories first, then compare addresses with a mapping tool such as the process’s Linux maps view. A large gap between two addresses does not prove a corresponding amount of physical memory is resident. The program does not print function pointers by converting them to void* , because that conversion is not a general portable C object-pointer operation. SLIDE 24: Worked example — Estimating stack growth

LECTURE NARRATION
Suppose a recursive function consumes roughly 256 bytes of stack per call and the usable thread stack is 8 MiB. Ignoring guard pages and other frames, the crude upper bound is 8 × 1024 × 1024 / 256 = 32768 frames. Real safe depth is lower because startup frames, alignment, libraries, and variable frame sizes consume space too. The calculation is an estimate, not a recursion guarantee.
