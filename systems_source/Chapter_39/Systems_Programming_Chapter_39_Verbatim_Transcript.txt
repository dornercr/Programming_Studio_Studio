SLIDE 1: Chapter 39 — Process Termination

LECTURE NARRATION
Termination ends execution, but it does not erase every trace of a process immediately. The operating system retains enough information for a parent to learn how a child finished. A robust parent separates ordinary exit, signal termination, and temporary state changes rather than interpreting a raw status integer directly. [ R17 ]

SLIDE 4: 39.1 exit

LECTURE NARRATION
The C library’s exit performs normal termination processing, including registered exit handlers and standard-I/O cleanup. Returning from main has the corresponding normal-termination effect. _exit bypasses that user-space cleanup and is appropriate for many child failure paths after fork. Neither interface returns to the caller. Choose based on the process’s lifecycle, not merely on spelling. Using normal cleanup in an exec-bound child can flush copied buffers or invoke handlers intended for the original parent program.

SLIDE 6: 39.2 Exit status

LECTURE NARRATION
An exit status communicates a small result to the parent. Conventionally zero indicates success and nonzero indicates failure, but applications define the meaning of particular nonzero values. On the POSIX wait interfaces used here, ordinary exit status is retrieved from the appropriate encoded status through macros. Do not attempt to return a large integer or arbitrary data structure through exit status. Use a pipe, file, socket, or another explicit channel for richer results. Exit status should summarize completion, not replace a data protocol.

SLIDE 8: 39.3 wait

LECTURE NARRATION
wait waits for an eligible child and returns its process ID together with status information. It is useful when any child’s completion can be handled next. The parent must still inspect the status classification before extracting a particular result. A parent with several children should not assume that completion order matches creation order. Scheduling and workload determine which finishes first. Waiting for one specific slow child can delay handling other already-finished children, although it remains correct when the program deliberately chooses that policy.

SLIDE 10: 39.4 waitpid

LECTURE NARRATION
waitpid provides more control over which child or group is considered and whether the call blocks. With WNOHANG , a return of zero means that no matching status is currently available; it is not a child’s process ID and not an error. Retry an interrupted wait when appropriate. Check WIFEXITED before using WEXITSTATUS , and check WIFSIGNALED before using WTERMSIG . Options for stopped and continued children matter for job control, which requires a broader state machine than a simple run-and-wait launcher.

SLIDE 12: 39.5 Zombie processes

LECTURE NARRATION
A zombie is a terminated process whose parent has not yet collected the retained termination information. It is not executing instructions or holding its former address space as a normal live process. It does occupy bookkeeping that should eventually be released. A long-running supervisor that never reaps children can accumulate zombies. The solution is lifecycle management, not treating zombies as ordinary running tasks to be killed again. The parent must arrange to collect child status according to the applicable process and signal rules.

SLIDE 14: 39.6 Reaping children

LECTURE NARRATION
Reaping collects a child’s status and releases the retained termination bookkeeping. A parent should have one clear ownership policy for child status, especially when multiple threads or signal-driven code could attempt to wait for the same child. A common event-driven pattern treats SIGCHLD as a notification to check for available statuses and then repeatedly uses nonblocking waits until none remain. Standard signals can coalesce, so one notification must not be assumed to represent exactly one child event.
