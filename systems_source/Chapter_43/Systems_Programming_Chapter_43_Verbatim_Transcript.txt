SLIDE 1: Chapter 43 — Concurrent Execution

LECTURE NARRATION
Concurrent execution means that multiple activities can be in progress over overlapping intervals. Parallel execution means that work actually proceeds simultaneously on multiple execution resources. A single-core system can run concurrent activities by interleaving them, while a multicore system can combine interleaving with true parallelism. Concurrency adds possible execution orders. Correctness must hold for every execution permitted by the program’s synchronization and platform model, not only for the order observed during one successful run. Timing-based confidence is not a replacement for a state and ownership argument. [ R22 , R34 ]

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. SLIDE 4: 43.1 Concurrency

LECTURE NARRATION
Concurrency is useful when activities wait independently, respond to separate events, or need to overlap work. A server can handle another request while one request waits for data. A user interface can remain responsive while a background task computes. Concurrency also adds lifecycle obligations: cancellation, completion, resource ownership, and communication. Creating another thread is only one implementation choice. Processes, event loops, asynchronous operations, and task systems can provide different concurrency structures.

SLIDE 6: 43.2 Parallelism

LECTURE NARRATION
Parallelism uses multiple execution resources at the same time. It can reduce elapsed time when work can be divided and shared bottlenecks do not dominate. Adding threads does not guarantee parallel execution or useful speedup. The available parallelism depends on dependencies. Four cores cannot execute the next step of a strictly dependent chain before the current step supplies its input. Parallel design often begins by changing task decomposition or data organization rather than increasing thread count.

SLIDE 8: 43.3 Processes

LECTURE NARRATION
Processes provide separate address spaces and stronger default isolation than threads within one process. They communicate through explicit mechanisms such as pipes, sockets, or shared mappings. This can make failure containment and ownership clearer. Isolation has costs and exceptions. Communication may require copying or synchronization, and intentionally shared resources still need a protocol. A process boundary does not automatically make an unvalidated message safe or a shared file update atomic.

SLIDE 10: 43.4 Threads

LECTURE NARRATION
Threads share an address space and many process resources while retaining their own execution state. Sharing makes communication convenient but permits accidental conflicting access to ordinary objects. The central design question is which thread owns each mutable object and when ownership changes. An immutable object safely published to readers has a simpler contract than an object that every thread may update at any time.

SLIDE 12: 43.5 Interleavings

LECTURE NARRATION
An interleaving is one ordering of steps from several activities that preserves required within-activity order. Even a small example can have many interleavings. Source statements may correspond to several machine operations, so treating each line as an atomic step can hide failures. Use interleaving diagrams as models with explicitly defined atomic steps. They explain logical hazards but do not override language memory rules. An unsynchronized C++ data race is undefined behavior; it cannot be justified by saying that a particular hand-drawn interleaving seems harmless.

SLIDE 14: 43.6 Nondeterminism

LECTURE NARRATION
Nondeterminism means that the same apparent inputs can lead to different permitted execution orders or timing. Output order, completion order, and which thread obtains a lock first may vary. A concurrent program can still have deterministic results when synchronization and algorithm design make those ordering differences irrelevant. For example, independent partial sums combined after all workers finish can produce a fixed integer result when the arithmetic and partitioning are defined.

SLIDE 16: 43.7 Multicore execution

LECTURE NARRATION
Multicore hardware allows simultaneous instruction execution and maintains coherence for supported shared-memory accesses. Coherence does not make every multi-step operation atomic or provide all ordering needed by a language-level communication protocol. False sharing, cache-line movement, memory bandwidth, and scheduler placement can limit scaling. A correct design is the prerequisite; performance then depends on reducing unnecessary communication and contention while preserving the required synchronization.

SLIDE 18: Worked example — Enumerating an abstract lost update

LECTURE NARRATION
Model each of two activities as three steps: read a shared counter into a private temporary, add one to that temporary, and write it back. The model treats each step as atomic and enumerates all order-preserving interleavings. It is a mathematical state machine, not an execution of racy C++ code. Companion listing: ch43/interleavings.py The final value can be 1 when both activities read zero before either writes. It can be 2 when one complete increment precedes the other’s read. The lost update occurs because the intended read-modify-write operation was divided into separate steps without a coordination rule. The number of schedules is 6 choose 3 = 20 . Enumerating this tiny state space is feasible; real programs have vastly larger spaces. The scalable response is to establish invariants and synchronization rather than hope to test every timing arrangement.

SLIDE 22: Worked example — Concurrency without parallelism

LECTURE NARRATION
A single-core system can run many threads concurrently by time-slicing: one runs, is preempted or blocks, then another runs. Their executions overlap in time conceptually but not physically at the same instant. Parallelism requires multiple execution resources; concurrency requires overlapping progress and interleavings.
