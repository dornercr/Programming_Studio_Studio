SLIDE 1: Chapter 44 — Threads

LECTURE NARRATION
A thread’s lifecycle includes creation, execution, completion, and collection or joining. Shared objects must outlive every thread that accesses them, and exceptions during setup must not leave unowned running work. C++20’s std::jthread provides joining ownership, but it does not automatically solve a worker that waits forever. [ R34 ]

SLIDE 4: 44.1 Thread creation

LECTURE NARRATION
Creating a thread starts a new execution stream with a callable and arguments. Creation can fail because resources are unavailable. The new thread may begin executing before the constructor’s caller reaches its next statement. Prepare shared state before launching the worker. Capture references only to objects whose lifetimes extend through completion. Capturing a loop variable by reference can accidentally make several workers observe the same changing variable instead of distinct task indexes; capture each intended index by value.

SLIDE 6: 44.2 Thread termination

LECTURE NARRATION
A thread normally terminates by returning from its callable. An uncaught exception escaping a C++ thread function causes termination of the program under the standard thread interface; it is not automatically delivered to the creating thread. Catch worker failures inside the callable when recovery or reporting is required, and communicate them through an explicit channel such as an exception pointer protected by synchronization. Cooperative cancellation also requires the worker to check or wait on a supported stop condition; a stop request does not forcibly interrupt arbitrary blocking work.

SLIDE 8: 44.3 Joining

LECTURE NARRATION
Joining waits for a thread to finish and establishes the synchronization needed to observe its completed work. A std::thread must be joined or detached before its joinable destructor runs; otherwise the program terminates. std::jthread requests stop and joins during destruction when appropriate. Automatic joining is ownership help, not a deadlock cure. Destroying a joining thread object while holding a mutex the worker needs can block forever. Scope objects so that locks are released and shutdown conditions are established before joining.

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. SLIDE 10: 44.4 Shared address spaces

LECTURE NARRATION
Threads can access the same globals, heap objects, and explicitly shared stack objects. Shared addressability does not imply permission to perform unsynchronized conflicting operations. Ordinary mutable state needs ownership or synchronization. Read-only data is simpler, but its initialization must be safely published and its lifetime maintained. A pointer to immutable bytes is still unsafe after the owner destroys or reallocates the storage.

SLIDE 12: 44.5 Thread-local state

LECTURE NARRATION
Thread-local state gives each thread a distinct instance, reducing accidental sharing. C++ thread_local variables have thread storage duration and initialization/destruction rules that differ from automatic locals. Thread-local counters can reduce contention, but an aggregate result still requires a collection phase. Thread-local storage also consumes resources per thread, so a design with enormous thread counts can multiply memory costs.

SLIDE 14: 44.6 Thread stacks

LECTURE NARRATION
Each thread has a stack for its calls and automatic storage under the usual implementation model. A pointer into another thread’s stack can be shared, but the designated object must remain alive and accesses must be synchronized. Large automatic arrays and deep recursion multiply stack pressure across threads. A thread-per-connection server can consume substantial virtual and committed resources even when each worker appears simple. Resource budgeting should include stack and scheduler overhead, not only application payload buffers.

SLIDE 16: 44.7 Thread scheduling

LECTURE NARRATION
The scheduler decides when runnable threads execute. Thread creation order does not determine completion order. A blocked thread may not resume immediately when its condition becomes true because it must also obtain CPU time and any required lock. Avoid using sleeps to establish correctness. A delay that appears sufficient on one machine can fail under load, debugging, or different scheduling. Use joins, mutexes, condition variables, or explicit atomic protocols to express the required relationship.

SLIDE 18: Worked example — Independent partial sums

LECTURE NARRATION
Four workers sum disjoint ranges of the integers 1 through 100. Each writes a distinct array element. The parent combines results only after the worker owners leave scope and join. Companion listing: ch44/partial_sums.cpp The expected result is 5050. There is no conflicting access to the same array element during worker execution, and joining completes before the parent’s reads. Adjacent elements may still share a cache line, so the design can exhibit false sharing in a more write-intensive workload without containing a language-level data race. This example demonstrates correctness, not useful speedup for 100 additions. Thread creation overhead is likely to dominate such a small workload. A performance experiment should reuse workers or use sufficiently large tasks while preserving the same partitioning argument.

SLIDE 20: Worked example — Joining a worker

LECTURE NARRATION
A main thread launches a worker to compute a partial result. If main reads the result before synchronizing, it may observe incomplete state. Calling join waits for the worker to terminate and establishes the required completion relationship for the thread abstraction. After joining, resources associated with a joinable thread can be reclaimed according to the API.

SLIDE 22: Worked example — Thread-local versus shared state

LECTURE NARRATION
An automatic local variable inside a thread function typically resides in that thread’s stack, while a global variable is in the process address space shared by all threads. Two threads can each have distinct local counters but race on the shared global counter. Storage placement affects sharing semantics.
