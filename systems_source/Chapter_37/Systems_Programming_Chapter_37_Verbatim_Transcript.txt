SLIDE 1: Chapter 37 — Process Creation

LECTURE NARRATION
Process creation separates an execution environment into independently scheduled participants. On POSIX systems, fork creates a child whose initial state resembles the parent’s at the call boundary, but the two processes receive different return values and can immediately follow different paths. The resemblance must be interpreted carefully. Private memory has independent modification semantics, while inherited descriptors can reference the same underlying open objects. Treating everything as either “fully copied” or “fully shared” produces errors. [ R15 ]

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. When this topic appears in real systems code, separate what the language guarantees from what a compiler, operating system, ABI, ISA, or particular machine happens to do. SLIDE 4: 37.1 fork

LECTURE NARRATION
fork returns once in the parent and once in the child after successful creation. In the parent it returns the child’s process ID; in the child it returns zero. On failure, the parent receives -1 and no child is created. The child begins after the call, not at the beginning of main . Every branch must therefore be explicit about which process owns which cleanup and continuation responsibilities. A child intended to execute a new program should not accidentally fall through into the parent’s main loop when execution fails.

SLIDE 6: 37.2 Parent process

LECTURE NARRATION
The parent retains its identity and receives a handle-like process ID for the child. It must decide whether to wait immediately, continue concurrently, or supervise several children. It also remains responsible for closing inherited communication endpoints it does not use. A parent cannot assume that it executes first after the fork. Scheduling can run the child before the parent reaches its next statement. Any ordering requirement must be established through waiting or communication, not inferred from source order in the parent’s branch.

SLIDE 8: 37.3 Child process

LECTURE NARRATION
The child has its own process identity and private execution state. It can modify ordinary private variables without changing the parent’s copies. It may execute a new program, perform bounded work, or participate in a pipeline. After a fork from a multithreaded process, only the calling thread appears in the child, while copied library and mutex state can reflect locks held by threads that no longer exist there. Until a successful exec, the child must obey the applicable async-signal-safe restrictions. The examples here create children from single-threaded programs. [ R15 , R20 ]

SLIDE 12: 37.5 Address-space duplication

LECTURE NARRATION
The child receives an address space with corresponding mappings according to the interface’s rules. Ordinary private memory initially contains the same values, but later modifications are logically independent. Shared mappings remain shared according to their mapping semantics. User-space I/O buffers are also memory. If buffered output exists before a fork and both processes later perform normal stream flushing, the same buffered bytes can be emitted twice. Flush deliberately before forking when appropriate, or ensure that an exec-bound child’s failure path uses _exit rather than normal buffered cleanup.

SLIDE 14: 37.6 File-descriptor inheritance

LECTURE NARRATION
The child’s inherited descriptors refer to the same open file descriptions as the corresponding parent descriptors. They can share current offsets and file status flags. Closing the child’s descriptor releases its reference without closing the parent’s separate descriptor-table entry. This sharing is useful for pipelines and redirection but can also cause surprises. A child’s read can advance the offset subsequently observed by the parent. An accidentally retained pipe write end can prevent another process from seeing end of file.

SLIDE 16: 37.7 Copy-on-write

LECTURE NARRATION
Copy-on-write can avoid physically copying all private pages immediately. Parent and child initially share backing while hardware permissions trigger separation when a private write requires it. The interface promises the observable private-memory behavior, not an eager byte-for-byte copy at the instant of creation. The amount of memory actually duplicated depends on later writes, mappings, allocator activity, and kernel policy. Forking a large process is therefore not automatically equivalent to immediately allocating another complete physical copy, but it is also not free.

SLIDE 20: Worked example — Interpreting fork returns

LECTURE NARRATION
After a successful fork , the parent receives the child’s positive PID while the child receives zero. Both continue from the instruction after the call. Code commonly branches on the return value to assign parent and child responsibilities. A negative return in the parent-side call indicates failure and no child was created.

LECTURE NARRATION

Writes can therefore interact through a shared offset unless the program coordinates them or opens separate descriptions. The address spaces are logically separate, but kernel objects can remain shared.
