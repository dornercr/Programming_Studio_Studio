SLIDE 1: Chapter 35 — Buffered I/O

LECTURE NARRATION
Buffering groups small operations into larger transfers. It can reduce system-call overhead and provide convenient formatting, but it adds state whose visibility and failure behavior the program must understand. The application buffer, the C library’s stream buffer, the kernel page cache, and persistent storage are separate layers.

SLIDE 4: 35.1 System-call overhead

LECTURE NARRATION
A system call involves an ABI transition, validation, and kernel work. Performing one call for every character can make that overhead significant compared with the useful transfer. Grouping bytes amortizes the fixed portion of the cost. The exact cost is workload- and platform-dependent. A benchmark comparing one-byte writes with block writes should control the destination, total bytes, buffering mode, and error handling. Sending output to a terminal can measure rendering and terminal behavior as much as syscall overhead.

SLIDE 6: 35.2 User-space buffering

LECTURE NARRATION
A user-space buffer accumulates output or retains input already fetched from the kernel. The library can satisfy several application operations without another system call. That improves efficiency but means an application operation may complete before the underlying descriptor has seen all corresponding output. The buffer has ownership and lifetime requirements. When supplying storage to an interface such as setvbuf , keep that storage alive for the required duration and configure buffering before performing other stream operations as required by the interface. Do not use a short-lived local array as a long-lived stream buffer.

SLIDE 8: 35.3 Standard I/O

LECTURE NARRATION
The C standard-I/O library provides formatted and block-oriented operations such as fprintf , fread , and fwrite . It tracks buffering, position-related state, end-of-file state, and error state. These are library operations, not one-to-one aliases for system calls. [ R8 ] Check the return values appropriate to each interface. fread and fwrite count complete elements, not always raw bytes unless the element size is one. A short input result requires distinguishing end of file from an error using stream state.

SLIDE 10: 35.4 FILE*

LECTURE NARRATION
A FILE* refers to a library-managed stream object. It is not an integer descriptor and must not be passed where an int fd is expected. On POSIX systems, fileno obtains the associated descriptor for supported streams, but mixing raw descriptor operations with buffered stream operations requires careful coordination. The library may have read ahead or retained unwritten output. A raw read , write , or lseek can therefore interact with a different logical position than the programmer expects. Prefer one I/O abstraction for a given workflow unless there is a clear synchronization plan.

SLIDE 12: 35.5 Read buffering

LECTURE NARRATION
Read buffering obtains a block from the underlying endpoint and serves smaller application reads from that block. The descriptor offset may advance beyond the next byte the application will receive from the library buffer. This explains why duplicating a descriptor does not duplicate a FILE* ’s user-space buffer state. It also explains why switching abruptly between buffered and unbuffered reads can appear to skip data. The bytes may already be inside the library’s buffer rather than waiting at the kernel offset.

SLIDE 14: 35.6 Write buffering

LECTURE NARRATION
Write buffering delays or groups output until the buffer fills, a flush occurs, or another defined event requires transfer. fflush requests that buffered output be sent through the stream’s underlying write path and reports failure if that cannot be completed. fflush does not provide the same durability guarantee as fsync on an appropriate descriptor. It moves data out of the library buffer; the kernel and device may still retain it. Likewise, fclose must be checked because buffered output can fail during final flushing. [ R33 ]

SLIDE 16: 35.7 Buffer cache

LECTURE NARRATION
The kernel’s file cache retains file data in memory to avoid repeated device access and to batch writes. On Linux, discussion of ordinary file data commonly centers on the page cache. This cache is distinct from CPU caches and from user-space standard-I/O buffers. A warm-cache benchmark may primarily measure memory copying and kernel paths, while a cold-device benchmark includes storage access. Do not label both simply “disk speed.” State whether the relevant data was cached and avoid globally disruptive cache-manipulation commands in ordinary application labs.

SLIDE 20: Worked example — Why buffering reduces calls

LECTURE NARRATION
Writing 1 byte at a time for 4,096 bytes can require 4,096 system calls if unbuffered. Accumulating those bytes in a 4 KiB user-space buffer can reduce the transfer to roughly one write call. The total data is unchanged, but fixed per-call overhead is amortized across more bytes.

SLIDE 22: Worked example — Flush boundaries

LECTURE NARRATION
A buffered output library may hold bytes in user space until the buffer fills, a flush is requested, the stream closes, or policy triggers a flush. Therefore seeing a successful formatting call does not prove the bytes are already on durable storage. Buffering, kernel caches, and storage persistence are separate stages.
