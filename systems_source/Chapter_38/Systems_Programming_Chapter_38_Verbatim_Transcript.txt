SLIDE 1: Chapter 38 — Program Execution

LECTURE NARRATION
The exec family replaces the calling process’s program image. It does not create a new process by itself. This distinction makes fork followed by exec useful: the parent retains its program, while the child replaces its own image with the requested executable. [ R16 ]

SLIDE 4: 38.1 exec

LECTURE NARRATION
The exec family provides interfaces with different argument and environment conventions. Some accept an argument vector; some accept a variable-length argument list. Interfaces with a p variant search according to documented path rules, while execve takes an explicit pathname and environment vector. Choosing an interface is also a security decision. Searching a mutable or attacker-influenced path can execute an unintended program. Supplying an explicit known path and a controlled environment makes the selection easier to reason about, although executable identity and filesystem permissions still matter.

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. SLIDE 6: 38.2 execve

LECTURE NARRATION
execve(path, argv, envp) requests replacement using a pathname, a null-terminated argument-vector array, and a null-terminated environment-vector array. A successful call does not return to the old program. Failure returns -1 with errno describing the error. The strings and pointer arrays must remain valid until the call completes. The kernel constructs the new program’s initial state; the old address space is not retained as ordinary live C objects after success. Do not place essential parent-only cleanup after exec and expect it to run on success.

SLIDE 8: 38.3 Program replacement

LECTURE NARRATION
Replacement installs new code, data, stack, and related execution state while preserving the process’s identity and selected attributes according to the interface. It is not a normal function call into another executable. Open descriptors generally remain unless marked close-on-exec or affected by a documented rule. This is how a shell arranges standard input and output before executing a command. It is also why accidentally inherited descriptors can leak access into a program that never requested it.

SLIDE 10: 38.4 Arguments

LECTURE NARRATION
argv is an array of pointers to strings ending with a null pointer. Conventionally argv[0] identifies the program name, while later entries contain arguments. An argument containing spaces remains one argument when represented as one array element; no shell parsing is performed by execve itself. Avoid constructing a shell command string when direct argument passing is sufficient. Direct vectors preserve argument boundaries and avoid interpreting metacharacters as shell syntax. Validation is still required for the target program’s own option and input semantics.

SLIDE 12: 38.5 Environment

LECTURE NARRATION
The environment is a collection of strings conventionally formatted as NAME=value . Programs and libraries can use it to select paths, locale behavior, configuration, and other settings. Inheriting every variable is convenient but can make behavior depend on the launching context. A controlled launcher should decide which variables to preserve, replace, or omit. Never treat environment variables as automatically trustworthy merely because they came from the parent. Security-sensitive execution requires a deliberate environment and privilege policy.

SLIDE 14: 38.6 Process images

LECTURE NARRATION
A process image includes the executable mappings and initialized runtime environment needed to begin the new program. The loader and dynamic linker perform work beyond the source-level function call used to request replacement. Some signal-related state changes across exec while other state persists according to the documented rules. For example, caught signal dispositions are reset in the ordinary case, while the signal mask is preserved. A launcher that blocks signals during setup must restore the intended mask before executing a program that expects normal delivery. [ R16 , R21 ]

SLIDE 18: Worked example — Exec does not create a second process

LECTURE NARRATION
A child created with fork can call execve to replace its program image. The PID remains the same because execve transforms the calling process rather than spawning another one. On success, the old code, stack, and most mappings are gone, and execution begins in the new program’s startup path.
