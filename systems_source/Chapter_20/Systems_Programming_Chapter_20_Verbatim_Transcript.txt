SLIDE 1: Chapter 20 — Protected Control Transfer

LECTURE NARRATION
Control flow can leave a program for reasons beyond a source-level function call. A device may need attention, an instruction may encounter an invalid condition, or the program may explicitly request an operating-system service. The processor and kernel cooperate to save enough state, select an appropriate handler, and eventually continue or terminate the interrupted activity. Terminology depends on context. In this chapter, fault and trap use the architectural distinction when discussing x86 exceptions. They are not C++ exceptions, and the informal phrase “trap into the kernel” does not imply that every system call is an x86 trap-class exception. [ R3 ]

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. When this topic appears in real systems code, separate what the language guarantees from what a compiler, operating system, ABI, ISA, or particular machine happens to do. Then identify the evidence you would inspect to test the claim without overgeneralizing from a single successful run.

SLIDE 4: 20.1 Exceptions

LECTURE NARRATION
An architectural exception arises in relation to instruction execution. Examples include a page fault, an invalid instruction, or a divide error. The processor identifies the condition and transfers control through a configured mechanism. The saved state allows the handler to determine what happened and decide whether execution can continue. A language exception such as throw std::runtime_error(...) belongs to a different abstraction. Its implementation may unwind call frames entirely in user space. Although both mechanisms redirect control, their causes, handlers, and guarantees differ. Do not infer operating-system privilege changes from the presence of a C++ try statement.

SLIDE 6: 20.2 Interrupts

LECTURE NARRATION
An interrupt is commonly an externally generated event delivered to a processor, such as a timer or device notification. Its timing is asynchronous with respect to the program’s intended instruction sequence. The interrupted program did not necessarily request the event and may have no direct relationship to the device that generated it. Interrupt handling must preserve the context required by the architecture and kernel. A handler may acknowledge an event, make work runnable, and defer lengthy processing. Interrupts are one reason that elapsed wall time can exceed a program’s own CPU execution time. They are also one reason that a single-core system can exhibit interleavings even without simultaneous application execution.

SLIDE 8: 20.3 Traps

LECTURE NARRATION
In the x86 exception classification, a trap is reported after the instruction associated with it has completed. The saved instruction location generally supports continuation after that instruction. Debugging facilities use trap-like mechanisms to regain control at intentional observation points. The word is also used more broadly in operating-systems discussions for a deliberate transfer into privileged handling. When reading documentation, identify which meaning applies. A precise trace should state whether the current instruction will be retried, whether the next instruction will run, or whether execution will end. Those distinctions matter more than an ambiguous label.

SLIDE 10: 20.4 Faults

LECTURE NARRATION
A fault is reported in a way that can support restarting the faulting instruction after the underlying condition is corrected. A page fault is the central example: the instruction attempts a memory access, translation or protection checks fail, and the kernel decides whether the access is legitimate and recoverable. Recoverable does not mean automatically recovered. A legitimate demand-paged access may cause the kernel to install a mapping and retry the instruction. An access to an invalid address may instead lead to a signal and process termination. The same architectural entry mechanism can therefore serve both routine resource management and error reporting.

SLIDE 12: 20.5 System calls

LECTURE NARRATION
A system call is an explicit request for a kernel service through an operating-system ABI. A C library wrapper translates a source-level interface into that ABI and translates the result back into the library’s conventions. Some library operations require several system calls; others require none for a particular invocation. The Linux x86-64 system-call register convention is not identical to the System V function-call convention from Chapter 17. In particular, the fourth integer system-call argument uses %r10 , not %rcx , and syscall has specific effects on %rcx and %r11 . Handwritten wrappers must respect the correct ABI. This book normally uses documented C interfaces instead of embedding raw system-call assembly. [ R46 ]

SLIDE 14: 20.6 User-to-kernel transition

LECTURE NARRATION
A protected entry transfers control to a destination configured by privileged software. The entry path establishes the kernel’s execution environment and records state needed for a return. Do not picture every entry as an ordinary call instruction that simply pushes a return address on the application’s stack. For example, x86-64 syscall does not itself perform a conventional push of the entire user context onto a kernel stack. The processor provides specified register and control-state changes, and kernel entry code performs additional work, including establishing suitable stack state. The exact entry sequence is architecture- and kernel-dependent. The stable lesson is that user-supplied state must not be trusted merely because execution is now privileged. [ R3 ]

SLIDE 16: 20.7 Kernel-to-user return

LECTURE NARRATION
Before returning, the kernel prepares a valid user execution context and a result. The return may resume the original user instruction stream, deliver a signal through an arranged user-space path, or select another runnable task before the original one eventually continues. A system call that blocks is not completed by busy-waiting in user code. The kernel can place the caller in a waiting state and schedule other work. When the relevant event occurs, the caller becomes eligible to run again. Becoming runnable and actually receiving CPU time are distinct events; scheduling determines the latter.

SLIDE 18: 20.8 Timer interrupts

LECTURE NARRATION
Timer facilities let the kernel regain control and account for or schedule work. A runnable process cannot assume that avoiding voluntary system calls grants it indefinite uninterrupted use of a CPU. The hardware timer and scheduling mechanisms provide opportunities to reconsider execution. Modern systems need not use a simplistic fixed periodic tick for every purpose. Exact timing and scheduling policy vary. For reasoning about an application, the important fact is that preemption can occur between operations that appear adjacent in source code. A sequence is not atomic merely because it is short or usually finishes within one timer interval. [ R38 ]

The following sequence is a conceptual model, not a promise about every kernel implementation: The load may ultimately produce the same value it would have produced had the page already been resident. SLIDE 22: Worked example — System-call round trip

The kernel validates the descriptor and user buffer, performs or schedules the operation, places a result in the calling convention’s return location, and returns to user mode. The library wrapper then exposes the result to C code.

SLIDE 24: Worked example — Fault versus interrupt

LECTURE NARRATION
A page fault is synchronous with the instruction that attempted the access: retrying that instruction may succeed after the mapping is fixed. A timer interrupt is asynchronous with respect to the current instruction stream and is generated by hardware timing. Both transfer control to privileged handlers, but their causes and restart semantics differ.
