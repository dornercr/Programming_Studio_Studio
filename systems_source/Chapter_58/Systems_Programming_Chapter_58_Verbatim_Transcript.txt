SLIDE 1: Chapter 58 — Exploit Mitigations

LECTURE NARRATION
Mitigations reduce the consequences or feasibility of exploiting certain bugs. They are defense in depth, not substitutes for memory safety. A program can contain a serious vulnerability even when it is compiled with hardening flags, uses randomized addresses, and has non-executable data pages. Treat mitigation status as a property to inspect in the actual build and deployment. A flag written in a document is not evidence that the final executable or runtime environment enforces the intended protection. [ R3 , R31 , R45 ]

At graduate level, do not treat this as a term to memorize. Identify the contract being described, the state or representation it constrains, and the assumptions that must remain true. SLIDE 4: 58.1 Stack canaries

LECTURE NARRATION
Stack-protector instrumentation places a check value in selected stack frames and verifies it before returning through the protected path. Some overwrites can then be detected before corrupted state is used in a normal return sequence. Coverage depends on compiler options and generated code. A canary does not prevent the original out-of-bounds write, protect every object, or guarantee detection of every corruption pattern. It is a detection barrier for a subset of consequences.

SLIDE 6: 58.2 Non-executable memory

LECTURE NARRATION
Non-executable permissions prevent instruction fetches from designated data regions. Separating executable code from writable data reduces one class of attack opportunity. The processor and operating system must support and enforce the mapping policy. Non-executable data does not prevent all control-flow misuse or data-only corruption. An attacker does not necessarily need to introduce new executable bytes to cause harm. The underlying invalid write, stale pointer, or authorization error still requires repair.

SLIDE 8: 58.3 Address-space randomization

LECTURE NARRATION
Address-space randomization varies locations of mapped regions to make useful addresses less predictable. Position-independent executables and libraries support relocation under the relevant loader model. Randomization is not confidentiality by itself. Information disclosure can reveal addresses, and entropy varies with architecture and configuration. Do not disable randomization to make an application appear more stable; investigate invalid address assumptions instead.

SLIDE 10: 58.4 Memory permissions

LECTURE NARRATION
Memory permissions restrict reading, writing, and execution at mapping granularity. A least-permission design avoids writable executable regions and removes unneeded access. Read-only mappings can protect immutable tables from accidental modification. Changing permissions is a privileged service request and may require translation invalidation. Permissions still do not distinguish two objects inside one writable page. They reinforce region-level boundaries while language and application rules govern object-level behavior.

SLIDE 12: 58.5 Privilege separation

LECTURE NARRATION
Privilege separation divides a system so that components handling untrusted input possess only the authority they need. A small privileged component can perform narrow validated operations for a less-privileged parser or worker. The communication interface becomes a security boundary and must validate message type, size, identity, and requested action. Splitting into processes without reducing authority or validating requests merely relocates the same risk. Failure recovery should also specify what happens when one component exits midway through an operation.

SLIDE 16: Worked example — What a stack canary checks

LECTURE NARRATION
A compiler can place a random guard value between vulnerable local data and control-sensitive stack state. Before returning, generated code verifies that the guard is unchanged. A sequential overflow that crosses the canary is likely detected, but the mechanism does not prevent every memory error and is not a substitute for bounds safety.

LECTURE NARRATION

Even with PIE and ASLR, information disclosures or other weaknesses can undermine address uncertainty, so mitigations are layered rather than absolute.
