SLIDE 1: Chapter 19 — Kernel Fundamentals

LECTURE NARRATION
A running application can calculate addresses, perform arithmetic, and call functions, but it does not have unrestricted authority over the machine. The kernel establishes the environment in which those actions occur. It manages resources shared by mutually untrusting programs and provides controlled ways to request services that a program cannot perform directly. The important boundary is not between “ordinary code” and “special code.” It is between execution contexts with different permissions. Kernel code is software, but hardware mechanisms give that software the authority to configure mappings, handle devices, and control execution. This chapter describes the Linux/x86-64 model; other architectures and kernels divide these responsibilities differently. [ R3 , R10 ]

SLIDE 4: 19.1 Kernel

LECTURE NARRATION
The kernel is the privileged core of an operating system. Its responsibilities include scheduling runnable work, maintaining virtual memory, mediating file and device access, and implementing interprocess communication. It also maintains bookkeeping: which descriptors a process owns, which pages may be written, and which operations the process’s credentials permit. Not every operating-system service must execute inside the kernel. A command interpreter, a graphical desktop, and many service managers are user-space programs. The design boundary varies among monolithic kernels, microkernels, and other arrangements. Regardless of architecture, a request must be validated at the point where it crosses a trust boundary. Moving an operation into a service does not eliminate the need for access control.

SLIDE 6: 19.2 User mode

LECTURE NARRATION
User mode is an execution mode with restricted authority. In the usual x86-64 Linux arrangement, application instructions execute at current privilege level 3. An application may access its permitted memory and execute ordinary arithmetic, branch, and data-movement instructions. It cannot simply rewrite the active page-table root or disable hardware interrupts. User mode is not synonymous with “untrusted person” or “unimportant program.” A privileged administrator’s ordinary application still runs in user mode. Its credentials may cause the kernel to approve more requests, but those credentials do not turn every application instruction into a ring-0 instruction. Distinguish software authorization from hardware execution privilege .

SLIDE 8: 19.3 Kernel mode

LECTURE NARRATION
Kernel mode allows execution of operations needed to control protected machine state. On the reference platform, the kernel normally executes at privilege level 0. Entry into this mode occurs through configured mechanisms rather than by an application choosing an arbitrary destination and declaring itself privileged. Kernel mode does not make software infallible. Invalid pointers, synchronization bugs, and incorrect bounds checks remain possible. Their consequences can be more severe because the kernel has broader authority. Nor does kernel mode imply that every virtual address is mapped or that every memory access succeeds. The currently installed mappings and protection features still matter.

SLIDE 10: 19.4 Privilege levels

LECTURE NARRATION
A privilege level is a hardware-defined part of execution state. x86 provides four numbered rings, although ordinary Linux application/kernel separation primarily uses rings 3 and 0. Virtualization adds another dimension of control; “hypervisor” is not adequately explained by pretending that x86 simply has a normal ring numbered minus one. Privilege checks apply to particular operations and accesses. Accessing a supervisor-only page and executing a privileged instruction are different checks, although both can prevent user code from performing unauthorized work. Software credentials form an additional policy layer. A successful mode transition therefore does not automatically authorize the requested operation: the kernel still checks arguments, ownership, capabilities, and resource limits.

SLIDE 12: 19.5 Protected resources

LECTURE NARRATION
Protected resources include physical memory mappings, device registers, scheduling state, privileged processor controls, and objects governed by operating-system policy. A disk block may contain another user’s data. A device command may affect the entire machine. A page-table edit may expose memory that was intended to remain isolated. Applications receive controlled references rather than raw authority whenever possible. A file descriptor identifies an entry in a process’s descriptor table; it is not a physical disk address. The kernel interprets the descriptor in the caller’s context and applies the object’s rules. This indirection makes it possible to share resources selectively while preserving a central place to enforce policy.

SLIDE 14: 19.6 Dangerous instructions

LECTURE NARRATION
Some instructions alter machine-wide or privileged execution state. Examples include operations involving control registers or interrupt-enable state. Hardware restricts these instructions so that an ordinary process cannot take over the machine by executing a short instruction sequence. An attempted prohibited operation raises an architectural exception rather than granting the requested authority. [ R3 ] Other instructions are not privileged but can still be dangerous when used incorrectly. An ordinary store can corrupt a program’s own heap. Integer division can fault for an invalid divisor. “Unprivileged” means permitted at the current hardware privilege level, not harmless. Labs in this book inspect and model privileged behavior; they do not require running privileged instructions or changing kernel settings.

SLIDE 16: 19.7 Hardware protection

LECTURE NARRATION
Hardware protection supplies mechanisms such as permission checks on translations and controlled entry points for exceptions and system calls. The kernel configures these mechanisms, and the processor enforces them during execution. Software policy and hardware enforcement are complementary: a policy without enforcement can be bypassed, while a mechanism without correct policy can faithfully enforce the wrong permissions. Protection operates at particular granularities. A writable page normally permits stores throughout the mapped writable region; it does not know that a C++ vector currently contains only five elements. Consequently, process isolation does not provide complete object-level memory safety. Bounds, lifetime, and concurrency correctness remain responsibilities of the language implementation and program design.

SLIDE 22: Worked example — Protecting kernel memory

LECTURE NARRATION
Page-table permissions mark kernel mappings inaccessible to ordinary user-mode accesses. A user pointer that numerically resembles a kernel address does not grant permission to read it. If the CPU checks the access in user mode and protection forbids it, control transfers to the kernel’s fault path rather than completing the load.
